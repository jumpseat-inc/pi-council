## Root-cause write-up (Deliverable 2) — with evidence

The historical symptom ("stock pi 0.85.0 loads no pi-council extension") root-caused during this card's deliberation (steps 2–6; all closed, rulings R-1/R-2 binding). The four required blocks, each cited:

### (i) The env-keyed parent/child mode split at `extensions/index.ts:117-121`

The extension's default factory entry branches on a single process-env variable before any command registration:

```ts
const seatName = process.env.COUNCIL_SEAT;
if (seatName) {
    runChildMode(pi, repoRoot, seatName);
    return;
}
```

Evidence: `extensions/index.ts:117-121` (installed-code read; `grep -n COUNCIL_SEAT extensions/index.ts` → line 117, the branch 118-121). Line-number correction is on the record: earlier passes cited 66-69; the Skeptic's step-4 objection 2 CLOSED-RED for 66-69 / CLOSED-GREEN for 117-121 (card step-4, obj. 2).

When `COUNCIL_SEAT` is present, `runChildMode` (extensions/child.ts) does exactly: `initHubIdentity(...)`, `loadSeat(...)` (throws on unknown seat → child exits nonzero), `registerHubTools(...)` if the seat has the hub grant, `startSeatMcp(...)`, and a `pi.on("tool_call")` allowlist guard. **It never calls `pi.registerCommand`** — child mode registers zero slash commands, on every pi version (the mechanism is version-independent).

### (ii) Zero commands → unregistered command → silent model-dispatch fallthrough

With zero registered commands, a council command name like `/council-eval` is an unregistered command to pi and falls through to pi's unknown-command path: a **real model dispatch** instead of a missing-feature diagnostic. There is no `Failed to load extension` diagnostic on this path because the extension *factory succeeds* — `loadExtension` (pi `dist/core/extensions/loader.js`, `createExtension` + `createExtensionAPI` + `await factory(api)`) returns a healthy extension; the child branch simply registered nothing. `dist/main.js` maps loader errors to the `Failed to load extension "${path}": ${error}` diagnostic (dist/main.js, `EXTENSION_LOAD_FAILURE_HINT` region); a genuine load *throw* produces that diagnostic, the silent child-mode downgrade produces nothing.

Evidence (real-binary runs, both recorded):
- Clean env, installed pi, consumer with local pin, `pi --approve -p "/council-eval"` → **exit 0, `[council-eval] usage:` printed** (this run's probe, 0.84.2 binary; reproduced by step-4 objection 3 on 0.85.0).
- `COUNCIL_SEAT=judge` added → **exit 1, no usage, "No API key found for the selected model."** — the unregistered command hit the model-dispatch path and failed fast only because no key was present (this run's probe; step-4 objection 4 CLOSED-GREEN: with a key the dispatch hangs — exit 124 timeout).
- Cost hazard: with a valid key present, the fallthrough pays for a real LLM dispatch (FLLWUP-14's "unexpected-cost hazard" framing, card Intent).

### (iii) The FLLWUP-14 probe-contamination finding

FLLWUP-14's "stock pi 0.85.0 loads no extension" observation came from a **contaminated council-runner seat session**, not from the kitty smoke harness. The confirmation is on the FLLWUP-14 card's own step-8 deviation record, verbatim (deviation (1), card `council/cards/FLLWUP-14.md`, step 8):

> "the COUNCIL_SEAT/COUNCIL_JOB_ID/COUNCIL_RUN_ID env of this runner's session makes the extension enter child mode and register nothing — `run.sh` unsets them; found at bring-up, not assumed"

The discovery probe (owner job-10.1) was launched from inside a council-runner seat session and inherited `COUNCIL_SEAT=council-runner` → child mode → zero commands → misroute. The kitty smoke harness itself is contamination-proof **by construction**:
- `smoke/run.sh:22` forwards only `-e OPENROUTER_API_KEY -e SMOKE_PHASE=${SMOKE_PHASE:-}` into the container — no council vars cross the container boundary.
- `smoke/search-smoke/run.sh:39` explicitly `unset COUNCIL_SEAT COUNCIL_JOB_ID COUNCIL_RUN_ID PI_SESSION_FILE`, and `:20` pins `PI_VERSION="0.84.3"` — the harness never exercises 0.85.0 at all.

So: no clean-env 0.85.0 load failure has ever been observed; every observed instance is the child-mode downgrade. The structural lesson is what spec §3's explicit-env requirement encodes: any process spawned from inside a seat session inherits `COUNCIL_SEAT`/provider keys, so a test that forwards inherited env would contaminate itself exactly the way the FLLWUP-14 probe did.

### (iv) The no-loader-drift evidence

There is no 0.84.3→0.85.0 extension-load/API drift:
- `pi-manifest.js` and `package-manager.js` are **byte-identical** between 0.84.3 and 0.85.0 — `cmp` exit 0 (card step-4, objection 1, CLOSED-GREEN for those two files).
- `loader.js` differs only in the `isBundledNode` refactor (local definition in 0.84.3 → import from `config.js` in 0.85.0) — functionally identical for the npm-global/devDependency path (card step-4, objection 1, CLOSED-RED non-fatal for the blanket byte-identity claim; the no-API-drift conclusion holds; step-5 Consolidator "Settled").
- The loader entry surface the verification depends on — `discoverAndLoadExtensions(configuredPaths, cwd, agentDir, eventBus)` at `dist/core/extensions/loader.js`, re-exported at the package entry `dist/index.js:10` — is verified present at that relative path in 0.84.x (read) and re-verified on the lock-resolved version in Task 4 below.

### Lock resolution: `0.85.1` predicted, `0.84.3` delivered — and why

The deliberation's verified `0.85.0` shares **byte-identical** theme machinery with `0.85.1` (`diff -r` of the whole `theme/` dir: empty) — so the entire upper band `[0.85.0, 0.86.0)` fails this repo's theme contract; the band's two in-range members `0.85.0`/`0.85.1` were empirically checked (0.85.0 ≡ 0.85.1 by diff), `0.84.2`/`0.84.3` checked green (0.84.3's theme dir ≡ 0.84.2's, differing only in a `stripBom` cosmetic in `theme.js`; `dark.json`/`light.json` identical).

- [ ] **Step 1: Write the fixture**

```ts
// FLLWUP-21 driver fixture — NOT a test. Prints one JSON line describing how
// many slash commands the pi-council extension registered through the
// installed devDependency's discoverAndLoadExtensions, then exits 0.
//
// Env: FLLWUP21_REPO_ROOT — absolute repo root. The process env is fully
// explicit (constructed by the test); this driver adds nothing.
import { discoverAndLoadExtensions } from "@earendil-works/pi-coding-agent";
import { mkdtempSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";

const repoRoot = process.env.FLLWUP21_REPO_ROOT;
if (!repoRoot) {
	console.log(JSON.stringify({ error: "FLLWUP21_REPO_ROOT not set" }));
	process.exit(0);
}
const scratch = mkdtempSync(join(tmpdir(), "fllwup21-driver-"));
try {
	const { extensions, errors } = await discoverAndLoadExtensions(
		[join(repoRoot, "extensions")],
		repoRoot,
		scratch,
	);
	if (errors.length > 0) {
		const e = errors[0];
		console.log(JSON.stringify({ error: `${e.path}: ${e.error}` }));
	} else {
		console.log(JSON.stringify({ commands: extensions[0]?.commands.size ?? -1 }));
	}
} catch (err) {
	console.log(JSON.stringify({ error: err instanceof Error ? err.message : String(err) }));
}
process.exit(0);
```
