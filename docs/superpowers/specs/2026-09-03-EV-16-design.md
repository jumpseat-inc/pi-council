# EV-16 — Council model eval system (design)

Settled design for card EV-16 (epic EPIC-4). This document is the write-up
of the Council's deliberation (rounds 1–3, Skeptic verification, step-6
product-owner/steward ruling on grader topology) plus the two binding Phase 1
rulings (R-1 storage, R-2 repeat default). It derives nothing new; it records
what the deliberation settled and what the rulings bound. An owner reading
only this file must not be able to reach two different designs.

## Goal (from the card)

> A design spec and implementation plan under docs/superpowers define the
> eval harness architecture, scoring rubric, per-run model override, and
> repeat-run confidence methodology so each implementation card cites one
> authoritative source

## Binding rulings (immutable for this run)

- **R-1 (storage)** — eval results records live under `council/eval-results/`,
  local-only telemetry, self-gitignored like `runs/` (the convention-12
  pattern). Not committed to git. The spec names this location; EV-20 writes
  there; EV-21 reads from there and its empty state is truthful on a fresh
  checkout.
- **R-2 (repeat default)** — the default repeat count is **3**; the caller
  raises or lowers it explicitly via `--repeat N`. There is no implicit
  all-models sweep — the matrix contains only what the caller names. The
  spec records this default and its cost rationale; EV-20 implements it.
- **Step-6 ruling (grader topology)** — the grader is a **harness-dispatched
  sibling of the cell** (parent = the command job, same parent as the cell
  driver). Cell↔verdict linkage is by an explicit `cellId` field on the
  verdict record — not by `parentJobId`. Cell-subtree cost = the cell driver
  and whatever it spawns; the grader is structurally outside that subtree, so
  no exclusion rule is needed in cost/latency aggregation. Section 6 records
  the full ruling text the spec commits to.

## 1. The cell-invariance contract (load-bearing)

**The only thing that varies across cells is the model id.** The fixture, the
grader's model, the harness-as-human policy, and the environment are pinned
as part of the fixture. Every item in this spec is a clause of that contract,
in dependency order:

1. The fixture pins everything-but-model (section 3).
2. The rubric grades against a pinned grader (sections 5–6).
3. The override is the only free variable (section 4).
4. The forest is the measurement unit (section 7).
5. Variance is terminal-state + numeric (section 8).

The invariant is the **(model, thinking) pair**, and it is only as strong as
the dispatch surface: `buildChildArgv` exposes no sampling knobs, so the
harness pins file state and policy but controls sampling only
**statistically** — the repeat dimension is the control for the unpinnable
dimension.

## 2. What "accurately measure" means

For a multi-step procedure run and a single seat turn alike: **score =
fraction of rubric criteria passed, 0..1**; cost, elapsed, and tokens are
**reported dimensions, not score inputs**. "Accurately" means only the model
varies: same fixture, same rubric version, same repo starting state — each
cell runs in a scratch state, never the live tree. The operational definition
of accuracy for a multi-step command is inherited from the smoke test's
philosophy ("never trust a claim, re-run reality": typecheck, the test suite,
exact CLI-output probes re-run by the harness, not taken from seat prose),
generalized to an N×M×repeat matrix.

## 3. Item 1 — Eval harness architecture

### 3.1 Engine module and data files

- A new engine module `extensions/eval*.ts` implements the harness. Data
  files — fixtures and rubrics — live under `council/` (repo-root consumer
  data, seeded by the scaffold), with repo-local shadowing per AGENTS.md
  convention 5.
- EV-20 is a slash command whose handler calls the engine code directly —
  **NOT an LLM-orchestrated loop**. The harness reuses hub dispatch/wait and
  `council_dispatch`'s shared path (AGENTS.md convention 7: reuse, don't fork
  the hub).
- Each cell executes against a **disposable scratch worktree** seeded from
  the fixture (smoke-test precedent — procedures like /council merge
  branches, set board state, commit; running them against the caller's live
  tree would corrupt comparison state). Only results records are written
  back to the caller's `council/eval-results/`.

### 3.2 Why `runs/` cannot be the comparison store

`pruneRuns` keeps only the last **15** runs at `session_start`
(`extensions/runs.ts:147–162`). A mid-matrix prune would silently delete
evidence. Eval results are durable evidence and live **outside** the
ephemeral `runs/` boundary (R-1). The read-owner of `council/eval-results/`
is a new eval module **outside** the AGENTS.md convention-12 closed
quarantine list (`runs.ts`, `tree.ts`, `transcript.ts`, `navigator.ts`); no
file in the runs/ set reads the eval-results path.

### 3.3 Harness-as-human policy (structured rulings)

/council and /features-deliver contain human-in-the-loop gates (the merge
gate, delivery rulings). The harness plays the human, and that is a **fixture
property**: standing rulings are **machine-applicable structured policy**
blocks (one per procedure: /council merge-gate verdict, /features-deliver
delivery ruling), evaluated by a **pure, unit-testable engine** — not
smoke-style prose, because eval has no human in the loop and a
deterministic-gate rubric criterion cannot consult prose. The harness-as-
human policy is part of the fixture (section 9).

### 3.4 Task-id → fixture-dir → rubric-file wiring

Defined once here, referenced by both the run and grade paths:

| Task id | Fixture dir | Rubric file |
|---|---|---|
| `council-eval <task> <model...>` | `council/fixtures/<task>/` | `council/fixtures/<task>/rubric.json` |

The fixture directory is the unit of task identity: a task id names a
fixture directory, and that directory carries its own rubric file. EV-18
fills fixture directories; EV-19 grades by the rubric file each fixture
names. A fixture without a rubric file fails loudly at load (no silent `[]`).

## 4. Item 2 — Per-run model override (EV-17)

### 4.1 The mechanism: one env-carried third layer, canonical

The override is a **third layer** above `.council.json`, applied only on the
eval dispatch path — never a mutate-then-restore of `.council.json` or seat
frontmatter. The canonical carrier is **one env-carried key,
`COUNCIL_EVAL_MODEL`**, carrying `provider/id` or `provider/id:thinking`
(the same qualified-model + optional `:thinking`-suffix grammar that
`.council.json` and frontmatter share — one parser, `qualifiedOrThrow`-style,
not a second grammar).

**Precedence, exactly:** per-dispatch `model`/`thinking` param on
`council_dispatch` > `COUNCIL_EVAL_MODEL` env > `.council.json` override >
seat frontmatter. The per-dispatch params are optional sugar that win when
present; the env var is canonical so EV-17 implements one path, not two.

### 4.2 Application point and invariants

- `council_dispatch` reads the env override **after `loadSeat` and before
  both the catalogue check and `buildChildArgv`** — the same insertion point
  where `seat.model`/`seat.thinkingLevel` are currently resolved and checked
  (`extensions/hub-tools.ts` ~89–130).
- The resolution must **write the effective (model, thinking) back onto the
  seat before the catalogue check** — otherwise the check validates the
  frontmatter model while the spawn runs a different one, and the
  manifest/argv/getAvailable all diverge.
- The effective model passes the **same live catalogue check**
  (`ctx.modelRegistry.getAvailable()`) `council_dispatch` already runs:
  unknown model → refuse loudly, no fallback. The loud error names the
  **overridden** model.
- The effective value is written to the spawned job's manifest `model`
  field via the existing `spawnJob({ model: seat.model })` path — EV-17's
  "visible in the transcript" acceptance.
- The env override is set on the **spawned job's env** (`hub.ts:137` honors
  per-job `env:`), **never the parent's `process.env`**. It is ambient
  inside the eval subtree and invisible to every non-eval dispatch; siblings
  (the grader, the next cell) never see it. `childEnv` (`runs.ts:139–141`)
  propagates it to descendants with no further work — the same mechanism
  that already carries `COUNCIL_RUN_ID`/`COUNCIL_JOB_ID`.
- A grandchild's `council_dispatch` (re-entered inside the child process via
  `runChildMode` → `registerHubTools`) applies the same chain: explicit
  param → inherited `COUNCIL_EVAL_MODEL` → `.council.json` → frontmatter,
  re-running `qualifiedOrThrow` + the catalogue check against the effective
  model, and writing the effective value to argv + manifest + child env.

## 5. Item 3 — Scoring rubric (EV-19)

- **Shape:** an ordered list of named criteria. Each criterion is either a
  **deterministic gate** (definite pass/fail: gates green, `validate.py`
  clean, artifact present) or a **recorded judge verdict** (the existing
  `judge.md` PASS/REJECT used as data).
- **Scoring:** unweighted pass/total, 0..1. Weighting is a policy debate for
  a future card; unweighted scores are stable across rubric versions.
- **Re-grade reproducibility:** deterministic gates are re-runnable;
  judge verdicts are **recorded at grade time** into the result record and
  re-graded by **replay**, with the grader's model id stored in the record
  (`gradedBy`). Re-grading under a different pinned grader writes a second
  verdict record keyed by `gradedBy` — **append-only, never overwrite**.
- **Validation:** rubrics schema-validate at load; a fixture lacking a
  rubric fails loudly (no silent `[]`).

## 6. Item 4 — Grader topology and verdict records (step-6 ruling)

The full ruling text is on the card record; this section commits the spec to
it. The grader is the judge-seat dispatch that grades a cell's open-ended
rubric criteria.

1. **Grader dispatch site = the harness, never the cell driver.** The eval
   harness, after the cell driver settles and its result record is written,
   dispatches the judge seat as a harness-owned job with the cell job's id as
   `cellId` (a new param on `council_dispatch`, the same injection point
   EV-17 adds for `model`/`thinking`). The judge dispatch carries the
   fixture-pinned grader model as an explicit `model` param (no reliance on
   the ambient `COUNCIL_EVAL_MODEL` env inheritance — the explicit param
   beats the env), and the harness writes the verdict
   record with `cellId` + `gradedBy` + per-criterion pass/fail + cost/
   latency attribution to a `grading` scope (not the `cell` scope).
2. **Cell subtree = `parentJobId`-chain rooted at the cell job.** The grader
   is OUTSIDE this subtree (its `parentJobId` is the command job, same as
   the cell driver). Forest aggregation sums cost/latency/turns over
   subtrees; the **cell** column reports cell-subtree spend, the **command**
   column reports command-subtree spend, the **grading** column reports
   grader-subtree spend. Three columns, not one. **No exclusion rule.**
3. **Verdict record schema:**
   `{ cellId, repeat, gradedBy, fixtureVersion, rubricVersion, perCriterion: [{criterionId, verdict, evidence}], gradedAt, gradingUsage: {input, output, cost, elapsedMs, stopReason} }`.
   `cellId` is the linkage field; topology is not. `gradedBy` is the model
   id that ran the grade (appended across re-grades; first write wins for
   the cell, subsequent writes are new records).

   **§6.3 amendment (EV-20 ruling, binding):** `VerdictRecord` gains
   `repeat: number` (projected by `projectVerdictRecord` from `meta.repeat`).
   The store key becomes `(cellId, repeat, gradedBy, fixtureVersion,
   rubricVersion)` — three grader dispatches for repeats 1..3 of one cell
   write three readable records. `cellId` is the stable aggregation identity
   `(taskId, model, thinking)`; the version pair rides the key alongside
   `repeat`/`gradedBy`, so a fixture bump produces a new version-keyed set
   rather than fragmenting the aggregation identity. `cellId` string form:
   `taskId|model[:thinking]`. Symmetric mirror of the ResultRecord key ruling.
4. **Cell drivers have NO authority to dispatch graders.** No fixture rubric
   criterion may route through a cell-driver-spawned grader — the harness
   owns all grader dispatches. The judge seat's `spawns: []` is already
   correct for this; the harness's grade loop is what calls the judge,
   never a cell-driver LLM.
5. **Both env-carried `COUNCIL_EVAL_MODEL` AND harness-owned grader dispatch
   with explicit `model` param are required, in that order.** The
   env-carried override carries the cell-model value to the cell driver
   (section 4); the grader dispatch then sets the fixture pin as an explicit
   `model` param on the harness's `council_dispatch` call so it beats the
   env. The cell-model carrier and the grader-pin carrier are different
   surfaces with different precedence rules.

## 7. Forest telemetry — the RunManifest extension

Command-level cost/latency is **sum over the job forest rooted at the
command's job**, not a single job. Today `writeJobManifest`
(`extensions/hub.ts:89–101`) persists only id/seat/model/parentJobId/pid/
sessionId/state/startedAt/settledAt/exitCode — no usage, no stopReason, no
elapsedMs — and `report()` holds them in memory only. The one genuinely new
piece of plumbing:

- **Extend `RunManifest` with `usage` and `stopReason` at `settle()`**
  (`elapsedMs` is already derivable from persisted `startedAt`/`settledAt`,
  so only two fields are truly new).
- Forest aggregation = Σ over the `readManifests` subtree rooted at the
  command job's `parentJobId`.
- This touches the `hub.ts is stable` boundary (AGENTS.md convention 7) —
  the change ships **with a failing test first**, never a silent field
  addition.

## 8. Item 5 — Repeat-run confidence methodology (EV-20/EV-21)

- **Default repeat count is 3** (R-2); the caller raises or lowers it
  explicitly via `--repeat N`. There is no implicit all-models sweep — the
  matrix contains only what the caller names. **Cost rationale (verbatim
  from the deliberation):** a full 16-inventory × M-models × 3 sweep is
  hours of dispatch; the no-implicit-sweep rule is a cost guard.
- **Per-cell (task × model) mean, sample σ, and n** are computed from the
  records alone. Each record carries: task, model, thinking, repeat index,
  per-criterion pass/fail, score, cost, elapsed, tokens, stopReason, rubric
  version, fixture version, repo state.
- **"A difference is real" = the confidence interval on the mean difference
  excluding zero.** Honestly: at n=3 that interval is wide, so the
  leaderboard renders **TRIAGE, not asserted ordering** between close models
  — "do not claim an ordering whose variance doesn't support it" is a
  first-class rule.
- **Terminal-state histogram alongside mean/σ.** This codebase exhibits
  variance as different terminal states (flash-model variance pause state,
  stalled, informational timeout, `stopReason=length` empty-done surfaced as
  model-config defect). A confidence method defined only over numeric score
  variance is blind to the observed failure modes.
- **`stopReason=length` is FLAGGED, never scored 0.** Score is over
  **completed repeats only**; the cell record carries `n_attempted` vs
  `n_graded` plus the terminal-state histogram; a majority-flagged cell
  renders as **indeterminate triage**, not a low number. Scoring length as 0
  conflates config failure with capability and makes the score unstable
  under the documented remediation (raise the floor, re-run, the same
  capability scores differently — the two numbers were never comparable).

## 9. Fixture schema (EV-18)

A fixture directory `council/fixtures/<task>/` contains:

- **`fixture.json`** — task id, name, repo-state seed (the starting state the
  scratch worktree is seeded from), the procedure/command to run, the
  **harness-as-human policy** (structured rulings block, section 3.3), the
  **pinned grader model** (`graderModel`, resolved from the fixture file,
  never from `.council.json`), and the rubric reference.
- **`rubric.json`** — the rubric (section 5).
- The fixture pins everything-but-model: repo state, grader model,
  harness-as-human policy, environment.

## 10. Falsifiable acceptance criteria

Each item's acceptance is a runnable claim, not prose:

**A. Harness architecture (EV-18/EV-20)**
- A1. A cell run against a scratch worktree leaves the caller's live tree
  byte-identical (no board/card/commit mutation outside the scratch copy).
- A2. A fresh checkout with no `council/eval-results/` dir renders the
  leaderboard's empty state truthfully; `validate.py` remains green.
- A3. No file in the runs/ set (`runs.ts`, `tree.ts`, `transcript.ts`,
  `navigator.ts`) references the eval-results path; only the new eval module
  does.
- A4. The structured-rulings engine is pure and unit-testable: the same
  policy block + same cell state yields the same verdict, with no I/O.

**B. Model override (EV-17)**
- B1. Precedence (pure): extract `resolveEffectiveModel(seat, envVal?,
  param?)`; assert param > env > `.council.json` > frontmatter for all four
  combinations, including `:thinking` suffix parsing in all three override
  sources.
- B2. Dispatch seat S under env `COUNCIL_EVAL_MODEL=M`: root argv contains
  `--model M`; if S spawns a grandchild, the grandchild's manifest `model`
  field is M; frontmatter and `.council.json` untouched.
- B3. Catalogue check validates the **effective** model: frontmatter model in
  catalogue and env override unknown provider/id → dispatch refuses with the
  loud error naming the overridden model.
- B4. Subtree scope, no residue: dispatch cell A under X, cell B under Y,
  grader G pinned P; every descendant manifest in A's subtree has
  `model == X`, B's `== Y`, G's `== P`; `process.env.COUNCIL_EVAL_MODEL` is
  undefined in the parent after all dispatches.

**C. Rubric (EV-19)**
- C1. Re-grade reproducibility: record R re-graded yields the same
  per-criterion pass/fail and score (judge criteria replayed, gates re-run).
- C2. Replay append-only: re-grading under a different pinned grader writes a
  second verdict keyed by `gradedBy`; the original record is byte-identical.
- C3. A fixture lacking a rubric fails loudly at load (no silent `[]`).

**D. Grader topology (step-6 ruling)**
- D1. Grader isolation: grader's `parentJobId` == the command job (sibling of
  the cell); cost/latency aggregation over the cell subtree equals the sum
  excluding the grader node, with no exclusion rule in the aggregator.
- D2. Grader invariance: fixture pins judge model M1 while `.council.json`
  pins M2; the grade step's judge dispatch argv carries `--model M1`;
  `record.gradedBy === M1`.
- D3. Cell drivers cannot dispatch graders: no fixture rubric criterion
  routes through a cell-driver-spawned grader; the judge seat's `spawns: []`
  is unchanged.

**E. Confidence (EV-20/EV-21)**
- E1. Variance honesty: two n=3 cells with overlapping score CIs render as
  tied/adjacent (triage), never an asserted ordering.
- E2. Length semantics (pure): cell-summary over
  `[{stopReason: length, done, empty}, {done, ok}]` yields
  `{completed: 1, lengthFlagged: 1, score: 1.0}` — not `{score: 0.5}`.
- E3. A cell with 2/3 done + 1/3 `stopReason=length` reports the
  terminal-state histogram; the leaderboard does not collapse it to a bare
  mean/σ.

**F. Forest telemetry**
- F1. Forest telemetry round-trip: extend `RunManifest`; write →
  `readManifests` round-trips usage/stopReason; `sumSubtree(rootId)` over a
  3-deep chain equals the hand-computed sum.
- F2. The RunManifest extension ships with a failing test first (convention
  7).

## 12. Scope guard

This card writes the spec and the matching plan only. No engine code changes
land on this card. The RunManifest extension (section 7) is specified here
but implemented by EV-20; the override layer (section 4) is implemented by
EV-17. Nothing in this spec asserts a design choice as settled that the
deliberation left open.
