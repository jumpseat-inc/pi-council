# EV-69 design — deterministic routing to Verify mode

Card: EV-69 (`council/cards/EV-69.md`), epic EPIC-13. This spec is the
settled design from the card's full deliberation (3 rounds + skeptic attack +
design-fix round + synthesis) as amended by the product-owner's step-6 ruling
(job-22, appended verbatim to the card). It is written to be implementable
from this file alone. Nothing in it reopens a settled point.

## 1. The contract (card goal, verbatim)

> A card whose recorded ledger decision resolves to Verify runs council steps 7
> through 12 with zero deliberation dispatch, and a falsifier over the
> manifests of a scripted harness run whose dispatches are produced by the real
> council_route tool proves that run's dispatch multiset — ROOT mode Verify,
> one owner dispatch, exactly one skeptic dispatch and no second
> branch-verification skeptic, one judge goal evaluation, and zero principal,
> designer, consolidator, product-owner and steward dispatches — while
> claiming nothing about whether a live facilitator called council_route, which
> the manifest record cannot show.

The last clause is a condition on the headline claim, not fine print: the
falsifier proves the manifest shape of a scripted run; it claims nothing about
a live facilitator's behavior. The harness must invoke the **real**
`council_route` tool function (not a stub of it) and assert
exactly-one-mode-manifest; the scripted-vs-live gap itself is never claimed
closed.

**Binding rulings applied:** R4 (Verify = owner+skeptic+judge; Direct = owner
only; Deliberate = full panel; NO designer in Verify), R3 (packaged policy
ships `mode: "off"`; tests set modes explicitly), and the step-6 ruling's
Items A/B/C (re-route block placement and roster; designer-loss residual and
its conditions; the goal text above).

## 2. Substrate facts (verified against source; rely on these, re-verify details at implementation)

- `extensions/gate.ts` — `loadGatePolicy(repoRoot)` (`mode`: "off" | "advisory"
  | "active"), `loadGateQuestions`, `loadGateDecision` (policy `version`),
  `decide(answers, policyVersion): string`, `GATE_DECISION_MODES`,
  `MODE_PANELS` (Deliberate = owner, skeptic, principal, designer,
  product-owner, consolidator, judge; Verify = owner, skeptic, judge; Direct =
  owner). Roster composition is a binding ruling, never tuning data.
- `extensions/gate-state.ts` — `ParsedCard { id, title, goal, acceptance,
  touchedFiles }`; `buildGateState(card, repoRoot)` hashes the FULL packed
  state: `JSON.stringify` of the five sections `card, touchedFiles, wiki,
  rulings, tests` — so the hash is a function of the **repo tree**, not the
  card alone. It **throws** on empty/missing acceptance or any empty field
  (`card.<k> must be a non-empty string`). Touched-file entries are
  `{ path, linesChanged }`.
- `extensions/gate-ledger.ts` — schemaVersion 2; `appendGateCall(input)`
  writes ONE pre-serialized line (stateHash, questionSetVersion, answers with
  absent-as-null, resolvedMode, policyVersion, basis, …) — no outcome line;
  `readGateLedger` is tolerant; `rederiveResolvedMode(record, decide)`
  recomputes the mode from ONLY the stored line; records carry **no cardId**.
- `extensions/gate-run.ts` — `runGate(state, questions, { repoRoot, policy,
  decisionPolicy })` issues EXACTLY ONE model call and writes exactly one
  ledger line; it loads nothing itself. This card adds one OPTIONAL opt
  `basisSuffix?: string` (see §5).
- `extensions/gate-tool.ts` — `registerGateTool(pi, repoRoot)`: the parent-only
  `council_gate` intake tool; verdict opacity (EV-66); passes
  `touchedFiles ?? []` at the call site.
- `extensions/runs.ts` — `DispatchMode = "Deliberate" | "Verify" | "Direct"`;
  `RunManifest.mode?` written root-only (EV-68); `readManifests(repoRoot,
  runId)`; manifests carry `seat` + `mode` and **no role and no card id**;
  re-entry is same-run (`COUNCIL_RUN_ID` pinned via `childEnv`).
- `extensions/index.ts` registers `registerGateTool` on the parent path only.

## 3. New pure module: `extensions/gate-route.ts`

Sibling of `gate-state.ts`. **Import fence:** may import `gate-state.ts`,
`gate-ledger.ts`, `gate.ts`, and the `DispatchMode` type from `runs.ts`. It
MUST NOT import `gate-run.ts`, `gate-transport.ts`, `gate-render.ts`, or
`gate-tool.ts` — "no gate call from the routing read" is a property of the
import graph, pinned by a canary test, not a tested hope. It contains **no
mode literal of its own** (single literal source: `MODE_PANELS` /
`GATE_DECISION_MODES` from `gate.ts`, `DispatchMode` from `runs.ts`).

Exports:

### 3.1 `parseCardFile(md: string): ParsedCard`

The ONLY card-markdown extractor in the engine: frontmatter `id`/`title`/
`goal` + the `## Acceptance` section body (missing/empty ⇒ `acceptance: ""`;
the function does NOT throw on an unpackable card — `resolveRoute` classifies
the failure). No TS card-markdown parser exists today (`validate.py` is
Python and stays out of the engine path). This is also the **shared
extractor**: the `council_gate` intake tool's field normalization is
refactored, behavior-preserving, to collapse onto this module's normalization
so intake and routing parse one artifact. The behavior-preserving edit MUST
preserve `touchedFiles ?? []` at the call site and the fail-loud field naming
(`gate: ${slot}...` messages) or the EV-66 tool tests legitimately move.

### 3.2 `resolveRoute(card: ParsedCard | string, repoRoot): RouteResult`

Pure-with-fs, **no model call in any branch, ever**. Returns
`{ mode: DispatchMode; source: "recorded" | "fallback" | "full-unpackable";
stateHash?: string; matchedCallId?: string; basis: string }`. Rules in order:

1. `loadGatePolicy(repoRoot).mode === "off"` ⇒ `{ mode: "Deliberate", source:
   "fallback", basis: "gate mode off — no recorded decision" }`. No hash
   computed, no ledger read, no budget load (this ordering also sidesteps
   `resolveGateStateBudget`'s throw on a stripped off-mode policy).
2. Card not packable (missing/empty `## Acceptance`, or any empty
   id/title/goal) ⇒ `{ mode: "Deliberate", source: "full-unpackable", basis:
   <the thrown message> }` — catch around `buildGateState`; no hash, no
   ledger read, no gate call. Such a card can never have a matching record
   (intake would have thrown packing it); full path is the only consistent
   outcome and the safe side. Never silent, never mis-routed reduced.
3. Compute `stateHash = buildGateState(card, repoRoot).stateHash` with
   `touchedFiles: []` (the same value intake passed — anything else can never
   match). Consequence to state plainly: wiki/tree drift changes the hash even
   with identical card text — **unchanged packed state** is the contract;
   unchanged card text is necessary but not sufficient.
4. Read the ledger; select `kind: "call"` records with `stateHash === hash`
   that are **valid**: `record.policyVersion ===
   loadGateDecision(repoRoot).version` AND `rederiveResolvedMode(record,
   decideWithCurrentPolicy) === record.resolvedMode`. Invalid lines are
   dropped, never thrown on.
5. No valid match ⇒ `{ mode: "Deliberate", source: "fallback", basis: "no
   recorded decision for the current packed state" }`. **No gate call is
   issued by the routing read** — re-gating a drifted state is the next
   intake's job (`council_gate` at /features-new), not step 1's.
6. Valid matches, all agreeing ⇒ **latest in file order wins** (file order,
   not `recordedAt` — injectable clocks; the outcome join is already
   last-wins; same-bytes duplicates are expected re-measurements).
7. Valid matches, disagreeing ⇒ **strongest valid mode wins** under
   Deliberate > Verify > Direct — a later disagreeing line for an identical
   hash is evidence the decision is unstable, and taking the newest silently
   would resolve that instability toward the cheaper mode.
8. A matching failed-call record (`failure.class` present, fail-closed
   `resolvedMode: "Deliberate"`) is a valid recorded decision used verbatim.

Only a ledger's verbatim recorded `resolvedMode` can ever produce `Verify` or
`Direct` from this function; every non-match, drift, ambiguity, unpackable
card, off policy, and read error returns `Deliberate` with a named basis.

### 3.3 `observedTouchedFiles(repoRoot: string, headSha: string): string[]`

`git diff --name-only <base>..<headSha>` where `<base>` is the merge-base of
`origin/main` and `headSha`. Executed **read-only in the main checkout**
(diffs mutate no branch state — main-repo branch-state immutability holds;
the head worktree is where the branch lives, but the read is a pure diff).
Paths repo-root-relative. **Commit-range form with the base pinned; no
working-tree read, never ambient `git status`** (EV-64's explicit-input
rule). Protocol: `origin/main` is resolved ONCE at run start and never
re-fetched mid-card; the base is pinned then.

### 3.4 Re-check predicate and helpers

- `recheckOwed(matchedStateHash, currentPackedStateHash): boolean` — the
  pure call-gating predicate: `rebuiltStateHash !== matchedStateHash`. It
  decides only whether a re-gate call is owed; what the override fires on is
  decided by the model call (§5). No path-pattern policy file, no
  file-set-derived question heuristic.
- `strongest(a: GateDecisionMode, b: GateDecisionMode): GateDecisionMode` —
  rank helper implementing Deliberate > Verify > Direct (the escalation-only
  ratchet clamp; never a `MODE_PANELS` set-difference).
- `effectiveModeForCard(repoRoot, runId, runnerJobId): DispatchMode` — the
  **mode authority** for the merge check. Card-scoped subtree read over the
  run's manifests: locate the ROOT manifest(s) with `id === runnerJobId`
  (escalation re-entry dispatches a fresh runner, so a card may have several
  ROOTs — **union the card's ROOT subtrees**), flatten only those subtrees.
  Deliberate iff the subtree union contains ≥1 **generator** dispatch from
  the set `{ principal, designer, consolidator }` — explicitly NOT
  `MODE_PANELS.Deliberate` minus `MODE_PANELS.Verify`, because
  product-owner is dual-role (a Deliberate panel seat AND the escalation
  ruling seat dispatchable on a Verify card) and a set-difference
  derivation would misclassify an escalated Verify card as Deliberate.
  Otherwise the ROOT manifest's `mode` stands. ROOT absent ⇒ throw with a
  named basis (fail-safe HALT/full — EV-70's line, never a reduced
  fallback). Reads manifests only (pure over `readManifests`); the
  `/council-eval` stray-dispatch case is excluded structurally because only
  the runner ROOT's subtree is read.

## 4. New tool layer: `extensions/gate-route-tool.ts`

`registerRouteTool(pi, repoRoot)` registers ONE parent-only tool,
**`council_route`** — registered in `extensions/index.ts` on the parent path
next to `registerGateTool` (mirroring the `council_gate` seam), never via
`registerHubTools` (which the child path also calls — `council_route` must
not exist in seat children). The tool imports `runGate`/transport: it IS the
sanctioned gate caller for re-checks; the fence protects the pure module,
not the tool.

Tool params: `{ op: "route" | "recheck" | "authority"; cardPath: string;
headSha?: string; runId?: string; runnerJobId?: string }`.

- **`op: "route"`** (step 1) — read the card file, `parseCardFile`,
  `resolveRoute`; return `{ mode, source, basis, stateHash?, matchedCallId? }`.
  The tool **returns the mode to the caller** — the EV-66 verdict-opacity
  ruling does not apply here: the facilitator IS the router and cannot route
  on a hidden verdict. Enforcement is procedural (tool + amended procedure);
  the falsifier over manifests is the teeth.
- **`op: "recheck"`** (step-8→9 boundary; `headSha` required) — resolve the
  route first (same rules as above). If the route is not a valid recorded
  reduced mode, return the fallback result unchanged. Otherwise compute
  `observedTouchedFiles(repoRoot, headSha)`, rebuild `buildGateState` with
  those observed paths (as `{ path, linesChanged }` entries — derive
  `linesChanged` from the diff; any positive integer is acceptable since the
  hash depends on the packed bytes, and the value must be recorded honestly).
  - Rebuilt hash **equals** the matched record's hash (including the
    intake-recorded-`[]`-and-observed-empty case) ⇒ the record stands, route
    unchanged, **zero calls**, return the unchanged route.
  - Rebuilt hash **differs** ⇒ issue **exactly one** `runGate` call (loading
    policy/questions/decision exactly as intake does; policy mode must not
    be "off" — `runGate` already throws on that). Its normal v2 call line —
    with the **rebuilt (observed) stateHash**, real answers, real basis — IS
    the "ledger line recording the re-route". No new record kind,
    schemaVersion stays 2, no ledger-pin edit. The route becomes
    **`effective = strongest(recordedMode, verdict)`** (the escalation-only
    ratchet: a re-gate may move the mode toward greater deliberation, never
    below it). Append `basisSuffix` per §5. Return the effective mode and
    the new callId.
- **`op: "authority"`** (EV-70-facing; `runId` + `runnerJobId` required) —
  `effectiveModeForCard`; used by the features-deliver merge check. EV-69
  guarantees the function and this surface; EV-70 owns the merge-check
  fixture and its HALT lines.

## 5. The ratchet in `basisSuffix`

`runGate` gains one OPTIONAL opt `basisSuffix?: string` — an option on the
input, NOT a new line field; when present it is appended to the appended
line's `basis` (still one write, one line, schemaVersion 2). Semantics:

- Re-gate lands **Deliberate** on a recorded Verify/Direct card (UP-escalation):
  no suffix — the verdict's own basis names the fired override.
- Re-gate lands **Direct** on a recorded Verify card (the ratchet holds
  Verify): `basisSuffix` carries the ratchet note, e.g.
  `composite 3.80 ≥ direct threshold 3.40 — ratchet holds Verify` (the
  wording is implementation's, but it MUST name that the recorded mode
  holds over the verdict and must not invent a fired override — no
  override fired on a Direct landing).
- Execution clamps in the tool layer: `effective =
  strongest(recordedMode, verdict)`; execution follows `effective`, the line
  records the **verdict verbatim** (`rederiveResolvedMode(line) ===
  line.resolvedMode` by construction — the documented recomputability check
  stays true for every future consumer; EV-65 Q1 untouched; EV-67 renders
  verbatim). The merge-check authority never reads the line — it reads the
  forest (§3.4), which is already ratchet-aware.

No cross-run leak: the re-gate line's stateHash is the rebuilt (observed)
hash; a later run's intake-`[]` read never matches it.

## 6. Procedure amendments (exact amended surface — Item A)

The amended surface of `council/procedures/council.md` is an EXPLICIT list of
exactly three things; nothing else in the file changes:

1. **Step 1** — amended so that a recorded mode is authoritative and step 1's
   full-vs-mechanical judgment is the fallback. The amendment MUST include:
   - Call `council_route` (op `route`) before judging. If it returns a
     recorded mode, that mode is authoritative — do not re-judge it; pass it
     as the dispatch `mode`. If it returns a fallback/unpackable result,
     proceed with step 1's own judgment below (this keeps the packaged `off`
     default from silently converting every card to full deliberation).
   - **The surface-touching bit is recorded REGARDLESS of recorded mode**
     (Item B condition 1): it feeds step-13 designer routing and — on the
     Verify path — the skeptic's step-9 dispatch input, so branch
     verification looks at the rendered surface. On the fallback path the
     bit still gates `designer` seating as today.
   - A step-1 judgment that disagrees with a matching record does not reopen
     the routing; it is filed as a follow-up card.
2. **The step-8→9 boundary sentence** — amended so the facilitator calls
   `council_route` (op `recheck`) with the branch head immediately BEFORE
   the skeptic dispatch (the first dispatch after a branch exists), and that
   on the Verify path the step-9 dispatch input includes the recorded
   surface-touching bit. If the re-check re-routes to Deliberate, proceed to
   the re-route block below.
3. **ONE new named re-route block, placed AFTER the step-8→9 re-check,
   RESUMING AT STEP 3** (Item A ruling). Step 2 stays BYTE-IDENTICAL. The
   block:
   - declares its own roster: `principal` + `designer` per rule (designer
     seated when step 1 recorded the card surface-touching);
   - states that the owner's **first-pass record is its pushed step-8
     branch** — the already-settled owner dispatch is not repeated;
   - runs steps 3–6 (bounded exchange, skeptic attack, synthesis, routing)
     against that first-pass record;
   - writes the spec (step 7);
   - re-dispatches the owner at step 8 **ONLY IF the deliberation overturns
     the design** — then against the existing branch, same run; if the
     design confirms the branch work, that dispatch verifies rather than
     re-implements;
   - continues through steps 9–12 as usual.

Exactly-one-owner is a per-path invariant: clean Verify ⇒ owner==1;
the re-route arm makes NO owner-count assertion (the owner is re-dispatched
only on overturn, so its count is design-dependent).

The Deliberate column of `MODE_PANELS` seats `designer` unconditionally under
a recorded Deliberate (R4), replacing step 2's surface-touching conditional —
the conditional survives only on the fallback path; this is a consequence,
not a new amendment surface.

## 7. features-deliver.md — mode-aware merge-check criteria

The five criteria become a mode→criteria table keyed on the card's routing
mode (read mechanically via `council_route` op `authority` — the run
substrate, never a seat's report):

| Mode | Criteria |
|---|---|
| Deliberate | the current five, verbatim |
| Verify | **all five hold**, with criterion 3's basis mode-scoped to the **single** Verify skeptic dispatch (there is no step-4 attack round to draw objections from) |
| Direct | criteria 1, 2, 5 (no skeptic, no judge — the test suite is the gate) |

The Direct column is defined in prose here; **EV-70 owns the Direct fixture
and the two EV-70 HALT lines** (`no recorded execution mode`, `requires a
goal evaluation and none is recorded`). EV-69 guarantees Verify cards always
have both a recorded mode and a judge dispatch, which the falsifier proves.

## 8. Item B — the designer-review loss, named in the spec's own words

A recorded Verify on a surface-touching card seats no `designer` (R4; no gate
override covers surface-touching — verified against decision.json during the
deliberation). A user-visible redesign could therefore route Verify and lose
the design review the old full-council path guaranteed. This card accepts
that loss as a TEMPORARY, NAMED residual under the ruling's conditions:
(1) step 1 records the surface-touching bit regardless of recorded mode, and
it feeds step-13 designer routing and the Verify skeptic's step-9 dispatch
input; (2) the step-14 wiki ingest names the gap in its own words (a raw
note under `vault/raw/`, not a hand-edit of `vault/wiki/`); (3) step 13 files
ONE follow-up card (`epic: EPIC-13`) whose home is the gate's QUESTION SET —
a fourth user-visibility question landing under EV-72's pre-registration
discipline, with the question-set version bumped. Per R4, no designer is
seated in Verify — the residual is procedural compensation, not seating.

**the real `council_route` tool function is invoked** for the route read and

  answers an override-firing decision ⇒ EXACTLY ONE new v2 call line naming

  principal/designer/consolidator present in the dispatch set; **NO

- **Ratchet arm (C1).** On a Direct-landing fixture: (a) the line's
  `resolvedMode` is Direct AND `rederiveResolvedMode` agrees; (b)
  `council_route` returns effective Verify; (c) the subtree read gives
  Verify; (d) the basis contains the ratchet sentence. The re-route arm must
