# EV-78 — Follow-up disposition decisions as repo-overridable packaged data

Design spec, written from the settled deliberation (rounds 1–3, skeptic step 4,
consolidator step 5) plus the binding product-owner ruling of 2026-09-21
(`vault/raw/2026-09-21-po-ev78-thresholds-schema-ruling.md`, appended to the
card record). Nothing here reopens a settled point.

## Goal restatement

The follow-up review's typed question set and decision policy are packaged
data under `council/gate/followup/`, resolved whole-file with a repo-local
override first-hit, failing loud on any unknown key — mirroring the shipped
card-gate loaders (`loadGateQuestions`, `loadGateDecision` in
`extensions/gate.ts`) arm for arm, with the followup-specific vocabulary and
the ruling's schema decisions.

**Out of scope (later cards):** `decideFollowup`, the behavioral exactly-one
partition proof, transport, ledger, rendering — EV-79's surface and beyond.
This card ships loaders + packaged data + tests only.

## Exports (all in `extensions/gate.ts`, sibling to the gate loaders)

```ts
export const FOLLOWUP_DISPOSITIONS = ["File", "Merge", "Drop"] as const;
export type FollowupDisposition = (typeof FOLLOWUP_DISPOSITIONS)[number];
/** Ruling Q2: the override lane's disposition is a declared subset —
 * File is unreachable by override. */
export type FollowupOverrideDisposition = Exclude<FollowupDisposition, "File">;

export interface FollowupOverrideRule {
	question: string;
	option: string;
	basis: string;
	disposition: FollowupOverrideDisposition;
}

export interface FollowupDecisionPolicy {
	version: string;
	/** question id → composite weight (positive). */
	weights: Record<string, number>;
	/** question id → the criterion option that counts as redundant evidence
	 * (renamed from the gate's `mechanical`; see below). */
	countedOption: Record<string, string>;
	/** Confidence floors for the floored answer types of the followup
	 * vocabulary — exactly `choice` (noul carries noulThreshold instead,
	 * same as the shipped gate where score/choice floor and noul does not). */
	floors: { choice: number };
	noulThreshold: number;
	noulProbabilityOf: string;
	thresholds: { merge: number; drop: number };
	overrides: FollowupOverrideRule[];
}

export function loadFollowupQuestions(repoRoot: string): { version: string; questions: Record<string, GateQuestion> };
export function loadFollowupDecision(repoRoot: string): FollowupDecisionPolicy;
```

## Loader mechanics

### `gateDirs(repoRoot, ...sub)`

Generalize the private `gateDirs(repoRoot)` to `gateDirs(repoRoot, ...sub)`
(default empty). With no `sub` it is byte-identical for existing callers
(`gate.ts:172,248,424` — verify at implementation). The followup loaders call
`gateDirs(repoRoot, "followup")` → `<repo>/$CONFIG_DIR_NAME/council/gate/followup/`
then `<PKG_ROOT>/council/gate/followup/`, first-hit whole-file, no field merge
(R5; the existing `readGateFile` already owns this).

### Shared helpers, verbatim

Reuse `readGateFile`, `gateFail`, `nonEmptyString`, `describeShape`,
`basisSafeString`, `unitNumber` as-is — no fork, no byte-parity test arm
(settled point 8). The one shared validator that changes,
`validateGateQuestion`, changes inside:

### `validateGateQuestion` gains an optional `allowedTypes` parameter

Signature becomes
`validateGateQuestion(file, keyPrefix, raw, allowedTypes: readonly GateQuestionType[] = QUESTION_TYPES)`.
The default keeps both shipped call sites byte-identical (the card gate keeps
admitting `score` — pinned by the existing suite staying green in the same
run, skeptic O5). The followup call passes `["choice", "noul"]`, so its type
FAIL lists exactly `"choice", "noul"` with the token `score` absent. The
type-set parameterization lives inside the private validator, not in a
wrapper — a wrapper special-casing `score` would leak the gate's
`choice, noul, score` expected-list into followup FAIL copy.

Note: with `allowedTypes = ["choice", "noul"]`, the `score` criteria branch
(the ordered string-array arm) is unreachable for followup questions; the
`criteria` shape follows the type as shipped (option→description record for
`noul`/`choice`).

### `loadFollowupQuestions`

Mirror `loadGateQuestions` (root object, unknown-key refusal, `version`
non-empty, `questions` non-empty record, per-question
`validateGateQuestion(..., ["choice", "noul"])`). Same `version`
convention; packaged value `"followup-questions-1"`.

### `loadFollowupDecision`

Mirror `loadGateDecision` arm for arm, with the ruling's deltas:

- **Root keys:** `version, weights, countedOption, floors, noulThreshold,
  noulProbabilityOf, thresholds, overrides`. `mechanical` is not in the set →
  a followup policy carrying `mechanical` is an unknown-key one-line FAIL
  (settled point 3 — the rename is real, not an alias).
- **`weights`:** identical parse (non-empty record, positive finite numbers,
  FAIL naming `weights.<id>`).
- **`countedOption`:** same shape check as the gate's `mechanical` — record
  keyed by question id, ids ≡ `weights` ids (missing id → FAIL naming
  `countedOption`; extra id → FAIL naming `countedOption.<id>`), non-empty
  strings. Referential bytes mirror `gate.ts:449–460` (skeptic O4).
- **`floors`:** object with exactly the sub-key `choice`
  (unknown sub-key → FAIL naming `floors.<key>`, expected-list exactly
  `choice`); value in `[0, 1]` via `unitNumber(file, "floors.choice", v, 0)`.
- **`noulThreshold`:** `unitNumber(file, "noulThreshold", raw.noulThreshold, 0)`;
  **`noulProbabilityOf`:** non-empty string — both as shipped.
- **`thresholds` (ruling Q1):**
  1. must be a JSON object — `Array.isArray` guard kept; an **array value
     fails loud** as the shape FAIL naming `thresholds` (the same
     `expected an object with merge and drop thresholds`-class line; the JS
     `typeof` trap the shipped loader already handles stays handled);
  2. any sub-key other than `merge`/`drop` → FAIL naming
     `thresholds.<key>`, expected-list exactly `merge, drop`;
  3. `merge` — finite number **> 0**, else FAIL naming `thresholds.merge`
     (`expected a finite number > 0`, FLLWUP-74 class-1 mirror of
     `gate.ts:466–473`);
  4. `drop` — finite number ≥ 0, else FAIL naming `thresholds.drop`
     (mirror of the shipped `direct`);
  5. **strict `merge < drop`**, else FAIL naming `thresholds` — one numeral
     tighter than the shipped `verify ≤ direct` because equality empties the
     Merge band.
- **`overrides` (ruling Q2):** array; per rule: object (not array);
  `question`, `option`, `basis` non-empty strings with `basisSafeString`
  BEFORE the referential check (FLLWUP-74 class-4-before-class-3, as
  shipped); `disposition` — a non-empty string in `{Merge, Drop}`; missing
  or `File` or any other value → FAIL naming `overrides.<i>.disposition`
  with an expected-list naming exactly `"Merge", "Drop"` — the token `File`
  is absent from that list. Unknown rule keys → FAIL naming
  `overrides.<i>.<key>`. Referential check: `question` id must exist in
  `weights`, mirroring the shipped override referential arm.

### The structural partition (loader-proven; behavior is EV-79's)

Under the ruling's rules the partition is structural: File = composite
`< merge` (non-empty since `merge > 0`), Merge = `[merge, drop)` (non-empty
by strict `<`), Drop = `≥ drop`; File is the composite's else-arm, never
declared in data. EV-78's loader proves this structure; the behavioral
exactly-one proof (`decideFollowup` walking floors → overrides → composite,
unanswered → File, R4 precedence) is EV-79's (settled point 4).

## Packaged data

### `council/gate/followup/questions.json`

Three questions in the candidate-redundancy domain, same shape as the
shipped gate questions (`type`, `instructions`, `criteria` record):

- `duplicate` — `noul`: "Is this card substantially the same work as an open
  card or a same-run sibling?" (`yes`/`no` criteria descriptions).
- `alreadyDone` — `noul`: "Is the work this card describes already resolved
  or marked obsolete on the board?" (`yes`/`no` criteria).
- `actionable` — `choice`: "Is there a concrete change a card could carry
  here?" (`yes`/`no` criteria).

`version: "followup-questions-1"`.

### `council/gate/followup/decision.json`

```json
{
	"version": "followup-decision-1",
	"weights": { "duplicate": 1, "alreadyDone": 1, "actionable": 1 },
	"countedOption": { "duplicate": "yes", "alreadyDone": "yes", "actionable": "no" },
	"floors": { "choice": 0.6 },
	"noulThreshold": 0.6,
	"noulProbabilityOf": "yes",
	"thresholds": { "merge": 1.0, "drop": 2.0 },
	"overrides": [
		{ "question": "alreadyDone", "option": "yes", "basis": "already resolved or obsolete", "disposition": "Drop" },
		{ "question": "duplicate", "option": "yes", "basis": "same work as an open card", "disposition": "Merge" }
	]
}
```

`countedOption` names the redundant-evidence option per question, so the
composite drives *away from* File as redundancy rises — the correct inversion
of the card gate's direction (where `mechanical` drives toward the
reduced-scrutiny end). No `policy.json` equivalent: the followup shares
`GATE_PINNED_MODEL`/endpoint/`gate` section, and the one on-disk budget stays
`council/gate/policy.json` via `loadGatePolicy` (settled point 10 — no
`followup/policy.json`, ever; EV-80's note).

## Tests — `test/ev78-followup-data.test.ts`

On the `test/gate.test.ts` fixture pattern (temp `repoRoot` via
`fs.mkdtempSync`; packaged resources resolve through `PKG_ROOT`; fixture
forcing through the override path per R5 — packaged files are never edited):

1. **Packaged load** — `loadFollowupQuestions`/`loadFollowupDecision` on the
   real repo root return the packaged files intact; the three dispositions
   are spelled exactly `File`, `Merge`, `Drop` (vocabulary pinned).
2. **First-hit whole-file override** — a repo-local fixture dir with a
   distinctive `questions.json` (a question the packaged set lacks; the
   packaged question absent) shadows whole-file; same for `decision.json`.
3. **Fail-loud arms** (each pinned to its exact FAIL bytes):
   - malformed JSON;
   - unknown root key (each file);
   - override `disposition: "Delete"` → FAIL naming `overrides.<i>.disposition`;
   - **ruling Q2:** override `disposition: "File"` → FAIL naming
     `overrides.<i>.disposition`, expected-list exactly `"Merge", "Drop"`;
     missing `disposition` → same subject;
   - **ruling Q1:** the three skeptic array exhibits —
     `[{at:1.0, disposition:"Drop"},{at:2.0, disposition:"Merge"}]`,
     `[{at:1.0, disposition:"Merge"},{at:2.0, disposition:"File"}]`,
     `[{at:1.0, disposition:"Merge"}]` — plus the owner's round-3 schema
     sketch array, each pinned load-FAILing on the **array-rejection line
     naming `thresholds`**;
   - `merge: 0` → FAIL naming `thresholds.merge`;
   - `merge == drop` (strict-ordering) → FAIL bytes naming `thresholds`;
   - override `question` id absent from `weights` → FAIL;
   - out-of-range floor (e.g. `floors.choice: 1.5`) → FAIL naming
     `floors.choice`;
   - question `type: "score"` → FAIL with expected-list exactly
     `"choice", "noul"` (O5);
   - `countedOption` missing an id / carrying an extra id → FAIL naming
     `countedOption` / `countedOption.<id>` (O4);
   - followup `mechanical` key → unknown-key FAIL (rename pinned).
4. **Same-run gate green** — the card-gate `score` acceptance stays green in
   the same run (`test/gate.test.ts` unchanged and passing); `gateDirs()`
   with no `sub` byte-identical for existing callers (existing gate tests
   passing is the pin).

## Known limitations carried forward

- No cross-file referential validation questions↔decision (gate precedent;
  flagged for EV-79's caller — settled point 9).
- **Named residual (ruling):** a `drop` above the max attainable composite is
  load-legal — Drop is then structurally unreachable by composite (still
  reachable by override). Home: the first threshold-move card (arrives as its
  own card per the intake ruling).
- Version-keyed, whole-file-first-hit, default-`off` surface: the shape is
  one loader block + one test file to flip pre-merge (ruling reversibility).
