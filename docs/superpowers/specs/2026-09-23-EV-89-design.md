# EV-89 — Systematize Phase 1 open-judgment rulings into a durable class-enumerated record

Design spec — settled by the EV-89 deliberation (rounds 0–2), the Skeptic attack
(O1–O4), the consolidator synthesis (points 1–15), and the product-owner ruling on
J1/J2 (appended verbatim to the card). This spec writes up what was settled; it
derives nothing new.

## 0. Scope boundary (ruling-settled)

**EV-89 ships the mechanism only. This run writes no `council/phase1-rulings.json`.**
The product-owner ruling (J1) holds that population fails the fold-in test: no
acceptance bullet (1–10) requires populated EPIC-23 data, and the fence's absent→skip
and unresolved-entry-green arms make the card's acceptance fully green with no record
file at all. J2 is moot for this run, and carries a fixed fence: should this run ever
write the record, P1-1's closed three-write enumeration does not cover the commit, and
extending it requires a new P1 ruling recorded by the human on EPIC-23's Phase 1 record
*before* the first push — absent it, the shipped refusal/HALT governs, never a silent
push. The designer's held position (Phase 1's last step commits the record before
dispatch) is a sentence in the *amended procedure* — mechanism, binding future runs,
not this one — and survives unchanged.

Out of scope (synthesis point 12, uncontested): engine changes (`extensions/*`), the
seats schema, the gate ledger, seeding the record into `council/scaffold/`, and writing
EPIC-23's actual class rulings.

## 1. The artifact (synthesis points 1, 4, 5, 6)

`council/phase1-rulings.json` — the **class-enumeration record** (this name
disambiguates it from council.md step 12's "the run's Phase-1 record", which continues
to mean card-face rulings; no `council.md` edit is made — Principal round 2,
uncontested). Sibling of `council/board.md` (P1-4). Shape: an **ordered array** of
entries, each carrying `class`, `stakes`, and **exactly one** of:

- `ruling` — a non-empty string (uniform string; no polymorphic per-tier shapes —
  designer conceded in round 1 final);
- `reason` — a non-empty string beginning with the structured prefix `n/a: ` (P1-6).

`stakes` carries one of the three tier literals, in acceptance 8's order:
`card` → `run-committing` → `portfolio`. Class names are **canonical prose strings**
(the refusal token and record key are the same surface as the procedure text; snake_case
is rejected as a second canonical — settled round 1). No `version` field (no named
consumer; gold-plating — settled round 1).

## 2. The class list in Phase 1 (acceptance 1, 8; synthesis point 2)

`council/procedures/features-deliver.md` Phase 1 replaces the current
"Surface-touching cards raise the most predictable class…" prose with a closed,
ordered enumeration of **exactly five** named open-judgment classes, rendered under
three stakes-tier headers, ordered per-card reversible → run-committing →
portfolio-level:

| Tier | Canonical class string (pinned verbatim) | Prompt elaboration (question-shaped, one line) |
|---|---|---|
| Per-card reversible | `surface copy` | What exact words does a person see on a visible surface? |
| Per-card reversible | `state and field naming` | What is this state, field, or status called, here and everywhere it renders? |
| Run-committing | `uncertainty display` | How much uncertainty does the run show a person about data with no realtime availability and no prices? |
| Run-committing | `error and empty-state text` | What does a person read when the run has nothing to show or something failed? |
| Portfolio-level | `gate user-visibility` | Is the routing gate's verdict shown to the human, or kept as information only? |

The procedure states this list is **the single source the run reads** (acceptance 1).
The prose pin is the class list's only third copy (§6); `validate.py` carries **zero**
canonical class-name strings (EPIC-14 J2 rule; acceptance-9 scoping pin — Principal
round 2). The "Record each ruling on the card face it applies to" paragraph stays for
card-specific judgments; class-level rulings move to the record.

## 3. The fence in `validate.py` (acceptance 4, 10; P1-4; O2 remedy)

Both packaged `validate.py` copies change **in lockstep** (root +
`council/scaffold/council/validate.py`; T3/T5 byte-parity cascade in scope — §7):
a structural-and-grammar check on `council/phase1-rulings.json` — **never
completeness, never membership, never anti-shrug** (synthesis point 9; bullet 4
mandates pin-enforcement only). Named `FAIL:` lines, never a traceback, following the
`check_gate_registrations` absent-file-skip precedent (`council/validate.py` gate-policy
fence):

- file absent → skip, exit 0 (consumer repos that never run `/features-deliver` stay
  green — the exact "No policy.json, nothing to pre-register" arm);
- unreadable JSON → named FAIL;
- top-level `classes` not an array → named FAIL;
- entry not an object → named FAIL (O2 remedy: today a `42` entry is a TypeError
  traceback);
- entry missing `class`, or duplicate `class` → named FAIL;
- both `ruling` and `reason` present in one entry → named FAIL (O2 remedy);
- `ruling` present but empty string → named FAIL (O2 remedy);
- `reason` present but not beginning `n/a: ` → named FAIL (P1-6 grammar);
- `stakes` missing or not one of the three tier literals → named FAIL;
- `stakes` sequence not non-decreasing in tier order (`card` → `run-committing` →
  `portfolio`) → named FAIL (owner round-2 convergence; the ordered array whose order
  nothing checks is a comment, not an invariant).

No completeness check: an entry with neither `ruling` nor `reason` is simply
**unresolved**, and validate stays green — exactly as a `Backlog` card does. The
tier-literal enum is the only class-adjacent data the fence knows.

## 4. The refusal (acceptance 3, 5; P1-5; synthesis point 8)

Stated in Phase 1's text: before dispatching any `council-runner`, for **each** named
class the record carries neither a `ruling` nor an `n/a:` reason for, the orchestrator
issues one line per unresolved class — all of them, not first-only — with the fixed
stem, the class interpolated verbatim:

```
Phase 1 unresolved: <class>
```

The text states explicitly that this refusal is a distinct, named literal — **not** the
run's generic `HALT:` environment-failure line — so an operator can locate the
unresolved class from the refusal text alone. The class-enumeration record's commit
clause (§5) and this refusal share one property: the procedure names the requirement,
never self-authorizes (FLLWUP-60 posture).

## 5. The commit-authorization clause (synthesis point 14; riding judgment)

One unconditional sentence in Phase 1 (the FLLWUP-60 clause shape, exactly as the
product-owner ruling settled it — unconditional about the authorization requirement,
silent on when population happens):

> Any run that commits the class-enumeration record (`council/phase1-rulings.json`) to
> `main` does so only under a recorded, run-scoped, human-granted Phase-1 authorization
> recorded **before** the run's first record push; without it, the run refuses the push
> and halts — the push is never silently executed.

This run grants itself nothing: P1-1's closed enumeration covers exactly three writes,
not this one (skeptic closed-green on the enumeration's exactness), and no extension is
sought (J1/J2).

## 6. The prose pins (`test/prose.test.ts` pattern; acceptance 3, 8, 9)

Extending `councilMarkdown()`'s pattern, with O1's remedy folded in — **every ordered
pin carries a presence guard (`indexOf ≥ 0`) before asserting order** (O1: a
monotonicity-only pin passes green on a file containing none of the strings):

1. All five canonical class strings appear in packaged `features-deliver.md`, each
   present (`≥ 0`) **and** in stakes order (monotonic `indexOf`).
2. The refusal: the `Phase 1 unresolved:` stem **and** the sentence that Phase 1 does
   not dispatch any `council-runner` while a named class carries neither a recorded
   ruling nor a not-applicable reason. Deleting or materially weakening either reds.
3. `council/phase1-rulings.json` appears in packaged `features-deliver.md` **and** in
   `council/agents/council-runner.md` (bullet 6's discoverability seam — the runner
   reads **two files** at `<escalation_contract>` step 1: the procedure = class list,
   the record = rulings; membership is LLM-judged; validate.py is grammar-only —
   synthesis point 13).
4. The `n/a: ` prefix appears in the procedure (bullet 7's grammar).
5. The anti-shrug sentence: "a not-applicable reason names the absent figure, not a
   placeholder" (designer's conceded home: prose + pin, never `validate.py`). The
   sophisticated-shrug residual ("n/a: not relevant to this epic" passes prefix and
   non-emptiness but says nothing) is named here as accepted, LLM-judged at Phase 1
   time — not fenced.
6. The ruling-scoping sentence (bullet 9): a Phase 1 recorded ruling binds every seat
   for the named classes only; it does not remove `designer` from deliberation and
   does not narrow any other design dispute's routing under council.md step 6.
7. The commit-authorization clause (§5) appears in Phase 1.

The corresponding runner-discoverability edit: `<escalation_contract>` step 1 in
`council/agents/council-runner.md` names `council/phase1-rulings.json` as where
standing class rulings live, card faces remaining the home of card-specific ones.
