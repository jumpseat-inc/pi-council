# EV-83 — Route the follow-up decision through `/features-deliver` Phase 3 and the council-runner escalation path

## Goal (from the card, binding)

`council/procedures/features-deliver.md` Phase 3 and `council/agents/council-runner.md`
both route each surfaced follow-up candidate through the follow-up decision, and a
container whose decision fails or cannot resolve returns the candidate as an
`ESCALATION` on its report and writes no card, proven by a runner fixture asserting
`ESCALATION` and zero unconfirmed cards.

This spec is the settled design from the card's full deliberation (three rounds,
skeptic attack, consolidator synthesis — see `council/cards/EV-83.md`) plus one
binding product-owner ruling
(`vault/raw/2026-09-22-po-ev83-confirmation-authority-ruling.md`). An owner reading
only this file implements exactly what is written here; nothing below is open for
redesign.

## Binding rulings this design implements

- **R6** — the disposition outcome rides `DONE` and `ESCALATION` only; `RETIRED`
  keeps its documented card-withdrawal meaning verbatim; `<return_contract>` is not
  edited (the four-tag list is byte-unchanged).
- **EV-78** — the runner names the recorded decision, never overrides it; outcome
  vocabulary is `File | Merge | Drop` from the recorded line.
- **EV-82 composition-site answer** — `runFollowupReview`
  (`extensions/followup-tool.ts:87`) followed by `renderFollowupLinesFromRepo`
  (`extensions/followup-render.ts:242`) is the ONE follow-up composition
  (FLLWUP-96). EV-83 adds its **second caller**; it never builds a second
  composition.
- **The confirmation-authority ruling (2026-09-22, binding).** The recorded
  (engine-minted) gate decision is the container's disposition *source*, never its
  confirmation. In-container, the confirmation act belongs to a ruling seat reached
  through the orchestrator's `ESCALATION` service. Therefore: a runner with a
  resolved `active` disposition also escalates — carrying each drafted candidate by
  title with the recorded `Mode:` line verbatim as the disposition to be
  **ratified** — writes nothing, and applies + writes only on the resumed dispatch
  whose input contains the confirming ruling, at which point `DONE` carries the
  per-candidate outcome lines. `advisory` routes to `ESCALATION` keyed on the
  result-level `mode` flag exactly like `off`, carrying rendered advisory lines as
  information only, basis advisory-only. The three escalation arms must stay
  **distinguishable by basis**: failed/unresolved (engine failure bytes),
  confirmation-pending (the recorded `Mode:` line), advisory-only (information
  lines). `council.md` §13 is **not** edited by EV-83.

## Design

### 1. Engine half — one child-mode tool `council_followup_review`

A single new tool wraps both exported composition halves and returns, in one
result, the mechanical per-candidate facts **plus** the rendered disposition lines
— so every basis byte in a runner's report is engine-derived by construction, not a
model echo. It is a second *caller* of the same composition; FLLWUP-96 intact.

- **Child-mode only.** Registered inside `runChildMode` (`extensions/child.ts`)
  when the seat carries the grant — never in `extensions/index.ts`'s parent path.
  The parent-session pair `council_followup_gate`/`council_followup_render` and
  their registrations stay byte-unchanged.
- **`mergeTargets` stays a tool parameter**, passed through to
  `renderFollowupLinesFromRepo`; the tool must not absorb the dedup pass.
- **Grant keyword `followup`**, mirroring the `hub` precedent (convention 8),
  wired at exactly three sites:
  1. `extensions/seats.ts` — `grantsFor` returns `{ hub, followup }` with
     `followup: t.has("followup")`; `buildChildArgv` pushes
     `council_followup_review` into the `--tools` allowlist when followup-granted.
  2. `extensions/child.ts` — `runChildMode` registers the tool when
     `grantsFor(seat).followup`; `isCallAllowed` permits
     `council_followup_review` under the grant (control: `council_dispatch`
     stays governed by the hub grant only).
  3. `council/agents/council-runner.md` frontmatter — `tools:` gains `followup`
     (current line ends `... task, hub`).
- **`extensions/index.ts` comment rewritten** (the EV-82 comment at ~line 632
  currently says "EV-83's runner seam is the exported runFollowupReview, not a
  tool" — a category error an LLM container cannot import TS): the *composition*
  is the exported `runFollowupReview` + `renderFollowupLinesFromRepo` pair (never
  a second composition); the *transport* into a child container is the granted
  `council_followup_review` tool.
- The tool implementation calls `runFollowupReview(candidates, repoRoot, opts)`
  then `renderFollowupLinesFromRepo(...)` against the actual result object (the
  join is by `callId` in-process — no model re-transmission of mechanical facts).
  The result exposes:
  - the result-level `mode` flag (`"off" | "advisory" | "active"`) — the runner's
    escalation routing keys on this flag, never on per-candidate strings;
  - per candidate: `title`, `callId`, `status` (`"ok" | "failed"`), and the
    rendered line verbatim (the literal `Mode: <disposition> — <basis>` byte
    sequence for a resolved candidate; `gate call failed: <reason>`, a
    total-failure literal, or a `FOLLOWUP_RENDER_FALLBACK` literal for an
    unresolved one).
- **The resolved-vs-failed discriminator is `status`/failure state, never the
  disposition string.** Verified shape (skeptic probe 1, closed-green): the
  followup `failRun` (`extensions/gate-run.ts:455–484`) records a failed call's
  ledger line with `resolvedMode: "File"` and
  `basis: "gate call failed: <reason>"` — mode-indistinguishable from a resolved
  `File`. The render half never emits a `Mode:` line for a failed record
  (`classify` → `{kind:"callFailed"}`). A resolved candidate is exactly
  `status: "ok"` with a rendered decision line.

### 2. Prose half — Phase 3 of `features-deliver.md`

Replace the current follow-up sentence (the prose tests pin the
`Every follow-up filed` anchor; locate by anchor, never line range):

> **Every follow-up filed** during the run, the same way `/council` step 13
> requires of an attended run: never a prose bullet, always its own card, drafted
> and confirmed before it's written. Each candidate's disposition is the recorded
> follow-up decision at step 13's confirm gate — the ledger names the recorded
> disposition per candidate by its draft title and never re-decides one — and a
> candidate whose decision failed, did not resolve, or is held awaiting its
> confirming ruling is **held** by its draft title in this ledger, recorded only
> through its runner's `ESCALATION` (no card filed, no silent drop), so the next
> runner can resume it against the same drafted title.

This covers both escalation arms the ruling names — failed/unresolved AND
confirmation-pending — as a pointer agreeing with §13. `council.md` §13 itself is
**not** edited.

### 3. Prose half — the `<followup_decision>` block in `council/agents/council-runner.md`

A new block placed **after** `<escalation_contract>` (not inside
`<return_contract>` — R6). Content, all of it pinned by prose tests:

1. **Record, never re-decide.** At step 13, call `council_followup_review` ONCE
   with every drafted candidate in draft order. The recorded decision is the only
   disposition source; you never re-decide a candidate the render already
   answered, and you never override a disposition into a different one.
2. **Identifier = the drafted title.** A candidate's identifier at the report's
   action point is its draft title — drafts carry no `FLLWUP-N` id until a card
   is written.
3. **Resolved ⟺ `status: "ok"` with a rendered decision line.** Never key
   resolution off the ledger's `resolvedMode`: a recorded failure carries the
   fail-safe `File` as its ledger `resolvedMode`; `status: "failed"` / the
   `gate call failed:` basis is the discriminator, never the mode string. Never
   read `council/gate-ledger.jsonl` directly — the tool result is the only
   interface.
4. **In-container routing: every surfaced candidate ends step 13 as an
   `ESCALATION` before any write.** The three modes differ only in what the
   packet carries:
   - resolved `active` — carry the recorded `Mode:` line verbatim as the
     disposition to be **ratified**; the basis names confirmation-pending. The
     recorded decision is the disposition source, never the container's
     confirmation; the confirmation is the ruling that reaches you in your
     dispatch input.
   - `advisory` — carry the rendered advisory lines verbatim **as information
     only**, never as an applied disposition; the basis names advisory-only, not
     a call failure.
   - `off` — no line; say so plainly; the confirming seat decides from scratch.
   - failed/unresolved — carry each affected candidate's draft title and the
     verbatim engine-derived basis (`gate call failed: <reason>`, a total-failure
     literal, or a render fallback literal), with the explicit statement that no
     card was written.
   In every arm: write nothing first — no card to `council/cards/`, no board
   transition for the affected candidate, no candidate silently dropped, no retry
   that would double-record the call. The candidate is **held, not filed** —
   recorded by its draft title in your report and resumable by the next runner
   against the same drafted title.
5. **Apply only on a confirming dispatch.** When a resumed dispatch's input
   contains the confirming ruling, apply it: write only the cards the ruling
   confirmed, and on `DONE` present the per-candidate outcome as a **bullet list
   keyed by draft title** — one bullet per candidate, each carrying the applied
   disposition line verbatim (you do not paraphrase). A candidate disposition
   never rides `RETIRED` and never rides `HALT`.
6. **`HALT` pin.** A `HALT` report states **`no disposition reached`** for any
   candidates in flight, or the structured partial state:
   `partial: dispositions reached for N of M candidates — <titles whose
   disposition was reached>, held: <titles whose disposition was not reached>`.
7. **R6 boundaries restated in place (not by editing `<return_contract>`).**
   `RETIRED` keeps its card-withdrawal meaning; outcome vocabulary stays
   `File | Merge | Drop` on `DONE`/`ESCALATION` only.

### 4. Invariants (byte baselines — re-expressed, never deleted)

- `<return_contract>`'s four-tag list: byte-unchanged (prose test slices the tag
  bullets and asserts byte identity).
- `RETIRED`'s clause: byte-identical, **zero `Drop`** and **zero `candidate`**
  occurrences in its span (three-assertion test).
- `council.md` §13: byte-unchanged — EV-82's existing prose tests over it must
  pass untouched.
- Phase-3 prose tests pin: the `Every follow-up filed` anchor retained; the new
  sentence names step 13's confirm gate, the draft-title identifier, the
  held/`ESCALATION` route, and the confirmation-pending coverage; the usage block
  anchor retained.

## Test plan

Red-at-base is recorded per the seven-field convention
(`vault/wiki/red-base-evidence.md`) for the card-goal falsifier; the other pins
are conventional failing-test-first.

1. **Grant/sandbox unit tests** (red at base): `grantsFor(seat)` returns
   `followup` true iff frontmatter carries it; `buildChildArgv` output for
   `council-runner` contains `council_followup_review` (absent at base);
   `isCallAllowed("council_followup_review")` flips true with the grant, stays
   false without it; control `council_dispatch` unchanged.
2. **The runner fixture** (`test/hub.test.ts`-style, the card-goal falsifier): a
   stub child spawned via `hub.spawnJob` against a `mkdtemp` fixture repo with a
   failing transport and a drafted candidate. **The red-at-base half is the
   tool-surface assertion** (skeptic 8a's correction): the fixture fails at base
   because `council_followup_review` is absent from the child's allowlist /
   `isCallAllowed` — the stub composition alone was proven to pass at base and
   must not be the red evidence. Asserts on the settled `JobReport.output`: first
   line `ESCALATION`; the candidate's draft title present; the verbatim
   `gate call failed: <reason>` basis present; **zero new files under
   `council/cards/` — the no-write pin (skeptic 8b's correction; a `FLLWUP-\d+`
   regex over the report is NOT the pin, since realistic draft titles contain
   `FLLWUP-` ids)**; the ledger has exactly one line, `resolvedMode: "File"`,
   `failureClass` recorded.
3. **Arm-shape tests** (offline): `off` → `{ mode: "off", recorded: 0 }`, zero
   ledger lines, render `["off"]`, transport never called; `advisory` → resolved
   line carries the `(advisory)` qualifier, no enforcement field; `active`
   resolved → the `Mode: <disposition> — <basis>` byte sequence. A routing
   fixture that treats `resolvedMode: "File"` as resolved on a failed call must
   **fail** (the trap discriminator).
4. **Join-miss tests**: a forged/absent `callId` echo renders
   `FOLLOWUP_RENDER_FALLBACK.joinMiss` (`recorded followup call not found in
   ledger`), never a disposition line — the model-echo fragility the wrapper
   removes; render params without a gate result fail loud.
5. **Prose tests**: every pin listed in §Design.3–4 above, plus the
   `followup` grant present in `council-runner.md` frontmatter, plus §13
   byte-unchanged.
