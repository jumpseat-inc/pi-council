# EV-4 Design — Theme Compliance and Live Repaint of Council Surfaces

**Date:** 2026-08-25
**Status:** Approved by Council deliberation (Round 1 independent pass → Round 2 convergence → Skeptic attack (17/17 closed-green) → Consolidator synthesis) + product-owner rulings (Step 6)
**Card:** EV-4 (EPIC-1). The epic's design authority is
`docs/superpowers/specs/2026-08-25-council-theme-design.md` (EV-5), §4
"Activation semantics" and §5 "Surface compliance". This spec is the
EV-4 contract: the settled compliance audit, the live-repaint pinning
test, the council-owned palette helper, the mid-session watcher, and the
acceptance tests. It does not reopen anything the deliberation closed and
does not reweigh the rulings.

## 1. Goal

Every council-drawn element — the `/council-tree` modal (backdrop, panel
borders, selection cursor, job glyphs, transcript headers, block labels,
footer hints) and the transcript viewer, plus the non-modal council text
(widget, `/council-jobs`, `/council-init`) — draws from pi theme tokens,
nothing hardcodes a hex or ANSI code that ignores the active theme, and an
open modal repaints when the active theme changes mid-session. The
deliberation established that the modal already rerenders against the
live theme Proxy every frame (no capture-at-open), so the load-bearing
deliverable is **the pinning test**, not new repaint code.

## 2. Binding rulings applied (do not reweigh)

- **RULING 1 (off-transition, product-owner, step 6):** keep the last
  materialized theme, warn via notify, and document that reverting to the
  user's prior theme requires a restart. Do NOT implement live off-revert
  (it re-opens EV-3's strict-whitelist block predicate and the custom-pair
  resolution question for a marginal UX win).
- **RULING 2 (council-owned status surface, product-owner, step 6):**
  display nothing. Do NOT add a one-line council-driven status surface
  reading the materialized instance. The live repaint itself is the
  answer to "did the theme apply?".
- **Phase 1 NAME-1 (binding):** the theme family name is `pi-council` and
  nothing else; shipped names `pi-council-dark` / `pi-council-light`
  (EV-1) are the only registered names. The in-memory `Theme` is never
  registered and writes no on-disk theme — `getResolvedThemeColors` /
  `getThemeByName` name-lookup can never reach it.
- **EV-3 zero-settings-write (binding, carried forward):** `ui.setTheme`
  is used **only** in its `instanceof Theme` branch; the string branch
  (which writes pi's settings.json) is forbidden. The extension never
  writes pi's settings.json — not at activation, not in the watcher.
- **§4 authority (epic spec):** everything materialized is in-memory —
  no tempfile, no on-disk theme copy. Reading shipped assets from
  `PKG_ROOT/themes` is not a write.
- **AGENTS.md 9.6 (binding):** council-drawn output draws only from pi
  theme tokens via `fg`/`bg`/`bold` — no literal hex, ANSI escapes, or
  256-index literals — and strings handed to `setWidget` / `notify` stay
  plain text (styling there is pi's job, never inline ANSI).

## 3. Ground truth established by the deliberation (Skeptic-closed)

All 17 Skeptic objections closed-green in Round 3 (full suite 203 pass /
2 skip / 0 fail + tsc clean before and after probes). The load-bearing
facts the design rests on:

1. **Live repaint chain is complete today.** The factory theme argument
   is the module-level live Proxy (theme.js:641‑648 — property access
   reads `globalThis[THEME_KEY]` at call time), not a value taken at open.
   `setThemeInstance` (theme.js:689‑696) swaps the global, sets
   `currentThemeName = "<in-memory>"`, and fires the onThemeChange
   callback (single-slot — the extension must NEVER call it itself);
   pi's only registration is `ui.invalidate()` →
   `updateEditorBorderColor()` → `requestRender` (interactive-mode.js:761‑765).
   `TUI.invalidate()` walks the whole overlay stack calling
   `overlay.component.invalidate()` (tui.js:429‑434). The council overlay
   wires `invalidate: () => tree.invalidate()` and `CouncilTree.invalidate()`
   clears the width-keyed content cache (`this.cached = undefined`), so the
   next `compositeOverlays` frame re-renders the open modal against the
   live Proxy. **Both** `CouncilTree` and the footer/backdrop read their
   theme through the same argument. The 2s refresh timer is belt-and-braces.
2. **No baked-in stale-ANSI state other than the width cache.** The only
   cached line content is `CouncilTree.cached`, which `invalidate()`
   clears. `TranscriptView` recaches every render (no cache — Skeptic P5
   closed-green).
3. **`setWidget(string[])` never colorizes; a factory-form widget is
   ignored in rpc-mode** (rpc-mode.js:123‑131) and is not re-invoked on
   theme change. Plain strings are the honest build for the widget,
   /council-jobs, and /council-init; their "carry token codes" acceptance
   is a **zero-ANSI assertion** (nothing to go stale, satisfies AGENTS.md
   9.6).
4. **Name-based surfaces** (`/settings` registration, sentinel name,
   HTML-export palette) are pi-limitations: a registered theme without a
   `sourcePath` throws at `loadResultThemeJson` ("does not have a source
   path"), and `materializeTheme` passes no options so the in-memory
   instance has neither name nor sourcePath. Anything name-lookup-based
   can never see the merged palette — this bounds what "carrying the
   council palette" can mean.
5. **HTML export is broken under in-memory activation — epic-visible
   regression, pi-side.** `exportToHtml` resolves `themeName` from
   `[options.themeName, settings.getTheme()]` filtered through
   `getThemeByName !== undefined`; with the settings leaf unset or
   `"light/dark"` this yields `undefined` → `generateThemeVars(undefined)`
   → `getResolvedThemeColors(undefined)` → `name := currentThemeName =
   "<in-memory>"` → `loadThemeJson("<in-memory>")` throws "Theme not
   found" (uncaught in the export path). With the leaf literally
   `"light"` / `"dark"` the export silently renders the builtin pair
   (accent `#8abeb7`), not the council palette — a second, silent mode.
   The fix is pi's; this card documents it with a pinning test and files
   follow-ups.
6. **onThemeChange is a single-slot callback owned by pi** — the
   extension never calls it. The re-render chain completes without
   extension code touching it.

## 4. The lone new helper: `resolvedPalette(variant)`

Council-owned, pure, in `extensions/theme-activation.ts` (same module as
EV-3's helpers so the merge/resolve/fallback machinery is shared).

```ts
// Pure — no I/O, no TUI, no pi import. Returns the MERGED resolved hex map
// for a variant (base + repo overrides), i.e. the palette the in-memory
// Theme is built from.
export function resolvedPalette(variant: "dark" | "light"): Record<string, string>;
```

Composition (each stage already exists except the last):

1. `loadShippedTheme(variant)` — EV-1 base (PKG_ROOT).
2. `mergeThemeSection(base, config[variant])` — EV-2 repo overrides
   (vars first, then colors; repo wins per key).
3. `resolveThemeColors(withThemeColorFallbacks(merged.colors), merged.vars)`
   — EV-3 resolver: var-refs → hex, fallback chain (scrollbarThumb →
   selectedBg, searchMatchBg → selectedBg, searchMatchText → text,
   thinkingMax → thinkingXhigh) applied.
4. **Hex the 256-index values** — the one new pure step: copy pi's
   unexported `ansi256ToHex` (theme.js:826, ~15 lines) as a council-owned
   `ansi256ToHex(code: number): string`, applied to any numeric entry.
   The shipped `pi-council` palettes use 256-index accents under
   `256color` mode; the helper must return `#rrggbb` for every key so the
   returned map is a plain hex palette, testable against EV-1's shipped
   asset and against expectations.

Signature: variant is the primary argument; config is read via
`loadThemeConfig(repoRoot)` at call time, with an optional `config`
override for testability, mirroring the EV-3 pattern where the caller can
pass values the pure parts need.

**Non-goals (explicit):** `resolvedPalette` does NOT re-wire pi's export,
does NOT register a name, does NOT touch `/settings`. `getResolvedThemeColors`
and `getThemeExportColors` keep their shipped behavior (regression
asserted — EV-4 leaves the shipped-name lookup byte-identical to EV-1's
un-merged map).

## 5. The live-repaint PINNING test (the deliverable; not code)

The deliberation converged on: **if the pinning test is green, no repaint
code ships.** If it is red, the seam is the `navigator.ts` overlay
`invalidate` wiring — a bugfix, driven test-first. The test is the
contract that live repaint is real.

`test/theme-repaint.test.ts` (new, deep-imports pi's real pieces):

1. **Positive (same-instance repaint, no re-open):** render one
   `CouncilTree` overlay via the module `theme` Proxy path with a real
   pi `Theme` instance A (variant dark, accent #febc38),
   capture the ANSI lines; then `setThemeInstance` a real pi Theme B built from
   the same variant but a distinct accent (e.g. a color differing from
   A's), `invalidate()` the same overlay (exactly what pi's
   `TUI.invalidate()` does), and render against that same overlay with the
   SAME width. Assert the accent line carries B's exact ANSI bytes
   (`\x1b[38;2;...m`). No re-construction of the overlay between renders.
2. **Negative (isolates the seam):** same sequence but without calling
   `invalidate()` between renders → the cached content lines still carry
   A's ANSI (the width cache is the only stale state, and clearing it is
   the fix the test proves).
3. **Proxy-trace:** assert the factory receives the live Proxy (its
   accent resolves per-call), i.e. `theme.accent` read AFTER
   `setThemeInstance(B)` on the same proxy object returns B's value —
   proving "captured at open" is false at the value level.
4. **Transcript re-paint:** `TranscriptView` renders anew each render with
   no cache — render with A, switch B, render again with no invalidate,
   assert B's ANSI appears (P5).

Reach the real pi theme module via `loadPiThemeModule()` (existing EV-3
pattern) and `setThemeInstance` the way the TUI does (the deep import from
`@earendil-works/pi-tui`'s theme controller, or the modal `theme` Proxy
surface). Build B with `materializeTheme` or `new Theme` per EV-3. The
suite must pass with and without `COUNCIL_INTEGRATION=1` (no live model
dispatch).

## 6. Zero-ANSI compliance tests (already-tokens)

`test/theme-compliance.test.ts` (new):

1. **Widget:** spy on `uiCtx.ui.setWidget` via `renderWidget`; assert every
   string in the array has no `\x1b[` byte and no literal `#hex`.
2. **/council-jobs:** the notify string built in `index.ts` contains no `\x1b[` and no `#hex`.
3. **/council-init:** the scaffold summary notify string contains no
   `\x1b[` and no `#hex`.
4. **Modal/viewer:** every line returned by `CouncilTree.render` and
   `TranscriptView::render` output consists only of the theme's own
   `getFgAnsi` / `getBgAnsi` sequences (P9 no-foreign-ANSI): render with
   the real EV-1 dark theme, collect the ANSI bytes used, and assert each
   is a value `theme.fg`/`theme.bg` could produce for that terminal.
   (NavTheme is already token-only by construction; this pins it.)
5. **Grep-audit as a unit test** (not git-grep): walk
   `extensions/*.ts` and assert the only `\x1b` / `#[0-9a-fA-F]{3,8}`
   hits are in the whitelisted comment block (navigator.ts:24‑26) and
   test fixtures — the codebase stays hardcode-free (P3).

## 7. The `.council.json` mid-session watcher

**Scope decision (settled, cannot be reopened):** the watcher reacts to
**`.council.json` edits only** — the file the conversation opened, the
file the user edits to restyle the council. Shipped theme files
(`themes/*.json`) are silent no-ops: editing them while pi has an
in-memory instance already cannot reach it, and re-registering them
does not change the live instance. `settings.json` is NEVER watched
(name-block transitions are handled by the decision table below).

### Arm condition

- Arm inside `session_start`, right after `activateTheme` (index.ts).
- **Only when `loadThemeConfig(repoRoot)` is not undefined at that moment.**
  No config at session start → no watcher at all, forever that session,
  and this is documented: a theme section appearing mid-session after a
  session that started without one is **unsupported** (deliberation-closed).

### Shape

New `extensions/theme-watcher.ts`:

```ts
export interface CouncilConfigWatcher {
  close(): void;   // idempotent; closes fs watcher + debounce timer
}

export function watchCouncilConfig(
  ctx: ExtensionContext,   // notify + hasUI guard (mirrors activateTheme)
  repoRoot: string,        // .council.json lives at <repoRoot>/.council.json
): CouncilConfigWatcher;
```

- `fs.watch` the **parent directory** of `<repo>/.council.json` (i.e.
  `repoRoot`), not the file: `fs.watch` on a watched file dies under an
  editor's rename-burst save (save-temp-then-rename replaces the inode).
  Filter events to `basename === ".council.json"`; because those same
  rename flows replace the path itself, re-arm (close + recreate the
  watcher) on `rename`/`delete` events for that basename.
- ~250ms **debounce, last-write-wins** (a burst of `rename` events from
  one save must fire exactly one reload — P10/P10).
- `unref()` the watcher handle; `close()` it in `session_shutdown` (the
  existing handler) — no lingering handle across sessions.
- `settings.json` is never inside the watched names set (filter).

### Reload semantics (the decision table — settle here, per Round-2 + RULING 1)

On a debounced, filtered change:

1. `let config: ThemeSection | undefined; try { config = loadConfig(repo); }`
   — malformed / throw → `ui.notify("council theme: {msg}", "warning")`
   and **stay armed** (the watcher keeps listening; a later valid save
   reloads — Skeptic F.2 closed-green).
2. `config === undefined` (section removed, or `enabled: false`) →
   **RULING 1: keep the last materialized theme.** No `setTheme` is
   called (that would mean `ui.setTheme(string|revert)` fiction —
   zero-write rule), notify `"council: theme removed — keeping the last
   council theme active; restart to revert", "warning"`. Documented
   (see §10).
3. `config` present → re-run the exact `activateTheme` decision path of
   EV-3 (whitelist raw settings leaf, variant pin/terminal, ...); on
   `activate`: `materializeTheme` the new overrides → `ui.setTheme(instance)`
   (instanceof branch, zero settings writes) + notify the new variant.
   On `{block}` (the settings.json got a concrete name like `"gruvbox"`
   while we were watching): notify warning — pi has already displaced us,
   there is nothing to undo (a constellation the ruling's keep-last does
   not prevent; the block notify is the existing EV-3 tri-state reused).
4. **Never** touch `onThemeChange`, `setThemeName`,
   `settingsManager` — the extension only ever calls `ui.setTheme(instance)`.

The whole step-3 body reuses `activateTheme`'s existing logic; the
watcher's own contribution is debounce + re-arm + the `{removed}`
branch (RULING 1). Testability: `watchCouncilConfig` exported takes the
same injectable settings-file list as `activateTheme` for raw-setting
reads.

Documented limitation (in README-theme + the code comment above the
arm site): the watcher does NOT notice a NEW `.council.json` appearing
mid-session in a repo that had none at start — arm is session-start-gated.

## 8. What stays plain text (deliberate, not degraded)

- **Widget** (`renderWidget`, index.ts:89‑107): `setWidget("council",
  string[])` — plain strings, zero ANSI. Colors don't freeze, nothing
  goes stale on a theme switch, nothing no-ops in rpc-mode. The
  function-form temptation is rejected (Skeptic D.1/D.2 closed-green:
  setWidget never re-invokes the factory on theme change; rpc-mode drops
  factory widgets).
- **`/council-jobs`** (`ctx.ui.notify(lines.join("\n"), "info")`): plain
  text.
- **`/council-init`** summary: plain text.
- **RULING 2:** there is no "current theme: pi-council-dark (in-memory)"
  line anywhere. The live repaint of the modal is the answer to "did the
  theme apply?" — verified by the pinning test.

Acceptance = the zero-ANSI assertions of §6. No colorization code is
added to any of these three.

## 10. Documentation + follow-ups (cards at step 13)

**Documentation (in-scope, part of the PR):**

- `README.md` / the theme docs (EV-5's `docs/council-theme-system/`) gets
  a short "Live theme editing" note: `.council.json` edits repaint live
  (~250ms); removing the theme section keeps the last materialized theme
  until restart (RULING 1); a theme section added mid-session to a repo
  that had none is not watched; `settings.json` is never touched.

  `/export` throws "Theme not found: <in-memory>" (settings leaf unset
  or `"light/dark"`); with the leaf `"light"`/`"dark"` it silently
  exports the builtins palette. Both are pi-side, documented in the
  wiki/README, pinned by tests.

## 11. Out of scope (do NOT implement in this card)

- Any string-branch `ui.setTheme` call, any settings.json write.
- Name registration / sentinel theme / `/settings` changes.
- HTML export palette carrying; `isLightTheme` behavior.
- Editing `onThemeChange`/`setThemeInstance`/`theme.js` internals.
- Watching `settings.json`; watching files in a repo that had no
  `.council.json` at session start.
- Any per-token coloring of the widget / notify / command text
  (function-form widget, colored job table) — rejected in deliberation.
- Status-surface line (RULING 2).
