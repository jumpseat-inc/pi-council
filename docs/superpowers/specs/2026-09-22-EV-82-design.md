# EV-82 design — Record and render the follow-up decision at step 13's pre-write confirm gate

Card: `council/cards/EV-82.md` (EPIC-10). Mode `Deliberate` (recorded routing,
fallback source). Surface-touching: YES — `designer` seated as the third generator.
This spec is the settled design from the card's three-round deliberation plus the
step-4 skeptic attack and the step-5 consolidation; nothing here reopens what the
Council closed. Binding rulings applied throughout: R7 (the `## Merged from:` format
and the merge chat line), R8 (the four unavailable-state literals, FLLWUP-75 shape),
R9 (the unconditional board/open-card/sibling dedup pass in every mode), R0b (the
pre-write pin, `FLLWUP-69`'s halves stay its own), R0a (cards name the step, never a
line range), P1-2 (byte order delegated to the seated `designer`; mandatory
constituents pinned by test).

## 1. What the card adds

Two parent-session tools, a pure render module, and a step-13 prose insert. A
facilitator executing `/council` step 13 (1) calls `council_followup_gate` once with
every drafted candidate — this is the engine-side composition that records one typed
follow-up decision per candidate in the gate ledger — then (2) calls
`council_followup_render` to obtain the per-candidate disposition lines and
unavailable-state lines, which it presents at the existing draft-then-confirm gate.
Under `advisory` the lines are information; under `active` the confirmed disposition
is applied **after** confirmation; under `off` no decision is recorded and step 13
remains an unqualified human review that still carries the unconditional dedup pass.
No mode writes a card before confirmation.

**Composition-site fact (recorded for FLLWUP-96's promotion):** EV-82 builds the
first engine-side composition that loads both `council/gate/followup/questions.json`
and `council/gate/followup/decision.json` and reaches `buildFollowupState`. It lives
in ONE function (`runFollowupReview`) with up to two callers (EV-82's tool; EV-83's
runner/Phase-3 path). FLLWUP-96's followup half is unblocked by this card's landing;
its "one site that legitimately holds both" premise holds as a single function with
up to two callers; an EV-83 fork would be its two-site promotion question. EV-82 does
NOT implement the questions↔weights equality check — it leaves the single call site
for that card.

## 2. `extensions/followup-tool.ts` — the record side

**`runFollowupReview(candidates, repoRoot, opts)`** — pure-with-fs orchestrator, the
single composition site:

1. `loadGatePolicy(repoRoot)` FIRST; if the resolved mode is `off`, return the
   mechanical no-op `{ mode: "off", recorded: 0 }` BEFORE any followup loader, the
   packer, any fetch, any ledger line, or any widget. This ordering is load-bearing:
   an off repo-local policy may omit `gateStateBudgetTokens`, and `buildFollowupState`
   throws on its absence (skeptic-verified at head). Precedent: `gate-tool.ts`'s R3
   arm, `gate-route.ts` rule 1.
2. `loadFollowupQuestions(repoRoot)` + `loadFollowupDecision(repoRoot)` (whole-file
   first-hit, fail-loud loaders).
3. **Sequentially per candidate** (draft order): siblings = the other candidates in
   this call (one call carries all drafts; the sibling set is the run's drafted set by
   construction); `buildFollowupState(candidate, repoRoot, siblings, boardPath)` with
   `boardPath = path.join(repoRoot, "council", "board.md")` (the tool derives the
   board path; the cards-dir pair rule rides `dirname(boardPath)` inside the packer);
   then `runFollowupGate(state, questions, policy, decisionPolicy, { repoRoot })` —
   one ledger line per candidate on both arms. A `runFollowupGate` failure arm
   (`{status:"failed", decision:{disposition:"File", basis:"gate call failed:
   <reason>"}, failure:{kind,reason}}`) is recorded, not thrown.
4. **Same-title draft sets (skeptic O2, named behavior):** `buildFollowupState`
   throws loud when a sibling title equals the candidate's title or when two siblings
   share a title. For such a set every candidate fails per-candidate: the tool
   catches, and each candidate yields a mechanical-result entry with `callId: null`
   and a generic message, with **zero ledger lines written for the thrown
   candidates**. The confirm gate still proceeds — the fail-safe direction is the
   human. The design does not dedupe or rename on the tool's side; the degradation is
   named, tested, and safe.
5. **Mechanical result** (what the tool returns): `{ mode, candidates: [{ title,
   callId, status, boardIds, siblingTitles }] }` plus the off no-op shape.
   - `boardIds` is the **open-only projection** of `sections.board`:
     `sections.board.filter(e => e.state !== "Done").map(e => e.id)` (principal D1).
     A reference matching a Done card id matches neither list and fails loud by
     construction.
   - Verdict-free facts only: title, callId, status, boardIds, siblingTitles. No
     disposition, no basis, no verdict token in any returned string on any arm.
   - `opts.callId` is never passed by the tool (default `randomUUID` keeps callIds
     uncorrelatable by the reading model).
   - A thrown pre-POST guard surfaces as a generic message with `callId: null` —
     never `runFollowupGate`'s own guard text — and zero ledger lines for that
     candidate.
6. **Widget:** an in-flight line naming the candidate — `followup gate: call in
   progress · <title>` — replaced not appended, zero lines after settle (in the
   `finally`), in the EV-66 grammar. The exact bytes may be adjusted by the owner to
   match the shipped widget helpers; the shape (replaced-not-appended, zero after
   settle, candidate named) is pinned.
7. **Mid-run flip:** `loadGateConfig`/`loadGatePolicy` are lazy-at-call; the mode is
   read inside execute per invocation, never hoisted to registration. A `.council.json`
   `gate.mode` edit between two invocations is visible to the next one.

**`council_followup_gate`** — thin parent-session tool wrapping `runFollowupReview`,
registered in `extensions/index.ts`'s parent path only (exactly the
`council_gate`/`council_gate_render` posture; never `registerHubTools` — a child seat
structurally cannot call a parent-session tool, which is why EV-83's seam is the
exported function and not a tool). Parameters: `candidates: [{title, goal}]` in draft
order. No `boardPath` parameter.

## 3. `extensions/followup-render.ts` — the render side (pure)

**`renderFollowupLines(result, records, targets?)`** — a pure function over the
record tool's result and the ledger records (join key: **callId ONLY**; identical
candidate titles collide in an append-only ledger). No fs beyond reading the ledger
via `readGateLedger`; no `loadGateConfig` re-read; no `gate-run.ts`/
`followup-tool.ts` import; it cannot re-issue the gate call. Import graph: `decisionLine`,
`readGateLedger`, typebox only. Purity is pinned by a source-string canary (the
module's own source contains no `fs.` usage, no `node:fs` import, no
`gate-run.ts`/`followup-tool.ts` import) — NOT by an import-graph claim, because
`gate-ledger.ts` itself imports `node:fs` transitively (skeptic O3).

**Byte order (designer's final settlement per P1-2, append-order):**

```
Mode: <File|Merge|Drop> — <basis> — <title>[ → <target>] (<advisory|active>)
```

- The line is composed as `decisionLine(record) + " — " + title + (target ? " → " +
  target : "") + " (" + qualifier + ")"`. `decisionLine(record)` stays byte-intact as
  a contiguous prefix; `gate-ledger.ts` is unchanged — no new export, its
  module-level `Mode:`-ownership comment stands untouched, and no second
  `Mode:`-prefixed format expression exists anywhere.
- `<disposition>` from the record's `resolvedMode`; `<basis>` verbatim from the
  record's `basis` (never render-authored prose; byte-identity pinned).
- `<title>` verbatim from the tool input (no truncation, no id fallback — drafts have
  no allocated id; siblings carry no id; a 200-char title renders 200 chars).
- `[ → <target>]` present iff disposition is `Merge` AND the facilitator supplied a
  target. Arrow and slot are omitted together when no target was supplied — no
  dangling `→`, no `?` placeholder (the absent arrow is the signifier for the human's
  next move). Two states must not collapse: (i) no target supplied → the no-arrow
  line renders, the candidate falls to the human, and under `active` no Merge
  application proceeds without a resolved target (prose-pinned); (ii) a supplied
  reference that resolves to nothing → a loud named failure.
- `(<advisory|active>)` from the record's `advisory` flag — NOT a render-time
  `loadGateConfig` re-read. The record is the audit truth of what governed the
  recorded decision; a re-read could mislabel after a mid-run flip. Coupling pin: the
  step-13 prose states the applying arm executes **the recorded disposition the line
  names**, not the current config.

**The D3 discriminator (the grammar-continuity proof):** for every disposition ×
mode × target-supplied combination, `renderLine.includes(decisionLine(record))` is
true. This is the test that pins "continuous with the shipped
`Mode: <disposition> — <basis>` grammar".

**Separator note (skeptic O5, conditional):** the em-dash separator stability
(exactly one ` — ` from `decisionLine` plus one from the suffix) holds for
em-dash-free, newline-free bases; `basisSafeString` screens only the override
strings, and the failure arm's basis is runtime-constructed. The render therefore
flattens the rendered reason (newline → space) so `gate call failed: <reason>` is
always one line, pinned by a cell test with a newline-bearing body; P14 is restated
as conditional and does not gate.

**`resolveFollowupTarget(reference, { boardIds, siblingTitles })`** — pure resolver,
the ONLY resolver (keeps EV-80's precedence from forking): board-id-exact before
sibling-title-exact; a value matching both resolves to the board id; an unresolvable
reference fails loud with a named failure (never a silent `File`, never silently
re-pointed); a Done-id reference fails loud because Done ids are absent from the
flattened lists by construction. Input is the flattened mechanical-result lists, not
full `FollowupSections` (board titles are used neither for resolution nor display; a
future need is a new input, not a schema widening).

**`followupSuffix({ title, targetId?, qualifier })`** — the suffix composer, exported
only for the byte tests.

### The four unavailable-state literals (R8, FLLWUP-75 shape)

One literal line per unavailable state, replaced not appended, zero literal lines
when the gate resolves — no deliberation, failure, or verdict wording beyond the
exact literals:

- `off` — bare literal, no expanding sentence. Rendered once, above the drafts.
- `credential unresolved` — bare literal. Maps from `failure.kind/class ===
  "no-api-key"`.
- `model-card coming-soon` — bare literal. Maps from `failure.kind === "http-404"`
  (a render-side heuristic, pinned by test and commented as such in the module; no
  shared transport-taxonomy edit — when the model-card page gains a real availability
  signal, the class and the mapping amendment land together in a future card; EV-82
  leaves the seam where `gate-run.ts` reserved `failure.kind` for it).
- `gate call failed: <reason>` — per-candidate, `<reason>` the verbatim failure
  reason from the ledger basis (newline-flattened). Renders under the failed
  candidate's card, replacing its disposition line.

**Placement rules (D4-corrected aggregation):** a total-failure literal (`off`,
`credential unresolved`, `model-card coming-soon`) renders once above the drafts iff
EVERY candidate's record (or the `off` no-op) shares that state; otherwise each
affected candidate gets its literal under its own card, replacing its disposition
line, and the above-drafts slot renders nothing. Two differing total-failure states
in one set → per-record literals only. The `off` case degenerates cleanly: recorded
0, no per-candidate entries, one `off` literal above the drafts.

**Off-literal render input shape (skeptic O4):** the render input carries a
result-level mode flag; `renderFollowupLines({ mode: "off", candidates: [] }, [])` →
exactly `["off"]`. The `off` cell has no record and no per-candidate callIds; the
mode flag is what the cell renders from.

**Join miss** (a callId in the result with no ledger record, or vice versa): a
fallback literal, loud in tests, never a fabricated `Mode:` line.

**No double-`gate:`-colon guard:** the per-candidate literal renders verbatim
`gate call failed: <reason>` — never `gate: gate call failed: <reason>`.

## 4. `council/procedures/council.md` step 13 — the prose insert

A minimal insert into step 13, keeping the existing draft-then-confirm structure and
addressee (the confirmation act is addressed to the human in the prose; this
autonomous run re-homes the act through its own dispatch structure without the
procedure's addressee changing):

1. **The record call:** after drafting, before presenting — call
   `council_followup_gate` once with every drafted candidate, then
   `council_followup_render`, and present the returned per-candidate lines at the
   confirm gate.
2. **The three enablement states named:** `off` — no decision is recorded, the review
   is an unqualified human review (the prose names that the tools are still invoked
   and return the `off` state — the render tool is invoked unconditionally so the
   `off` literal renders, per R9's "the reader is still asked to look at the board");
   `advisory` — the rendered lines are information, never enforced; the human's own
   edit/drop/approve governs; `active` — the disposition applies **only after
   confirmation**, executing the recorded disposition the line names, not the current
   config (the D2 apply-clause pin).
3. **R9, unconditional dedup pass:** the board/open-card/sibling dedup pass is
   unconditional prose present in every mode including `off` — the human is asked the
   dedup question whether or not a model answered it first. `gate.mode` switches
   whose decision is applied, never whether the reader looks at the board. The pass
   is also the producer of the merge-target reference the facilitator supplies to the
   render call.
4. **R0b, the pre-write pin:** step 13 states the human's confirmation precedes any
   card write. The literal `confirmed at ledger level` appears only inside a sentence
   that negates it (e.g. "cards are never confirmed at ledger level after the fact —
   confirmation precedes any write"). `FLLWUP-69`'s Phase-1-row half and its
   unsanctioned-posture sentence stay `FLLWUP-69`'s; `FLLWUP-69` stays `Backlog`,
   `epic: EPIC-9`.
5. **Merge-target supply (R7):** when the dedup pass identifies a merge target, the
   facilitator supplies it as the per-candidate `mergeTarget` reference to
   `council_followup_render` (board id or sibling title); the renderer validates it
   exactly (board-id-exact before sibling-title-exact).
6. **The `## Merged from:` write (R7):** after confirmation, the merged-into card
   gains, verbatim:

   ```
   ## Merged from:

   - <source-title>
   - <source-title>
   ```

   Heading with trailing colon; one blank line; one markdown bullet per source
   candidate, each bullet the source candidate's title verbatim — no id, no
   disposition tag, no rationale. Single-source merge into a board card → one bullet;
   two same-run sources into one target → two bullets; order is the order recorded.
   The section is written only after confirmation (post-confirmation-only pin), by
   the facilitator — no card-writing tool is built; the recognized
   mechanical-enforcement gap stays `FLLWUP-69`'s class. A sibling target means the
   target candidate's own written card names both source candidates; a board target
   means the existing board card is edited to name the source candidate. Plus the
   chat line naming the target (`→ <target>` on the disposition line).
7. **Confirmed `Drop`:** files nothing; the disposition line already names the
   candidate's own title as the cost.

## 5. Test plan (TDD — every item failing before its implementation)

   zero ledger lines; `buildFollowupState` never reached under off.

   + `advisory`; the success arm carries `advisory`; `resolvedMode` = the disposition;
   `policyVersion` = the followup decision policy's version.

   shape.

   open-only projection (a Done id never appears).
7. FLLWUP-96 composition — `runFollowupReview` loads both followup files and reaches
   `buildFollowupState`; a mismatched pair fails loud.
8. Resolver precedence — board-id-exact before sibling-title-exact; both-match →
