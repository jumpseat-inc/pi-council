# EV-75 — Legacy `council/gate/policy.json` cannot silently disagree with `.council.json`

**Status:** settled design from the EV-75 Council deliberation (Deliberate mode, run `2026-09-20T08-59-16-719Z-259999-vjf6un`, jobs 4.1–4.5). Phase 1 rulings R1/R2/R3/R5 and the EV-73 step-13 product-owner ruling (candidate copy) are binding.

## Goal (verbatim from the card)

A consumer whose `council/gate/policy.json` carries a `mode` key FAILs loud naming that file, the key, and its `.council.json` `gate.mode` replacement, while a policy file carrying only tuning data resolves unchanged with no new `FAIL:` line; a test proves both the loud-migration path and the tuning-only unchanged path.

## The change

Replace the generic unknown-key `FAIL:` bytes **for the single key `mode`** in `extensions/gate.ts`'s `loadGatePolicy` with the adopted candidate copy:

```
FAIL: <file> has an invalid mode — unknown key; gate enablement moved to gate.mode in <repoRoot>/.council.json — remove this key and set gate.mode there
```

- `<file>` = the actual policy file path returned by `readGateFile` (names the repo-local shadow when present, never the packaged file).
- `<repoRoot>/.council.json` = `path.join(repoRoot, COUNCIL_CONFIG_FILE)` — literally the path `loadGateConfig` reads; the pointer is truthful by construction. (Byte identity of this copy against the card face and the vault ruling record was skeptic-verified: exactly 2× U+2014, no en-dash, "gate" never "jev".)

### Placement: a dedicated `mode` pre-check BEFORE the unknown-key loop

```ts
if ("mode" in raw) {
	const detail = `unknown key; gate enablement moved to ${configFile} — remove this key and set gate.mode there`;
	throw new Error(`FAIL: ${file} has an invalid mode — ${detail.replace(/[\r\n]+/g, " ")}`);
}
```

(`configFile = path.join(repoRoot, COUNCIL_CONFIG_FILE)`; the snippet names the shape, the implementer writes the final code.)

- The pre-check sits **before** the `Object.keys(raw)` loop and before all value validation. Settled by skeptic test O2: the in-loop path is JSON insertion-order dependent, so an in-loop branch would let `{bogus: 1, mode: "advisory"}` mask the migration pointer. `mode` must win over sibling unknown keys; pinned by test T3.
- The throw is a dedicated single-line `new Error`, NOT `gateFail` — `gateFail`'s template tail (`— set a valid value or remove the key to use the packaged default`) is wrong for this key and must not be generalized for one caller. There is no `newlineSanitized` helper in the module; `gateFail` inlines `.replace(/[\r\n]+/g, " ")` — re-derive the same inline sanitization (skeptic O8).

### Contract sentence (binding on the implementation)

EV-75 changes **only the emitted text for the single key `mode`**; for every other input the accept/reject outcome and the resolved `GatePolicy` are byte-identical to the pre-EV-75 tree.

Explicitly unchanged:
- `loadGateConfig` — untouched. Packaged default stays `off`.
- The generic unknown-key `FAIL:` for every non-`mode` key — unchanged bytes.
- The tuning-only resolution path (`policyVersion`/`model`/`endpoint`/`gateStateBudgetTokens` validation, EV-64 budget-absent rule, whole-file shadowing) — untouched.
- The `ALLOWED_POLICY_KEYS` membership predicate — do NOT "clean up" the prototype-chain `in` while editing this loop (`"toString" in ALLOWED_POLICY_KEYS` is prototype-true today; changing accept/reject for prototype-named keys violates the contract sentence). Pinned by the T6 characterization test.
- `gate-state.ts`'s lenient `resolveGateStateBudget` — not this card (recorded follow-up EV-73 item (4), board FLLWUP-81).
- No auto-migration: `loadGatePolicy` stays a pure read path; nothing writes `policy.json` or `.council.json`; no scaffold change; no `policyVersion` bump; no re-registration.

### Known tradeoff (do not test unconditionally)

If `.council.json`'s `gate` section is itself invalid, `loadGateConfig` (which runs first) throws the config FAIL; the migration pointer is delayed one read. Loud both reads. No test may assert the migration FAIL in that compound state.
