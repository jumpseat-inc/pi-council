# EV-81 — Reuse the gate's Jev transport with a human-bound fail-closed posture

Design spec, settled by the EV-81 Council deliberation (2026-09-21). This document
writes up what the deliberation closed; it derives nothing new. The deliberation
record lives on `council/cards/EV-81.md`.

## Goal (card, verbatim)

The follow-up decision calls the pinned `typesafe/jev-1.13` decisions endpoint and, on
any refusal, timeout, non-2xx, unparseable body, or unresolved credential, records
`gate call failed: <reason>` and falls back to the human pre-write confirm gate while
producing zero `Drop` and zero automatic `Merge` dispositions, proven by an
unreachable-endpoint fixture.

Binding rulings applied: intake R0 (module-boundary posture, offline-provable; the
end-to-end "reaches step 13" arm is EV-84's), R2 (vocabulary exactly
`File | Merge | Drop`), R1 (one `gate.mode` governs both domains), R0a (cards name
steps, never line ranges), and the fold-in ruling
(`vault/raw/2026-09-21-po-ev79-step13-followup-confirmation.md`, item 2 — the
probability-range residual is EV-81's own; re-card trigger discharged by the
shared-helper fix below). FLLWUP-96 stays out of scope.

## Settled design

### Module placement and reuse seam

`runFollowupGate` is **colocated in `extensions/gate-run.ts`** as a fenced section
with its own header narrative (the two fail-safe targets — Deliberate-with-panel vs
literal-File — are separated by the section, not by a file boundary). Zero new exports
besides `runFollowupGate` and its `FollowupRunResult` type. The reuse is of the
**transport seam**, imported verbatim: `GateTransport`,
`openRouterDecisionsTransport`, `parseDecisionsResponse`, `toWireQuestions`,
`GATE_REFUSAL_MARKER`, `GATE_FORBIDDEN_PATH` from `gate-transport.ts`. It is a mirror
of `runGate`, not a parameterization of it: `runGate` is hard-coupled to the card
vocabulary (`decide`, the `Deliberate` fallback via `MODE_PANELS`,
`GateDecisionPolicy`) and is not generalized. Precedent: EV-80's no-shared-core fork
with parity pins.

`import type { FollowupState }` from `./followup-state.ts` — type-only (erases
followup-state/parseCardFile/gate-route from the runtime bundle; skeptic O8 probe).
No import cycle (`gate.ts` does not import `followup-state`).

Doc consequence, same change: `gate-transport.ts`'s "gate-run.ts is the only runtime
consumer" header claim becomes false — amend it (two runtime consumers, one-way import
edge intact), never leave it stale.

### Signature and return

```ts
export interface FollowupRunResult {
	status: "ok" | "failed";
	decision: FollowupDecision; // { disposition: "File" | "Merge" | "Drop", basis }
	callId: string;
	failure?: { kind: string; reason: string };
	reportedModel?: string | null;
	modelDrift?: { pinned: string; reported: string };
}

export async function runFollowupGate(
	state: FollowupState,
	questions: GateQuestionSet,
	policy: GatePolicy,
	decisionPolicy: FollowupDecisionPolicy,
	opts: RunFollowupOpts,
): Promise<FollowupRunResult>;
```

Positional parameters (deliberately not lifted into an opts mirror of `RunGateOpts`
beyond the injection surface) — state this in the section header so the next caller
does not guess; `RunGateOpts` keeps `policy`/`decisionPolicy` inside the opts object
and the two conventions are siblings, documented. `RunFollowupOpts` carries exactly
the injection surface `RunGateOpts` carries minus `basisSuffix`: `repoRoot` (required),
`transport?`, `apiKey?`, `now?`, `timeoutMs?` (default `GATE_CALL_TIMEOUT_MS`),
`callId?`, `ledgerPath?`. **No `basisSuffix` opt** — the EV-69 ratchet note is a
card-gate concept with no followup analogue.

The failure decision is a **literal** constructed by the orchestration:

```ts
{ disposition: "File", basis: `gate call failed: ${f.reason}` }
```

— never routed through `decideFollowup`, never touching `MODE_PANELS`. `File` IS the
human-confirm fallback (per `decideFollowup`'s own fail-safe design); no separate
fallback field, no new vocabulary (R2). The `failure {kind, reason}` beside the
decision is load-bearing: EV-82's unavailable-state render distinguishes
`gate call failed: <reason>` from `credential unresolved` by `failure.kind`, and
EV-83's `ESCALATION` composes from the same kind+reason — a caller holding only
`FollowupDecision` would have to string-match the basis.

### Ledger posture

The orchestration appends — never the transport. Exactly one `appendGateCall` line per
call, both arms:

- **Failure line**: `answers: {}` (appendGateCall fills every asked id null — absent,
  never a zero), `resolvedMode: "File"`, `failureClass` from the shared taxonomy
  (`no-api-key | timeout | network | http-<status> | http-400-refusal |
  invalid-response | internal-error` — the same `transportFailure` classification),
  `basis` exactly `"gate call failed: " + <reason>` (verbatim reason once, inside
  basis only), `drops: state.drops` (`FollowupDropRecord[]` → `GateDropRecord[]`
  structural assignability, EV-80-pinned).
- **Success line**: knownIds filter with `unknownAnswerIds`, answers verbatim,
  `model`/`provider`/`usage`/`generationId` from `parseDecisionsResponse`,
  `resolvedMode` = the disposition verbatim.
- **Both arms**: `policyVersion: decisionPolicy.version`,
  `questionSetVersion: questions.version`, `advisory = policy.mode === "advisory"`.

**Deliberate divergence (spec-mandated phrasing):** `policyVersion` carries the
**followup decision policy's** version (`"followup-decision-1"`), NOT a mirror of
`runGate`'s literal `policy.policyVersion`. The shipped `runGate` writer is the buggy
side (verified end-to-end, skeptic O1: every live card-gate line carries
"gate-policy-1" while `resolveRoute` validates against "gate-decision-1", so EV-69's
recorded-decision fast path is dead in production); EV-81 writes the corrective
direction and does not replicate the bug. The shipped fix is carded at step 13, out of
EV-81's scope by the fold-in test.

Routing safety: `gate-route.ts` rejects any recorded `resolvedMode` not in
`GATE_DECISION_MODES`, so `File`/`Merge`/`Drop` lines can never produce a reduced mode;
the followup stateHash (over the followup packer's bytes) cannot collide with a card's.

### Domain discriminator

**Vocabulary disjointness pinned by test — no `domain` field, no `gate-ledger.ts`
change.** `GATE_DECISION_MODES` and `FOLLOWUP_DISPOSITIONS` are disjoint at runtime;
the test asserts the intersection is empty by importing both constants, plus
`resolveRoute` over a mixed followup+card fixture returns the card line's result
unchanged. EV-84 identifies followup lines by `resolvedMode ∈ FOLLOWUP_DISPOSITIONS`.
A `domain` field would be fully redundant state, derivable under disjointness, and a
redundant field that can contradict its derivable value is worse than inference; no
shipped consumer needs a tag (EV-71 precedent: a field needs a named consumer).

### Pre-POST guards (all throwing, zero POSTs, zero ledger lines)

Mirrored verbatim from `runGate`:

1. `policy.mode === "off"` → throw programming error (R1: the same resolver,
   `loadGatePolicy`, feeds both domains; the mode-off short-circuit lives in the
   CALLER before `buildFollowupState` — `followup-state.ts`'s own comment assigns it
   there, and an off policy may omit the budget key, so letting the call site reach
   the packer would throw from the packer instead).
2. `policy.model !== GATE_PINNED_MODEL` → throw naming the pin.
3. `policy.endpoint.includes(GATE_FORBIDDEN_PATH)` → throw naming the never-path.
4. Noul join check: `decisionPolicy.noulProbabilityOf` must name a criteria key of
   every noul question (live for the packaged followup data: two noul + one choice).

Credential resolution — **reuse, not fork**:
`opts.apiKey !== undefined ? opts.apiKey : resolveOpenRouterApiKey()` — byte-identical
to the expression `extensions/preflight.ts` runs, so runtime parity with the run-start
loud failure is by construction. The acceptance's "fails loud at run start" arm is
EV-76's preflight, already shipped and domain-agnostic under R1; this card adds no
second preflight. The no-api-key `failRun` stays as defense-in-depth (class
`no-api-key`, reason "no OpenRouter API key resolved (OPENROUTER_API_KEY env or stored
credential)"), mirroring `runGate` exactly.

Advisory: `advisory = policy.mode === "advisory"` recorded on the line (EV-66 intake
semantics; EV-82 renders as advisory — computed and recorded, never enforced).

### The probability-range residual (the fold-in ruling's how)

`sideProbability`'s choice branch currently returns any finite value. The fix: a
**finite value outside [0,1] throws** (names the question id, the option, the value,
and the expected range). Absent/non-numeric still contributes 0 — missing evidence
drags toward the safe side and must NOT become an error, or the gate's
unanswered-question posture breaks. Frozen `gate-decide` expectations for
absent/non-numeric probabilities stay byte-identical.

The throw's message is **domain-neutral from birth** (names id, option, value,
`[0,1]`; neither `gate:` nor `followup:` prefixed). Grounds (as corrected by the
skeptic's O4 probe, not the round-2 narration): the NEW choice-branch throw WILL fire
from the followup path — the choice branch has no floor-arm pre-validation (unlike the
noul branch, which `followupFloor` pre-validates with the `followup:` grammar before
the helper is reachable, so no existing `gate:`-prefixed message leaks into the
followup domain today; the noul-branch leak claim is withdrawn as a non-leak) — and
the reason rides verbatim into `gate call failed: <reason>`, which EV-82 renders.
Catch-and-reprefix is string surgery on error text and is rejected.

**Re-card trigger status: discharged.** The shared-helper fix closes both arms: the
followup path (out-of-range → throw → the orchestration's invalid-response catch-all →
`File` with `gate call failed:` basis — the posture the ruling blessed) and the shipped
card gate (out-of-range → throw inside `decide()` → `runGate`'s invalid-response
catch-all → recorded `Deliberate`, where a malformed probability could today push a
composite toward `Direct` — the dangerous direction). The PO's named re-card trigger
("if EV-81 lands the check at the followup parse site only…") never comes into effect.

## Offline fixture design (the unreachable-endpoint arm)

Injected transport doubles only — the default suite never constructs
`openRouterDecisionsTransport`. The test imports `GATE_PINNED_MODEL` and
`GATE_ENDPOINT` from `./gate.ts` (never re-declared literals — the acceptance names
this) and asserts on the captured request: `url === GATE_ENDPOINT`,
`body.model === GATE_PINNED_MODEL`; the forbidden-path guard throws on a mutated
endpoint. State is a minimal synthetic `FollowupState` object literal (the runner
needs only `stateHash`, `stateBytes`, `drops`); no fs, no timers in the orchestration
— the timeout lives entirely in the transport (the EV-65 split).

Variants, each asserting the FULL posture (status failed;
`decision.disposition === "File"`; basis exactly `gate call failed: <reason>`, the
verbatim reason; exactly one ledger line with `resolvedMode: "File"`, `failureClass`,
every asked id null; zero `Drop` and zero `Merge` anywhere in result or line): network
failure; timeout; http-500; http-400-refusal (body containing `GATE_REFUSAL_MARKER`,
imported); 2xx garbage → `invalid-response`; explicit `apiKey: null` → `no-api-key`;
out-of-range probability → `invalid-response` → `File`.

## Owner test obligations (numbered)

1. **Fixture matrix** (`test/ev81-followup-run.test.ts`) — the variants above; any
   `Drop`/`Merge` on an injected failure fails the test.
2. **Guard parity** — all five guards mirrored and each tested: off → throw before any
   POST, zero ledger lines; model pin; endpoint never-path; noul join; credential
   expression identical to preflight.ts.
3. **`policyVersion`/`questionSetVersion` on the followup line** — asserted against
   `loadFollowupDecision(repoRoot).version` and `loadFollowupQuestions(repoRoot).version`
   (i.e. "followup-decision-1" / "followup-questions-1"), never literals.
4. **Range residual, red-at-base then green-after-fix** — `decideFollowup` with a
   weighted choice answer carrying `probabilities{no:1.5}` returns
   `{Drop, "composite 2.30 ≥ drop threshold 2.00"}` at base; after the helper fix it
   throws → the orchestration returns `File` via the invalid-response path.
5. **Card-gate side of the helper fix** — shipped `decide()` with out-of-range probs →
   throws → `runGate` records `invalid-response` → `Deliberate` (was: possibly
   `Direct`). Honest blast-radius accounting, not an extra feature.
6. **Vocabulary disjointness + mixed-fixture routing** — intersection empty by
   imported constants; `resolveRoute` over a ledger holding one followup line + one
   card line returns the card line's result, unaffected.
7. **One-pin request assertions** — captured `url === GATE_ENDPOINT`,
   `body.model === GATE_PINNED_MODEL`; mutated endpoint throws before POST.
8. **Doc-claim updates** — gate-transport single-consumer comment amended; the EV-80
   assignability pin gains `runFollowupGate` as a real consumer.
9. **Frozen gate-decide expectations** — absent/non-numeric probabilities still
   contribute 0; existing expectations byte-identical.
10. **One-call-line-per-call failure posture** — answers all null, every asked id null,
    `resolvedMode: "File"`, `failureClass` from the taxonomy, basis exact; zero
    `Drop`/`Merge` anywhere; a directory-snapshot diff around the call shows the only
    mutation is the single ledger line (zero writes before confirmation).
11. **Off short-circuit ordering** — `runFollowupGate` throws on off; the caller
    short-circuit before `buildFollowupState` prevents the packer's absent-budget
    throw from an off policy.

Plus the four repo gates: `bunx tsc --noEmit`, full `bun test`,
`python3 council/validate.py`, `bash council/preflight.sh`.
