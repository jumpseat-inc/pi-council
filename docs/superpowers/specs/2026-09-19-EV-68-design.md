# EV-68 — Card execution mode recorded on the run manifest (settled design)

Status: settled by the full-council deliberation of 2026-09-19 (owner job-14.1,
principal job-14.2, skeptic job-14.3, consolidator job-14.4). Every design
point below is either settled by a skeptic test that actually ran (green) or is
a binding card constraint. Nothing here is open.

## Goal (the card's own contract)

The root dispatch manifest of a card executed in Deliberate, Verify, or Direct
mode carries `mode` set to that literal, and a test over a fixture forest
proves the three modes are distinguishable from manifests alone while a
manifest with no `mode` field still satisfies `readManifests` and `sumSubtree`
unchanged.

## The four-link flow (settled, skeptic O-1 green)

`mode` traverses exactly four surfaces; no fifth exists (skeptic O-1: the sole
`writeManifest` caller is `hub.ts` `writeJobManifest`; the only `spawnJob`
callers are `council_dispatch` in `hub-tools.ts` and the eval path in
`dispatch.ts:103`, which deliberately does not pass mode; `respawn`'s sole
caller is `job-retry.ts:70`):

1. **`extensions/runs.ts`** — export the closed union
   `export type DispatchMode = "Deliberate" | "Verify" | "Direct";` beside
   `RunManifest`, and add to `RunManifest`:
   `/** EV-68 — card execution mode recorded on the ROOT dispatch manifest.
    * Optional: absent on pre-EV-68 manifests and on every dispatch whose
    * caller did not supply it. Never inherited by sub-dispatches. */
   mode?: DispatchMode;`
   `DispatchMode` is the single literal source — EV-69/EV-70 import it; they
   never re-declare it. (This is an execution-mode namespace, distinct from
   navigator's `ctx.mode` TUI-surface strings.)
2. **`extensions/hub-tools.ts` (`council_dispatch` parameters)** — add
   `mode: Type.Optional(Type.Union([Type.Literal("Deliberate"), Type.Literal("Verify"), Type.Literal("Direct")]))`
   next to the `cellId`/`model`/`thinking` precedent. The tool schema is the
   runtime gate: pi's `validateToolArguments` runs before `execute` (skeptic
   O-3 green: accepts the three literals + absent; rejects bogus values; an
   optional `null` is normalized away). Pass `mode: params.mode` into the
   `hub.spawnJob` opts.
3. **`extensions/hub.ts`** — `Job` gains `mode?: DispatchMode`;
   `spawnJob`'s opts type gains the same. `respawn`'s `...prev` spread carries
   `mode` across attempts unchanged (skeptic O-4 green) — one manifest serves
   all attempts (EV-39 cardinality A); mode is a fact about the dispatch, not
   the attempt.
4. **`extensions/hub.ts` (`writeJobManifest`)** — one line after the
   `nextAttemptAt` spread:
   `...(job.mode !== undefined ? { mode: job.mode } : {})`
   `"mode"` writes last, tab-indented via the existing `writeManifest`;
   existing keys never move.

## What deliberately does not change (settled by construction + O-2 green)

- No reader changes: `tree.ts`, `navigator.ts`, `usage-block.ts`,
  `usage-store.ts`, `spend.ts`, `cost-baseline.ts`, reconciliation — zero
  edits. Every reader is field-scoped and none iterates manifest keys
  (skeptic O-2: same-function-both-sides over the real reader code —
  `buildTree` structure, `textTree` lines, `sumSubtree`, `formatWaitReport`,
  `browsableAttempts` all byte-equal against mode-bearing vs mode-stripped
  controls; a legacy manifest's bytes contain no `mode` key).
- Mode never rides `childEnv` — no env propagation, so it can never leak into
  descendant dispatches (verified: no `COUNCIL_MODE`-class env exists today).
- Root-only by construction: only a dispatch whose caller explicitly supplied
  `mode` carries it. Child-hub dispatches without the param write no `mode`
  key. The eval path is mode-less.
- Supervisor stall/timeout/kill semantics untouched; `tick`/`settle`/`cancel`
  constants and paths unmodified (diff-asserted at implementation, O-6).

## The optional-field contract (binding pins)

1. **Absence is key-absence, not `null`/`"None"`** — the spread gate emits no
   key when `job.mode === undefined`; a no-mode write is byte-identical to
   pre-EV-68 output (skeptic O-2 probe: `spread-gate with undefined …
   byte-identical reconstruct: true`).
2. **Key order** — `"mode"` appended last (after `nextAttemptAt`); existing
   keys never move.
3. **Single literal source** — `DispatchMode` lives only in `runs.ts`.
4. **Root-only / non-inheriting** — per-dispatch, never inherited, never
   copied into `childEnv` or descendant spawns.
5. **Retry stability** — `mode` unchanged across attempts of the same job
   (asserted, not incidental).
6. **TS-only union on the write side** — the spread gate checks
   `!== undefined`; the tool schema is the runtime gate; no second runtime
   validator in `writeManifest`.

## The tests (test-local fixture forest; never a packaged seed)

One new test file (e.g. `test/ev68-mode-manifest.test.ts`), plus additions
where the hub write path is exercised. The fixture forest is hand-built in a
fresh `mkdtemp` repoRoot via `writeManifest` — **never** under
`council/fixtures/<task>/seed/` (skeptic O-5 green: a manifest there changes
the pinned `sha256` `treeDigest` and the packaged loader refuses it).

Reader half (pure, mkdtemp):

1. **Distinguishability from manifests alone** — three roots tagged
   Deliberate/Verify/Direct (plus mode-less children with usage, plus one
   legacy root with no `mode`); after `readManifests`, the three roots yield
   exactly the three distinct literals and every child + the legacy root yield
   `undefined`.
2. **Absence shape** — the legacy manifest's raw bytes contain no `"mode"`
   key (`!("mode" in JSON.parse(bytes))`); `readManifests` yields `undefined`,
   never `null`.
3. **Sum identity in the same test** — `sumSubtree` over the legacy root and
   over an identically-shaped tagged root return the same number; each root's
   sum equals the hand-computed fixture sum; a manifest with no `usage` still
   sums as 0.
4. **Same-function-both-sides inertness** — run `readManifests`,
   `sumSubtree`, `buildTree`→`flattenTree`→`textTree` over (a) the forest
   with the three mode-bearing roots and (b) a byte-equivalent forest with
   the `mode` key stripped; assert the numeric sums and the emitted text
   lines are byte-equal.

Write-path half (Hub + STUB child, the established `test/hub.test.ts`
pattern):

5. **Mode writes** — spawn a job with `mode: "Verify"` → the on-disk manifest
   parses with `mode === "Verify"`; `"mode"` is the last key.
6. **No-mode write is byte-identical** — spawn without mode → the manifest's
   key set equals the pre-EV-68 key set **within the same state class**
   (O-4 hazard: settled and running writes differ in the state-gated
   `stopReason`/`settledAt` keys even today; compare like against like —
   a settled no-mode control vs a settled no-mode treatment, never settled
   vs running).
7. **Retry stability** — one retry `respawn` on a mode-bearing job → the
   single manifest still carries the same mode.
8. **Non-inheritance** — a child-hub dispatch (Hub constructed with
   `parentJobPath`) without the param writes no `mode` key.

## Implementation obligations carried from the deliberation

- O-4 wording hazard: state-pinned key-set assertion (test 6 above).
- O-6 diff assertions: the merged diff touches no `tick`/`settle`/`cancel`
  code or timing constants, and no renderer gains a `mode` column — both
  review-asserted, documented in the implementation's record.
- Red-base record (seven fields per [[red-base evidence]]): the
  distinguishability falsifier runs red at the pre-mechanism base (nothing
  writes `mode` today) and green at head; required at implementation time.
- Baseline for regression: `bun test test/hub.test.ts test/tree.test.ts`
  was 46 pass / 0 fail on the deliberation worktree.

## Out of scope

- Any routing decision (EV-69), Direct-mode merge semantics (EV-70), spend
  accounting (EV-71), threshold tuning (EV-72), or rendering `mode` anywhere
  in a surface.
- Card-frontmatter changes (schema fixed by hard convention).
- Any runtime validator beyond the tool schema.
