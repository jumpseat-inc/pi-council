# EV-30 design — invocation-scoped spend record from the invoking session plus its job subtree

- **Card:** `EV-30` (epic `EPIC-7`), `council/cards/EV-30.md`
- **Status:** settled by the step-2–6 deliberation and the step-6 `product-owner`
  ruling; this document is the write-up, not a re-derivation. Nothing settled
  in steps 2–6 is reopened here.
- **Binding inputs:** Phase 1 ruling **R-4** (`boundary=session=<sessionId>
  entries=<firstId>..<lastId> jobs=<n>` for the resolved form) and the
  **step-6 product-owner ruling** appended verbatim to `council/cards/EV-30.md`.
  Where this document and the card disagree, the ruling wins.
- **Scope:** the pure accounting function plus the one call-site that makes the
  invocation boundary durable. No durable store (EV-31), no exit-point
  reporting (EV-32), no provider-reported cost (EV-29).

## 1. Problem

`EPIC-7`'s chain starts at EV-28 (the full usage tuple in the hub's manifest
record). EV-30 is the bridge: the invoking parent session has **no manifest at
all** — the hub writes manifests only for the jobs it dispatches — so the
hub's job forest is not the invocation's spend. Attended runs cannot express a
run total today because every top-level manifest carries `parentJobId === null`
(`extensions/hub.ts:94`); `sumSubtree(manifests, "job-1")`
(`extensions/runs.ts:188-201`) covers one seat, not the run.

Given the invoking session's JSONL and the invocation's run directory, EV-30
returns a **spend record**: an own-session half (the four usage kinds pi counts
on the active leaf chain at or after the invocation boundary) and a subtree
half (the sum over the invocation's job forest), each labelled with its own
accounting basis and source.

Grounding: wiki `run-transcripts` (the manifest/session substrate,
`getEntries()` order, `findSessionFile`), `hub-job-supervision` (manifest
identity, `parentJobId`, `startedAt`), `repository-grounding`. The spend record
itself is a new surface the wiki does not cover.

## 2. Settled design

### 2.1 Module and purity

New module **`extensions/spend.ts`** — pure: no `node:fs`, no `ctx`, no hub
import. It imports types only: `SessionEntry` / `CustomEntry` etc. from
`@earendil-works/pi-coding-agent`, and `Usage` / `UsageSource` / `RunManifest`
from `./runs.ts`.

`extensions/runs.ts`, `extensions/hub.ts`, `extensions/transcript.ts` and
`extensions/navigator.ts` are untouched. `sumSubtree`'s
`(manifests, rootId, metric)` shape cannot return a `Usage` or a node count,
and `runs.ts` is tested substrate; a new pure module is the settled home
(rejected alternative d1).

### 2.2 Record shape (ruling items 2, 5, 6)

```ts
export interface SpendBoundary {
  sessionId: string;            // the invoking session (getSessionId())
  resolved: boolean;            // ruling item 3 flag
  firstEntryId: string | null;  // null iff !resolved
  lastEntryId: string | null;   // null iff !resolved
  jobCount: number;             // forest node count; 0 iff !resolved
}

export interface SpendRecord {
  boundary: SpendBoundary;
  ownSession: Usage;            // usageSource: "session-reconciled"
  subtree: Usage;               // usageSource: "stream-assistant"
}
```

- **No `total` field** and **no new `UsageSource` union member** (ruling item
  2). `UsageSource` stays its EV-28-ruled two members. A combined number is
  EV-32's render concern, derived where both bases are explicit.
- The subtree half's **`usageSource: "stream-assistant"` is the lower-bound
  statement** (ruling item 5); no extra lower-bound string or field is added.
- **No `computedAt` stamp, no job-id set, no idempotence stamp** (ruling item
  6). The record is valid **only when written once at its producing exit**.
  Persistence idempotence belongs to EV-31's store, not this record.
- The nested grouping above is this write-up's reading of the ruling; the ruled
  constraints are the ones listed in this subsection.

`costBasis` on both halves is `"catalogue-estimate"` today (EV-29 flips the
subtree to `"reported"` when provider charges land; the field already exists per
EV-28 R-3).

### 2.3 Boundary label

```ts
export function formatBoundaryLabel(record: SpendRecord): string;
```

- **Resolved** (R-4, byte-exact):
  `boundary=session=<sessionId> entries=<firstId>..<lastId> jobs=<n>`
- **Unresolved** (ruling item 3, byte-exact):
  `boundary=session=<sessionId> entries=unresolved jobs=<n>`

`<sessionId>` is always the **invoking** session's id
(`ctx.sessionManager.getSessionId()`), never `RunManifest.sessionId` (that is a
child job id, `extensions/hub.ts:96`). On the unresolved path the label is
still self-describing (`entries=unresolved`), and `boundary.resolved === false`
is the machine-readable discriminator. `<n>` is `boundary.jobCount`, which is
`0` on the unresolved path.

### 2.4 The boundary marker — durable, synchronous, fail-closed

The procedure command handler at `extensions/index.ts` (`pi.registerCommand`
loop, the `handler: async (args, ctx) => …` around `index.ts:215-231`) is the
only place the invocation boundary exists. `pi.sendUserMessage` is
fire-and-forget `void` and no event carries the appended entry id, so the
boundary must be anchored before the send.

New exported helper in `spend.ts`:

```ts
export function recordInvocationBoundary(
  pi: { appendEntry<T = unknown>(customType: string, data?: T): void },
  ctx: { sessionManager: { getLeafId(): string | null; getEntry(id: string): SessionEntry | undefined } },
  command: string,
  runId: string,
): string | null;
```

Behaviour:

1. `pi.appendEntry("council-invocation", { command, runId, at: Date.now() })`
   in **both** the TUI and the headless branches of the handler, synchronously,
   **before** `pi.sendUserMessage(...)`. The
   `pi.appendEntry` wiring is synchronous (`agent-session.js:2029-2033` →
   `sessionManager.appendCustomEntry`), so the TUI fire-and-forget contract
   (`index.ts:221-223`) and the headless `waitForIdle` teardown hazard
   (`index.ts:224-227`) are untouched.
2. Read the id back with `ctx.sessionManager.getLeafId()` — `pi.appendEntry`
   returns `void` (`extensions/types.d.ts:985`), so the id is observable only
   via the leaf read-back (Skeptic O2).
3. **Fail closed** (Skeptic/principal Held #7): assert the entry now at that
   leaf id is `type === "custom" && customType === "council-invocation"`. If the
   read-back leaf is not the marker (stale/replaced session; wiki
   `headless-pi`, "Stale ctx after session replacement"), **return `null`** and
   write no further state. An unresolved boundary is always preferable to a
   wrong one.
4. Return the marker id on success.

The marker does not participate in LLM context (`CustomEntry` is ignored by
`buildSessionContext`, `session-manager.d.ts:56-67`). It is parent-mode only:
`index.ts:118-121` returns into `runChildMode` before procedure registration, so
seats never stamp, and **EV-31/EV-32 must not assume a marker always exists**.

### 2.5 Boundary resolution — append order, not parentId

```ts
export function spendRecord(opts: {
  entries: SessionEntry[];        // ctx.sessionManager.getEntries()
  leafId: string | null;          // ctx.sessionManager.getLeafId()
  sessionId: string;
  markerId: string | null;        // the marker id, or null if unknown
  manifests: RunManifest[];       // readManifests(repoRoot, runId)
}): SpendRecord;
```

Resolution rule (settled by Skeptic **O1 `closed-red`** against owner's
`parentId === markerId` rule):

1. Walk the active leaf chain: build a by-id map over `entries`, walk
   `parentId` from `leafId` to a root, reverse. A marker that is absent from
   `entries`, or present but **not on this chain**, is *off-branch*.
2. The boundary entry is the **first entry after the marker in
   `getEntries()` append order** that is `type === "message"`,
   `message.role === "user"`, and on the active chain.
3. If `markerId` is null, the marker is off-branch, or no such user entry
   exists → **boundary unresolved** (see §2.8).

Append order is the only reliable discriminator because `prompt()` runs
`_flushPendingBashMessages` / `_flushPendingCustomMessages` and
`await this._checkCompaction(...)` **before** the injected user message exists
(`agent-session.js:874-875,895`); `appendCompaction` re-parents the leaf
(`agent-session.js:1826`), and the user message is persisted later at its
`message_end` on the then-current leaf (`agent-session.js:398`). On the long,
compaction-heavy runs this record exists to measure, the user message's
`parentId` is the compaction entry, not the marker. The append-order rule
survives that path by construction and still never matches procedure content
(so two invocations with identical `$ARGUMENTS` resolve their own markers).

Recovery of the marker id at compute time (exit-time callers that no longer
hold the in-memory id) is a one-line append-order scan: the **last** `custom`
entry with `customType === "council-invocation"` on the active chain. That
helper, if needed, lives in `spend.ts`; it is interface completion for
EV-31/EV-32, not a change to any settled decision.

### 2.6 Own-session half (`usageSource: "session-reconciled"`)

Sum over the active-chain entries **at or after the resolved boundary entry**,
inclusive, walking the raw chain — **not** `buildContextEntries`
(`session-manager.d.ts:150-158` drops compacted-away entries; the card requires
"pi counts all entries, including those compacted away"). Four kinds, matching
pi's own enumeration (`usage-totals.js:18-32`, `agent-session.js:2658-2663`):

| entry | usage field |
|---|---|
| `type:"message"` + `message.role:"assistant"` | `message.usage` (required) — also the only kind that increments `turns` |
| `type:"message"` + `message.role:"toolResult"` | `message.usage` (optional) |
| `type:"compaction"` | `entry.usage` (optional) |
| `type:"branch_summary"` | `entry.usage` (optional) — **included** per ruling item 1; no scope field |

Entries before the boundary contribute nothing. Off-chain entries contribute
nothing. `turns` is assistant-only, mirroring `hub.ts:197`. `reasoning` is
accumulated independently and never re-added into `output` (EV-28 invariant).
The wire→record flattening reuses the EV-28 Q1 clause verbatim
(`extensions/runs.ts:5-16`): `cost.{input,output,cacheRead,cacheWrite,total} →
costInput/costOutput/costCacheRead/costCacheWrite/cost`; missing components
coerce to `0`, never `NaN`. `cacheRead` is accumulated, never folded into
`input`; `totalTokens` accumulates.

### 2.7 Subtree half (`usageSource: "stream-assistant"`)

**Eligible roots** = manifests with `parentJobId === null` **and**
`startedAt >= Date.parse(boundaryEntry.timestamp)`. The **forest** is each root
closed over its `parentJobId` descendants. One rule covers every shape:

- attended `/council` — sibling top-level seats are all eligible roots
  (`parentJobId` is `this.run.parentJobPath ?? null`, `hub.ts:94`, and attended
  top-level jobs have no parent path);
- nested autonomy — a runner's own `job-N` is a time-eligible root and its
  `job-N.x` descendants close under it (`child.ts:20-24`);
- multiple invocations in one session share one run dir (`initHubIdentity(
  mintRunId())` is per-session, `index.ts:161`) — the time filter excludes
  earlier invocations' jobs.

Clock alignment is real: entry timestamps are written as ISO strings at append
(`session-manager.js:792`) and `job.startedAt = Date.now()` at spawn
(`hub.ts:119`), same process clock; `>=` is the correct edge.

Each node contributes its `RunManifest.usage` per numeric metric; a manifest
with no `usage` (pre-EV-28, or a partial write) counts in `jobCount` and adds
`0` — the same tolerance `sumSubtree` already has (`runs.ts:196-198`).
`jobCount` = number of nodes in the forest (roots + descendants), not roots
only. `usageSource: "stream-assistant"` and `costBasis: "catalogue-estimate"`
are stamped on the summed `Usage`.

Deliberate scope cut, recorded per ruling item 5: **reconciliation is scoped to
the invoking session this card**. The seat session files sitting beside the
manifests hold strictly more usage than the stream projection
(`findSessionFile`, `runs.ts:134-152`; `sessionDir: dir`,
`hub-tools.ts:184-185`); per-node reconciliation is a follow-up (M4), and the
subtree's `usageSource` is the machine-readable lower-bound statement.

### 2.8 Unresolvable boundary and edges (ruling items 3, 4, 7)

- **Boundary unresolvable** (marker absent, off-branch, or no on-chain user
  entry after it): the record is a **zero on both halves** —
  `ownSession` and `subtree` are all-zero `Usage` values, `jobCount = 0`,
  `boundary.resolved = false`, `firstEntryId = lastEntryId = null`, and the
  label renders `entries=unresolved`. Never an error, never a throw.
- **"Rotated session" is defined for this card as *boundary unresolvable***
  (ruling item 4). The card's edge-case text is read as zero **both** halves,
  and "rotated" is replaced with `boundary-unresolvable` in tests and prose.
- **Zero dispatched jobs** → no eligible roots → subtree all-zeros,
  `jobCount = 0`, own-session intact, boundary resolved.
- **Pruned/absent run directory** → `readManifests` returns `[]`
  (`runs.ts:102-108`) → same as zero jobs.
- **In-memory session** (`getSessionFile() === undefined`) → entries come from
  the live manager; an empty session yields an unresolved boundary and a
  zero record, no throw (Skeptic O6).
- **`lastId` is bound** (ruling item 7) to the **last entry id on the active
  leaf chain at compute time** — `leafId` itself, obtained by walking
  `parentId` from `leafId` (the same chain the own half sums). "Last file
  entry" is forbidden: it silently includes entries on abandoned branches. No
  end marker is written.
- **`turns`** for tool-result/compaction/branch-summary usage is not counted
  (assistant-only), mirroring `hub.ts:197`.

## 4. Test plan (owner meets a failing test first)

Fixture: a session JSONL written to `mkdtemp` (header with the invoking session
id, an assistant so `_persist` has written the file, the marker, a
pre-boundary assistant with usage, the boundary user message, an on-chain
assistant with `cacheRead`/component cost, a tool-result with usage, a
compaction with usage, a `branch_summary` with usage, and an **off-branch**
sibling with usage), parsed with pi's exported `parseSessionEntries`; manifests
via `writeManifest` / `readManifests`. Hand sums asserted as literals.

1. **T1 — full fixture (acceptance).** `ownSession` equals the hand sum over
   active-chain entries at/after the boundary (assistant + tool-result +
   compaction + `branch_summary`); `subtree` equals the hand sum over the
   forest, and the manifest set includes a **pre-boundary job that must be
   excluded**; `boundary.jobCount`; resolved label byte-equals
   `boundary=session=… entries=<firstId>..<lastId> jobs=<n>`.
2. **T2 — pre-boundary exclusion:** the pre-boundary assistant's usage is absent
   from both halves.
3. **T3 — zero jobs** (empty manifest set) → subtree all-zero, `jobs=0`, no throw.
4. **T4 — pruned run dir** (`rmSync` then `readManifests`) → same as T3.
5. **T5 — boundary-unresolvable (marker absent)** → all-zero both halves,
   `boundary.resolved === false`, label
   `boundary=session=… entries=unresolved jobs=0`, no throw.
6. **T6 — chain scoping:** an off-branch entry with usage is excluded; a
   compacted-away on-chain entry is included; an off-branch user message after
   the marker is not chosen as the boundary.
7. **T7 — partial wire cost** `{total: 0.001}` → components `0`, `cost 0.001`,
   never `NaN`.
8. **T8 — invocation isolation, rewritten.** A **later** invocation's record
   excludes an earlier invocation's jobs (the direction the time rule
   guarantees). The "vice versa" assertion is **deleted** (Skeptic O4
   `closed-red`: the forest is a point-in-time filter, not an invocation
   identity). Add the point-in-time/recompute-drift property explicitly: the
   same record recomputed later from the same run dir can grow — which is why
   the record is valid only written once at exit (ruling item 6), with EV-31
   owning recompute basis.
9. **T9 — ruling item 2:** no `total` on the record; `ownSession.usageSource
   === "session-reconciled"` and `subtree.usageSource === "stream-assistant"`
   simultaneously; `reasoning` accumulated independently.
10. **T10 — legacy manifest** without `usage` counts in `jobCount`, adds 0.
11. **T11 — stamp round-trip and fail-closed (O1/O2/O7):** drive a real
    `SessionManager` in memory (`SessionManager.inMemory(cwd)`, see Skeptic
    probe `/tmp/ev30-skeptic/probe-boundary.ts`): seed an assistant, stamp the
    marker via a faithful `pi.appendEntry` shim, assert the marker id equals the
    post-append `getLeafId()`, insert an intervening `appendCompaction`, then
    the injected user message; assert `spendRecord` resolves the boundary to the
    **injected user message** (append-order rule), not the compaction. Also
    assert fail-closed: when the post-append leaf is not the marker,
    `recordInvocationBoundary` returns `null`.
12. **T12 — identical args, two invocations:** two markers in one session with
    identical `$ARGUMENTS` resolve to their own user entries (no content
    matching).
13. **T13 — four-kind enumeration:** a session with `branch_summary` usage
    yields the 4-kind sum, not the 3-kind sum (O3, ruling item 1).
14. **T14 — `lastId` (ruling item 7):** an abandoned-branch entry after the
    leaf does not become `lastId`; `lastId === leafId`.
