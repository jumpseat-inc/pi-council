# EV-73 — Gate enablement lives in `.council.json`; the pin stays in code

Status: **settled design** (full council, mode Deliberate; steps 2–6 complete).
This spec is written up from the card's deliberation record — it derives
nothing afresh and reopens nothing the Council closed. Binding rulings
applied: EPIC-14 Phase-1 R1–R5; the wave-3 card-context ruling (job-33); the
step-6 product-owner ruling (job-2, appended verbatim to the card face). The
`goal:` line on `council/cards/EV-73.md` (post-amendment) is the exact
contract; where this spec and the goal disagree, the goal governs.

## 1. `loadGateConfig` — the single enablement resolver

New exported function in `extensions/gate.ts`:

```ts
export function loadGateConfig(repoRoot: string): { mode: GateMode }
```

- Reads the repo's committed `.council.json`, reusing the existing config-path
  constant from `seats.ts` (`gate.ts` already imports `PKG_ROOT` from there —
  no new dependency direction). A top-level `gate` sibling is invisible to
  `loadCouncilConfig` by construction (it reads only `parsed.council`); like
  `theme` and `retry`, `gate` gets its own independent loader, not a key read
  through the seat-override path.
- Resolution, exhaustive:
  - `.council.json` absent ⇒ `{ mode: "off" }` — byte-identical to today's
    packaged-default behavior.
  - `gate` key absent ⇒ `{ mode: "off" }`.
  - `gate: {}` (section present, `mode` absent) ⇒ `{ mode: "off" }`.
  - `gate` present but not a JSON object (bare string, array, number, null) ⇒
    single-line `FAIL:` naming `gate` — never coerced.
  - Unknown key inside `gate` ⇒ `FAIL:` naming `gate.<key>` (a typo such as
    `"gate":{"mod":"active"}` must fail loud, never silently resolve `off`).
  - `gate.mode` not one of `GATE_MODES` (case-sensitive: `"Active"` fails) ⇒
    `FAIL:` naming `gate.mode`.
  - Malformed JSON / non-object root ⇒ the existing fail-loud single-line
    shape naming the file.
- Every failure goes through the existing `gateFail` mechanism (single line,
  newline-sanitized detail).

## 2. Composition, not reader surgery

- `loadGatePolicy(repoRoot)` calls `loadGateConfig` FIRST — mode resolved
  before `policy.json` is read — then validates the policy file exactly as
  today minus `mode`, and returns `GatePolicy` with `mode` populated from the
  resolved config.
- `GatePolicy` keeps its `mode: GateMode` field. The three runtime readers
  (`gate-tool.ts`, `gate-route-tool.ts`, `gate-route.ts`'s `resolveRoute`
  step-1 off short-circuit) and `gate-run.ts`'s pre-POST off guard all read
  that one resolved value — no reader edits, no second `.council.json` read
  site. "Three readers" remains true by construction; `gate-run.ts` consumes
  the same resolved object, so it is not a fourth direct config reader.
- Lazy-at-call is preserved: `loadGateConfig` runs inside `loadGatePolicy` at
  gate-tool-call time, never eagerly at parent init — a malformed `gate`
  section throws one `FAIL:` at the gate tool call; unrelated session startup
  never crashes on it. Document the named hazard in the `loadGateConfig`
  docstring: a mid-run `.council.json` edit flips routing on the next gate
  read (same run-config-stability class as seat-model edits).

## 3. `mode` leaves `policy.json`

- Remove `"mode"` from `POLICY_KEYS`/`ALLOWED_POLICY_KEYS`. A policy file
  (repo-local or packaged) carrying `mode` hits the existing generic
  unknown-key `FAIL:`, verbatim — **no specialization for `mode` in this
  card** (product-owner ruling job-2 item (a)). The enriched migration copy is
  EV-75's; its candidate bytes are recorded on EV-75's face, under R5's
  wording constraint.
- The packaged `council/gate/policy.json` drops its `"mode": "off"` line in
  the same change: with no `.council.json` `gate` section the packaged default
  must still resolve `off`, and `loadGatePolicy`/`loadGateDecision` must
  validate clean on the packaged tree. (Observed: the worktree's packaged
  file still carries `mode` — the owner applies the drop.)
- No `policyVersion` bump, no re-registration (`validate.py`'s
  `check_gate_registrations` reads `policyVersion` only).

## 4. EV-64 budget rule re-expressed against the RESOLVED mode

- Clause 2 becomes: `gateStateBudgetTokens === undefined && resolvedMode !==
  "off"`, where `resolvedMode` is `loadGateConfig`'s output — never
  re-derived from `policy.json` (which no longer carries a mode).
- Clause 1 unchanged: present ⇒ validated unconditionally in every mode,
  before any short-circuit; `gateStateBudgetTokens: 0` under an off resolved
  mode still fails the positive-integer check (off does NOT relax the
  present-value shape).
- The off short-circuit ordering in the three readers is preserved:
  `loadGatePolicy` (now config-first) → off short-circuit → `buildGateState`.
  A repo with config off and a budget-less repo-local `policy.json` loads
  clean; the identical policy with config `active` throws the clause-2
  `FAIL:`.

## 5. FLLWUP-74's four refusal classes, in `loadGateDecision`

Each a single-line `FAIL:` naming file and key (the `gateFail` template,
except class 4's pinned bytes below):

1. **`thresholds.verify > 0` refused.** Today `verify: 0` is accepted — a
   live defect (skeptic O2, closed-green: `decide()` re-derives a failed call
   as Deliberate on "composite 0.00 ≥ verify threshold 0.00" while the ledger
   records differently). `direct` keeps `≥ 0` plus the existing verify ≤
   direct cross-check.
2. **Unknown `floors`/`thresholds` sub-key refused** (today extras are
   silently ignored). Each parent enumerates its own allowed set — the error
   names which parent is wrong (`floors.bogus — unknown sub-key; expected one
   of choice, score`).
3. **`overrides[i].question` absent from `weights` refused** (`FAIL:` naming
   `overrides.<i>.question`). Weights parse before overrides, so no reordering
   is needed.
4. **Multi-line basis strings refused** (product-owner ruling job-2 item (b)):
   a `loadGateDecision` refusal on the three `decision.json` strings
   `decide()` interpolates into a basis line — `overrides[i].question`,
   `overrides[i].option`, `overrides[i].basis` — whose content can render a
   multi-line basis. **Refuse the input, never sanitize it.** `weights` keys
   are DROPPED from class 4 — not kept defensively (skeptic O1, closed-red,
   confirmed by the ruling: `decide()` uses `weights[id]` as a numeric
   multiplier, never interpolating the key into a basis line; a newline
   `weights` key matches no question and drags toward Deliberate, the safe
   side). Pinned bytes (designer P5):

   ```
   FAIL: <file> has an invalid <key> — value contains a line break; basis lines must be single-line
   ```

   `<key>` is the dotted path (`overrides.0.question`, …). The check runs on
   the raw string (`\r` or `\n` ⇒ refuse) before any sanitization could hide
   the cause; the template's "set a valid value or remove the key" tail is
   deliberately dropped — for a multi-line string there is no in-place valid
   value.

Order within an override rule: shape checks (class 4) before the referential
check (class 3). Packaged `council/gate/decision.json` must validate clean
under all four amended classes.

## 6. Single-resolution-site canary

A test (mirroring `gate-route.test.ts`'s T1 import fence) asserts the only
module touching `.council.json`'s `gate` key is `extensions/gate.ts` — zero
config-path literals in the three reader modules, exactly one `loadGatePolicy`
call each. Use the **transitive** precedence form for the recheck body
(skeptic O5: the recheck's `buildGateState` textually precedes its direct
`loadGatePolicy` call; precedence runs through `resolveRoute`).

## 7. No scaffold change

`council/scaffold/.council.json` seeds nothing for gate: absence-is-off is the
feature, and seeding would make "section absent" and "section set to off" look
like two states when the acceptance says they are byte-identical
(designer P9 withdrawn round 2). Discoverability rides EV-75's enriched
`FAIL:`, `/council-gate` (EV-74), and EV-77's documentation.

## 9. The pin stays in code

`GATE_PINNED_MODEL` (`typesafe/jev-1.13`) and `GATE_ENDPOINT` stay hard code
constants enforced in `gate-run.ts`; a non-pinned model cannot reach the
transport. No `policyVersion` bump, no re-registration.

## 10. Test plan (TDD; `fs.mkdtempSync` roots, never the real repo)

From the deliberation's testable claims (owner round-1 (f), principal's six,
designer P1–P10, skeptic O8's named settling tests):

- **Packaged default**: no `.council.json`, packaged tree ⇒ `loadGatePolicy`
  returns `off`; gate-tool no-op byte-identical to current.
- **`loadGateConfig`**: absent file/section ⇒ off; three modes resolve;
  `gate:{}` ⇒ off; bare-string `gate` refused; unknown gate sub-key `FAIL:`
  names `gate.mod`; invalid and case-wrong mode `FAIL:` names `gate.mode`;
  malformed JSON single-line.
- **Transitive equality**: `loadGatePolicy(repo).mode ===
  loadGateConfig(repo).mode` for `gate.mode` ∈ {absent, off, advisory,
  active}.
- **Migration FAIL**: `policy.json` containing `mode` ⇒ the exact single-line
  unknown-key `FAIL:` (verbatim tail "set a valid value or remove the key to
  use the packaged default"), even with config off; packaged `policy.json`
  has no `mode` key and still resolves `off`.
- **Budget**: advisory + budget-less ⇒ clause-2 `FAIL:`; the same policy with
  config off ⇒ loads clean; present-but-invalid budget ⇒ clause-1 `FAIL:` in
  every mode.
- **Refusal classes 1–4**, including the newline-bearing `overrides.0.question`
  test; each `FAIL:` matches `^FAIL: .* has an invalid .+ — .+$` with no
  embedded newline; packaged `decision.json` clean under all four.
- **Readers**: gate-tool off no-op unchanged; advisory reachable purely from
  `.council.json`; route step-1 short-circuit driven by config; gate-run mode
  originates from config; pin guards unchanged.
- **Canary** per §6.
- **Gate-scoped failure**: init equivalent completes; the throw happens at
  the gate tool call only.

Existing tests that set modes via repo-local `policy.json` fixtures switch to
`.council.json` `gate` fixtures.
