# EV-3 Design — Activate the Council Theme on Session Start

**Date:** 2026-08-25
**Status:** Approved by Council deliberation (Round 1 independent pass → Round 2 convergence → Skeptic attack → Consolidator synthesis)
**Card:** EV-3 (EPIC-1). The epic's design authority is
`docs/superpowers/specs/2026-08-25-council-theme-design.md` (EV-5), §4
"Activation semantics — four-state table (ruled, binding)". This spec is the
EV-3 contract: the settled activation decision, data flow, construction
path, session-start wiring, and acceptance tests. It does not reopen
anything the deliberation closed.

## 1. Goal

At session start the council extension materializes the `.council.json`
theme section (EV-2) into a pi `Theme` instance and activates it so the TUI
renders in the configured palette; a repo without a theme section leaves pi's
theme exactly as the user configured it.

## 2. Binding rulings applied (do not reweigh)

- **Phase 1 Ruling (recorded, binding):** pi's `"theme": "light/dark"` setting
  (auto-follow terminal appearance) is **not** an explicit theme choice and
  does **not** block council activation; the council theme still activates and
  follows terminal appearance with its own dark/light pair. Only a concrete
  theme name (e.g. `"theme": "gruvbox"`) in settings.json blocks council
  activation. This is the four-state table (§4 of the epic spec), rows a–d.
- **NAME-1 (Phase 1):** the theme family name is `pi-council` and nothing
  else; the dark/light variants materialize as `pi-council-dark` /
  `pi-council-light`. These are the shipped asset names (EV-1) — the
  in-memory instance carries no registered name and writes no on-disk theme.
- **§4 authority:** the epic design spec §4 "writes nothing to disk" is
  strict — in-memory `new Theme(...)`, **no tempfile**, no on-disk theme
  copy. Reading shipped assets from `PKG_ROOT/themes` is not a write.
- **`setThemeInstance` / `<in-memory>` (settled):** activation goes through
  `new Theme(...)` + `ui.setTheme(instance)` — the `instanceof Theme` branch
  (interactive-mode.js:1945–1955) calls `themeController.setThemeInstance` →
  `setGlobalTheme(instance)`, sets `currentThemeName = "<in-memory>"`, and
  makes **zero** `settingsManager` calls. The string branch (which writes pi's
  settings.json) is **forbidden**. The extension never writes pi's
  settings.json.

## 3. The module

New file `extensions/theme-activation.ts`. It holds a **pure decision
function** plus integration glue and the construction/activation path. As
EV-2 did for `loadThemeConfig`/`mergeThemeSection`, the pure parts are
unit-testable without a real TUI or a live session; pi's real `Theme`,
`detectTerminalBackgroundFromEnv`, and `getCapabilities` are reached by
deep-import at test time.

All theme-family and config constants come from `extensions/seats.ts`
(`loadThemeConfig`, `mergeThemeSection`, `loadShippedTheme`, `PKG_ROOT`).
Paths use `CONFIG_DIR_NAME` / `PKG_ROOT` — never a hardcoded `.pi`
(AGENTS.md 3, 4).

### The decision function

```ts
// Pure — no I/O, no TUI. The caller passes the raw values read off disk.
export type ThemeActivationDecision =
  | { action: "activate"; variant: "dark" | "light" }
  | { action: "noop" }
  | { action: "block"; themeName: string };

export function decideThemeActivation(
  config: ThemeSection | undefined,
  rawSetting: unknown,        // the raw settings.json "theme" leaf, project-wins-resolved
  configVariantPin?: "dark" | "light", // from config.variant when !== "auto"
  terminalTheme?: "dark" | "light",    // detectTerminalBackgroundFromEnv() result, sync
): ThemeActivationDecision;
```

- `config === undefined` → `{ action: "noop" }` (**rapid gate** — returns
  immediately and reads no settings).
- **Whitelist** — activate iff `rawSetting` is absent (`undefined`) or one of
  `"light/dark"`, `"dark"`, `"light"`; everything else, including a
  custom `A/B` pair like `"nord-light/nord-dark"`, blocks (row d). **Never
  route through `parseAutoThemeSetting`** — it inverts any `A/B` pair into an
  auto pair (Skeptic #2, #11 closed-green). A string with `/` is a concrete
  named arrangement → block.
- **Which block tuple carries which variant:**
  - If `config.variant` is pinned `"dark"` / `"light"` → that variant.
  - Else (auto, including the state-(a) unset and state-(b) `"light/dark"`
    cases) the variant is `terminalTheme ?? "dark"`. `terminalTheme` is the
    result of pi's exported **`detectTerminalBackgroundFromEnv()`** (sync,
    COLORFGBG-luminance heuristic), called by the glue, passed in — not
    re-implemented. Environment heuristic mirrors pi's sync fallback only
    (non-gating caveat).
- The state-(c) settings literal `"dark"`/`"light"` that passed the
  whitelist activates directly via the whitelist — it is **not** a fallback
  step in the variant chain.

## 4. Data flow

```
session_start
  └─ ctx.ui (ExtensionUIContext)
  └─ read raw settings.json theme leaves off disk:
       getAgentDir()/settings.json  (global)
       <repo>/CONFIG_DIR_NAME/settings.json  (project)
       project wins at the leaf → rawSetting
  └─ config = loadThemeConfig(repoRoot)          // EV-2; undefined = off
  └─ terminal = detectTerminalBackgroundFromEnv() // pi's exported, deep-imported
  └─ decision = decideThemeActivation(config, rawSetting, configVariant, terminal)
  └─ buildMaterializedTheme(config, decision)    // pure
       │  base = loadShippedTheme(decision.variant)      // path.join(PKG_ROOT,"themes",...)
       │  merged = mergeThemeSection(base, config[decision.variant])
       │  resolved = resolveThemeColors(merged.colors, merged.vars)  // reimplemented, see §5
       │  fg/bg split (8 bg keys)
       │  mode = getCapabilities().trueColor ? "truecolor" : "256color"
       └─ new Theme(fgColors, bgColors, mode)
  └─ ui.setTheme(instance)        // instanceof-Theme branch, zero settingsManager
  └─ notify tri-state (§6)
```

- **Raw settings off disk:** read `getAgentDir()/settings.json` and
  `<repoRoot>/<CONFIG_DIR_NAME>/settings.json`, JSON-parse, and resolve the
  `theme` leaf with **project-wins** precedence before feeding the decision
  function. **Never read `ui.theme.name`** — after any
  `ui.setTheme(instance)` it is `"<in-memory>"`. Precedence: project wins
  at the leaf (the file the user is actually editing).
- **In-memory Theme construction:** build the merged JSON (base +
  per-variant override block merged in EV-2 order — `vars` map first, then
  `colors`, repo wins per key).
  Resolve var-refs to concrete hex **before** `new Theme(...)` — pi's
  constructor throws on a non-hex var-ref. Split the **8 bg keys**
  (`selectedBg`, `scrollbarThumb`, `searchMatchBg`, `userMessageBg`,
  `customMessageBg`, `toolPendingBg`, `toolSuccessBg`, `toolErrorBg`) out of
  `colors`; the rest go to `fgColors`. Mirror the internal fallback behavior:
  `scrollbarThumb ← selectedBg`, `searchMatchBg ← selectedBg`,
  `searchMatchText ← text`, `thinkingMax ← thinkingXhigh` (Skeptic #5
  verified the real fallback chain against the omp orange `#febc38` accent and
  `selectedBg`).
- **`ui.setTheme(instance)`:** the instance branch is the literal
  `ui.setTheme(theme: string | Theme)` call. This is the zero
  `settingsManager` path. **Do not call `settingsManager`, do not write pi
  settings.**

### Session-start wiring

Insert activation inside the existing `pi.on("session_start", ...)` handler in
`extensions/index.ts`, **before** `initHubIdentity(mintRunId())` and the
widget, matching the settled ordering from the epic spec §4 (index.ts:109–135).
Wrap the whole activation block in a `try/catch` so a malformed
`.council.json` / unexpected throw **notifies and returns, never crashes
session_start**. The notify tri-state (`§6`) runs inside the `try` (a
`loadThemeConfig` throw is caught and reported).

## 5. Mode detection

`getCapabilities()` is **not** on the pi-coding-agent public API nor the theme
module (Skeptic #6 closed-red). Import it from `@earendil-works/pi-tui` (the
module pi's own `createTheme` imports it from) and use
`getCapabilities().trueColor ? "truecolor" : "256color"`. (Substitute
equivalent: `chalk.level >= 2`.) The env heuristic mirrors pi's sync fallback
only. Set the `mode` argument on the `Theme` constructor from this `buildMode()`
result.

## 6. Notify tri-state (in-scope, low-priority, removable layer)

- **activate:** `ui.notify("council theme: pi-council-{variant}", "info")`
- **block:** `ui.notify("council theme: blocked (settings.json has
  '{raw}')", "warning")`
- **no-section / noop:** silent.
- Non-gating: absence of the notify layer does not change the activation
  decision or the construction path (Skeptic #9 open-untested, non-gating by
  settled design). Guard with `hasUI` where sensible. Notify strings are
  plain text, no inline ANSI (surface-compliance, epic §5(b)).

## 7. Acceptance (corrected card text)

Under in-memory activation the card's draft acceptance line "`getThemeByName`
resolves the materialized theme" is **unsatisfiable** (an in-memory `Theme`
sets `this.name` but registers nothing). It is **deleted** and replaced with
the instance-color-identity and namespace split assertions — the corrected
acceptance for this card:

1. **Instance color identity:** with a theme section present, after session
   activation the activated `Theme` instance's resolved colors deep-match the
   merge→resolve of `(loadThemeConfig‑variant base, repo.overrides)`: i.e.
   `resolveThemeColors(mergeThemeSection(loadShippedTheme(variant),
   section[variant]).colors, .vars)` equals the colors used to construct the
   activated `Theme`.
2. **Namespace:** `getThemeByName("pi-council-dark")` after activation still
   returns EV-1's shipped **un-merged** palette — in-memory activation never
   collides with the registered names. (Skeptic #10 closed-green.)
3. Correct `rawSetting` blockarity against the settings-file stubs: no section
   → noop; `theme: "gruvbox"` → block; `theme: "light/dark"` → activate;
   persisted `"dark"` → activate. Pure decision-table test.
4. Settings files byte-identical after activation (no mutation — settle the
   two stubbed settings.json are untouched).

These are unit-testable without a real TUI (deep-import of pi's real `Theme`
and `detectTerminalBackgroundFromEnv`).

## 8. Tests

`test/theme-activation.test.ts` (new). Pieces:

1. **Decision table (pure).** All rows a–d + custom `A/B` (`"nord-light/
   nord-dark"`) + `undefined` + absent config → `{noop}`; whitelist
   {undefined, "light/dark", "dark", "light"} → activate; every other string
   → block. Two out-of-band pure-probe tests replace any
   `parseAutoThemeSetting` call-site with the strict-whitelist result.
2. **Construction identity (deep-import).** Build Theme via the module from
   merged JSON both in truecolor and 256color mode; assert ANSI codes match
   the real `fg`/`bg` output of pi's own `createTheme`-style construction
   (accent #febc38 `\x1b[38;2;254;188;56m`, selectedBg `\x1b[48;2;49;54;63m`,
   fallback chain scrollbarThumb→selectedBg, searchMatchBg→selectedBg,
   searchMatchText→text, thinkingMax→thinkingXhigh).
3. **Namespace untouched:** after constructing an in-memory Theme and calling
   `ui.setTheme(instance)` in a stubbed ctx, `getThemeByName("pi-council-
   dark")` still returns the EV-1 shipped un-merged palette. (Probe uses
   `Theme` + asserts no name was registered.)
4. **Mode detection:** `buildMode()` (from `getCapabilities().trueColor`,
   imported from `@earendil-works/pi-tui`) yields `truecolor` when the stubbed
   capability reports true and `256color` otherwise.
5. **No-op:** with `config === undefined`, activation reads no settings file
   (spy on readFileSync) and makes no `setTheme` call.

Run the four gates in full (`bun install --frozen-lockfile`, `bunx tsc
--noEmit`, `bun test`, `python3 council/validate.py`).
