# EV-2 Design — Theme Configuration in the Scaffold `.council.json`

**Date:** 2026-08-25
**Status:** Approved by Council deliberation (Round 1 independent pass → Round 2 convergence → Skeptic attack → Consolidator synthesis)
**Card:** EV-2 (EPIC-1). The epic's design authority is
`docs/superpowers/specs/2026-08-25-council-theme-design.md` (EV-5); this spec
is the EV-2 contract. Where this spec and the EV-5 §3 *working proposal*
differ, **this spec wins** — the EV-5 spec is updated in the same PR (see §9).

## 1. Goal (as conformed, per spec §8 one-word fix)

The scaffold `.council.json` carries an editable theme section that
`loadThemeConfig` parses and validates and that merges repo overrides over
the shipped omp defaults. (The card's draft goal named `loadCouncilConfig`;
spec §8 settled the sibling loader and outranks the draft wording. The
card's goal text was conformed in this run.)

## 2. The settled shape

Top-level `theme`, a sibling of `council` (never nested inside it):

```json
{
  "council": { "<seat>": { "model"?, "thinking"? }, ... },
  "theme": {
    "enabled": true,
    "variant": "auto",
    "dark":  { "vars": { "<varName>": "<value>" }, "colors": { "<tokenName>": "<value>" } },
    "light": { "vars": { "<varName>": "<value>" }, "colors": { "<tokenName>": "<value>" } }
  }
}
```

- **`enabled`** — optional boolean. Absent/true = on (presence implies
  enabled); `false` = off. The scaffold seeds `true` so the off switch is
  discoverable.
- **`variant`** — required in the seeded section, `"auto" | "dark" |
  "light"`. Validated but **not resolved** by EV-2 (`auto` → dark/light is
  terminal-dependent and is EV-3's job). Absent `variant` defaults to
  `"auto"`.
- **`dark` / `light`** — optional per-variant override blocks. Absent block
  = no delta for that base. Each block has two optional sub-objects:
  - `vars` — keys must be **vars declared in that variant's shipped file**
    (per-variant vocabulary; dark and light var sets differ — see §4). An
    override here transitively recolors every token whose shipped value
    references the var.
    Values: hex / 256-index / var-ref / `""`.
  - `colors` — keys must be pi theme token names (**ThemeColor ∪ ThemeBg**,
    the 51 shipped keys + 4 optional: `scrollbarThumb`, `searchMatchBg`,
    `searchMatchText`, `thinkingMax`). An override here pins that token
    only.
    Values: hex / 256-index / var-ref (must resolve to a declared var of
    that variant) / `""` (use pi's default — a valid override value,
    distinct from an absent key).
- **No `name` key.** The family name `pi-council` (NAME-1) lives in the
  shipped asset names (`pi-council-dark` / `pi-council-light`) and the
  merge-base path — never a config key. A `name` key inside `theme` is an
  **unknown key and throws** (strict unknown-key rejection inside `theme`).
  This is a recorded application of the Phase 1 shape ruling + NAME-1: the
  ruling's "name `pi-council`" requirement is satisfied by family identity,
  not a redundant key with exactly one legal value.

## 3. Loader and reserved key

- New sibling loader `loadThemeConfig(repoRoot: string): ThemeSection |
  undefined` in `extensions/seats.ts`, beside `loadCouncilConfig`.
- `theme` is a **reserved key** skipped in `loadCouncilConfig`'s loop: the
  loop today reads only `parsed.council` entries, so a top-level `theme`
  sibling is already invisible to it — no return-shape change. Add the
  one-line reserved-key guard so the **mis-nested** `council.theme` never
  parses as a phantom seat override (verified current behavior:
  `{"council":{"theme":"dark"}}` THROWS `must be qualified as provider/id`;
  `{"council":{"theme":{"enabled":true}}}` produces a phantom empty seat —
  the guard closes both).
- Malformed JSON throws naming the file, same message shape as
  `loadCouncilConfig` today.
- **Off switch** — `loadThemeConfig` returns `undefined` for: absent
  `theme` key; `theme: false`; `theme: null`; `theme: 0` (any falsy
  non-object); `theme: { "enabled": false }`. `theme: {}` returns
  `{ variant: "auto" }` (presence implies enabled; absence means absence of
  the **whole key**, never absence of `enabled`). A non-falsy non-object
  (`theme: "on"`) is invalid and throws naming the file.
- Return shape is `{ enabled?: boolean, variant: "auto"|"dark"|"light",
  dark?: { vars?, colors? }, light?: { vars?, colors? } }`.

## 4. Merge semantics (data-in/data-out over JSON)

- **Base:** the shipped asset JSON read from disk via
  `path.join(PKG_ROOT, "themes", "pi-council-{dark,light}.json")` —
  **never `getPackageDir()`** (that is pi's install dir and would silently
  load pi's built-in theme, accent `#8abeb7`). `PKG_ROOT` is already
  exported from `extensions/seats.ts`.
- **Pure function:** `mergeThemeSection(baseJson, overrideBlock?)` returns
  the full merged JSON `{ vars, colors, export }`.
- **Order per variant:** merge the `vars` **map** first (repo wins per key),
  then the `colors` map (repo wins per key). **Never resolve the base's
  var-refs to hex before or during the merge** — un-overridden tokens keep
  their var-refs so a repo `vars` edit transitively recolors every
  referencing token at Theme construction. Var-ref resolution happens only
  at Theme construction, after both maps merge.
- **`export` is preserved** untouched from the base through the merge
  (`pageBg`/`cardBg`/`infoBg` are not overridable in EV-2 — out of scope,
  deferred).
- **Repo wins**; absent section means "no theme config" (activation decides
  what that implies).
- The merge function is pure and unit-testable without pi's loader.

## 5. Validation (fail-fast, message naming the file)

- Malformed JSON → throw naming the file.
- `theme` root not object (and not a recognized falsy) → throw naming the
  file.
- Unknown key anywhere inside `theme` (including `name`) → throw naming the
  file and the key.
- `variant` not in `auto|dark|light` → throw naming the file.
- `vars` key not a declared var of that variant → throw naming the file,
  the key, and the variant. (Cross-variant pins throw deterministically:
  `dark.vars.teal` throws, `light.vars.accent` throws — `teal` is light-only,
  `accent` is dark-only.)
- `colors` key not in the valid token set (51 shipped keys + 4 optional) →
  throw naming the file and the token.
- Value not hex (6-digit, matching pi's `hexToRgb` — 3-digit `#fff` is
  rejected by pi and must be rejected at parse), not an integer 0–255
  (256-index), not a var-ref to a declared var of that variant, and not `""`
  → throw naming the file. Var-refs in `colors` resolve against the
  **merged** vars of that variant.
- `enabled` not boolean → throw naming the file.

## 6. Scaffold

- `council/scaffold/.council.json` gains the theme section, seeded minimal
  (a delta, not a palette dump):

  ```json
  "theme": {
    "enabled": true,
    "variant": "auto"
  }
  ```

  No `dark`/`light` shells, no `name`.
- `scaffoldInto` behavior is unchanged (non-clobbering copy-when-absent).
  A fresh scaffold into an empty temp repo writes the section; a re-run
  over a user-edited `.council.json` is byte-for-byte a no-op on that file
  — **including** a pre-existing `.council.json` that lacks `theme` (no
  `theme` key is added; existing repos get no theme config until the user
  writes one — absence = off).
- **Delta acceptance (restated per Skeptic objection 2):** "the default
  scaffold section matches the shipped omp palette" means:
  `mergeThemeSection(loadShippedTheme("dark"), seededSection)` deep-equals
  the shipped dark JSON and `mergeThemeSection(loadShippedTheme("light"),
  seededSection)` deep-equals the shipped light JSON — the seeded section
  has no override blocks, so merging it with either base is identity. The
  test runs against **both** variants; `variant: "auto"` is not resolved by
  EV-2, so the merge-identity test exercises the merge function directly
  with each base.

## 7. Test expectations — the verified var-consumer graph

The transitivity tests MUST be written against the graph verified by the
Skeptic probe against the shipped files (not the spec's stale §3 example,
not the card draft):

| var | dark consumers | light consumers |
|---|---|---|
| `blue` | `[border]` only | `[border, mdLink, thinkingLow]` |
| `cyan` | `[borderAccent, bashMode]` | — (no `cyan` var in light) |
| `accent` | `[accent, mdListBullet]` | — (no `accent` var in light) |
| `teal` | — (no `teal` var in dark) | `[accent, borderAccent, mdCode, thinkingMedium]` |

(Full graph verified against the shipped files: dark consumers also include
green→[success, toolDiffAdded], red→[error, toolDiffRemoved],
cyan→[borderAccent, bashMode], gray→[muted, thinkingText, toolOutput,
mdCodeBlockBorder, mdQuote, toolDiffContext], dimGray→[dim, mdLinkUrl,
thinkingMinimal], darkGray→[borderMuted, mdQuoteBorder, mdHr, thinkingOff];
light consumers include green→[success, mdCodeBlock, mdListBullet,
toolDiffAdded, bashMode], red→[error, toolDiffRemoved], yellow→[warning,
mdHeading], mediumGray→[muted, thinkingText, toolOutput, mdCodeBlockBorder,
mdQuote, mdQuoteBorder, mdHr, toolDiffContext], dimGray→[dim, mdLinkUrl],
lightGray→[borderMuted, thinkingOff]. Tests only need the four rows above,
but write them against the real graph, never from memory.)

- `thinkingLow` and `mdLink` are **literal hexes** in dark (`#178fb9`,
  `#0088fa`), NOT var-refs — a `vars.blue` override does not recolor them in
  dark.
- `mdHeading` is a literal `#febc38` in dark — unaffected by var overrides.
- Design of the transitivity tests: `dark.vars.cyan = "#123456"` →
  `merged.vars.cyan === "#123456"` AND `merged.colors.borderAccent ===
  "cyan"` and `merged.colors.bashMode === "cyan"` (var-refs survive the
  merge). `dark.vars.blue = "#336699"` → `merged.colors.border === "blue"`.
  `dark.colors.accent = "#ff8800"` → `colors.accent === "#ff8800"` while
  `mdListBullet` still follows the var.
- Two-layer probe (same key name, different layer): `dark.vars.accent =
  "#123456"` → resolved `colors.accent` AND `colors.mdListBullet` follow
  the var; `dark.colors.accent = "#654321"` → `colors.accent` is the pin,
  `mdListBullet` unchanged.
- Layering order: `dark.vars.cyan = "#123"` AND `dark.colors.border =
  "#888"` → `colors.border === "#888"` (colors wins for the same token),
  `colors.bashMode === "cyan"` (vars wins where no colors override).
- Per-variant independence: `dark` overrides never touch the merged light
  JSON (deep-equals shipped light), and vice versa.

## 8. Acceptance tests (from the card, conformed)

1. `loadThemeConfig` returns the parsed theme section; unit tests cover
   happy path, missing section (`undefined`), malformed JSON (throws naming
   file), invalid token (throws naming file), falsy off-switch forms
   (`false`/`null`/`0`/`enabled:false`), and override merge (repo wins).
2. Scaffold test: fresh `scaffoldInto` into an empty temp repo writes the
   theme section (`{"enabled":true,"variant":"auto"}`); re-running into a
   repo with an existing `.council.json` leaves it byte-for-byte untouched
   (including one that lacks `theme`).
3. Delta acceptance: seeded section merges to byte-identical shipped dark
   and shipped light (§6).
4. Zero blast radius: `loadCouncilConfig` return shape unchanged
   (`{"theme":{...}}` → `{}`); `{"council":{"theme":{...}}}` yields no
   `"theme"` seat entry after the reserved-key guard; existing tests
   (seats.test.ts, scaffold.test.ts) stay green without edits to their
   expectations.
