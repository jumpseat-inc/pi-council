# EV-28 design — full usage tuple and cost provenance in the hub usage record

- **Card:** `EV-28` (epic `EPIC-7`), `council/cards/EV-28.md`
- **Status:** settled by the step-6 product-owner ruling; this document is the
  write-up, not a re-derivation. Nothing settled in steps 2–6 is reopened here.
- **Scope:** capture + persistence + rendering of the full usage tuple in the
  hub. No session reconciliation, no durable store, no exit-point reporting.
- **Design record:** `council/cards/EV-28.md` § "Step 2"–§ "Step 6 —
  product-owner ruling (verbatim, binding)". Phase 1 rulings R-1/R-2/R-3 and
  the step-6 ruling are binding; this spec applies them.

## 1. Problem

`Job.usage` keeps only `input`, `output`, a catalogue-estimated scalar `cost`
and `turns`. The wire `Usage` that the hub already parses carries
`cacheRead`, `cacheWrite`, `reasoning`, `totalTokens` and a per-component
`cost` breakdown, and ingestion drops all of them
(`extensions/hub.ts:191-199`). The persisted `Usage`
(`extensions/runs.ts:5-9`) has no field to receive them, so:
- nothing downstream can report the real token composition;
- the dollar figure carries no provenance (it is always a catalogue estimate,
  never a provider charge);
- a dispatch that produced no assistant message still renders a head line
  reading `cost=$0.0000`, which reads as "zero spend, fine".

Grounding: wiki `run-transcripts` (the manifest substrate),
`hub-job-supervision` (the accumulation loop and the wait-report line),
`eval-store-contract` (the append-only record whose `cellScope.usage` this
change brushes against).

## 2. Settled design

### 2.1 One `Usage` declaration — flat shape, in `extensions/runs.ts`

The persisted `Usage` becomes the single declaration of the tuple; the inline
duplicate at `extensions/hub.ts:19` is deleted in favour of an import.

```ts
export type CostBasis = "catalogue-estimate" | "reported";
export type UsageSource = "stream-assistant" | "session-reconciled";

export interface Usage {
  input: number;
  output: number;
  cacheRead: number;        // accumulated, never folded into input
  cacheWrite: number;
  reasoning: number;        // subset of output — accumulate independently, never re-add
  totalTokens: number;
  cost: number;             // scalar aggregate; the compatibility anchor
  costInput: number;
  costOutput: number;
  costCacheRead: number;
  costCacheWrite: number;
  turns: number;
  costBasis: CostBasis;     // R-3
  usageSource: UsageSource; // step-6 ruling Q4
}

/** Numeric metrics only — the two string-valued fields cannot be summed. */
export type UsageMetric = Exclude<keyof Usage, "costBasis" | "usageSource">;
```

Two doc-comments are **required** on `Usage` (the step-6 ruling lands them
here):

1. **Wire→record clause (Q1):** on ingestion, `u.cost.input →
   usage.costInput`, `u.cost.output → usage.costOutput`, `u.cost.cacheRead →
   usage.costCacheRead`, `u.cost.cacheWrite → usage.costCacheWrite`, and
   `u.cost.total → usage.cost`; partial cost objects (e.g. `{total:0.001}`)
   coerce the missing components to 0, never `NaN`; the card goal's dotted
   `cost.input|…` refer to the wire components that ingestion flattens, not to
   a nested record shape.
2. **Capture-scope clause (Q4):** capture is a stream projection of assistant
   `message_end` events on the child's stdout only — tool-result and
   compaction usage are absent. The persisted `usageSource` field is the
   machine-readable statement of that scope.

`costBasis` and `usageSource` are **required** on the record shape: the write
path always emits them. Reads of legacy manifests stay tolerant via `?? 0`
(and `?? "catalogue-estimate"` if a value is ever read off a legacy manifest).

### 2.2 Ingestion (`extensions/hub.ts:191-199`)

Keep the existing `message_end` + `role === "assistant"` gate. Extend the
accumulation with `?? 0` / `|| 0` guards:

- `cacheRead += u.cacheRead || 0`
- `cacheWrite += u.cacheWrite || 0`
- `reasoning += u.reasoning || 0` — **never** added into `output` (pi-ai
  documents `reasoning` as a subset of `output`; the provider already counts
  it there)
- `totalTokens += u.totalTokens || 0` — provider-reported, **never** derived
  from the component sum
- `costInput += u.cost?.input || 0`, `costOutput += u.cost?.output || 0`,
  `costCacheRead += u.cost?.cacheRead || 0`,
  `costCacheWrite += u.cost?.cacheWrite || 0`
- `cost += u.cost?.total || 0` (unchanged)

Invariant (tested): on the wire, `cost.total === cost.input + cost.output +
cost.cacheRead + cost.cacheWrite` (pi-ai `models.js:547`), so the accumulated
scalar equals the sum of the four accumulated components.

### 2.3 Initializer stamps the provenance defaults (`extensions/hub.ts:133`)

The single `Job.usage` initializer becomes:

```ts
usage: {
  input: 0, output: 0, cacheRead: 0, cacheWrite: 0, reasoning: 0, totalTokens: 0,
  cost: 0, costInput: 0, costOutput: 0, costCacheRead: 0, costCacheWrite: 0,
  turns: 0,
  costBasis: "catalogue-estimate",
  usageSource: "stream-assistant",
},
```

Manifest and report agreement is **by construction**: the manifest writes
`job.usage` (`hub.ts:101`) and `report()` copies it (`hub.ts:265`), so both
observe the same object shape and the same `costBasis`/`usageSource` values.
No sync discipline is added.

`JobReport.usage` and `TerminalTelemetry.usage` (`eval-runner.ts:272`) are
typed as the imported `Usage` (the full tuple).

### 2.4 Eval-store boundary — explicit whitelist (Q3)

`StoredResultRecord.cellScope.usage` is serialized into the append-only
`council/eval-results/` store, and today it is a direct reference assignment
to `report.usage` (`eval-runner.ts:311-318` via `:438`) — so every new field
would silently enter the durable record. That is barred: the eval-store
contract's recorded shape (`{input, output, cost, turns}`) stays intact.

At `eval-runner.ts:312-313`, build `cellScope.usage` by **explicit pick**:

```ts
usage: {
  input: input.terminal.usage.input,
  output: input.terminal.usage.output,
  cost: input.terminal.usage.cost,
  turns: input.terminal.usage.turns,
},
```

`CellScope.usage`'s declared shape in `eval-rubric.ts:80` is unchanged. The
whitelist is at the assignment site, not the type site (structural typing
would accept the wider literal). Widening this record to the full tuple rides
a separate follow-up card that amends `vault/wiki/eval-store-contract.md`; it
is **not** done here.

`JudgeOutcome.gradingUsage` / `projectVerdictRecord` (`eval-rubric.ts:212`)
keep their O4-narrowed shape — untouched.

### 2.5 Head line (`extensions/hub-tools.ts`)

Extract an exported pure formatter and splice it into `formatReport`:

```ts
export function formatUsageSegment(u: Usage): string {
  const money =
    u.costBasis === "reported"
      ? `cost=$${u.cost.toFixed(4)} (reported)`
      : `cost≈$${u.cost.toFixed(4)} (catalogue)`; // ≈ is U+2248
  return `turns=${u.turns} tokens=in ${u.input}/out ${u.output}/cR ${u.cacheRead}/cW ${u.cacheWrite}/reason ${u.reasoning}/total ${u.totalTokens} ${money}`;
}
```

`formatReport` keeps the identity prefix and appends the usage segment only
when the suppression predicate fails:

```ts
const identity = `[${r.id}] seat=${r.seat} state=${r.state}${stop} elapsed=${mins}m`;
const suppressed = r.usage.turns === 0 && r.output === "";
const head = suppressed ? identity : `${identity} ${formatUsageSegment(r.usage)}`;
```

Composition rules (binding, Q5):
- fixed token order `in / out / cR / cW / reason / total`;
- label collapse **only** for the cache fields: `cacheRead`→`cR`,
  `cacheWrite`→`cW`; persisted field names are unchanged;
- `reason` label for the persisted `reasoning` field (avoids collision with
  `stopReason` earlier on the line); persisted field stays `reasoning`;
- no thousands separator anywhere;
- `/` separators with one space each side, no trailing space;
- `turns` stays on the line, immediately before `tokens=`;
- money rightmost, `(catalogue)`/`(reported)` directly after the figure with
  no space before the parenthesis;
- the whole line must fit one line at **≤160 columns** at both fixtures in
  §3.2. A future fixture exceeding 160 is a follow-up card, not a Q5 change.

Export `formatUsageSegment` and `formatReport` so the byte-length and
string-equality tests can call them directly.

### 2.6 Zero usage and suppression semantics

- **Zero-usage dispatch that emitted an assistant message** (e.g.
  `turns > 0`, all counters 0): renders all-zero fields plus
  `cost≈$0.0000 (catalogue)`. Never suppressed.
- **No assistant message** (`turns === 0 && output === ""`): the identity
  prefix `[id] seat= state= … elapsed=…m` still renders; only the usage
  segment is omitted. This binds across every terminal state (`done`,
  `failed`, `stalled`, `timeout`, `cancelled`). The existing
  `⚠ done but no text output` warning still renders and remains the
  discoverable signal.

## 3. Acceptance and required tests

### 3.1 Card acceptance, mapped

| Card acceptance line | Where satisfied |
|---|---|
| Fixture with input 100 / cacheRead 900 / cacheWrite 0 / output 10 + cost breakdown accumulates `cacheRead` 900 and every token field separately | §2.2 + test T1 |
| Persisted manifest and `council_wait` report agree on the tuple and `costBasis = catalogue-estimate` | §2.3 + test T4 |
| Head line names the token split and the basis; not a scalar dollar total | §2.5 + tests T5/T6 |
| `bun test`, `bunx tsc --noEmit`, `python3 council/validate.py` stay green | gates, §4 |

### 3.2 Required tests

- **T1 — ingestion tuple.** Drive `processLine` with an assistant
  `message_end` whose usage is `{input:100, output:10, cacheRead:900,
  cacheWrite:0, reasoning:7, totalTokens:1010, cost:{input:0.0003,
  output:0.0001, cacheRead:0.0009, cacheWrite:0, total:0.0013}}`; assert
  `cacheRead === 900` (the card's core red today), each token field
  separately, each cost component separately, and `cost === 0.0013`. Two
  sequential `message_end`s accumulate. `reasoning` is never added into
  `output`.
- **T2 — cost post-condition.** For the T1 fixture,
  `cost === costInput + costOutput + costCacheRead + costCacheWrite`.
- **T3 — partial cost object.** Wire usage `{cost:{total:0.001}}` (today's
  stub shape) yields all four components `0`, never `NaN`.
- **T4 — manifest/report agreement.** Spawn under `run:` opts, settle,
  `readManifests`; the manifest `usage` deep-equals the `report()` usage, with
  `costBasis === "catalogue-estimate"` and
  `usageSource === "stream-assistant"`.
- **T5 — head-line bytes.** The acceptance-fixture line (id/seat/state/
  stopReason/elapsed + the §2.5 values) measures **≤160** columns; the
  `cacheRead 9000` variant also measures **≤160**; `≈` is asserted as
  `"\u2248"`; a `costBasis:"reported"` fixture renders `cost=$… (reported)`.
  Reference measurements at `[job-1] seat=owner state=done stopReason=stop
  elapsed=2.3m` (facilitator-measured, not a threshold): acceptance fixture
  = 144 cols, `cR 9000` variant = 145 cols. The test pins the ≤160
  threshold; these two numbers are the fixtures to pin it at.
- **T6 — zero usage renders zeros.** A job with `turns > 0` and all-zero
  counters still carries the usage segment with all-zero fields and
  `cost≈$0.0000 (catalogue)`.
- **T7 — suppression.** A job with no assistant `message_end` (`turns === 0`,
  `output === ""`) renders the identity prefix and **no** usage segment; the
  report string contains no `cost≈`/`cost=$`. Cover at least one non-`done`
  terminal state to pin the state-independence.
- **T8 — eval-store whitelist.** After `gradeAndPersist`, the parsed
  `StoredResultRecord.cellScope.usage` keys are exactly
  `{input, output, cost, turns}` — no `costBasis`, `usageSource`, `cacheRead`,
  `cacheWrite`, `reasoning`, `totalTokens`, or `cost*` component.
- **T9 — legacy manifest tolerance.** A manifest whose `usage` lacks the new
  fields sums as `0` through `sumSubtree`; `sumSubtree(…, "costBasis")` is a
  tsc error under `UsageMetric`.
- **T10 — `usageSource` persisted.** The manifest carries
  `usageSource === "stream-assistant"` for a hub-captured job (T4 covers the
  assertion; assert the union member is exercised by a fixture with the
  `"session-reconciled"` literal to prove the type accepts it).

Existing tests that construct `usage` literals (roughly: `test/hub.test.ts`,
`test/runs.test.ts`, `test/tree.test.ts`, `test/eval-runner.test.ts`,
`test/eval-leaderboard.test.ts`, `test/rubric.test.ts`,
`test/ev16-verification.test.ts`) must compile against the widened required
shape — either by adding the new fields or by helper construction. No test may
be narrowed, stubbed, or suppressed to make the widened type compile.
