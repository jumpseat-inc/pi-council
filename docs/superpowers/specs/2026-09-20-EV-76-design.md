# EV-76 — Run-start preflight fails loud when the gate is on and no OpenRouter credential resolves

Design spec from the EV-76 council deliberation (rounds 1–2 + skeptic attack, step 4,
all closed-green). Everything here is settled by that record; the implementer reads
this file, not the deliberation.

## Problem

The run-start preflight — `/features-deliver` Phase 0's `bash council/preflight.sh`
and `/council` step 0's identical invocation — must halt a run when the repo's
resolved decisions-gate mode is not `off` and no OpenRouter credential resolves.
Today the unconditional OpenRouter check inside the (consumer-owned, data-class,
never-refreshed) `council/preflight.sh` halts any no-credential run, but it names
neither the decisions gate as the consumer nor the stored-credential remediation,
and a check that lives only in that script never reaches repos already
`/council-init`-ed (AGENTS.md convention 6: `council/preflight.sh` is in
`DATA_FILES`; `/council-update` never writes it).

## Settled mechanism

1. **New file `extensions/preflight.ts`** (engine; never under `council/scaffold/`,
   so it cannot enter the scaffold walk or the TOOLING/DATA set-equality guard).
   Pure core:

   ```ts
   export function runStartGatePreflight(
     repoRoot: string,
     opts: { apiKey?: string | null } = {},
   ): string | null
   ```

   - mode ← `loadGateConfig(repoRoot)` (extensions/gate.ts — the ONE resolver;
     never re-parsed in shell or re-implemented here). A `loadGateConfig` throw
     (malformed `.council.json`) propagates as its own single-line `FAIL:`
     `gateFail` error — fail loud, never default to `off`.
   - mode `off` ⇒ return `null` (proceed; add nothing).
   - mode `advisory`/`active` ⇒ credential ← `opts.apiKey !== undefined ?
     opts.apiKey : resolveOpenRouterApiKey()` (extensions/provider-cost.ts:477 —
     env `OPENROUTER_API_KEY` → stored typed `api_key` credential for provider
     `openrouter` → null; runtime parity by construction, the check IS the
     resolver).
   - credential resolves ⇒ return `null` (proceed; print nothing — silent pass).
   - credential is null ⇒ return the single-line literal below (newline-
     sanitized like `gateFail`; it is a constant + the mode enum value, so no
     injection surface).

2. **Endorsed FAIL literal** (R5-constrained; byte-verified by the skeptic against
   every constraint: contains `decisions gate`, `OPENROUTER_API_KEY`,
   `openrouter api_key`; zero `jev`; zero embedded newlines; exactly one `FAIL:`):

   ```
   FAIL: decisions gate is enabled (mode "<mode>") but no OpenRouter credential resolved — set OPENROUTER_API_KEY, or run /login openrouter in pi to store an openrouter api_key credential, then re-run preflight
   ```

   `<mode>` is the resolved mode value (`advisory` or `active`). Wording is the
   seat's within R5 (Phase-1 ruling, applied at step 6): names the decisions gate
   as the consumer and both remediations; never "jev".

3. **New parent-only tool `council_preflight`** (engine). Registered in
   `extensions/index.ts`'s parent block ONLY — the exact pattern of
   `registerGateTool`/`registerRouteTool` (never folded into `registerHubTools`;
   `child.ts` calls only `registerHubTools`; `hub-tools.ts`/`child.ts` never
   mention it). Behavior: call the pure core with `repoRoot`; if it returns a
   line, the tool returns that line as its result (the facilitator's stop-on-
   `FAIL:` rule then halts the run); if `null`, the tool returns a pass result.
   The tool **never spawns** `council/preflight.sh` and contains no spawn/exec of
   it — the script stays invoked by the procedure text exactly as today. The
   check's correctness rides the same trust class as the existing preflight
   invocation (LLM-followed procedure prose); no mechanical single-FAIL guarantee
   is claimed beyond that, honestly recorded.

4. **Procedure text** — packaged `council/procedures/council.md` step 0 and
   `council/procedures/features-deliver.md` Phase 0 each gain ONE new step,
   ordered BEFORE the unchanged `bash council/preflight.sh` line: invoke the
   `council_preflight` tool on the repo root and stop on any `FAIL:` line it
   returns (same stop rule both procedures already state for the script). No
   `$COUNCIL_PKG_ROOT` placeholder is added — the tool approach sidesteps
   package-root location entirely; `renderProcedure`'s substitution set is
   unchanged.

## Why this shape (deliberation-settled, skeptic-verified)

- **In-process transport**: the parent pi process is the only TS runtime whose
  presence at run-start is guaranteed at a consumer site; bun + installed
  node_modules there are not.
- **Reach**: procedures are never scaffolded (scaffold tree is exactly 8 files)
  and the command scan resolves them repo-override-FIRST-BY-FILENAME with
  packaged fallback — so the packaged text (with the new tool line) reaches every
  existing consumer at package update, with zero reliance on the vintage of the
  consumer's `council/preflight.sh`.
- **Exactly one authoritative FAIL** by ordering: gate-on + no-cred ⇒ the tool's
  FAIL returns first and the procedure halts before the script runs (the script's
  own `fail()` is echo+exit-1, so it can never stack internally); gate-off +
  no-cred ⇒ tool silent, script's existing generic FAIL byte-identical; gate-on +
  cred ⇒ tool silent, script passes (same env, same auth.json); malformed config
  ⇒ single-line throw halts. No non-obedience double exists (skeptic O6).
- **Shell grep is not the runtime rule** (skeptic O3): a concrete auth.json
  (oauth-typed openrouter + api_key-typed google) passes the script's grep
  predicate while the resolver returns null — parity must ride
  `resolveOpenRouterApiKey()`, which the mechanism does by construction.
- **Import safety** (skeptic O8; convention 7): `gate.ts`, `provider-cost.ts`,
  `seats.ts` pull no hub, no child_process, no network at module level.
- **Line-level byte-identity**: the card's clause binds printed output lines. The
  off-mode transcript gains one `council_preflight` tool unit at every run-start
  — recorded as a framing deviation, never called byte-identity. With a
  transcript-framing reading the card's own "reaches existing consumers without
  refreshing preflight.sh" clause would be unsatisfiable for any mechanism.

## Tests (the card's named behaviors plus the settled pins)

All in `test/` (bun:test, mkdtemp trees, never the real repo). **O10 hygiene:
every enabled-no-credential case must run with `OPENROUTER_API_KEY` deleted from
the test process env (`env -u` semantics / `delete process.env...`), or it
silently tests a credentialed world on this machine.**

1. **Enabled-no-credential FAIL (the card's named test)**: temp repoRoot with
   `.council.json` `gate.mode: "advisory"` (and again `"active"`), env key
   removed, agent dir pointed at an empty temp dir → `runStartGatePreflight`
   returns the literal byte-`===` (one `FAIL:`, no `\n`, no `jev`, contains
   `decisions gate`, `OPENROUTER_API_KEY`, `openrouter api_key`).
2. **Off-mode add-nothing (the card's named test)**: absent file / `gate: {}` /
   no `gate` key / `mode: "off"` → returns `null` (nothing added; the existing
   unconditional check's output is untouched because no preflight script is
   modified — asserted by the byte pins in 5).
3. **Stored-credential parity**: temp agent dir with a stored typed `api_key`
   credential for `openrouter`, no env → `null`. Plus an injected-env case and
   an oauth-typed-credential-does-NOT-count case (runtime parity both directions,
   O2/O3).
4. **Malformed gate config fails loud**: invalid mode / bad JSON → the thrown
   single-line `FAIL:` message surfaces verbatim (caught, no stack).
5. **Byte-identity pins**: `council/preflight.sh`, `council/scaffold/council/
   preflight.sh`, `smoke/fixture/council/preflight.sh` unchanged (digest or
   fixture cmp pin — the mechanism must not touch any preflight script).
6. **Parent-only registration pin** (precedent `test/gate-render.test.ts:330`):
   `council_preflight` registered in the parent block only; absent from
   `hub-tools.ts`/`child.ts`.
7. **Ordering/reach pins**: both packaged procedures name `council_preflight`
   and its step appears BEFORE the unchanged `bash council/preflight.sh` line;
   per-filename override semantics (skeptic O5): the pins assert the PACKAGED
   text, not a shadowed copy.
8. **Non-spawn pin**: source-level — the tool module never references or spawns
   `council/preflight.sh` and calls no spawn/exec primitive.

## Recorded limitations (carry onto the card, not defects)

- Single-FAIL is ordering-conditional on invocation obedience (same trust class
  as the existing preflight.sh invocation).
- Only consumers that shadow `council.md` or `features-deliver.md` by filename
  opt out of the check (convention #5; O5 precision).
- No automated e2e falsifier that a stale-preflight consumer reaches the FAIL —
  procedure-text pins are the falsifier (designer escalation note; follow-up
  material, not blocking).
- `features-new.md` has no preflight step — out of scope here; follow-up card
  material.
- A wrapped-tool design (tool spawns the script on pass) would make single-FAIL
  mechanical minus one obedience point — recorded follow-up material, rejected
  here as card creep.
- O10 env hygiene: enabled-no-credential tests must delete `OPENROUTER_API_KEY`
  from the environment — standing discipline for this suite.
