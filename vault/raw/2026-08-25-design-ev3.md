## Where I land

**The genuinely open decisions per spec §8 (EV-3 row) and my design
positions, each grounded in the artifact above.**

### (1) Module structure — one new file, plus the smallest session_start hook

- New: `extensions/activate-theme.ts` — the pure decision function
  AND the integration glue. Naming the file after its purpose (not
  "theme.ts", which collides with pi's deep-import path) keeps the
  grep surface honest.
- Touched: `extensions/index.ts` — one new `import` + one new call
  inside `session_start` BEFORE the existing `initHubIdentity` /
  `pruneRuns` / `connectParentServers` block (rationale below).
- Tests: `test/theme-activation.test.ts` for the pure function
  (unit, no real TUI, no settingsManager mutation); a single smoke
  assertion that the activation path through `loadThemeFromPath` +
  `setThemeInstance` does not touch settings.json (state-byte
  equality before and after).

Why one file, not three: the pure function and the integration share
their inputs and outputs (the merge is the same on both sides).
Splitting into "decision", "activation", "merge" is three files of
~30 lines each, none independently meaningful, and three places a
reader has to jump. The skill that picks up the file later does not
benefit from the fragmentation.

### (2) The pure decision function's signature and unit-testable claims

```ts
export type ActivationDecision =
  | { kind: "noop" }                                    // no theme section, or off switch
  | { kind: "block"; reason: "settings-pinned"; themeName: string }  // (d)
  | { kind: "activate"; variant: "dark" | "light"; section: ThemeSection };

export function decideActivation(args: {
  themeSection: ThemeSection | undefined;
  projectSettingsRaw: string | undefined;   // raw "theme" value from <repo>/CONFIG_DIR_NAME/settings.json
  globalSettingsRaw: string | undefined;    // raw "theme" value from <agentDir>/settings.json
  terminalTheme: "dark" | "light";         // synchronous detection result
}): ActivationDecision;
```

- Pure: no I/O, no `Date.now()`, no `Math.random()`. Takes the
  project/global raw values as inputs, not as file paths — the
  caller does the disk read.
- Returns a tagged union, not a multi-field object, so the caller
  cannot forget to inspect `kind` (the switch is exhaustive at the
  type level).
- Caller does project-vs-global merge by **project wins** if both
  present (project wins — spec §4 + AGENTS.md). If only one is
  present, that one wins. If neither, both are `undefined`.

**Unit-testable claims** (each a single `expect(...).toEqual(...)`):

1. `themeSection === undefined` → `{kind:"noop"}`. Two subcases:
   `.council.json` absent (no file read at all), and `theme` key
   absent / off-vocabulary (`false` / `null` / `0` / `""` /
   `{enabled:false}`).
2. `themeSection` present, both `*SettingsRaw === undefined` →
   `{kind:"activate", variant: themeSection.variant === "auto" ?
   terminalTheme : themeSection.variant}`.
3. `projectSettingsRaw === "light/dark"` →
   `{kind:"activate", variant: themeSection.variant === "auto" ?
   terminalTheme : themeSection.variant}` (spec §4 state (b) — auto-
   follow does not block).
4. `projectSettingsRaw === "dark"` or `"light"` →
   `{kind:"activate", variant: ...}` (spec §4 state (c) — persisted
   literal does not block).
5. `projectSettingsRaw === "gruvbox"` (or any other concrete name not
   matching `^[^/]+$` AND not equal to `"dark"` or `"light"`) →
   `{kind:"block", reason:"settings-pinned", themeName:"gruvbox"}`
   (spec §4 state (d)).
6. `projectSettingsRaw === undefined`, `globalSettingsRaw ===
   "gruvbox"` → `{kind:"block", ...}` (project absence falls through
   to global — and the global pinned name still blocks).
7. `themeSection.variant === "dark"` overrides `terminalTheme ===
   "light"` → `{kind:"activate", variant:"dark"}` (explicit pin
   honored, even on a light terminal).
8. `themeSection.variant === "auto"` AND `terminalTheme === "light"`
   → `{kind:"activate", variant:"light"}` (auto follows terminal).
9. The Phase-1 ruling is encoded in claim 4 and is the single line
   that distinguishes spec §4 from a naïve implementation that would
   block on literal `"dark"`.

**Detection rule for "any other concrete name"**: a string that is
neither `undefined`, nor `"light/dark"` (the pair), nor exactly
`"dark"` or `"light"`. The pair is detected by `parseAutoThemeSetting`
returning a non-undefined object; the literal built-ins are matched
by string equality. Everything else with a `/` (malformed pair) is
treated as a concrete pinned name and blocks — the same defensive
default the rest of pi uses.

### (3) Auto-variant resolution when settings.json carries no literal dark/light signal

`terminalTheme: "dark" | "light"` is an INPUT to `decideActivation`,
not derived inside it. The integration glue calls
`detectTerminalBackgroundFromEnv()` (synchronous, COLORFGBG-based)
and feeds the `.theme` field into the pure function. When no hint
exists, `detectTerminalBackgroundFromEnv()` returns
`{theme:"dark", confidence:"low"}` — the same default `getDefaultTheme()`
gives pi itself. The user sees the same dark palette they would have
seen without the extension; no silent surprise.

I deliberately reject the async OSC-11 path
(`detectTerminalThemeForAuto({ ui })`) for activation. Reasons:

- The OSC-11 query needs the TUI to render at least one frame to
  fire; activation runs at session_start, which is BEFORE first
  render in the typical session. An async path would either (a)
  defer activation past the first user-visible frame (the "flash
  of wrong palette" hazard), or (b) require a second pass on a
  later tick, which means the user types into a default palette
  for a beat before the council palette kicks in.
- COLORFGBG is what `getDefaultTheme()` and the synchronous parts
  of pi itself rely on. We match pi's own fallback semantics exactly.
- For users who care about accurate terminal-background detection,
  the scaffold seeds `variant: "auto"` and they can pin to `dark` or
  `light` explicitly. The README's "what you get" snippet teaches
  this.

### (4) Theme construction from the merged JSON — no third on-disk copy

The merged shape is `{vars, colors, export}`. We need a `Theme`
instance. The three paths:

- **(a) Tempfile + `loadThemeFromPath`** — write merged JSON to
  `os.tmpdir()/council-active-{pid}-{ts}.json`, call
  `loadThemeFromPath(tempFile, "truecolor")`, capture the Theme,
  unlink the file. Uses pi's public construction API.
- **(b) Deep-import pi's `createTheme`** — not exported; would
  require extending the `PiThemeModule` interface in
  `test/theme-loader.ts` and trusting internal API stability
  across pi versions. Mirrors what EV-1/T4 already does, but for
  an internal symbol.
- **(c) Construct `new Theme(fgColors, bgColors, mode, {name})`**
  directly with our own `withThemeColorFallbacks` + `resolveThemeColors`
  — both of which would have to be reimplemented because they are
  not exported from pi's package. Duplicates pi's resolver logic.

I recommend **(a)** — temp file, immediate unlink, never under
`CONFIG_DIR_NAME`. The "no third on-disk copy" rule in spec §4 is
about the user's view of the theme inventory (`getAllThemes()`,
`/settings`, the agent dir); a tempfile under `os.tmpdir()` named
`council-active-*.json` that is gone by the time the function
returns is qualitatively different and is the only path that uses
public API. The acceptance criterion should pin this: the tempfile
lives under `os.tmpdir()`, is unlinked inside a `try/finally`, and
no file is left behind at any observable path under `CONFIG_DIR_NAME`.

Wait — re-reading spec §4 once more: "the in-memory route writes
nothing to disk and registers no name." A tempfile is "to disk".
The strict reading forbids (a). The pragmatic reading says (a) is
fine because the file is transient and never visible. **Escalate
this single line to product-owner if owner/principal disagree on
the strict reading.** Until then, (a) is my recommendation because
it's the minimum-surface-area construction path; (b) is the strict-
reading fallback at the cost of trusting pi's internal API surface
across versions.

### (5) Integration into `session_start` — order, and what NOT to do

Inside `extensions/index.ts`'s `session_start`:

```ts
pi.on("session_start", async (_event, ctx) => {
  uiCtx = ctx;
  // EV-3 — council theme activation (must precede first render of council UI)
  await activateCouncilTheme(pi, ctx, repoRoot);
  // ... existing sweepStalePids / initHubIdentity / pruneRuns / getHub / connectParentServers / widgetTimer
});
```

Rationale:

- `ui.theme` is a proxy on `globalThis[THEME_KEY]` set by
  `setGlobalTheme` (interactive-mode.js:1909 + theme.js:648-650).
  Whoever calls `setThemeInstance` first wins, until a later
  `setTheme*` call overrides.
- The `/council-tree` modal reads the theme via the factory's
  `(tui, theme) => Component` second argument (navigator.ts:164-176).
  Whatever theme is active when the modal is opened is what it
  draws. If activation hasn't run yet, the modal uses pi's default
  theme — wrong colors inside the modal, right colors outside it.
- Activation runs BEFORE `connectParentServers` because (a) MCP
  connect is best-effort and must never delay the theme (spec §4
  activation timing: "session_start alongside `initHubIdentity` /
  `pruneRuns` / `renderWidget`") and (b) an MCP connect failure
  should not leave the user without the council palette.
- Activation runs BEFORE `initHubIdentity` so the first
  `renderWidget` call — which fires immediately inside
  `getHub(repoRoot, renderWidget)` — sees the activated theme. (The
  widget is plain text today, so the visual effect is nil, but the
  ordering also matters for any future council UI in the widget
  area.)
- Activation is `await`-ed. The existing handler is sync; making
  it async is fine because session_start handlers may return a
  promise. The MCP connect is already `void`-fired for the same
  reason; we add a single awaited step.

**What we must NOT do**:

- Call `ctx.sessionManager.setTheme(...)` or any other
  `settingsManager.set*` API. Spec §4 explicit; verified in
  theme-controller.js:66-69 that the instance branch of
  `ui.setTheme` makes zero settingsManager calls. A naive
  implementation that calls `ui.setTheme("pi-council-dark")`
  would write to settings.json — silent violation.
- Read `ctx.ui.theme.name` to detect "is the council theme
  active?". After `setTheme(instance)`, `name === "<in-memory>"`
  (theme.js:709). Reading the name is not a useful signal.
- Run `initTheme` ourselves. `initTheme` is already called by
  pi's `InteractiveThemeController` constructor (theme-controller.js:19).
  Our session_start runs after that; we only re-set if activation
  applies. If activation does not apply, we leave pi's theme
  untouched — this is the no-op path.

### (6) Signifier for "did activation happen?" — a one-time notification

Without a notify, three failure modes become invisible:

- **State (d) block**: the user has `theme: "gruvbox"` in
  settings.json; the council theme does not apply; the user has
  no idea their `theme` section in `.council.json` was overridden.
- **Auto variant mismatch**: the user has `variant: "auto"` and
  a light terminal background that COLORFGBG can't detect
  (confidence:"low", defaults to dark); the dark palette renders;
  the user expected light because their terminal looks light to
  them.
- **Section present but empty / off**: the user typed `{}` or
  `{enabled:false}`; the council theme doesn't apply; the user
  has no idea they typed the off switch.

The notification surface:

- **`{kind:"activate"}` → `ctx.ui.notify("council theme: pi-council-{variant}", "info")`** — one line, the variant
  named so the user can verify against what they expected.
- **`{kind:"block"}` → `ctx.ui.notify("council theme: blocked (settings.json has \u2018gruvbox\u2019)", "warning")`** —
  the warning level signals "something to look at"; the message
  names the pinned theme so the user can decide.
- **`{kind:"noop"}` → no notify.** The user has no theme section
  OR the section is off; either way they have expressed an intent
  not to see a council theme, and a "council theme: off" notify
  would be noise in a TUI session that may run for hours.

The notification is a one-time `session_start` event; it does not
re-fire on every turn or every MCP connect. It is the user's only
window into the activation decision — making it silent is the
worst-case Gulf of Evaluation failure.

  `session_start`. Acceptance: "Editing `.council.json` mid-session
  (or restarting) applies the new palette; hot-reload behavior per
  pi's theme watcher." This is ambiguous; my reading is that
  restarting is EV-3's acceptance, mid-session recolor is EV-4's.
  Escalate this to product-owner if owner/principal disagree on
  whether EV-3 must implement a watcher.
- **Audit test for no-ANSI in council-drawn output** — spec §5,
  EV-4.
- **AGENTS.md convention 9.6** — spec §6, EV-4 (or whichever card
  owns the AGENTS.md change).

## Failure modes a person would notice (ranked by consequence)

1. **State (d) block — silent**. The user expects the council
   theme (they ran `/council-init`); their settings.json has a
   pinned `gruvbox`; nothing in the TUI tells them. They either
   notice (when they see their gruvbox palette and wonder why the
   scaffold didn't override it — lucky path) or they don't
   (unlucky path: they debug for an hour). **Mitigation**: the
   block-notify in (6). **Acceptance**: the warning notify fires
   exactly once per session_start, naming the pinned theme.
2. **Auto variant mismatch on a light terminal**. COLORFGBG is
   unset in many terminals (iTerm2, Apple Terminal, Windows
   Terminal); `detectTerminalBackgroundFromEnv` returns
   `{theme:"dark", confidence:"low"}`. The user sees dark on a
   light terminal. **Mitigation**: the activate-notify names the
   variant the user got; the README documents `variant:"light"`
   as the pin. **Acceptance**: the notify always names the
   resolved variant — never silent.
3. **Flash of wrong palette at startup**. Pi's `initTheme` runs
   in the InteractiveThemeController constructor
   (theme-controller.js:19) before the first extension event
   fires; the user sees a frame or two of pi's default before
   the council palette takes over at session_start. **Mitigation**:
   none possible from inside the extension — activation timing
   is settled by spec §4. **Documented cost**, not a fix. The
   README's "what you get" snippet should mention the palette
   change as the session starts so the user doesn't think the
   scaffold didn't apply.
4. **No-op when the scaffold isn't run yet**. The user installed
   pi-council and started a session without running
   `/council-init`; no `.council.json` exists; no activation; the
   user expects the omp look. **Mitigation**: the README
   documents `/council-init` as the enabling step. The scaffold
   is the action; without it, the off-switch semantics apply.
5. **Variant pin ignored because of auto detection**. The user
   writes `variant: "dark"` but the detection mechanism — which
   we don't even use for explicit pins — would have said light.
   Not a failure mode of this card; the pure function honors
   explicit pins verbatim (claim 7 above).
6. **`/council-tree` modal shows the wrong colors**. The modal
   reads theme via the factory's second argument; if activation
   hasn't run yet (timing race), the modal sees pi's default
   theme. **Mitigation**: activation runs before the modal can
   be opened (the modal is `ctrl+shift+t`, fired by user input,
   which is post-session_start). **Acceptance**: no race.
7. **Re-activation on `session_shutdown` → `session_start`
   cycle**. The temp file from a previous session is unlinked by
   `try/finally`; no leftover. The theme instance is GC'd when
   `globalThis[THEME_KEY]` is overwritten by pi's next
   `initTheme`. **Acceptance**: `setThemeInstance` stops pi's
   watcher; the next session's `initTheme` restarts it. No state
   leaks.

## Falsifiable predictions (smoke-test territory)

The following are hypotheses I cannot verify from the repo alone;
they are predictions the smoke test (or any in-situ CDP run) would
falsify. Each is phrased so a passing/failing observation settles it.

- **P1**: `loadThemeFromPath(tempFile)` returns a Theme whose
  resolved colors (via `getResolvedThemeColors(name)`) match the
  merged JSON after `withThemeColorFallbacks` + var-resolution,
  key-for-key for the 55-token map. The brand anchors (dark
  accent `#febc38`, border `#178fb9`; light accent `#5a8080`,
  border `#547da7`) hold after a `theme.dark.vars.accent →
  "#123456"` override.
- **P2**: `setTheme(themeInstance)` on a fresh Theme sets
  `globalThis[THEME_KEY]` to that instance and `currentThemeName`
  to `"<in-memory>"`; `getAllThemes()` does NOT include
  `pi-council-dark` or `pi-council-light` after activation
  (because the merged instance has no `name` field — or has the
  family name, which collides in `getAllThemes`). Spec §4
  requires the merged instance to be nameless in `getAllThemes`
  inventory. Verify by reading `registeredThemes` after
  activation: it must still contain only the two shipped files.
- **P3**: Activation runs but does not modify
  `<agentDir>/settings.json` or `<repo>/CONFIG_DIR_NAME/settings.json`.
  Byte-equal before and after; verified via `git status` clean
  and `stat -c '%Y'` unchanged.
- **P4**: The session_start handler runs after pi's
  `InteractiveThemeController` constructor (the controller calls
  `initTheme` in its constructor; session_start is dispatched
  after). Observable by `ui.theme.fg("accent", "x")` returning the
  council palette ANSI within the same session_start callback
  (after `activateCouncilTheme` returns) and pi's default ANSI
  before. The exact order depends on pi's init flow; P4 says
  activation ALWAYS precedes the first render of council UI,
  which is testable by opening `/council-tree` immediately after
  session_start and inspecting the border color.
- **P5**: State (d) block fires the notify; the notify text
  includes the pinned theme name. Observable by setting
  `theme: "gruvbox"` in project settings.json, launching pi,
  and reading the notify (it should appear in the TUI footer /
  message area).
- **P6**: `theme: "light/dark"` in project settings.json does
  NOT block; the resolved variant matches `terminalTheme` (or the
  scaffold's pin if not auto).
- **P7**: A repo without `.council.json` and a pi user with a
  custom theme selected via `/settings` retains that theme after
  session_start. Observable by selecting gruvbox in /settings,
  quitting, restarting, and seeing gruvbox.
- **P8**: The temp file under `os.tmpdir()` does not exist after
  `activateCouncilTheme` returns. Observable by listing
  `os.tmpdir()` before and after the call.

## Gulf analysis

- **Execution gulf** (the distance between "I want the omp look"
  and the action that gets it): the scaffold IS the action.
  Anything beyond "auto via scaffold" requires editing
  `.council.json`, which the README's "what you get" snippet
  teaches. The Execution gulf is closed by the scaffold's
  pre-authored `theme` section and the README's example — both
  are knowledge in the world, not in the head.
- **Evaluation gulf** (the distance between "did my theme apply?"
  and the visible signal): without the activate-notify, the user
  has no way to tell activation happened. With it, the notify
  IS the evaluation signal — the user reads "council theme:
  pi-council-dark" and knows. The block-notify is the same
  answer for the blocked case. The no-op case is silent BY
  DESIGN — the user opted out.
- **Conceptual model** the user has to form: "the council theme
  is active iff my `.council.json` has a `theme` section AND
  my settings.json doesn't pin a concrete name." This is the
  precedence rule from spec §4; the user encounters it once,
  in the README's "what you get" snippet, and never again unless
  they edit settings.json.

## Preferences (taste, ranked last)

- **One-time notify on activate and block, none on no-op**. The
  taste call here is whether to notify on no-op. I argue no,
  because (a) a no-op means the user expressed an off intent
  (either by omission or by `enabled:false`), and (b) a
  long-running session re-firing a notify at session_start every
  hour is noise. If observation later shows users are confused
  about why the scaffold's palette didn't apply, add a
  one-time `ctx.ui.notify("council theme: off (.council.json has
  no theme section)", "info")` and observe.
- **Notify text wording** — "council theme: pi-council-dark" vs
  "council theme activated (pi-council-dark)" vs
  "→ pi-council-dark". I prefer the tersest form; the TUI notify
  area is small and a long message gets truncated. Copy decision
  for the implementation card.
- **Whether to also `ctx.ui.setStatus("council-theme", "pi-council-dark")`**
  for a persistent footer indicator. Status updates in pi can
  crowd out other extensions; sticking to one-shot notify is
  safer. The smoke test would observe whether the status row
  conflicts with anything else the user has set.
