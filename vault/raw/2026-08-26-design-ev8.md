## Design position

The cleanest fix is one that borrows pi's vim modal-editor shape (Pattern 7
in `tui.md`) inside a `CustomEditor` subclass, exposes the new state on the
*editor's* own border (` NORMAL ` / ` INSERT `, in the same place vim uses)
and on a single-cell `▌` indicator prefixed to the highlighted row, and uses
the editor's own `isOnFirstVisualLine()` / `isOnLastVisualLine()` predicates
to make the multi-line rule a property of the editor's own model rather than
a heuristic we maintain. The widget below the editor stays a passive
display-only surface and gets its selection driven by the editor catching
arrows and forwarding them through a single pipe.

## Gulf closed

**Evaluation gulf, at the moment of "about to press a key."** Right now, a
person scanning the tree panel has no way to know whether the keys they
type next will land in the editor or in the tree — that information lives
inside the focus machinery, off-screen. This change exposes that bit on the
editor's bottom border in the same place vim puts `NORMAL`/`INSERT`, and on
the highlighted row in the panel below. It closes the execution gulf
secondarily: when the editor's border says `TREE`, Down/Up are guaranteed
to move the selection rather than scroll, so the person can act without
double-checking.

## Principle and evidence

- **Knowledge in the world beats knowledge in the head.** The current
  contract requires the person to remember that "down arrow navigates the
  panel below the editor, but only once you've given it focus somehow."
  That's a multi-syllable rule with no on-screen aid. The ` NORMAL ` /
  ` INSERT ` label on the editor's border — already a learned convention
  for every pi user who has tried `:e modal-editor.ts` — puts the rule on
  the screen. Apply this to `extensions/navigator.ts` *and* to a new
  `CouncilTreeEditor` extending `CustomEditor` registered via
  `ctx.ui.setEditorComponent` in `registerNavigator()` when the widget is
  visible (and unregistered when it closes).
- **Signifier, not affordance, is what tells the user focus is in the
  tree.** Pi's TUI does not give a `setFocus(widget)` API to give a
  belowEditor widget keyboard ownership — `interactive-mode.js:670-686`
  puts widgets and editor in a single `VStack` and only ever
  `setFocus(this.editor)` (rows 692, 1450 of `interactive-mode.js`).
  Whatever focus we display is therefore *symbolic*, applied at render
  time. The minimum signifier that works: keep the existing rendering of
  the highlighted row *identical* when the editor owns focus (so the
  single highlighted row always reads as "the row my keys target if I
  press enter"); add a single `▌` indicator cell at column 0 of that row,
  rendered with `theme.fg("accent", "▌")`, only when the tree holds
  focus. Use the existing `accent` token (`extensions/navigator.ts:31`,
  theme rows in `tui.md` Theming section).
- **Mapping: editor border ↔ panel highlight.** The two surfaces are
  stacked vertically and read by the same eye-movement; tying the
  border-mode label and the row indicator to the same boolean state
  (`treeFocused`) makes the affordance learnable in one observation.
  This is the row-vs-control mapping Norman is after, expressed in the
  matter this TUI has. Apply at the `CouncilTreeWidget.render()` call
  site and at the editor's `render()` override.
- **The vim precedent is precedent, not analogy.** `examples/extensions/modal-editor.ts`
  consumes j/k in normal mode without inserting them; we will consume
  ArrowUp/ArrowDown in tree mode without letting the editor scroll
  history. That is the same `handleInput`-override-then-`super.handleInput`
  shape: when `treeFocused && matchesKey(data, Key.down)` we update the
  widget's selected index, then `super.handleInput(data)` with the
  *swallowed* key replaced by the editor's "no-op" boundary behavior
  (Key.down only if not at last visual line). When
  `treeFocused && matchesKey(data, Key.up)` and `selectedIndex === 0` we
  release focus back to the editor and re-feed the up-arrow as a normal
  cursor move.
- **Multi-line rule — derive, do not redefine.** Pi's editor already
  owns `isOnFirstVisualLine()` and `isOnLastVisualLine()`
  (`chunk-E5KXRMZK.js:554`, the `tui.editor.cursorUp` branch beginning
  `this.isOnFirstVisualLine()&&(this.isEditor...`). The widget should
  test its own arrow only *at the visual edge*, never inside a
  multi-line draft. So:
  - `down` enters the tree only when `editor.isOnLastVisualLine()` AND
    `editor.getLines().length > 1` indicates there's a multi-line draft
    — but visually the cursor must already be on the final visual line
    anyway. The single rule "Down steals only on the last visual line,
    Up steals only on the first" covers both single- and multi-line
    drafts with no heuristic.
  - When the draft is single-line, the cursor is on both first and last
    visual line at once, so the rule degenerates cleanly: Down steals to
    the tree, Up from the top row returns to the editor. The card's
    "multi-line rule" deliberation is therefore moot — there's only one
    rule.
- **Safe default for keys the tree doesn't handle.** When the tree holds
  focus, letters and Tab/Enter/Esc reach the widget's `handleInput`;
  arrow keys are handled here. Anything else — `PageUp`, `PageDown`,
  `Home`, `End`, `Backspace`, printable characters, control sequences —
  must do the safe thing: release focus back to the editor *and replay
  the key into the editor*. This is the existing Escape-exits-NORMAL
  shape in vim; mirror it for "any unhandled key releases focus." It
  means a stray letter typed while the tree "appears" to own focus lands
  in the editor buffer, not silently dropped — the slip-vs-mistake
  distinction Norman insists on: a slip (wrong surface) is recoverable;
  a mistake (wrong intent) is the user's. Replaying classifies most
  cases as slips and exits quietly.
- **Forcing function for the irreversibly-costly key.** Enter is the one
  key where a slip would open the heavy transcript modal — not
  destructive, but disruptive (it steals the editor). The widget's
  Enter behavior should fire `onOpen` for the highlighted row (existing
  behavior in `extensions/navigator.ts:118`) and *not* return focus to
  the editor. That's the only case where the tree intentionally keeps
  focus against the user's next press.

## Falsifiable predictions

I am the design seat and cannot see the running interface. The following are
hypotheses the `skeptic` (and the rendering smoke / pure-seam tests the
`owner` adds under `test/ev8-*.test.ts`) must verify. Each one is either
**rendering** (a CDP smoke / frame-compare would catch it) or
**comprehension** (only a person's read can settle it).

### Rendering (testable)

- **R1.** When `treeFocused === false`, the widget's highlighted row
  renders without a `▌` left column. When `treeFocused === true`, the
  same row renders with a single `▌` cell at column 0 styled with
  `theme.fg("accent", "▌")`. CDP frame-compare with identity theme
  would show exactly one byte of difference (a single row, one column).
  *Falsifier:* `bun test test/ev8-focus-indicator.test.ts` builds a
  widget in both states and asserts `visibleWidth(selectedRow)` differs
  by exactly 1.

- **R2.** The editor's last visual border line ends with either ` INSERT `
  or ` TREE ` (8 visible columns), right-aligned against the editor's own
  width, in the same place vim's " NORMAL " appears. The label string
  is owned by the CustomEditor; do *not* reuse `tui.editor.cursorUp`'s
  history-overlay decoration. Falsifier: render the editor at width=80
  in both states; the trailing 8 columns of the last visible line are
  ` INSERT ` vs ` TREE ` exactly.

- **R3.** No theme keys are added. The two new foregrounds (`accent` for
  the marker, `dim` if the row is otherwise already at `dim`) are
  existing theme tokens; verify by grepping the PR for new token names.
  Falsifier: `grep -E "theme\\.fg\\([\"']([a-z]+)[\"']" extensions/navigator.ts`
  yields only tokens already on the documented palette.

- **R4.** `MAX_WIDGET_LINES = 10` is unchanged (EV-7 invariant). The
  `▌` indicator does not push a row over the line budget; if it would,
  that row is the *truncated* hint-line, not a real row. Falsifier:
  re-run the existing "caps rows" test with the new rendering; it
  still passes.

- **R5.** Widget `handleInput` is invoked from the editor path, *not*
  directly by pi — the widget has no Focusable implementation. Verify
  by calling `setFocus(this.widget)` from a test harness and asserting
  the widget does NOT receive input. This is the binding of the design.

### Comprehension (judgment; cannot be settled by smoke alone)

- **C1.** A first-time visitor who has *not* read this card can land
  on the panel, press Down, see a `▌` appear on the first row *and* see
  ` TREE ` on the editor border at the same time, and infer that their
  keystrokes now move between rows. A readable-text protocol with two
  people counts as a settlement; passing or failing the test is the
  decision the Skeptic cannot make alone.

- **C2.** The `▌` + ` TREE ` pairing, when focus is *not* on the tree,
  is invisible — the highlighted row reads the same as it did before
  EV-8, and the editor border reads ` INSERT `. The "no flashing state
  every render" rule must hold under a 2s refresh tick while running
  jobs are streaming. This is observable on a stream but may also be
  settled by watching the `cached` invalidation in
  `CouncilTreeWidget.render` (`extensions/navigator.ts:300-307`): the
  cached output must equal its prior output byte-for-byte when
  `treeFocused === false`, regardless of refresh.

- **C3.** The Esc-release-back-to-editor behavior is the "I want out"
  affordance, not the only one. Worth confirming that Esc releases
  focus from the tree even when the tree had it — i.e., the editor's
  normal Esc behavior wins. This is the analog of vim-NORMAL-Esc, and
  mirrors the precedent. Comprehension-check by reading the new code
  line.

- **C4.** The multi-line rule: a person composing a multi-line prompt
  with the cursor mid-draft, who presses Down, must *not* enter the
  tree — the cursor moves down a visual line as today. Only on the last
  visual line does Down transition. This is in tension with "always
  transparent feedback" because the feedback is the cursor's move, not
  any UI affordance. A short note in the hint line ("↓ at end of draft
  enters tree") is *not* required; the rule is in the editor's own
  model. Confirmed by reading the `CouncilTreeEditor.handleInput`
  source — no ` matchesKey(Key.down)` call site exists outside the
  `isOnLastVisualLine()` guard.

## Preferences, ranked last

These could not be grounded; they are taste.

- I prefer `▌` (full block, 0x258C) over `▶` or `→` for the focus marker.
  It's one visible column even at narrow widths and has no direction
  connotation that would conflict with the row being below the editor.
  But `▶` or `◆` would render fine — this is a one-cell token choice.
- I prefer putting the `INSERT`/`TREE` label on the editor's *bottom*
  border (inside the editor frame) over adding a separate status line.
  The vim example is the precedent; the existing editor border is
  already styled with theme tokens, so a `truncateToWidth(lastLine, w -
  label.length, "") + label` ends up looking like `vim`. If the owner
  chooses to draw an *outside* the editor status row, they may — but
  that adds a third surface to the focus-ownership contract and I'd
  want the rationale, not a default to it.

## What this card should NOT do (out-of-band escalations)

- **Do not** add a real `Focusable` implementation to the widget and try
  to get the runtime to focus it. The TUI surface does not delegate input
  to widgets (`interactive-mode.js:670-686`, the doc at `tui.md` Pattern
  5), and inventing that pathway is a redesign where a signifier would
  do — design-scope creep, per the doctrine. Escalate to `principal` if
  `owner` finds this forces them into a runtime-coupled implementation.
- **Do not** put the focus affordance on the editor border alone, or
  on the row indicator alone. Both surfaces are visible at the same time
  to the same eye, and decoupling them is a learned rule (Norman: never
  ask the user to bind two distant signifiers to one state).
- **Do not** introduce a new binding (e.g. Tab) for entering the tree.
  The card locks the contract: arrow keys only. Reopen the contract via
  `product-owner` if we discover a real up/down-corner case that the
  last/first-visual-line rule can't cover.
