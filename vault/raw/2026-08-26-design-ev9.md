> the inline tree. Phase 1 ruling (binding, immutable): progress renders

## Reading the API (the load-bearing seam for this card)

- `ctx.ui.setWidget(key, factory, { placement: "belowEditor" })`
  (`extensions/navigator.ts:491-505`, types
  `core/extensions/types.d.ts:97-100`) — this is the ONLY public API
  that owns the below-editor region. The factory is invoked ONCE
  (`interactive-mode.js:1698: component = content(this.ui, theme)`); the
  returned Component lives until `setWidget(key, undefined)` or
  `session_shutdown`. `dispose()` fires on `setWidget(key, undefined)`
  and from `clearExtensionWidgets()` (interactive-mode.js:1704-1714).
- **Two widget regions**, each as a `Map<string, component>`:
  `extensionWidgetsAbove` and `extensionWidgetsBelow`
  (`interactive-mode.js:309-310`). The belowEditor region is the same
  `VStack` slot as the editor (interactive-mode.js:651-652:
  `{ widgetContainerBelow, shrink:1, minSize:0 }`); children in the Map
  stack vertically. Multiple keys in the same region stack.
- **MAX_WIDGET_LINES=10 applies only to the string-array path**
  (interactive-mode.js:1688: `content.slice(0, MAX_WIDGET_LINES)`; the
  factory branch at 1696-1699 has no slice). The EV-7 inline tree is a
  factory — it has no pi-imposed line cap. The cap is purely on the
  ambient `widgetLines` widget in `index.ts:72-86`. This is the
  load-bearing fact for EV-9: progress expansion can grow without
  violating any pi-side cap, because it lives inside the same factory
  component as the tree rows.
- `MAX_WIDGET_LINES` is the comment at `interactive-mode.js:1746` — it
  is the static constant; the only enforcement site is the
  string-array path. Confirmed by grep.
- The factory component returns whatever it returns; pi's
  `renderWidgetContainer(container, widgets, spacer, leadingSpacer)`
  (interactive-mode.js:1757-1772) just calls `container.addChild`
  on each. So a factory returning a Container with N children
  renders N lines vertically — no truncation.
- The widget container is `shrink:1, minSize:0` — it competes with the
  editor for vertical space. When the factory returns more children,
  pi reallocates and pushes the editor (and therefore message content
  above it) further up. This is the "push-up" behavior EV-7 settled on.
- `setFocus(component)` is public (`interactive-mode.js:631` and
  TUI's `setFocusInternal`); `setExtensionWidget` does NOT call
  `setFocus` — the editor remains focused after a widget set. This
  binds with the EV-8 editor-driven ruling: the editor stays focused;
  "tree focus" and "progress focus" are `controller.surface` states,
  not TUI focus.
- `ctx.ui.custom(factory, options)` (interactive-mode.js:2124) — the
  modal path the Phase 1 ruling REJECTS. Saved for completeness; this
  card does not use it.
- `theme.fg`/`bg`/`bold` are the only sanctioned color/bold accessors
  (AGENTS.md 9.6); `customMessageBg`, `border`, `accent`, `dim`,
  `success`, `warning`, `muted`, `bold` are the eight tokens in active
  use (`vault/raw/2026-08-25-design-ev4-round1.md` audit table). No
  literal hex, no ANSI escapes in council-drawn code.

## Design position

**The progress expansion is the same belowEditor widget component,
extended.** The factory passed to `setWidget("council-tree", ...,
{placement:"belowEditor"})` returns a `Container` whose first N
children are the tree rows (from the existing `CouncilTreeWidget`)
and whose last M children are the `TranscriptView` lines for the
selected session, behind a single `▾ progress for <seat> · esc back`
divider row. **No second widget slot. No modal.** Closing the
progress expansion removes the last M children and the divider; the
tree remains. The editor stays focused; `controller.surface` becomes
the union type `"editor" | "tree" | "progress"`. The mode label on
the editor's bottom border becomes `-- PROGRESS --` while the
progress is open (vim precedent, mirroring `-- TREE --`).

The smallest change that does this:

1. Extend `TreeFocusState.surface` from
   `"editor" | "tree"` to `"editor" | "tree" | "progress"`.
2. Add a `progressSessionId: string | null` field on the controller
   (parallel to `selectedSessionId`, but for the progress view).
3. Add a `routeEditorFocus` arm for `surface === "progress"` that
   consumes the TranscriptView handled set (`Up`/`Down`/`e`/`t`/`f`/`g`/`G`/`Esc`)
   AND `Enter` (no-op while in progress — Enter inside the
   transcript does not "open another progress"; it's a no-op, the
   progress is already open). Everything else forwards to super.
4. Extend the `CouncilTreeWidget` factory's `render` to return a
   `Container` that, when `controller.surface === "progress"`,
   emits `treeRows` followed by `progressHeader + progressLines`;
   when `controller.surface === "tree"` or `editor"`, emits only
   `treeRows`. The existing `render` body becomes the inner
   `treeRows(width)`; the factory wraps it in the Container.
5. Reuse the existing `TranscriptView` class verbatim — its
   `render(width)` already returns the right panel of styled lines.
   The factory holds one `TranscriptView` instance per open
   progress; `setOnChange(() => requestRender)` is unchanged.
6. `activateSession` (EV-8 enter action) checks the controller's
   current surface. If `surface === "tree"`, it sets
   `progressSessionId = sessionId`, advances `surface` to
   `"progress"`, ensures a `TranscriptView` is constructed for
   that sessionId, and requests a render. If `surface === "editor"`,
   it does nothing (EV-8's enter is only consumed while
   `surface === "tree"` per the routing kernel).
7. Closing is a single keystroke: `Esc` inside the progress calls
   `controller.setSurface("tree")` (or the existing
   `controller.exit()` shape, generalized). The transcript's
   `onClose` clears `progressSessionId`, disposes the
   `TranscriptView`, and leaves `selectedSessionId` intact — the
   tree's highlighted row is preserved on return.
8. The tree's last-activity rows keep updating while progress is
   open (EV-7's 2s `setInterval` runs unchanged, because the
   widget factory is the same component).

## Gulf closed

**Evaluation gulf, at the moment the operator presses Enter.** Today,
enter on the inline tree opens a full-screen modal that hides
everything — the tree, the editor, the message scroll — under a
backdrop (`withModalFrame` at `extensions/navigator.ts:78-114`). The
operator cannot tell from looking whether the transcript is still
live-streaming while the modal is up (it is, but the modality makes
the question feel irrelevant — the whole screen is "the modal"). After
EV-9: enter opens the progress **in the same region** the tree lives
in, with the tree rows still above. The operator can see:

- which subagent they opened progress for (the highlighted row in the
  tree above — preserved across open/close);
- whether other subagents are still making progress (the
  last-activity values in the rows above keep ticking);
- when their selected subagent settled (the row glyph changes from
  ● to ✓/✗ in the row above, in real time, alongside the progress
  they're watching).

This is the **comprehension** gulf — "what is going on across the
fleet while I watch this one seat?" — narrowed. It is a *structural*
narrowing, not a textual one: the answer is "look up," not "press
another key to find out."

Secondarily, **execution gulf at close**: today closing the modal
returns to a fresh modal-tree (the inline tree was already
rendered, but the operator had to dismiss the modal first to see
it); after EV-9, closing returns to the same tree in the same
state. The keystroke is the same `Esc`; the destination is the
right one. No "where am I now?" recovery cost.

## Principle and evidence

- **Knowledge in the world beats knowledge in the head.** The mode
  label `-- PROGRESS --` (mirroring `-- TREE --`) on the editor's
  bottom border tells the operator which surface owns the keys.
  EV-8 settled the label convention with vim precedent
  (`vault/wiki/designer.md`, EV-8 ruling 3: hard rule on `-- TREE --`
  style). Adding `-- PROGRESS --` is the same convention; the
  operator already knows what a mode label does because they just
  used `-- TREE --` 30 seconds ago. This is also the place to put a
  hint for the progress's own bindings, but I do not recommend a
  separate hint line — the divider row at the top of the progress
  panel carries the keymap (`↑↓ move · e expand · t thinking · f
  follow · esc back`), the same keymap that `TranscriptView.render`
  already puts on its title row (`navigator.ts:628`). No new
  discovery surface.
- **Mapping: editor border ↔ tree highlight ↔ progress divider.**
  Three signifiers, one source of truth. EV-8's editor border reads
  `controller.surface`; the tree's `�` reads `controller.surface ===
  "tree" && controller.selectedSessionId === row.sessionId`
  (`navigator.ts:386-391`); the progress divider reads
  `controller.surface === "progress"`. All three read from the same
  `controller` instance — single ground-truth, no drift. The mode
  label changes; the marker is the same; the divider appears; no
  pair can disagree.
- **Constraint: one widget slot, one region.** Pi's API
  (`interactive-mode.js:309-310`, `setExtensionWidget` at 1670) gives
  us two region slots (aboveEditor, belowEditor) and multiple keys
  per region. The Phase 1 ruling requires tree ABOVE progress within
  the same region. That constraint collapses the design space: the
  same factory component must render both regions' content. The
  factory is already `CouncilTreeWidget.render` returning a list of
  strings; the natural extension is to wrap those strings in a
  Container alongside the transcript's lines. This is the smallest
  change that satisfies the ruling.
- **The two gulfs: not a redesign where a Container would do.**
  Reusing `TranscriptView` is content parity by construction — its
  `render(width)` already implements the full content contract the
  card acceptance requires (live blocks, expand, thinking, follow,
  scroll, esc). Wrapping it in a Container inside the same widget
  factory is not a redesign; it is a relocation.
- **Constraint: the editor is always focused.** EV-8's product-owner
  ruling 1 (binding, `council/cards/EV-8.md` Step 6) settles this.
  EV-9 inherits: progress "focus" is a `controller.surface` state,
  not a TUI `setFocus` state. The progress's `TranscriptView`
  therefore does NOT need to be the TUI's focused component; the
  editor is. Keys reach the progress via the same
  `CustomTreeEditor.handleInput` override EV-8 installed. The
  routed keys become `view.handleInput(data)` directly inside the
  override, NOT via a TUI-level dispatch — exactly the way the tree's
  Up/Down are routed today.
- **Signifier for the seam.** When progress opens, the tree's
  highlighted row (the `▌` row) stays highlighted. That is the
  operator's anchor: "this is the seat whose progress I am reading."
  The row's last-activity text keeps ticking; if the seat settles
  while the operator is watching the transcript, the glyph in the
  row above flips from ● to ✓/✗. This is the most useful piece of
  ambient feedback the inline surface can give — and it is free,
  because the tree widget's 2s refresh does not depend on which
  surface is "active" in the controller.
- **No new theme tokens, no literal ANSI.** Reuses
  `extensions/transcript.ts` and `extensions/navigator.ts:524-645`
  unchanged for the TranscriptView; the divider row uses
  `theme.fg("dim", ...)` for the seam header and
  `theme.bold(...)` for the seat name token (mirroring
  `TranscriptView`'s `t.bold(...)` title at line 628). AGENTS.md 9.6
  binding.

## Concrete shape (the contract the owner writes against)

```
Container {
  // ─── Tree region (existing CouncilTreeWidget.render output, unchanged) ───
  Text[] treeRows: [glyph seat · activity age, ...]   // up to 9 rows
                                                      //   + 1 dim hint line
                                                      //   + 1 dim "... N more" if cap hit

  // ─── Progress region (only when controller.surface === "progress") ───
  Text divider:       "▾ <seat> progress · esc back"   // dim, single row
  Text[] viewLines:   [TranscriptView.render(width)]    // styled by TranscriptView itself
}
```

The tree rows render exactly as they do today (`CouncilTreeWidget.render`,
lines 370-410 in `navigator.ts`). The divider appears only when
`surface === "progress"`; the `viewLines` are produced by the
existing `TranscriptView.render(width)` (lines 624-642), called with
the same width the widget was rendered at. No
`withModalFrame` wrap (the Phase 1 ruling rejects it). No backdrop
(there is no backdrop for belowEditor regions; the tree widget today
already renders without a backdrop, which is the desired contrast —
a progress expansion that does not dim the message area above).

- **P9.** No new theme tokens. Falsifier: `grep -E "theme\\.fg\\(\\s*['\"]([a-z]+)['\"]\\s*,"

  (`accent`, `border`, `customMessageBg`, `dim`, `success`,
  `warning`, `muted`, `bold` per `vault/wiki/council-theme.md` §
  "Token-only drawing rule"). The progress divider uses `dim`;
  the TranscriptView uses `accent`/`success`/`dim`/`warning`/
  `muted`/`bold` (its existing palette).

- **P10.** Token-only drawing in the divider. Falsifier: assert
  the divider line, when the council theme is active, contains
  only theme-token-derived ANSI sequences. Pure-seam test: theme
  with recording `fg` spy; render; assert each emitted ANSI byte
  sequence matches `getFgAnsi("dim")` for the divider and the
  existing TranscriptView palette for view lines.

- **P11.** Height budget. The factory's total output is bounded
  by the visible terminal rows. Today, `CouncilTreeWidget.render`
  returns up to 9 rows + 1 hint line (the 10-line MAX is for the
  string-array path; the factory has no pi cap, but the EV-7
  widget caps itself at 9+1). Adding the divider (1 row) and
  TranscriptView output (M rows) means total height = 10 + 1 + M.
  Pi's layout container is `shrink:1, minSize:0`; the editor
  container is `shrink:1, minSize:3`. On a 24-row terminal, the
  message area + status + footer + editor (minSize 3) take ~7-10
  rows; belowEditor can claim the rest. Falsifier: render the
  factory at width 100 on a fake `terminal.rows=24`; assert the
  total line count fits in `terminal.rows - editorRows -
  messageRows`. If M is unbounded for a transcript with hundreds
  of blocks, the factory must window the TranscriptView's output
  to fit — `TranscriptView.render` already windowing-slice its
  output at `viewportRows` (line 642). The owner MUST pass a
  `viewportRows` to the TranscriptView that respects the available
  terminal rows. The honest answer: cap `viewportRows` at
  `max(3, Math.floor((termRows - editorMinRows - treeLines) / 2))`
  so tree and progress share the remaining rows roughly evenly.
  This is the load-bearing implementation detail; the design
  constraint is "tree above, progress below, both readable."

- **P12.** The widget factory is disposed properly. Falsifier: the
  factory's `dispose` clears the `TranscriptView.timer` (the
  existing `view.dispose()` at `navigator.ts:550` does), the tree
  widget's 2s timer (the existing factory dispose), and the
  `progressSessionId`. After dispose, re-invoking `/council-tree`
  to reopen must construct a fresh `TranscriptView` for the new
  selected sessionId, not reuse a stale one.

### Comprehension (judgment — settles only on a human's read)

- **C1.** A first-time operator who has just pressed Enter on the
  highlighted row and seen the progress expansion below the tree
  can answer, without reading any docs: (i) which seat am I
  watching? (the highlighted row above); (ii) what can I do in
  this view? (the divider's `esc back`, plus the
  TranscriptView-rendered keymap at the top of the view); (iii)
  how do I leave? (Esc, named in the divider). All three are
  on-screen.

- **C2.** While watching progress for one seat, the operator can
  tell at a glance when ANOTHER seat settles (the row above the
  progress flips from `●` to `✓` or `✗`, the row's last-activity
  text changes from `thinking` / `ran tool` to `settled` / `failed`).
  This is the comprehension gulf the card actually closes.

- **C3.** Returning from progress to the tree feels like
  *returning to the same place*, not opening a new view. The
  highlighted row is the same; the cursor on the input editor is
  where it was; the tree's last-activity ticks on. There is no
  "modal closing" moment — Esc just removes the divider and view
  lines.

- **C4.** The mode label transitions cleanly: `-- TREE --` →
  `-- PROGRESS --` on Enter, `-- PROGRESS --` → `-- TREE --` on
  Esc. The label is a promise about what the keys do; the
  operator's mental model of "I am in this mode, these keys do
  these things" is continuous across the open/close.

## Concrete routing table for the progress surface (the owner's spec)

The `routeEditorFocus` kernel in `extensions/focus-nav.ts:118-152`
needs a third arm. The current table is:

| key | surface==="tree" | surface==="editor" (tree open) | surface==="editor" (no tree) |
|---|---|---|---|
| Up | move (-1); at-top → exit to editor | if on last logical line, nothing (forward to super) | forward to super |
| Down | move (+1); at-bottom → exit to editor | if on last logical line, enter tree | forward to super |
| Enter | consumed → `onActivate(tui, selectedSessionId)` | forward to super | forward to super |
| Escape | exit to editor | forward to super | forward to super |
| other | forward to super | forward to super | forward to super |

For `surface === "progress"`, the table is:

| key | surface==="progress" |
|---|---|
| Up | forward to `view.handleInput(data)` (TranscriptView moves focused block up; turns off follow) |
| Down | forward to `view.handleInput(data)` (TranscriptView moves down) |
| `e` | forward to `view.handleInput(data)` (toggle expand on focused block) |
| `t` | forward to `view.handleInput(data)` (toggle thinking) |
| `f` | forward to `view.handleInput(data)` (toggle follow) |
| `g` | forward to `view.handleInput(data)` (scroll to top) |
| `G` (shift-g) | forward to `view.handleInput(data)` (scroll to bottom) |
| Enter | **consumed, no-op** (progress is already open; Enter inside the transcript does not open another progress; this is a forcing function against the slip "press Enter again, see what happens") |
| Escape | exit to `"tree"` surface, clear `progressSessionId`, dispose `view` |
| other (printables, ctrl+c, ctrl+d, PageUp, PageDown, Home, End, Backspace, Tab, arrows if surface!=="progress" etc.) | forward to `super.handleInput(data)` |

The "Enter is consumed, no-op" line is a **forcing function**
(Norman) against the slip "press Enter again." Inside the progress
view, Enter has no semantic — the progress is already open.
Consuming it silently (no observable feedback) is acceptable because
the operator's expectation is "Enter opens progress," and progress is
already open; pressing Enter again is a slip, and the safe, silent
default is correct. The mode label `-- PROGRESS --` makes this
discoverable: an operator who reads the label knows the handled set
is what the TranscriptView consumes, and Enter is not in that set.

The "other → super.handleInput" rule is **forward-unhandled**,
settled by EV-8 ruling 2 (binding) and inherited by EV-9 unchanged.
ctrl+c still interrupts the editor (or the running model); ctrl+d
still exits on an empty editor; printables still flow to the editor
buffer; nothing disappears silently.

The "Up/Down forward to view.handleInput" is critical: TranscriptView
already implements `Up`/`Down` to move its internal `focused` block
(navigator.ts:597-622); we do NOT route Up/Down through the tree's
`controller.move` — that would move the TREE'S selection while the
progress is open, which is wrong. The tree's highlighted row stays
frozen on the seat whose progress is open, exactly because
`controller.move` is not called while `surface === "progress"`.
This is the **stable mapping** Norman insists on: one signifier
(the `▌` row above) = one state (the seat whose progress is open).

## Preferences, ranked last

These could not be grounded; they are taste.

- **Divider wording.** I prefer `▾ <seat> progress · esc back`
  (single dim row, with `▾` U+25BE for the "open below" shape).
  Equally defensible: `— progress for <seat> (esc back)` with `—`
  (em-dash) as the separator, no glyph. The constraint is that the
  row is dim and names the seat + the close key; taste decides the
  glyph and the separator.
- **Progress viewport cap split.** If both tree and progress want
  more rows than the terminal has, who wins? I prefer splitting
  remaining rows 50/50 with a `Math.floor(remaining / 2)` cap on
  each. Defensible alternatives: tree wins (it is the operator's
  anchor); progress wins (it is the reason the operator opened it).
  This needs PO arbitration only if the smoke catches a terminal
  size where the split produces an unreadable result.
- **Whether the divider shows the seat's state glyph.** I prefer
  no glyph (the row above already shows it; duplicating is visual
  noise). Equally defensible: prepend the glyph for parity with
  the row above. Taste.
- **Mode label wording.** I prefer `-- PROGRESS --` mirroring
  `-- TREE --` (vim precedent). The binding is the LABEL STYLE
  (hard rule per EV-8 ruling 3); the WORD is taste.

## What I escalate to product-owner

- **Surface type expansion.** EV-9 extends
  `TreeFocusState.surface` from `"editor" | "tree"` to
  `"editor" | "tree" | "progress"`. This is a type change to a
  settled EV-8 type. If product-owner rules the type must stay a
  binary union (e.g., for "minimal change"), the alternative is
  a parallel `progressSessionId: string | null` field on the
  controller and a `view` field on the controller, with the
  routing kernel branching on `progressSessionId !== null`. This
  is uglier but preserves the EV-8 type. I argue for the union —
  the new value is a real state, not a derived flag, and the
  routing table reads more honestly with three named cases than
  with two cases plus a nullable field.
- **Enter inside progress: consumed no-op vs forward to
  TranscriptView.** TranscriptView's `handleInput` does not
  handle Enter (it handles Up/Down/e/t/f/g/G/Esc only — see
  `navigator.ts:597-622`); forwarding Enter to it would be a
  no-op anyway. So this is a design clarity call, not a behavior
  difference. I prefer the explicit "consumed" for the future-
  proofing: if TranscriptView ever grows an Enter handler (e.g.,
  "Enter to copy block"), the routing kernel is already correct
  and the contract holds.
- **Height budget split.** Listed under Preferences; route to PO
  only if the smoke flags a terminal where the split is
  unreadable.
