### CONFIRM-1 — command name `/council-leaderboard`

**Bind `/council-leaderboard`.** R-7 (already on the EV-21 card face) holds the copy and command-name decisions for this card's own deliberation; the seats converged on `/council-leaderboard` with the principal's `/council-eval-results` withdrawn as advisory. The deciding fact is symmetry with R-3: the write side is `/council-eval` (the matrix runner) and the read side is `/council-leaderboard` (the rank view) — two distinct verbs, two distinct surfaces, no name shadowing inside the `/council-` namespace. `/council-leaderboard` also reads correctly as "what you're invoking" (a leaderboard, not a result-set dump), which is the surface the acceptance describes — a ranking — not a raw store dump.

Options rejected:
- `/council-eval-results` (principal's round-1) — confuses the read surface with the write side's storage path (`council/eval-results/`); reads as a directory listing, not a ranking.
- `/council-rank` — narrower than what the surface delivers (it also reports n, σ, TRIAGE tier, fixture/rubric version columns); name implies a single axis.
- Defer to a follow-up card — R-7 already deferred this decision to EV-21; deferring again is the kind of recursion the seat's `<when_invoked>` warns against.

Spec text the writer lands:
1. New procedure file `council/procedures/council-leaderboard.md`, frontmatter `description: "Render the eval-results leaderboard (per-command and per-seat slices, with variance and triage)"`. Filename is the slash command per convention `procedure-commands.md`.
2. Registered alongside `/council-eval`; no argument grammar beyond `--help`; the no-arg form is the default render. No `[task]` filter in v1 (the surface is the leaderboard, not a per-task drill-down — drill-downs are a follow-up if anyone asks for them).
3. Any error copy or pointer that names the command uses `/council-leaderboard` — including the empty-state lines in J-1.

### CONFIRM-2 — landed-bug fix rides EV-21 (in-place version-pair-aware group key)

**Bind. The fix rides EV-21, not a follow-up card. Failing-test-first, additive CellSummary fields, in-place edit, byte-identity preserved for single-version stores.**

The deciding fact is the byte-identity contract between `summarizeStore` (live `/council-eval` summary, `extensions/eval-runner.ts:634`) and the leaderboard's `readAllResults → aggregateCell` path. Skeptic empirically confirmed the defect in the LIVE `/council-eval` summary: bumping a fixture version and re-running blends n_attempted=4, mean=0.625 from two incomparable rubric versions. The two surfaces are bound by "same-function-both-sides" (`extensions/eval-stats.ts` doc + Q1-D1 of the EV-20 ruling), so fixing only one side is mechanically impossible — the leaderboard would render a different aggregate than the summary the user just saw. That is the binding reason this rides EV-21, not a separate card; any change to the EV-20 store contract is portfolio-level and requires a fresh ruling (per `<escalation>`), but the records already carry `fixtureVersion` + `rubricVersion` (per `extensions/eval-rubric.ts:97-98`) and the writer already stamps them on disk (per Q1-D1 of the EV-20 ruling) — so this is a reader-side group-key correction, not a store-contract change.

This is a fold-in (not a new card) because the EV-21 acceptance says the view renders "per-command and per-seat rankings with repeat count, mean, and variance per row" from records that include `fixtureVersion` and `rubricVersion` as committed fields. The fold-in clause of the seat's authority holds: the work is needed to honestly meet the card's existing goal read as written. A new card would be required only if the fix needed to change the goal text — it does not.

Options rejected:
- **Fix only the leaderboard's reader** — rejected because it preserves the live summary's blended-aggregate defect; the two surfaces drift apart, which is the bug class `eval-stats.ts` was extracted to prevent.
- **Spin out a separate card** — rejected for the byte-identity reason above; the binding is structural, not preferential.
- **Re-bump the rubric version on the store** (drop old records) — rejected because it silently destroys real data the maintainer has run; the records are gitignored but the data is real.

Spec text the writer lands:
1. **Failing test first** in `test/eval-runner.test.ts`: seed the on-disk store with two `ResultRecord`s carrying different `(fixtureVersion, rubricVersion)` pairs but the same `cellId` and `scoredUnder`; assert `summarizeStore` produces TWO `CellSummary`s (one per version cohort), not one blended summary. Repeat for the leaderboard reader path. Test fails against today's `summarizeStore` (group key `${rec.cellId}\u0000${rec.scoredUnder}` ignores versions) and against any leaderboard reader that forgets the same group key. This test is the regression fence.
2. **In-place fix** to `summarizeStore` in `extensions/eval-runner.ts:634`: change the group key from `${rec.cellId}\u0000${rec.scoredUnder}` to `${rec.cellId}\u0000${rec.scoredUnder}\u0000${rec.fixtureVersion}\u0000${rec.rubricVersion}`. Same pure-function discipline; no I/O; no record-shape change.
3. **Additive `CellSummary` fields** in `extensions/eval-stats.ts`: `fixtureVersion: string` and `rubricVersion: string` populated from `records[0]` (single-version-per-summary invariant holds; if two versions ever sneak into one group, the writer has drifted — but `summarizeStore` already groups them apart, so this is a paranoid read). No existing test pins the merged-cohort behavior; no migration needed.
4. **Leaderboard reader** uses the same `readAllResults → aggregateCell` path as `summarizeStore` (per the same-function-both-sides contract). The leaderboard renders the version pair as a sibling row badge per the J-1 copy below — the data is now grouped correctly; the visualization follows.
5. **Version-pair disambiguation** in `summaryLines` (the live command summary that renders today) — append the version pair to the rendered cell line so a user looking at the live summary can tell cohorts apart without diving into the records. Add as a companion one-liner, not a copy rewrite: `... mean=... σ=... fixture=vX.Y.Z rubric=vA.B.C` when versions are present.
6. **Single-version byte-identity preserved**: when all records share a version pair, the summary's `mean`/`σ`/`n`/`histogram` are byte-identical to today's output for the same input (the only delta is the appended version stamp and the new `fixtureVersion`/`rubricVersion` on `CellSummary`).

This is not a schema amendment — the records already carry the version pair (per EV-20 Q1-D1); the bug is that the reader was ignoring a field the writer already stamped.

### J-1 — copy, J-2 — Phase-4 smoke, J-3 — kind limitation

#### J-1 copy — bind with one literal-reading tweak

**Bind the designer's settled copy as written, except for one label adjustment: the σ column header reads `σ`, not `VARIANCE` (the acceptance's word "variance" is the intent; the letter σ is the honest name of Bessel-corrected sample standard deviation).**

The deciding fact is **mechanism × user value**:
- **Mechanism.** Bessel-corrected sample standard deviation is σ by every statistics textbook; naming it `VARIANCE` while computing σ is a lie-of-imprecision the seat's `<re_grounding>` clause warns against (this product exists to serve users, not to flatter them). The seats' recommendation is the one-line label change: σ stays σ, header stays `σ`.
- **User value.** A maintainer who has run a small cell once and wants to know whether to trust the mean needs to read `σ` correctly, not as `VARIANCE`. The seats converged on σ for the literal character; that's the binding.

Empty-state spectrum is honest and the four-state copy (A: directory-missing; B: gate-only-only; C: n_graded=1; D: length-majority) is correct — each names the actual defect rather than papering over it. Empty-state A specifically points at the right command: `council/eval-results/ does not exist — run /council-eval <task> <model…>`. This is consistent with R-6 (the run command's name in copy) and with R-7 (copy deliberately deferred here, now bound).

Both slices (By command / By seat) by default is right — a maintainer asking "which model should I pin as owner?" wants the per-seat slice; a maintainer asking "which model runs `/council-eval` best?" wants the per-command slice; making them mutually exclusive is the wrong instrument. Both, default-on, with each labeled by its grouping axis.

Options rejected:
- Column header `VARIANCE` — literal reading of the acceptance is the wrong instrument here; the mechanism computes σ and the user deserves to know it.
- Empty-state collapsed to one generic line — loses the four-state honesty; a maintainer staring at `indeterminate (length majority)` needs to know whether the cell is deterministic and the model is bad (length-majority is data about the model, not a record defect) or whether the cell had no grader at all (B).
- Triaging tier phrase `tied` without `(±CI)` — the parenthetical is the source of the label's honesty; without it the tier reads as "the same number," which is not what `tied (±CI)` means (it means "overlapping CIs, cannot assert ordering").

Spec text the writer lands (this is the copy the leaderboard renders):
1. **Column headers**: `TASK MODEL GRADER n MEAN σ TRIAGE` (in that order).
2. **`n` rendering**: `n_graded/n_attempted` (e.g. `2/3`); when the gate-only `scoredUnder === "self"` sentinel applies, render as `gate-only (self)`.
3. **`σ` rendering**: Bessel-corrected sample standard deviation to three decimal places (matching `mean` precision); render `—` when `n_graded < 2`.
4. **TRIAGE tier phrases** (applied per row):
   - `leader` — single-model unchallenged top by CI-on-mean-difference (`compareCellTriage` of [rowScores] vs [nextBestScores] returns `tied: false` AND `meanDiff > 0`).
   - `runner-up` — second-place row similarly distinct from the leader.
   - `tied (±CI)` — `compareCellTriage` returns `tied: true` between this row and an adjacent row at the same rank slot.
   - `gate-only (self)` — `scoredUnder === "self"`, ranked separately per D2 ruling.
   - `indeterminate (length majority)` — `lengthMajority === true` (per `aggregateCell`).
   - `indeterminate (no graded repeats)` — `n_graded === 0` and `n_attempted > 0`.
   - `n<2 (need 2 to triage)` — `n_graded < 2`, regardless of `n_attempted`.
5. **Version pair as sibling rows in the per-task header** (`FIXTURE` and `RUBRIC` columns), with each (cellId, scoredUnder, fixtureVersion, rubricVersion) cohort as its own row group, ordered by `mean` DESC within the cohort and cohort-ordered by latest fixture+rubric first.
6. **Both slices by default**: the leaderboard renders the By-command slice AND the By-seat slice on a single screen, each labeled with its grouping axis. No toggle.
7. **Empty-state copy** (rendered in the slice where it applies):
   - **A — directory-missing**: `council/eval-results/ does not exist — run /council-eval <task> <model…> to start` (consistent with R-6; matches `/council-eval` per R-3).
   - **B — gate-only-only**: `results exist, all gate-only (self) — not rankable against graded cells; run a judge-bearing fixture to compare`.
   - **C — n_graded=1**: `n<2 — need 2 repeats to triage`.
   - **D — length-majority**: `indeterminate (length majority) — do not pin from this cell`.

#### J-3 — kind limitation (current-fixture-kind only)

**Accept the limitation. Do NOT amend the store schema. Disclosure copy binds.**

The deciding fact is the **cost-and-honesty trade-off the seats already weighed**:
- **Mechanism.** Fixtures carry a `kind` field on disk; the leaderboard resolves `kind` against the CURRENT fixture on disk, not against a historical kind stamped on the record. If a fixture was re-classified across versions, historical rows carry current kind. This is honest — kind is current-fixture-kind — and the disclosure copy makes that explicit.
- **User value.** A maintainer asking "which model is best for `wiki-query`-shape tasks?" gets a leaderboard that answers against today's taxonomy. That is the right answer 99% of the time; the 1% case where kind was re-classified gets a clear "kind reflects the current fixture" disclosure, not a silent misclassification.
- **Cost.** Amending the store schema (adding `kind` to `StoredResultRecord`, propagating it through `gradeCell` → writer → reader) is a structural change. It costs a divergent-payload throw on re-runs of any pre-amendment record (the writer would now see records without `kind` and refuse to write alongside amended records), and there is no backfill for the existing records — they remain kind-less. Seats strongly recommend accept; I agree.
- **Mitigations** baked in: (i) an `unknown` bucket when the fixture is missing on disk (the kind resolution fails soft, not hard — a deleted fixture does not crash the leaderboard), and (ii) the disclosure copy states explicitly that kind reflects the current fixture.

Options rejected:
- **Amend the store schema to carry `kind` on every record** — rejected for the re-run divergent-payload throw and the no-backfill cost; the disclosure + unknown bucket is a strictly cheaper way to get the same honesty.
- **Reject the limitation and defer to a follow-up card** — rejected because the limitation is real but bounded; the disclosure makes the bound visible; the cost of a card is spec/code churn for no user-value gain.
- **Refuse to render rows with current-kind mismatch** — rejected because it silently drops rows that are perfectly legible under the disclosure; the user loses signal.

Spec text the writer lands:
1. **Acceptance clause** (added to EV-21's acceptance): "kind is resolved against the current fixture on disk; historical rows carry current-fixture-kind. When the fixture is missing on disk, the kind renders as `unknown`."
2. **Disclosure copy** rendered in the per-task header: `kind reflects the current fixture (version vX.Y.Z); historical rows use the same kind`.
3. **No schema change** to `StoredResultRecord`, `VerdictRecord`, or any writer path. Pure read-side resolution.
