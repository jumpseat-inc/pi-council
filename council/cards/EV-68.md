## Intent

The three modes have to be observable where the run is already auditable. A
card's mode is decided from the ledger, carried into the dispatch that executes
the card, and recorded on that dispatch's manifest beside the seat, model, and
usage the manifest already carries — so a reader can tell from the records alone
which cards paid for deliberation and which did not, without consulting the
ledger or the deliberation transcript.

The backward-compatibility constraint is as important as the field. The manifest
is read by the job tree, the transcript navigator, the usage aggregation, and
the reconciliation path; an unrecognized field must be inert to all of them, and
a manifest written before this change must remain readable and summable
byte-identically. The mode therefore rides the existing write path as an
optional field, and the stall, timeout, and kill semantics of the job supervisor
are untouched.

Recording the mode on the card's frontmatter is deliberately not the mechanism:
the card schema is fixed and validated, and the mode is a fact about an
execution, not about the planned work.

## Acceptance

All three mode literals appear on fixture manifests and are distinguishable; a
manifest lacking the field reads and sums identically to today's behavior in the
same test; the job tree and usage aggregation handle a mode-bearing manifest
without a code path change beyond the optional field; and no supervisor timing
behavior differs.

## Position (EV-68, design pass — no edits made)

**Approach.** The mode flows through the exact same four-surface chain the EV-39/EV-42 fields already use — tool param → spawn spec → `Job` → spread-gated manifest write — and lands on `RunManifest` as a third optional field behind the same spread-gate discipline. The fixture-forest test is then pure-reader-side (like `test/runs.test.ts`) plus one hub-path test with the STUB child proving the write path. I read `runs.ts` (full), `hub.ts` (Job, `writeJobManifest` at lines 117–141, tick/settle/cancel write sites), `hub-tools.ts` (full dispatch tool), `tree.ts` (full), the navigator's mode language, and the wiki index pages `run-transcripts`, `hub-job-supervision`, `per-attempt-provenance`, `gate-parity`, `metered-deliberation-routing`.

### (1) How `mode` flows — named surfaces

- **`extensions/runs.ts`** — export `export type DispatchMode = "Deliberate" | "Verify" | "Direct";` and add to `RunManifest`: `mode?: DispatchMode` with a doc comment naming EV-68 and the ROOT-dispatch binding. Placing the type here means `hub.ts` and `hub-tools.ts` import one name and there is no second copy (the house rule the retry classifier learned the hard way).
- **`extensions/hub-tools.ts`, `council_dispatch` parameters (hub-tools.ts:135–149)** — add `mode: Type.Optional(Type.Union([Type.Literal("Deliberate"), Type.Literal("Verify"), Type.Literal("Direct")]))`. This is where gate-parity puts strictness: capability at selection ([[gate-parity]]). Typebox rejects anything but the three literals before `execute` runs. Pass `mode: params.mode` into the `hub.spawnJob` opts object (the object literal at hub-tools.ts:244–258).
- **`extensions/hub.ts`** — `Job` gains `mode?: DispatchMode`; `spawnJob`'s opts type gains the same. Because the Job holds it, **respawn carries mode unchanged for free** — correct, since one manifest serves all attempts (EV-39 cardinality A) and mode is a fact about the dispatch, not the attempt. `writeJobManifest` (hub.ts:117–141) gains one line, after the `nextAttemptAt` spread: `...(job.mode !== undefined ? { mode: job.mode } : {})`.
- **What deliberately does NOT change**: `childEnv` (runs.ts) does not carry mode; `tree.ts`, `navigator.ts`, `usage-block.ts`, reconciliation get zero edits. Root-ness is structural, not propagated: only the parent session's hub (`parentJobPath` undefined → `parentJobId: null`) can write a manifest the card calls ROOT, and only a dispatch the parent explicitly tags with `mode` carries it. A runner child's own dispatches go through the child's `council_dispatch` with no mode param → no mode field. The field never rides env — that is the whole ROOT-only story.

### (2) The optional-field contract to pin

- **Spread-gate discipline**: exactly the `stopReason`/`attempt`/`nextAttemptAt` pattern (hub.ts:133–140) — the key is *absent*, not `null` and not `"None"`. Absence is the discriminator for "pre-EV-68 manifest," same shape-discrimination idiom as EV-42's `m.attempts !== undefined`.
- **JSON shape/ordering**: new manifests carrying mode write `"mode"` last (after `nextAttemptAt`), tab-indented via the existing `writeManifest`. Existing keys never move, so a mode-less job's manifest is key-for-key identical to today's output — that's what makes the backward-compat claim checkable rather than aspirational.
- **Read-side inertness is pinned by construction, not by edit**: `readManifests` is a raw `JSON.parse` (runs.ts:199), `sumSubtree` touches only `usage` fields, `buildTree`/`textTree` touch only `id`/`parentJobId`/`state`/`pid`/`seat`/`attempt`/`startedAt`. TS-wise an unknown-at-runtime field on an optional property is inert. The contract is: *no reader may ever branch on `mode`* in this card — the test proves behavior, the review proves the negative.
- **TS enforcement only at the type level on the write side**: the spread gate checks `!== undefined`, so a runtime write of a bogus literal would pass — acceptable, because the tool schema is the runtime gate and nothing else writes manifests.

### (3) What the fixture-forest test must prove (one file, e.g. `test/ev68-mode-manifest.test.ts`)

1. **Forest fixture** in a fresh `mkdtemp` repoRoot via `writeManifest` (the established `manifest()` helper pattern, test/runs.test.ts:74): three roots tagged Deliberate/Verify/Direct, each with two mode-less children with usage; plus one legacy root with no `mode` and the same usage shape as one tagged root.
2. **Distinguishability**: after `readManifests`, a pure selector yields exactly the three distinct literals on the three roots and `undefined` on every child and the legacy root.
3. **Sum identity in the same test**: `sumSubtree` over the legacy root and over the identically-shaped tagged root return the same number (missing usage → 0 unchanged, runs.ts:269–276), and each root's sum equals the hand-computed fixture sum.
4. **Tree identity**: `buildTree` over the forest gives identical depths/parent-children/orphan flags whether or not `mode` is present — structure provably untouched.
5. **Write-path half** (hub, STUB child, the test/hub.test.ts:406 pattern): spawn with `mode: "Verify"` → on-disk JSON parses with `mode === "Verify"`; spawn without mode → `Object.keys(parsed)` equals the legacy pre-EV-68 key set exactly (this is the real "byte-identical" proof — read-side parse alone can't prove write-shape preservation); one retry respawn → mode survives unchanged on the single manifest.

### (4) Falsifiable risks

- **Env-inheritance regression**: the obvious wrong "elegant" move is threading mode through `childEnv` like `COUNCIL_SEAT`, which would stamp every descendant dispatch and violate the ROOT binding. Test: a child-hub dispatch (Hub constructed with `parentJobPath`, the test/hub.test.ts:37 pattern) with no mode param must produce a manifest with no `mode` key.
- **Render creep**: adding `mode` to `textTree` rows or `formatReport` heads would be a code-path change beyond the optional field and breaks the acceptance's "no code path change" clause. The card binds against it; a grep-level review check suffices (`tree.ts`, `hub-tools.ts` renderers).
- **Name collision noise**: `navigator.ts` already speaks `ctx.mode` (TUI surface mode, navigator.ts:72–90) — different namespace, no conflict, but seat prose/tests grepping `mode` get noisy; worth a deliberate doc comment on `RunManifest.mode` distinguishing execution-mode from surface-mode.
- **Red-base obligation**: if this card requires the red-base record, the falsifier (mode-literals-on-manifests test) must run red at the pre-mechanism base — it will, since nothing writes `mode` today; the seven-field record (base sha, transplant = the test file, verbatim `bun test test/ev68-mode-manifest.test.ts`, raw per-failure lines, worktree provenance, bare copy set, head half `0 fail`) is required at implementation time, not now.

**Tradeoffs accepted.** A union type on `RunManifest.mode` is TS-only on the write side (no runtime enum check in `writeManifest`) — worth it because the tool schema already gates at selection and adding a second runtime validator would duplicate a gate. Mode intentionally does not propagate to sub-dispatches; EPIC-13's later cards can extend the contract then if the routing ledger ever needs per-child tagging, and the minimal ROOT-only contract matches the card's binding verbatim.

#### principal (job-14.2)

- **Cross-seam reading**

  The manifest contract is owned by `RunManifest` in `extensions/runs.ts:68-96`, but that type is not writable except through one path: `writeManifest` (`runs.ts:110`) is called only from `hub.ts:119 writeJobManifest`, and `writeJobManifest` builds its object from the in-memory `Job` (`hub.ts:22-56`). So the mode has to traverse *four* links, not one:

  1. `council_dispatch` parameter schema (`hub-tools.ts:139-149`, next to the `cellId`/`model`/`thinking` precedent),
  2. `spawnJob` opts (`hub.ts:141-156`),
  3. `Job` carrier (`hub.ts:22-56`),
  4. the optional `RunManifest` field, spread-gated like `stopReason`/`attempt` at `hub.ts:136-137`.

  "Manifest type only" is insufficient: nothing outside the hub writes a manifest (`runs.ts:110` has exactly one caller, `hub.ts:119`), and the hub has no ledger, so if the value cannot enter through the dispatch input it can never be recorded for a card executed via the facilitator's procedure. Conversely the eval path (`dispatch.ts:103`) also calls `spawnJob` and simply won't pass it — correct, since an eval cell is not a card.

  The reader set stays inert because every reader is field-scoped and none iterates keys: `tree.ts:13-27` reads `id`/`state`/`pid`/`parentJobId`; `navigator.ts:236,345,351,398,492` reads `state`/`sessionId`/`startedAt` and delegates to `attemptEntries`/`browsableAttempts`; `usage-store.ts:393,431-437` reads `startedAt`/`exitCode`/`model`/`attempt`/`attempts`; `spend.ts:232-250` and `cost-baseline.ts:45-83` read `parentJobId`/`id`/`usage`. `readManifests` (`runs.ts:149-167`) is a bare `JSON.parse` with no validation — an unknown key is structurally inert.

- **Blind spots**

  - *Hub/supervisor view* (`hub.ts`) cannot see that "root" is a **per-dispatch** fact: if mode ever became ambient (inherited by child seats re-dispatching through the same `childEnv`/hub), descendants' manifests would carry it and "root-only" would be unreadable. The hub has no notion of card vs. sub-dispatch, so it can't enforce root-ness; it can only decline to propagate.
  - *Reader view* (tree/navigator/usage/reconciliation) cannot see the **write-time byte contract**: inertness is trivially true in-process but the card also promises byte-identity, which is a property of the spread-gate in `writeJobManifest`, invisible from any reader.
  - *Test-author view* cannot see that "fixture manifests" is ambiguous against `eval-fixtures.ts:494-515 sha256Tree`: if the EV-68 fixture forest is placed under `council/fixtures/<task>/seed/`, the pinned `treeDigest` changes and fixture load refuses it. The fixture forest must be hand-built in `test/` (the `cost-baseline.test.ts:60` / `hub.test.ts:mkdtemp` pattern), never a packaged seed.
  - *EV-69/EV-70 view* (routing + Direct) cannot see the enum location. If EV-68 declares the literal inline on the tool param, the next card re-declares it; the single source must live beside `RunManifest` in `runs.ts`.

- **Reframe**

  The proposed design is sound; no reframe needed. One sharpening the card already implies but should be pinned explicitly: **`mode` is a third axis of dispatch provenance alongside `attempt` and `attempts`, and it is per-dispatch, carried through retries, never inherited.** `respawn` spreads `...prev` (`hub.ts:205`), so the mode set at `spawnJob` survives attempt N automatically — that is the desired semantics and should be asserted, not left incidental.

- **Backward-compatibility clause must pin (so EV-69/EV-70 don't reopen this)**

  1. **Absence is the absence of the key, not `null`/`undefined`** — the spread-gate `...(job.mode !== undefined ? { mode: job.mode } : {})` in `writeJobManifest`. A no-mode dispatch's manifest JSON bytes are unchanged (same discipline as `stopReason`/`attempt`).
  2. **Single literal source**: a closed union `Mode = "Deliberate" | "Verify" | "Direct"` exported from `runs.ts`; EV-69/EV-70 import it, never re-declare. A fourth literal is a card-level decision, not a string a caller may invent.
  3. **Root-only / non-inheriting**: mode appears exactly on dispatches whose caller supplied it; the hub does not copy it into `childEnv` or into descendant spawns.
  4. **Retry stability**: mode is unchanged across attempts of the same job (`hub.ts:205` spread).
  5. **Reader-result invariance**: `readManifests`, `sumSubtree`, `buildTree`/`textTree`, `browsableAttempts`, and the usage-store harvest return values identical to a mode-less control — no function signature or return shape change.

- **Fixture-forest test must prove**

  1. Three manifests each carrying a distinct literal are distinguishable **from `readManifests` output alone** (`m.mode` equals each literal) with no ledger or transcript access; assert the set of literals is exactly the three.
  2. A fourth manifest in the same forest with no `mode` yields `!("mode" in JSON.parse(bytes))` and `readManifests(...)` returns `undefined` for `m.mode` — absence, not null.
  3. **Inertness by same-function-both-sides**: run `sumSubtree`, `buildTree`→`flattenTree`→`textTree`, and the usage-store manifest harvest over (a) the forest with the three mode-bearing roots and (b) a byte-equivalent forest with the `mode` key stripped; assert the numeric sums and the emitted text lines are byte-equal. This is the only form of "reads and sums identically" that is falsifiable rather than asserted.
  4. A retried mode-bearing job keeps its mode after `respawn` (`hub.ts:205`).

- **Falsifiable risk that the field is NOT inert**

  The premise holds for all four named readers (field-scoped access, no key iteration, no manifest schema validator). It fails only where a consumer does whole-object equality or byte-snapshots the manifest. I found no such manifest-level assertion: `hub.test.ts:277` is `expect(m.usage).toEqual(r.usage)` (field-scoped), `usage-store.test.ts:1082-1094` checks `"attempt" in m` (membership, not keys), and `cost-baseline.test.ts:160-173` pins imports and empty-forest behavior. **The concrete falsifier**: add a test asserting `Object.keys(m).sort()`/`JSON.stringify(m)` for a no-mode manifest against the pre-change bytes; if any reader or test pins manifest key set or bytes, that is where the field stops being inert. Second falsifier: place a mode-bearing manifest under `council/fixtures/<task>/seed/` and assert `loadFixture` still passes — it will fail on `treeDigest` (`eval-fixtures.ts:507-514`), proving the fixture forest must be test-local, which is the correct choice.

## EV-68 Synthesis

### Agreed design

Every seat converged on the same four-link flow:

1. `council_dispatch` in **hub-tools.ts** gains a Typebox literal-union `mode` parameter (`"Deliberate" | "Verify" | "Direct"`).
2. `mode` passes through **spawnJob opts** → **Job carrier**.
3. In **writeJobManifest** (hub.ts:119, the sole caller of `writeManifest`), the field is conditionally spread after `nextAttemptAt`: `...(job.mode !== undefined ? { mode: job.mode } : {})`.
4. `RunManifest.mode?: DispatchMode` is the optional field; `DispatchMode` is exported from **runs.ts** as the single literal source.

When the `mode` param is absent (eval dispatch at dispatch.ts:103, child-hub dispatches), no `mode` key appears in the written manifest. When present, `"mode"` is written last, tab-indented, existing keys never move. The field never propagates to sub-dispatches or childEnv.
