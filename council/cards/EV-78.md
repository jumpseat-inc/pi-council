## Intent

The follow-up decision has its own domain vocabulary — `File`, `Merge`, `Drop`
— so it cannot reuse the card gate's `decide()` or its question set. This card
ships the data surface: the packaged question set and decision policy, resolved
with the repo's whole-file, first-hit override pattern and failing loud rather
than defaulting silently. Validation mirrors the card gate's loader, so a
malformed file is a named `FAIL:` line and never an untested default.

## Acceptance

- `council/gate/followup/questions.json` and `council/gate/followup/decision.json`
  exist as packaged data; a repo-local file at
  `<repo>/$CONFIG_DIR_NAME/council/gate/followup/<name>.json` shadows the
  packaged file whole-file, first-hit, with no field merge.
- The question set is validated by the same per-question rules
  `council/gate/questions.json` uses (`noul`/`choice`; option→description
  `criteria`); malformed JSON, an unknown key, or an invalid value fails loud
  as one line of the form `FAIL: <file> has an invalid <key> — … `, never a
  silent default.
- The three producible dispositions are spelled exactly `File`, `Merge`,
  `Drop`.
- A loader test covers the packaged files, a repo-override fixture asserting
  first-hit whole-file resolution, and the fail-loud message for malformed
  JSON, an unknown key, and an unproducible disposition.
- The repo's typecheck, the full test suite, `python3 council/validate.py`, and
  the repo's preflight pass.
