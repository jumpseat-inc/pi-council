## Intent

The follow-up decision has its own domain vocabulary — `File`, `Merge`, `Drop`
— so it cannot reuse the card gate's `decide()` or its question set. This card
ships the data surface: the packaged question set and decision policy, resolved
with the repo's whole-file, first-hit override pattern and failing loud rather
than defaulting silently. Validation mirrors the card gate's loader, so a
malformed file is a named `FAIL:` line and never an untested default.

### Round 3 — owner (job-1.5) and principal (job-1.6)

**Point B — SETTLED by convergence:** rename to `countedOption` (valence-explicit; record keyed by question id → option string, same shape as the gate's `mechanical`); `mechanical` in a followup policy is an unknown-key one-line FAIL. **Point A — OPEN, a real design dispute:**
- **Owner (holds: ordered array of `{at, disposition}` records).** Rationale: the principal's own `merge == drop` objection is the verdict against the object — with per-key `{merge, drop}`, equal thresholds silently empty the Merge band and only a validation line stands between valid-looking JSON and a two-way decision; the array makes the partition a data property (ordered bands, strictly ascending `at`), doesn't freeze the key set at two (an EV-79 refinement is data, not schema), and gives the unproducible-disposition arm a natural subject `thresholds[i].disposition`. Loader rules: non-empty array; finite `at`; strictly ascending; every `disposition` in `FOLLOWUP_DISPOSITIONS`; repeated band dispositions legal (redundant but producible). Bands walked ascending, highest satisfied band wins, else-arm File in code. Schema sketch: `"thresholds": [{"at": 1.8, "disposition": "Merge"}, {"at": 2.8, "disposition": "Drop"}]`.
- **Principal (holds: named-key object `{merge, drop}`).** Rationale: the shipped precedent for a two-bound monotone partition is exactly the gate's named-key `thresholds: {verify, direct}` with named FAIL subjects (`thresholds.verify`, `thresholds.direct`, ordering FAIL on `thresholds`); rules `merge` finite > 0 (FLLWUP-74 class-1 mirror), `merge < drop` strict (equal empties the Merge band → loader-level unproducible arm). The array's justification is unnecessary — the already-agreed override `disposition` arm owns the unproducible-disposition subject, and the object supplies threshold-local unknown-key and ordering arms anyway. The array's "key set not frozen" is illusory: with `FOLLOWUP_DISPOSITIONS` exactly three and File reserved for the else-arm, any legal array is isomorphic to the object with more ceremony, while an unconstrained array admits any number of bands and a declared `File` band (else-arm duplication). Schema sketch: `"thresholds": {"merge": 1.0, "drop": 2.0}`.

Both sketches are complete on fail-loud coverage; each discounts the other's shape as ceremony. No settling test was named by either side — a schema-shape tradeoff with no falsifiable difference in observable loader behavior beyond its own FAIL subjects.

### Step 6 — routing and the binding ruling (resumed turn, f331a62 → this record)

**Routing re-read:** recorded mode `Deliberate` (fallback source), card not surface-touching (deliberation seated owner + principal only). The single open-judgment item (A — thresholds shape) routes to `product-owner`; the ruling arrived and is appended below verbatim. **Binding ruling (product-owner, card-level; no recorded human decision reversed):**

**Q1 — `thresholds` is the named-key object**, mirroring the shipped gate's `thresholds` parse arm-for-arm:
```json
"thresholds": { "merge": 1.0, "drop": 2.0 }
```
Loader rules: (1) `thresholds` must be a JSON object — **an array value fails loud** as the shape FAIL naming `thresholds`; (2) unknown sub-key → FAIL naming `thresholds.<key>`, expected-list exactly `merge, drop`; (3) `merge` finite **> 0** → FAIL names `thresholds.merge`; (4) `drop` finite ≥ 0 → FAIL names `thresholds.drop`; (5) **strict `merge < drop`** → FAIL names `thresholds`. Under these, the goal's "partition into exactly one of File/Merge/Drop" is *structural*: File = `< merge` (non-empty since merge > 0), Merge = `[merge, drop)` (non-empty by strict `<`), Drop = `≥ drop`. EV-78's loader proves structure; EV-79 keeps the behavioral proof.

The deciding reasoning: this domain's safety story *is* the monotone walk up from File (epic Intent: the safe side is the human; no failure may Drop or auto-Merge). Legal-but-non-monotone data — inverted valence, a declared File band, a structurally-dead Drop, `at: 0` killing File — makes the epic's central opinion a validation side-effect; fail-safe means **unrepresentable, not refused**. And the array's openness serves the one future R2 already excluded: with the vocabulary frozen at three and File as else-arm, the declarable band count *is* two — a third band would be a `version`-bumping schema change arriving as its own card either way. Parity across the two `decision.json` files is worth more than a novel second shape.

**O1/O2 become test obligations for the owner:** the three array-valued exhibits from the skeptic's enumeration, plus the owner's schema-sketch array, each pinned load-FAILing on the array-rejection line naming `thresholds`; `merge: 0` FAIL pinned naming `thresholds.merge`; strict-ordering FAIL bytes pinned naming `thresholds`. O4/O5 unchanged. **Named residual this ruling does not fix:** a `drop` above max attainable composite is load-legal; home is the first threshold-move card.

**Q2 (O3) — an override rule's `disposition` is restricted to `{Merge, Drop}`**; `File` fails loud naming `overrides.<i>.disposition`, with the expected-list naming exactly `"Merge", "Drop"` (token `File` absent). File already has its two mechanisms *outside* the override lane: R4's floors-before-overrides returns File on low confidence, and the composite's below-merge arm returns it otherwise; overrides' precedence exists solely to force the *destructive* dispositions on certain answers. `FOLLOWUP_DISPOSITIONS` (R2 vocabulary, EV-82's render subject) is unchanged; only the override field validates against a declared subset.

**Options rejected:** ordered `{at, disposition}` band array (owner) — its proven expressiveness is the defect in a fail-safe-File domain; owner's array *with* extra constraints — converges to the object for more ceremony; allowing `File` overrides — ships undesigned semantics in the restrict-later direction.
