## Intent

The invoking session has no manifest at all — the hub writes manifests only for
jobs it dispatches — so the hub's job forest is not the invocation's spend. This
card is the accounting function: given the invoking session's JSONL and the
invocation's run directory, it returns a spend record whose own-session half is
the hand-summable usage of entries at or after the invocation boundary
(assistant, tool-result and compaction usage; pi counts all entries, including
those compacted away) and whose subtree half is the sum over the invocation's
job forest. The boundary is the entry id of the user message the procedure
injects. The record names the boundary it covers, so a reader knows what the
number includes. Attended runs cannot express a run total today because every
top-level manifest has `parentJobId` null; the record is the first object that
can. Edge cases — zero dispatched jobs, a rotated session, an already-pruned run
directory — resolve to a zero subtree, never an error.

## Acceptance

- A fixture session plus a fixture manifest set yields own-session fields equal
  to the hand sum of entries at or after the boundary and subtree fields equal
  to the hand sum over the job forest, asserted by an automated test.
- A zero-job invocation returns a zero subtree.
- The record carries the boundary it covers.
- `bun test`, `bunx tsc --noEmit`, `python3 council/validate.py` stay green.

## Phase 1 rulings (features-deliver, binding for this run)

### (a) The design

**Where it lives.** New module `extensions/spend.ts`, pure (no `node:fs`, no ctx, no hub). Rationale: `runs.ts` is the on-disk substrate and already carries `sumSubtree` (`extensions/runs.ts:188-201`) whose single-metric, single-root signature would need a breaking reshuffle to serve this; `transcript.ts`/`tree.ts` are separate pure modules by the same pattern. It imports only types from `@earendil-works/pi-coding-agent` (package root re-exports `SessionEntry`, `parseSessionEntries`, `CompactionEntry` — verified at `node_modules/@earendil-works/pi-coding-agent/dist/index.d.ts:19`) and `Usage`/`RunManifest` from `./runs.ts`.

**Exported signatures.**

```ts
export interface SpendRecord {
  sessionId: string;      // invoking session (getSessionId())
  firstEntryId: string;   // the boundary user-message entry id (R-4 <firstId>)
  lastEntryId: string;    // last entry on the active branch at compute time (R-4 <lastId>)
  jobCount: number;       // manifests in the invocation forest
  ownSession: Usage;      // usageSource: "session-reconciled"
  subtree: Usage;         // usageSource: "session-reconciled"
  total: Usage;           // ownSession + subtree, fieldwise
}
export function spendRecord(opts: {
  entries: SessionEntry[];        // ctx.sessionManager.getEntries()
  leafId: string | null;          // ctx.sessionManager.getLeafId()
  sessionId: string;
  markerId: string | null;        // the council-invocation marker entry id
  manifests: RunManifest[];       // readManifests(repoRoot, runId)
}): SpendRecord;
export function formatBoundaryLabel(r: SpendRecord): string;
// → `boundary=session=<sessionId> entries=<firstId>..<lastId> jobs=<n>` (R-4, byte-exact)
export function recordInvocationBoundary(pi, ctx, command: string, runId: string): string | null;
// the stamp helper (below); returns the marker id
```

`total` serves EV-32 (report at every autonomous exit) so it doesn't hand-roll a 14-field sum — flagged for the ruling seat below.

**How the boundary is obtained.** `pi.sendUserMessage` is fire-and-forget `void` (`agent-session.js:2020-2028`) that internally awaits the *whole turn* (`sendUserMessage` → `await this.prompt(...)`, `agent-session.js:1161`), and the handler's `ctx.sessionManager` is a `ReadonlySessionManager` — no `appendCustomEntry`, no `getChildren` (`extensions/types.d.ts:225`; the Pick list at `session-manager.d.ts:163`). So the id cannot be captured from the send, but `pi.appendEntry(customType, data)` **is** on the ExtensionAPI (`extensions/types.d.ts:985,1249`; wired to `sessionManager.appendCustomEntry` at `agent-session.js:2029`) and is synchronous. `recordInvocationBoundary` stamps `pi.appendEntry("council-invocation", { command, runId, at: Date.now() })`, then reads `ctx.sessionManager.getLeafId()` — append advances the leaf to the new entry, so the leaf id *is* the marker id. The injected user message then appends as the marker's **child**. Resolution is therefore deterministic at any later time, from entries alone: `boundary = entries.find(e => e.parentId === markerId && e.type === "message" && e.message.role === "user")`. The marker survives `/reload` and session restarts; the record's `firstEntryId` is the user-message id, not the marker id, so R-4 holds verbatim.

**Own-session half.** Pure branch walk mirroring `getBranch` semantics: build a byId map from `entries`, walk `parentId` from `leafId` to root, reverse, slice from the boundary (inclusive). The raw chain is walked deliberately — **not** `buildContextEntries`, which omits compacted-away entries (`session-manager.d.ts:150-158`); the card requires "pi counts all entries, including those compacted away". Per entry: `type:"message"` + `role:"assistant"` → accumulate `message.usage` (required on `AssistantMessage`, `pi-ai/dist/types.d.ts:308`), `turns++`; `role:"toolResult"` → accumulate optional `usage` (`types.d.ts:347`), no turn; `type:"compaction"` → accumulate optional `entry.usage` (`session-manager.d.ts:53`). Wire→record flattening reuses the EV-28 Q1 clause verbatim: `cost.{input,output,cacheRead,cacheWrite,total} → costInput…cost`, missing components coerce to 0, never `NaN`. Entries before the boundary contribute nothing.

**Subtree half — attended-run rootlessness reconciled.** Attended top-level manifests have `parentJobId === null` (`hub.ts:94` — the parent's hub is minted with no `parentJobPath`, `index.ts:161`), so there is no single root and `sumSubtree(manifests, "job-1")` covers one seat only. The rule: **eligible roots = manifests with `parentJobId === null && startedAt >= Date.parse(boundaryEntry.timestamp)`; the forest is each root closed over `parentJobId` descendants.** `startedAt` is `Date.now()` at spawn (`hub.ts:119`), and jobs spawn only after the boundary entry exists — same process clock, no skew. This one rule covers every shape: (i) attended `/council` — sibling top-level seats are all eligible roots; (ii) autonomous parent → runner → `job-1.x` — the runner `job-1` is a time-eligible root and its descendants (written by the child's hub with `parentJobPath` = its `COUNCIL_JOB_ID`, `child.ts:20`) close under it; (iii) multiple invocations in one session share a run dir (`initHubIdentity(mintRunId())` is per-**session**, `index.ts:161`) — the time filter excludes earlier invocations' jobs; (iv) the runner's own manifest is never double-counted because the record is computed from the parent, whose boundary predates it. Deliberate scope cut: a runner **child** computing a record for its own card gets a zero subtree under this rule (its jobs carry `parentJobId "job-N" ≠ null`); child-side exit reporting is EV-32's concern and would need an optional `rootJobId` param then — not now.

**R-4 label.** `formatBoundaryLabel` renders the exact literal `boundary=session=${sessionId} entries=${firstEntryId}..${lastEntryId} jobs=${jobCount}`. Structured fields ride the record so EV-31 persists provenance without re-parsing.

**Edge cases.** Zero dispatched jobs → eligible roots empty → subtree all-zeros, `jobs=0`, own-session intact. Pruned run dir → `readManifests` already returns `[]` for a missing dir (`runs.ts:102-108`) → same as zero jobs. Rotated session (boundary unresolvable: marker id absent, or marker has no user-message child — `switchSession`/`fork`/`navigateTree`, `extensions/types.d.ts:254-296`) → **all-zero record**, no throw; the label still renders with the ids as known. Legacy manifests without `usage` count in `jobCount` and contribute 0 per metric (same tolerance as `sumSubtree`, `runs.ts:196-198`).

**Call sites.** Land in EV-30: (1) `extensions/index.ts` command handler — stamp the marker in **both** TUI and headless branches (synchronous, so the TUI fire-and-forget contract at `index.ts:221-223` is untouched) before `sendUserMessage`. Deliberately untouched: `hub.ts` (stable per AGENTS.md 7), `runs.ts` (substrate unchanged), `navigator.ts`/`transcript.ts` (the parent session isn't a run-dir JSONL), and the exit-time compute/write/report sites — those are EV-31's store and EV-32's reporting.

### (c) Open questions for a ruling seat

1. **What is "a rotated session"?** No rotation concept exists in pi's current session API (zero hits for "rotate" in `session-manager`/`agent-session`). I read it as boundary-unresolvable (session switched/forked, or marker off-branch). The card says these resolve "to a zero subtree" — my design zeroes **both** halves (no boundary timestamp → the forest can't be time-scoped). If a ruling wants the subtree computed anyway from the run dir, the record's honesty claim changes. Ruling needed.
2. **Unresolved-boundary label form.** R-4 defines `entries=<firstId>..<lastId>` only for resolved ranges. Empty ids render `entries=..` — acceptable, or `entries=none`?
3. **Subtree `costBasis`/`usageSource` under mixed constituents** — latent until EV-29 lands "reported". My default: `catalogue-estimate` whenever any constituent is an estimate (conservative label). Does the ruling want that, or per-half basis lists?
4. **`branch_summary` usage** (`session-manager.d.ts:63-64`, same mechanism class as compaction): the card names assistant/tool-result/compaction only. Include or exclude?
5. **`total` on the record now** (serving EV-32) or EV-32's render concern?
6. **`turns` for tool-result/compaction usage**: assistant-messages-only (mirrors `hub.ts:197`), or pi's own counting? I propose assistant-only.

### (d) Rejected alternatives

1. **Extend `sumSubtree` / put the function in `runs.ts`** — wrong home (substrate vs. reconciliation) and `sumSubtree`'s `(manifests, rootId, metric)` shape can't return a full `Usage` or `jobCount`; cost is a breaking reshuffle of tested substrate code.
2. **`buildContextEntries`-based scoping** — silently drops compacted-away entries; contradicts the card's explicit "including those compacted away"; would undercount long compaction-heavy runs.
3. **Post-hoc "last user message on the branch" boundary (no marker)** — zero call-site change, but breaks on multiple invocations per session, dies on `/reload` (in-memory capture), and misidentifies the boundary after any follow-up user message. The marker costs one session entry.
4. **Awaiting `pi.sendUserMessage` to capture the entry id** — it's fire-and-forget void (`agent-session.js:2020-2028`) whose internal promise spans the whole turn (`agent-session.js:1161`); awaiting would violate the TUI handler contract (`index.ts:221-223`) and invert the headless teardown hazard documented at `index.ts:224-227`.
5. **Single-root `sumSubtree(manifests, "job-1")`** — valid only when a root exists; attended runs dispatch siblings with `parentJobId null` (`hub.ts:94`), so there is no root; the forest rule covers both shapes with one rule.

#### Position — `principal`

### 1. Cross-seam reading — what the contract actually is today

**The invoking session (the "own-session" side).** The procedure handler is `extensions/index.ts:215-236`; it injects via `pi.sendUserMessage(routed)` (`:222` tui fire-and-forget, `:228` headless). That call is typed `void` on the extension API (`pi-coding-agent/dist/core/extensions/types.d.ts:980-983`), and no event carries the appended entry id (`MessageStartEvent` carries only `message`, `types.d.ts:592-595`; `InputEvent` carries only text/source, `:657-676`). The live session is reachable as read-only `ctx.sessionManager` (`types.d.ts:218-219` → `ReadonlySessionManager`, `session-manager.d.ts:140`), whose `getEntries()` is `fileEntries.filter(e => e.type !== "session")` — raw append order, abandoned branches included (`session-manager.js:995-997`). pi's canonical usage enumeration is four kinds, not three: assistant `message.usage`, toolResult `message.usage`, and `branch_summary` / `compaction` `entry.usage` (`pi-coding-agent/dist/core/usage-totals.js:18-32`; `core/agent-session.js:2658-2700`). `Usage.cost.total` is computed client-side from catalogue rates (`pi-ai/dist/models.js:540-548`) — so "catalogue estimate" is correct for both halves today.

**The run directory (the "subtree" side).** `initHubIdentity(mintRunId())` runs once at parent `session_start` (`index.ts:161`) and is frozen into the hub singleton on first `getHub` (`hub-tools.ts:28-37`, created at `index.ts:163`) — `getHub` never re-reads the identity. Every dispatch writes into that one `runId` dir (`hub-tools.ts:163-164`, `dispatch.ts:99-108`). Manifests are written by `Hub.writeJobManifest` (`hub.ts:88-101`) with `parentJobId: this.run.parentJobPath ?? null` (`:94`) and `id` from `allocateId()` (`:83-86`) — so at top level every job is `job-N` with `parentJobId: null`. Nesting only exists because a hub-granted child re-inits with `parentJobPath = COUNCIL_JOB_ID` (`child.ts:24`). Persisted usage is assistant-stdout-only (`hub.ts:189-199`), stamped `usageSource: "stream-assistant"` (`hub.ts:138`), and only flushed at spawn/stall/timeout/settle (`hub.ts:96, :154, :181, :241`).

**The mismatch the premise hides (five, in order of blast radius):**

- **M1 — the run directory is session-scoped, not invocation-scoped.** `runId` is minted per parent session (`index.ts:161`), so two `/council` invocations in one session share one directory and one forest. The card says "the invocation's run directory / that invocation's job manifests"; no artifact carries an invocation marker (`RunManifest` fields, `runs.ts:42-57`), so the invocation's job set is not derivable from the manifests alone.
- **M2 — the boundary id is produced by nobody.** `sendUserMessage` returns `void` and no hook exposes the appended entry id. The card's "the boundary is the entry id of the user message the procedure injects" is an intent, not a seam that exists.
- **M3 — the two halves are on different accounting bases.** Own-session = session enumeration (4 kinds); subtree = per-manifest stream projection (assistant only). EV-28 diagnosed this exactly (`council/cards/EV-28.md:206`) and Q4 reserved `usageSource:'session-reconciled'` "for the session-enumeration half — EV-30's goal" (`EV-28.md:617-627`). A single `Usage.usageSource` (and `costBasis`) cannot be single-valued across both halves.
- **M4 — the reconciliation data for the subtree already exists and is unused.** `RunManifest.sessionId === job.id` (`hub.ts:96`), children spawn with `--session-dir <runDir> --session-id <jobId>` (`hub-tools.ts:184-185`, `seats.ts:517`), and `findSessionFile(repoRoot, runId, sessionId)` resolves them (`runs.ts:134-152`). Each subtree node's full session (toolResult + compaction usage) is one call away; the card narrowly scopes reconciliation to the invoking session.
- **M5 — the card's enumeration omits `branch_summary`**, diverging from the pi enumeration it cites as its model ("pi counts all entries").

Related cross-card fact for EV-31: seat sessions live *inside* `runDir` (`sessionDir: dir`), including a council-runner's own session — so exit point 5's invoking session does not survive `pruneRuns` the way EV-31's "not under the run directory" premise assumes.

The only named consumer of a run total today is prose — `council/procedures/council.md:336` (per-run token ceiling), unimplemented and filed as FLLWUP-26.

### 2. Blind spots, named separately

- **Engine/hub view:** sees stdout assistant `message_end` and its own job-id counter; cannot see that its `runId` is session-scoped (it treats `parentJobPath` as the only identity it has), that its manifests carry no boundary marker, or that its seat's own session JSONL holds strictly more usage than the tuple it persists.
- **Session-JSONL/data view:** sees all four usage kinds and a flat append order; cannot see that file order ≠ descendant order (a branch written after the boundary is not the invocation's), that the boundary has no in-file marker, or that `getEntries()` includes compacted-away *and* abandoned-branch entries.
- **Procedure/injection view:** holds `ctx.sessionManager` and could snapshot `getLeafId()` or `appendEntry` a marker (API at `types.d.ts:984-985`), but is written fire-and-forget (`index.ts:222, :228`); it cannot see that the "run total" it is told to track has no object behind it.
- **Consumer (EV-31/EV-32) view:** will be handed "the invocation's spend"; cannot see the subtree undercount or the session-scope hazard, because EV-30's acceptance supplies exactly the right manifest set.

### 3. Reframe

**The seam is right; the deliverable's boundary is drawn one step too far out.** EV-28's principal already established the stream-vs-enumeration split and EV-28's Q4 ruling reserved this card's half — so bridge-building is correct. But the card frames the answer as a pure function over two inputs with an acceptance test that *constructs* both inputs. That makes the boundary and the forest given by the fixture, so the test proves the arithmetic and never exercises the two things that are actually missing: **who supplies the boundary id, and what scopes the manifest set.** A `spend.ts` that sums whatever lists it is handed will be called by EV-32 with the session's run dir and will report the whole session's spend as one invocation's — the attended-case overcount — and will sum a session-reconciled half into a stream-projected half, the basis defect the epic exists to remove (`EPIC-7` / `EV-30.md` Intent).

Concretely, I would draw the card's boundary as: (a) the pure accounting function **takes the boundary explicitly and does the manifest filtering itself** (so scoping is inside the tested unit), and its fixture manifest set must contain a pre-boundary job that it excludes; (b) the injection site gains a boundary-capture leg, tested at least once end-to-end; (c) the subtree-basis question is decided and recorded in the card rather than left for EV-32.

The alternative seam I reject: "ship the pure summer, leave all wiring to EV-32." Its concrete cost is that EV-32's five exit points (two of which run in one shared session) each need the same unwritten scoping logic, and the durable record EV-31 writes fixes a wrong number on disk. Rejecting it costs one extra tested seam (index.ts) and one recorded ruling; accepting it costs a wrong durable number.

### 4. Testable claims

1. **Pre-boundary exclusion.** Fixture: session with boundary at entry `u2`; manifest set with `job-1` (`startedAt` < `u2.timestamp`) and `job-2` (`startedAt` >). Assert the record's subtree excludes `job-1`. A sum-all-manifests implementation fails.
2. **`branch_summary` inclusion.** Session fixture carrying one `branch_summary` entry with `usage`. Assert the own-session cost/tokens include it (against `usage-totals.js:31`). Literal reading of the card's enumeration fails.
3. **Two invocations, one run dir.** Drive two procedure injections in one session with dispatches after each. Assert invocation 2's subtree ≠ Σ over all manifests in the run dir. Any session-scoped sum fails.
4. **Basis expressibility.** Assert the record can carry `own.usageSource === "session-reconciled"` and `subtree.usageSource === "stream-assistant"` simultaneously — or that the chosen type makes this a compile error (which is the defect, not a pass).
5. **Boundary capture without content matching.** Invoke the same procedure command twice with identical `$ARGUMENTS` in one session; assert the second record's `firstId` is the second injected user entry, not the first. A content-prefix implementation fails.
6. **Zero/edge.** Pruned run dir → subtree all zeros, no throw; `getSessionFile() === undefined` (in-memory session) → own half zeros, no throw.
7. **R-4 label.** Assert the exact `boundary=session=<sessionId> entries=<firstId>..<lastId> jobs=<n>` string, with `sessionId` = the *invoking* session's id (not `RunManifest.sessionId`, which is a child id, `hub.ts:96`).

### 5. Open questions for a ruling seat

- **Q1 — shape:** one combined `Usage` for the record, or one per half? `usageSource` and `costBasis` are single-valued on `Usage` (`runs.ts:19, :34-35`) and cannot describe a reconciled own half plus a stream-projected subtree half.
- **Q2 — subtree basis:** stream-projected (today's manifests) or reconciled per node via `findSessionFile` (`runs.ts:134`)? If stream-projected, must the record state that its subtree half is a lower bound?
- **Q3 — scoping:** does the function filter manifests by boundary (time or id range), or does the caller pre-scope? The card's goal is silent and the manifests carry no invocation marker.
- **Q4 — `lastId`:** what fixes it — session leaf, last file entry, or an end marker? R-4 fixes `firstId..lastId` but the card's own-session rule ("entries at or after the boundary") has no end. Branches/abandoned entries make this load-bearing.
- **Q5 — `jobs=<n>`:** count of all nodes in the forest, or roots only?
- **Q6 — signature/location:** session *file path* (re-parse, per the card's wording) or live `ReadonlySessionManager` (cheaper boundary capture, but the card says JSONL)? And which module — `extensions/runs.ts` or a new one?
- **Q7 — exit point 5:** the runner's own session sits under the pruned run dir; does the record carry a session path EV-31 can rely on, or does EV-30 need to guarantee the file survives?
- **Q8 — `cacheWrite1h`:** the JSONL `cost.cacheWrite` folds the 1h premium (`models.js:540-548`) while the flat `Usage` has no `cacheWrite1h`; is the resulting own-half divergence from its own cost components acceptable pending FLLWUP-29?

I agree the card is the right bridge and that EV-28 explicitly reserved the `session-reconciled` member for it; my disagreement is only that its acceptance test, as written, cannot fail on the two facts (boundary capture, manifest scoping) that are actually unowned.
