## Intent

The user-visible surface is the inline progress transcript at the smallest
viewports, including the one-row case granted at termRows 7. Today the
view's follow mode scrolls to the last line of the whole flattened output,
so the single visible row is the tail of a wrapped body with no block
identity. This card makes the floor legible.

The one-row line reuses EV-34's composed tool-call head for the focused
block, with the failure token as a trailing suffix, rather than inventing a
parallel one-row rendering. The granted viewport is computed at the factory
and must not be exceeded; the count half is retained as a regression guard
alongside the content half.

Depends on EV-34 (composed head and failure token) and EV-35 (focus).

## Acceptance

- Over the pinned layout vectors for termRows 7, 8, 9 and 40, the rendered
  line count is at least one and never exceeds the granted viewport.
- At one row, the visible line identifies the active block — its composed
  head, not a wrapped body continuation.
- EV-7/EV-8/EV-9 suites stay green; render output adds no literal color.

## Approach

**What today's code actually does (verified, file:line):**

1. **The granted viewport is `computeProgressLayout(...).progressLines`** (`focus-nav.ts:106-131`), and the card's pinned vectors already exist as green assertions: `(7,5)→(tree 1, sep 0, progress 1)`, `(8,5)→(1,1,1)`, `(9,11)→(2,1,1)`, `(40,11)→(11,1,23)` (`test/ev9-progress.test.ts:128-137`). So "termRows 7/8/9" all grant **one** progress row.
2. **The count half is already true — but by two uncoordinated clamps.** `TranscriptView.render` slices to its constructor `viewportRows` (`navigator.ts:817`), and `renderProgress` slices again to the current grant (`navigator.ts:432`). The hazard: `ensureView` **ignores the grant for an existing view** (`navigator.ts:438` — `if (this.viewFor?.sessionId === sid) return this.viewFor.view`), so once a job lands mid-progress, tree rows grow, the grant shrinks, and the view's constructor `viewportRows` (set at `navigator.ts:445`) is stale-large. The stale tail-window's *first* `grant` lines survive the outer slice — so after tree growth, the one-row line is a mid-body line picked from the wrong window. This makes grant re-sync load-bearing, not cosmetic.
3. **The content half fails exactly as the card says.** In follow mode `topLine = all.length − viewportRows` (`navigator.ts:815`); at grant 1 the single visible line is the last flattened line — for a trailing user/assistant unit the body is *always* rendered (`navigator.ts:745-751`), and `bodyLines` wraps long text (`navigator.ts:703-708`), so the floor line is a wrapped continuation with no block identity.
4. **EV-34's composed head is directly reusable:** `unitLines` returns the head `→ <label>  <arg>` (warning) with the muted ` ✗` failure suffix as element 0 (`navigator.ts:708-724`), marker prepended *before* truncation so narrow widths can't eat the `▌`. EV-35's focus clamp already lives in `render` (`navigator.ts:796-797`) — render already reconciles `focused` as a side effect.

**The design I would write up:**

- **Which block, and `follow`:** the one-row line is *always the focused unit's composed head* (element 0 of `unitLines(u, i, width, isFocused=true)`), satisfying R-COPY verbatim with no parallel one-row copy. To make "focused" honest in follow mode, `render` pins `this.focused = vis.length − 1` **only when the effective viewport is 1 and follow is on** — follow means "watching the live tail", so at a one-row floor the newest unit *is* the active block. Precedent for render-side focused reconciliation is the existing clamp at `navigator.ts:796-797`. Non-follow shows the user's chosen unit (up/down/g/G all set `follow=false`, `navigator.ts:757-777`). Empty transcript at grant 1 returns the existing dim placeholder (`(waiting for output · idle)` / `(no transcript)`), never `[]`, never the header.
- **Which layer owns the clamp:** `computeProgressLayout` stays the sole pure grantor; `renderProgress` becomes the *grant applier* — it propagates the current grant into the live view each render (a `setViewportRows(n)` mutator; the view has no line cache, so this is one field), fixing the stale-viewport hazard from tree growth. `view.render(width).slice(0, layout.progressLines)` at `navigator.ts:432` is **retained** as the count regression guard. The modal path (`openTranscript`, viewport `termRows−4 ≥ 6`) never reaches 1 and is untouched.
- **Floor-path width safety:** the one-row line is `truncateToWidth`'d (mirroring the toolCall head's own truncation at `navigator.ts:723-724`), because single-unit heads are deliberately untruncated today (`navigator.ts:722`).

## Tradeoffs accepted

- **Follow state is invisible at the floor** — the header carrying the `f follow(on)` suffix is `all[0]` and a one-row viewport can never show it. Accepted: the visible block snapping on arrow keys is the feedback; fixing that would need floor-specific chrome, which is a new surface.
- **Grant 2 (termRows 9 with one job) keeps the tail-window defect** — two wrapped continuation lines, no head identity. The acceptance pins only one row; extending unit-anchoring to viewport ≥ 2 would churn the pinned `(12,8)→(3,1,3)`, `(24,8)→(8,1,10)`, `(40,11)→(11,1,23)` vectors and EV-7/8/9 suites for no acceptance gain.
- **Focused-pin in follow mode is scoped to viewport 1**, so at taller viewports the `▌` can still scroll out of sight in follow mode — a pre-existing EV-35 asymmetry I deliberately do not "fix" here.
- **What I would NOT do:** no parallel one-row renderer or new copy (R-COPY); no unit-anchored window at viewport ≥ 2; no EV-35 key/marker/keymap changes; no literal ANSI/hex (AGENTS.md 9.6 — the line comes from `unitLines`, tokens only); no `hub.ts`, `transcript.ts`, modal-path, or layout-constant changes; no lowering of `PROGRESS_*` floors to make a count assert easier.
- **Residual risks:** `termRowsCap` staleness on mid-session terminal resize is pre-existing EV-9 capture-once semantics, out of scope; tree-row count is monotone within a run (manifests are only pruned at `session_start`), which is why the stale-viewport hazard is a shrink-only, growth-triggered bug.

## Cross-seam reading

**What the contract actually is today (four owners, not one):**

| Layer | Owns | Evidence |
|---|---|---|
| `focus-nav.computeProgressLayout(termRows, treeContentLines)` | the *split*: `avail = termRows-5`, then `treeLines/sepLines/progressLines`, with `progressLines >= 1` | `extensions/focus-nav.ts:104-120`; pinned pairs at `test/ev9-progress.test.ts:127-137` |
| `CouncilTreeWidget` | the *capture* (`termRowsCap` from `tui.terminal.rows`, once, in the factory) and the *final slice* | `extensions/navigator.ts:561-570`, `:388`, `:428-433` |
| `TranscriptView` | the *window* (`viewportRows` constructor-only; `follow` → `all.slice(maxTop, maxTop+vp)`) | `navigator.ts:628`, `:799-817` |
| `TreeFocusState` + editor routing | the *focus subject* (`focused` in the view; `surface` in the controller) | `navigator.ts:618-620`, `:766-779`, `:796-798`; `focus-nav.ts:188-199` |

Three facts the card's framing does not have:

1. **The grant is recomputed every render but never re-granted to the cached view.** `renderProgress` computes `layout` fresh (`:428`) and passes `layout.progressLines` to `ensureView` (`:431`), but `ensureView` returns the cached view when the sessionId matches and *ignores the argument* (`:437-440`). `view.viewportRows` is frozen at first construction (`:445`, field at `:628`). The widget's `slice(0, layout.progressLines)` (`:432`) masks this for the **count** half and does nothing for the **window**.
2. **The grant changes without any resize**, via EV-9's own O5 path. `computeProgressLayout(9, 1) = {avail 4, tree 1, sep 1, progress 2}` (`focus-nav.ts:105-110`); a second job lands mid-progress → `refresh()` (`navigator.ts:448-455`) → `computeProgressLayout(9, 2) = {tree 2, sep 1, progress 1}`. The grant drops 2 → 1 on a **cached** view whose `viewportRows` is still 2, so the single visible line is `all.slice(maxTop, maxTop+2)[0]` (`:814-817`) — a mid-body continuation. This is exactly the card's red state, reachable on a termRows **9** vector, and invisible to a test that pins `(termRows, treeContentLines)` once at open.
3. **"The granted viewport" is two quantities.** `avail` is the widget's budget; `progressLines` is the transcript's grant. The card asserts "the transcript's rendered line count" against "the granted viewport" — the spec must name both and assert both (today both hold; D8 already recorded the count half as a tautology retained as a guard).

**Subject disambiguation.** `focused` starts at 0 and is only mutated in `handleInput` (`:766-779`) — `poll()`/`render()` never advance it. So with `follow === true` (the default, `:620`) the *focused* unit is unit 0 while the *active* unit is `vis.length-1`. The card says "active block" in the goal and "the focused block" in the Intent/R-COPY; D9 ruled the mechanism on the focused block, and the card's own step-1 record names this as the open question. It is the load-bearing ambiguity: taken verbatim, "focused" makes the one-row floor show the **oldest** unit's head.

## Blind spots, named separately

- **Data/import side (`transcript.ts`, EV-33).** Cannot see that `visible()` filters thinking (`navigator.ts:679-684`), so "the active block" changes under the `t` toggle; cannot see that `firstArgOf` is untruncated here while the tree row truncates to 30 (`navigator.ts:238`) — the same event renders two different lengths two rows apart.
- **Render path (`TranscriptView`).** From inside the view the grant *is* a constructor constant; it cannot see that its caller re-slices, nor that its caller's grant moved. This is precisely how the frozen-grant divergence hides — the view's `maxTop` is consistent with its own stale `viewportRows`.
- **Layout (`focus-nav`).** `computeProgressLayout` is pure in `(termRows, treeContentLines)`; it guarantees `progressLines >= 1` about the *budget* and is silent about the *window* that consumes it. A caller can honour the budget and still show a body tail.
- **Editor/routing (`focus-nav` kernel).** Sees `surface` and consumes `up/down/e/t/f/g/G` without knowing whether they change a rendered line; at a 1-row grant, `routeEditorFocus` reports `up/down` as meaningful today only because follow-off shows `all[0]` (the header) at `focused: 0` (`:813-816`).
- **Widget factory.** Sees `tui` once, so from inside it the terminal never resizes; the modal path in the same file re-reads `tui.terminal.rows` per render (`:827`). Two surfaces, two capture policies, one file.
- **The acceptance itself.** A per-vector test built at fixed `(termRows, treeContentLines)` with one render will pass while the frozen-grant path (§2 above) stays red, because the count half is satisfied either way.

## Reframe

**Two nouns, not the mechanism.** The design is sound; I agree with R-COPY and D9 — reuse the EV-34 composed head (`unitLines`' toolCall head, `navigator.ts:699-708`, `✗` at `:706`), no parallel one-row renderer, token-only. Do not relitigate it. The reframe is:

1. **Replace "the granted viewport is computed at the factory" with "the grant is a per-render parameter with one owner and two consumers."** The widget computes `layout` per render and passes `layout.progressLines` into the view's *render* (e.g. `render(width, viewportRows = this.viewportRows)` or a `setViewportRows` call in `ensureView`), so the window and the one-row projection key on the **current** grant. Keep `slice(0, layout.progressLines)` (`:432`) untouched as the redundant count guard. Without this, the projection's `vp === 1` trigger is wrong on the termRows-9 transition and on any resize.
2. **Replace "the focused block" with "the active unit" = `follow ? vis[vis.length-1] : vis[fv]`**, read `focused`-only, never written back (EV-35 Q5 forbids cursor-stability work). Then the one-row line tracks what the user is watching under follow and what `e`/`t` act on when follow is off, and the marker stays honest: `isFocused` remains the same `vi === fv` expression (`:709`), so a fresh follow-on view at one row shows no `▌`, and `G`/`down` make the identity line navigable at the floor.
3. **The projection belongs in `TranscriptView.render`, not in `renderProgress`** — one renderer, T11 parity by construction (`test/ev9-progress.test.ts:309-320`), and the `vis.length === 0` case falls through to the existing empty-state line (`:797-798`).
4. **"Pinned layout vectors" are `(termRows, treeContentLines)` pairs, asserted against `computeProgressLayout`, never against literals.** D7 already proved a bare termRows number is false: `(40,11) → 23` vs `(40,1) → 31` (`vault/raw/2026-09-15-po-epic8-ruling.md:113-126`). Reuse the existing pair convention at `test/ev9-progress.test.ts:127-137`.

**Scope boundary to record explicitly:** EV-36 does **not** pin the header; at a 1-row grant the header cannot be the single line. FLLWUP-37 stays `Backlog` (its retirement condition — "retires for free if EV-36 consumes the overflow case" — must be a deliberate human/steward call, not an incidental consequence of this card).

**Design position**

The one-row line must be the focused unit's composed head with the `▌` marker at column 0 and the `muted "✗"` failure suffix where applicable — and only that line. Concretely: `TranscriptView.render` gains a `viewportRows === 1` branch that anchors the slice on `focusLine = starts[focused]` (the focused unit's head line in `all`) and ignores `follow`, which is meaningless at this size. The count half is already satisfied by `computeProgressLayout` (`progressLines ≥ 1` at `termRows ≥ 7`) and the factory's existing outer `slice(0, layout.progressLines)` at `navigator.ts:431`. Two halves, two functions, no overlap. R-COPY (binding) is honored: the one-row line *is* the EV-34 composed head for the focused block; no parallel one-row surface. R-MARKER is honored: `▌` is `TREE_ROW_MARKER`, the same constant the tree rows and `unitLines` already read.

**Gulf closed**

**Evaluation gulf, at the moment of "which block am I on?" on a one-row terminal.** Today the slice lands on the last wrapped body line of the transcript (`topLine = maxTop` in follow mode); the operator sees a string of text that names no tool, no arg, no success/failure, no block identity. The interface refuses to lie about what is visible — a forcing function. Cost: widening the terminal is the only way to see the body.

**Principle and evidence**

- **Mapping, single source.** Focused unit ↔ head line ↔ visible row at one line is one expression: `focused` (visible index) → `starts[focused]` (head line index in `all`) → `all[starts[focused]]`. All three are computed in the same `render` pass; no off-screen state can drift. Apply at `extensions/navigator.ts:813–817`.
- **Signifier reuse by construction.** `▌` is the same `TREE_ROW_MARKER = "\u258C"` constant the tree rows read (`navigator.ts:415`, `focus-nav.ts:38`) and `unitLines` reads (`navigator.ts:705`). R-MARKER binding.
- **Count is the layout function's contract.** `computeProgressLayout(7,·) === {avail:2, sepLines:0, treeLines:1, progressLines:1}` (`extensions/focus-nav.ts:103`); the factory's `slice(0, layout.progressLines)` is the runtime clamp. The card's acceptance bullet "never exceeds the granted viewport" is satisfied at this slice; the regression guard is a pure-seam assertion that `view.render(width).length ≤ viewportRows`.
- **Token-only.** Composed head uses `warning` (R-COPY); `✗` uses `muted`; marker uses `accent` — all on the documented palette. AGENTS.md 9.6 binding. `test/theme-compliance.test.ts` stays green.
