## Intent

The disposition must be a pure, testable function, not a prose rule. This card
ships `decideFollowup(answers, policy)`, returning `File`, `Merge`, or `Drop`
with a deterministic basis. Its fail-safe direction is inverted from the card
gate's: where a failed card-gate call resolves to the full Deliberate panel, an
unanswered or unsure follow-up answer resolves to `File` — the human-facing
side — so `Drop` and `Merge` are unreachable on unsure input. Precedence is
pinned: floors, then overrides, then the weighted composite, so a destructive
disposition can never land on an answer the model itself called unsure.

## Acceptance

- The function lives in one module, performs no fs/network/model call, and is
  asserted pure by two identical calls yielding byte-identical results.
- Precedence is pinned as floors → overrides → composite: any unanswered
  weighted question or below-floor answer returns `File` before any override is
  evaluated, so `Merge`/`Drop` are unreachable on those inputs; the fixed
  fixture set includes a firing override whose answer is below its floor and
  asserts `File` (a gated rule, not a dead one).
- A test asserts only `File`, `Merge`, `Drop` are returnable.
- A hard-override rule fires `Merge` (or `Drop`) deterministically on a
  confident answer in declared order; a test pins the order.
- Basis lines are single-line and byte-stable (fixed two-decimal formatting
  where a number is rendered); a snapshot test pins them.
- The repo's typecheck, the full test suite, `python3 council/validate.py`, and
  the repo's preflight pass.

**Signature and answer-shape types.**

```ts
export interface FollowupDecision {
	disposition: FollowupDisposition;
	basis: string;
}
export function decideFollowup(
	answers: Record<string, GateAnswer | null>,
	policy: FollowupDecisionPolicy,
): FollowupDecision;
```

Reuse `GateAnswer` (`{ type: string } & Record<string, unknown>` from `gate-ledger.ts`), exactly as `decide()` does, with runtime fail-loud validation naming the question id — ledger/re-derivation symmetry (`rederiveResolvedMode`-style `DecideFn` seam, gate-ledger.ts:226), no parallel type. The followup admits only `choice`/`noul` (`FOLLOWUP_QUESTION_TYPES`). A **`score` answer throws naming the id** — the followup policy has no `score` floor, so a score answer is unfloorable and R4 forbids proceeding on unfloored input; same for unknown types, missing `confidence` on choice, missing/`[0,1]`-violating `probability` on noul — each throws `followup: decideFollowup — answer <id> ...`.

**Precedence implementation (R4), each with its basis grammar** (single-line-ness and byte-stability *inherited*: interpolated strings are loader-validated single-line — `basisSafeString`, gate.ts:649 — numbers via private `fmt`, `toFixed(2)`):

1. **Floors + noul threshold + unanswered, first.** Iterate `Object.keys(answers)` order (deterministic, first failure wins): weighted question, answer `null` **or key absent** → `{ "File", "<id>: unanswered" }` — R4's sentence made literal; the gate skips nulls and lets 0-contribution drag, the followup hard-returns. An unweighted id's null is skipped (R4's letter says *weighted*; open point #3). `choice`: missing/non-numeric confidence → throw; `confidence < policy.floors.choice` → File, basis `"<id>: confidence X.XX < choice floor X.XX"`. `noul`: `p = sideProbability(...)`; `certainty = Math.max(p, 1-p) < policy.noulThreshold` → File, basis `"<id>: certainty X.XX < noul threshold X.XX"`.
2. **Overrides second, in declared order.** Answer absent → no fire. Fire test mirrors `overrideFires` minus `score`: choice `answer.value === option`; noul `sideProbability(id, option) > 0.5` — fired on the answer itself. On fire: `{ rule.disposition, "<id>? <option> (<rule.basis>) → <Disposition>" }` — the `→ <Disposition>` tail is the one grammar element the gate lacks; exact bytes pinned by snapshot, **open point #2** on the arrow glyph.
3. **Composite third.** `composite = Σ weights[id] * sideProbability(answer, countedOption[id])` over `Object.keys(policy.weights)` — raw sum, no normalization. Walk: `>= thresholds.drop` → Drop, basis `"composite X.XX ≥ drop threshold X.XX"`; `>= thresholds.merge` → Merge, basis `"composite X.XX ≥ merge threshold X.XX"`; else → File, basis `"composite X.XX < merge threshold X.XX"`. Drop checked before merge because strict `merge < drop` is loader-pinned.

**Fixture/test plan — `test/ev79-followup-decide.test.ts`** (offline, packaged data via `loadFollowupDecision` on a nonexistent repo root, tmpdir repos for loader-written fixtures, `bun:test`): (1) each disposition on packaged data, basis `toBe`-asserted; (2) fail-safe arm A (choice floor) with remaining answers composed so the composite alone would have said Merge — proves precedence, not just outcome; (3) fail-safe arm B (noul threshold) with `duplicate noul(0.55)` — certainty 0.55 < 0.60 → File despite `P(yes)=0.55 > 0.5` meaning the duplicate override *would* fire — half the carve-out; (4) unanswered weighted (`duplicate: null` with the remaining two summing to 1.40) plus key-absent variant; (5) the R4 carve-out on both floored types — `alreadyDone noul(0.55)` (Drop override fires on its own merits, below threshold → File) and `duplicate choice("yes", conf 0.4)` (Merge override would fire, confidence 0.40 < 0.60 → File), File + floor basis byte-exact; (6) override ordering pin — confident `duplicate yes` AND `alreadyDone yes` simultaneously → first declared rule wins (packaged: `alreadyDone` → Drop); (7) composite band walk on a tmpdir repo-local fixture (`overrides: []`, tuned thresholds) pinning exact-`==`-merge → Merge, exact-`==`-drop → Drop, one tick below each → lower band — **necessary because of the finding below**; (8) vocabulary-only-returnable — matrix-wide `disposition ∈ FOLLOWUP_DISPOSITIONS` plus the union is exactly `{File, Merge, Drop}`, plus a static typed-assignment assertion; (9) purity — two calls → whole-result `JSON.stringify` equality for every fixture; (10) fail-loud runtime arms — `score` answer, unknown type, missing choice confidence, missing/invalid noul probability, each throwing naming the id.

**Finding handed forward.** On the packaged policy, **the composite's Drop band is empty**: a noul answer needs certainty ≥ 0.60 to pass the floor, and firing the duplicate/alreadyDone overrides needs P(yes) > 0.5 — the on-floor, non-firing noul maximum for a yes-counted question is P=0.4 (certainty 0.6), so max non-override composite is 0.4 + 0.4 + 1.0 = 1.8 < 2.0. Every packaged-data Drop comes from an override. Consistent (thresholds are tuning data), but test 7's band walk **must** run on a tmpdir fixture, and the packaged `thresholds.drop: 2.0` is only meaningful post-tuning.

**Tradeoffs accepted:** colocation over extraction (gate.ts grows past ~1100 lines, carries two domains); loose `GateAnswer` reuse over a strict discriminated union (ledger symmetry; shape safety bought at runtime); composite-Drop tested on a local fixture, not packaged data.

**Open points handed forward:** (1) to the principal — gate.ts sibling vs. extraction (owner's position: sibling, extract-at-EV-80 if wanted); whether packaged `thresholds.drop: 2.0` should be retuned in this card or left as declared tuning data (owner: left); (2) to the skeptic — exact override-basis bytes `<id>? <option> (<basis>) → <Disposition>` and whether the `→` glyph is acceptable or should be `:` / `->`; (3) to the skeptic — unweighted-question nulls: R4's letter covers *weighted*; owner proposes skip-and-contribute-nothing, matching `decide()`; if the ruling intent was "any asked-but-unanswered question", the arm must widen.

### Round 1 — principal (first pass, job-4.2)

**Cross-seam reading.** The function sits between EV-81's transport answers and EV-81/EV-82's ledger+render — the exact seam the card gate's `decide()`/`gate-run.ts` already occupies, mirrored into the followup domain. EV-81 parses the decisions response, filters to known question ids (the `knownIds` pattern in `extensions/gate-run.ts`), and calls `decideFollowup(answers, policy)` with `Record<string, GateAnswer | null>` — the same transport-verbatim answer type the ledger stores (`gate-ledger.ts:45`) and that `decide()` takes. Reusing `GateAnswer` is what lets a recorded followup line re-derive through the same `DecideFn` seam. EV-79 must ship the return type now: `FollowupDecision { disposition: FollowupDisposition; basis: string }` + the same signature. EV-80 does **not** need a decided type (packer runs before the decision). EV-81 **does**: it returns `FollowupDecision`, writes `resolvedMode = disposition` + `basis` into the v2 call line. EV-82: `decisionLine` renders `Mode: <disposition> — <basis>` unchanged — the ledger's `resolvedMode` is "stored as a string so the ledger never couples to the mode vocabulary's evolution," and `resolveRoute` (`gate-route.ts`) keys matches on `stateHash` and filters `GATE_DECISION_MODES.includes(resolvedMode)`, so followup lines cannot pollute card routing as long as EV-80's hash is over followup state. No `include`/panel field — adding one is false symmetry with `GateDecision`.

**The load-bearing inversion the card does not spell out.** `decide()`'s floor phase iterates `Object.keys(answers)` and `if (!answer) continue` (`gate.ts:937`). That loop **structurally cannot detect an unanswered weighted question** — the unanswered id is absent from `answers`. R4 requires the followup to return `File` on unanswered, so phase 1 must iterate `Object.keys(policy.weights)`, treating absent/`undefined`/`null` as unanswered → `File`, *before* any override is evaluated. A faithful arm-for-arm mirror of `decide()` produces a dead fail-safe. This is the single most important thing this seam reading contributes.

**Module placement: `extensions/gate.ts`, next to `decide()`.** `sideProbability` and `overrideFires` (`gate.ts:868,884`) and `fmt` (`gate.ts:860`) are module-private; `FollowupDecisionPolicy` and `FOLLOWUP_DISPOSITIONS` already live there. A sibling module forces duplicating the noul-side/override-firing mechanics or exporting private helpers — a second source of truth for one mechanic. Purity is *behavioral* (two identical calls → byte-identical output), not statically provable — the shipped precedent (`test/gate-decide.test.ts`). If the owner instead chooses a separate module for a static fs-free proof, that trades a real type/helper dependency for a static assertion; name the trade, don't drift into it.

**Basis grammar (owner byte-pins).** Mirror `decide()`'s shapes, reuse `fmt`: `"<id>: unanswered"`; `"<id>: confidence <c> < choice floor <f>"`; `"<id>: certainty <c> < noul threshold <t>"`; override fires `"<question>? <option> (<basis>)"`; composite Drop `"composite <c> ≥ drop threshold <d>"`; composite Merge `"composite <c> ≥ merge threshold <m>"`; composite File `"composite <c> < merge threshold <m>"`. Single-line is guaranteed because EV-78 already refuses newlines in the three interpolated override strings (`basisSafeString`, `gate.ts:805`) and `fmt` never emits one.

**What EV-78 deliberately does not validate, and how EV-79 relates.** EV-78 validates each file independently; it does not check questions↔weights, `noulProbabilityOf` ∈ criteria, or override `option` ∈ criteria (EV-78 record, settled point 9). `decideFollowup(answers, policy)` takes no question set, so it **must tolerate** those gaps and cannot fail on them: a weight id with no question → always absent from `answers` → `File` (fail-safe by construction); an answer id not in `weights` → ignored (iterate `policy.weights` for phases 1 and 3, do not floor-check unweighted answers — unlike `decide()`, which floors every present answer); an override `option` absent from the question's criteria → cannot fire (`sideProbability` returns 0) → a gated-but-inert rule, not a crash. Conversely, a **malformed answer shape** (unknown `type`, missing numeric `confidence`/`probability`) should **throw naming the question**, not return `File`: `File` is a legitimate recorded decision, whereas a malformed answer is a defect EV-81's invalid-response catch-all converts to `gate call failed: …` → human. The noul-threshold arm returning `File` should be stated explicitly — the card says "below its confidence floor," and `noul` carries no confidence; R4's "confidence floors and the noul threshold first" is the binding text.

**Blind spots.** Owner (inside `gate.ts`) most likely to mirror `decide()` faithfully — which encodes the wrong loop (`Object.keys(answers)`), leaving the unanswered fail-safe unreachable. Skeptic will test each arm and the carve-out but cannot see the *contract* to EV-81/EV-82. PO/consolidator cannot see that the cross-file questions↔weights referential flag left "for EV-79's caller" has **no named owner on any of EV-79/80/81/82/83** — EV-79 is pure and cannot check it; EV-80 loads no decision policy; EV-81 imports constants only. The residual is real, named, and currently unowned.

**Reframe.** The proposed design is sound; no reframe needed. Two implicit decisions should be made explicit and pinned by test: (1) phase 1 iterates `policy.weights` (the unanswered detection), and (2) the noul-threshold arm returns `File`. One open point to hand forward: **the questions↔weights check has no named home** — decide it fails loud at the loader-composition site (EV-81/EV-82 wiring) and record that home on the card, or accept "a misconfigured weight always Files" as the documented safe behavior. Do not add it to `decideFollowup`.

**Testable claims:** (1) `decideFollowup({}, policyWithWeights)` returns `{"File", "<first-weight-id>: unanswered"}` — the unanswered arm is reachable and names the first declared weight id. (2) Two `answers` objects with identical key/value pairs inserted in different order produce byte-identical `basis` — basis order pinned to `policy.weights` key order, not answer insertion order. (3) noul 0.55 vs threshold 0.6 → File even when the `alreadyDone?yes` override fires — the R4 carve-out fixture. (4) An answer id absent from `policy.weights`, holding `{type:"nonsense"}`, does not throw and does not change the composite or the basis — unweighted answers are ignored. (5) A weight id absent from `answers` and one present as `null` both produce the same File/unanswered result — absent and null are one state. (6) A `choice` answer missing `confidence`, and a `noul` answer missing `probability`, each throw naming the question id. (7) Two overrides that both fire return the first in declared order. (8) Every `disposition` ∈ `FOLLOWUP_DISPOSITIONS` across the full fixture set; two calls byte-identical. (9) An unweighted id never contributes to the composite. (10) Placing `decideFollowup` in `gate.ts` keeps existing gate byte-behaviors green; any `sideProbability`/`overrideFires` refactor leaves every existing `decide()` basis string unchanged.
