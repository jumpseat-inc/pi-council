## Intent

The existing run directory is ephemeral telemetry — self-gitignored and pruned
to the last 15 runs at every parent `session_start` — so a usage record stored
there would be silently lost. This card writes a durable record that outlives
that prune. The council's answer to the human's traceability question is
embodied here: the record names the session JSONL path and the entry range it
was derived from, and read-back resolves that pointer to the surviving session
file, which is not under the run directory and therefore survives pruning. The
store lives at `getAgentDir()/council/usage/`, the durable council-state home
that already carries the 0600 atomic-write precedent; the human's proposed
`~/.pi-council` top-level home is not used. A person inspects the directory
directly, so it must be recognisable by naming and must state its empty and
unwritable behaviour.

## Acceptance

- A completed invocation's record is written, the run directory is then removed,
  and the record still reads back with its provenance pointer resolving to the
  surviving session file.
- The record names the session path and the entry range.
- `pruneRuns(repoRoot, 0)` does not remove the record.
- `bun test`, `bunx tsc --noEmit`, `python3 council/validate.py` stay green.

## Phase 1 rulings (features-deliver, binding for this run)

- **R-3 store** — the durable store is `getAgentDir()/council/usage/`;
  record files are named `<ISO-basic>_<runId>_<command>.json`; the directory
  carries a `README.md` naming the format; directory mode `0700`, file mode

## Owner — EV-31 first pass (design position)

### Approach

EV-31 is a small, honest persistence layer behind the already-settled EV-30 seam: a new module `extensions/usage-store.ts` (the I/O sibling of the pure `spend.ts`, following the `extensions/mcp/auth-store.ts` pattern — `getAgentDir()/council/usage/`, atomic tmp+rename, 0600 files, 0700 dir, README) that wraps a `SpendRecord` verbatim with a store-side provenance pointer and basis stamps, writes once per invocation, and offers a read-back that resolves the pointer against the surviving invoking-session JSONL. The invoking session's path comes from `ctx.sessionManager.getSessionFile()` (public on `ReadonlySessionManager`, `session-manager.d.ts:140`) — the file lives in pi's session dir (`~/.pi/agent/sessions/<encoded-cwd>/…`), not the run dir, so it survives `pruneRuns` by construction (wiki: [[run-transcripts]]). The write trigger is invocation completion at the earliest of forest-settle (hub `onChange`) or `session_shutdown` sweep — choose-once per marker, never recomputed.

**Stored record shape** (wraps, never mutates, the EV-30 record — ruling item 6: basis belongs store-side):

```ts
// extensions/usage-store.ts
export interface UsageProvenance {
  sessionId: string;
  sessionPath: string | null;     // absolute; null = unresolvable at write (never fabricated)
  firstEntryId: string | null;    // from SpendBoundary
  lastEntryId: string | null;
  boundaryResolved: boolean;      // mirrors SpendBoundary.resolved
  pointerStatus: "ok" | "no-session-file";
}
export interface StoredUsageRecord {
  spend: SpendRecord;             // EV-30 record byte-verbatim
  provenance: UsageProvenance;
  runId: string; command: string; repoRoot: string;
  writtenAt: string;              // ISO-8601 — the ruling-item-6 basis stamp
  basis: { trigger: "forest-settle" | "session-shutdown"; manifestsObserved: number };
}
export function defaultUsageStoreRoot(): string;              // getAgentDir()/council/usage
export function usageRecordName(writtenAtMs: number, runId: string, command: string): string;
export function persistInvocationUsage(storeRoot: string, input: {
  spend: SpendRecord; sessionId: string; sessionPath: string | null;
  runId: string; command: string; repoRoot: string;
  trigger: "forest-settle" | "session-shutdown"; manifestsObserved: number;
  now?: () => number;   // injectable clock, for the monotonic-write-clock test
}): { file: string; record: StoredUsageRecord };
export function readUsageRecords(storeRoot: string): StoredUsageRecord[]; // corrupt → skip (readManifests precedent)
export function resolveProvenance(pointer: UsageProvenance):
  { status: "ok" | "session-missing" | "range-missing"; sessionPath: string | null };
```

**Filename** (R-3, byte-exact): `<ISO-basic>_<runId>_<command>.json` where ISO-basic = `toISOString()` collapsed to `YYYYMMDDThhmmssSSS` (milliseconds kept — ISO 8601 basic permits fractional seconds; they're the collision margin). `runId` is already filename-safe (`mintRunId`), commands are `[a-z-]`. `README.md` names the format, is written non-clobberingly at first use at 0644 (a human-readable doc, deliberately not 0600; record files are 0600, dir 0700 via `mkdirSync` + explicit `chmodSync` so the mode holds regardless of umask).

**Write path**: index.ts's procedure handler already stamps the marker (`index.ts:227`) and today discards the returned id — EV-31 keeps it in a per-session pending ledger `{command, markerId, runId, sessionFile}`. On each hub change, for each pending invocation whose forest (point-in-time filter over `readManifests`) is fully settled → compute `spendRecord` at that moment, persist once, mark done. On `session_shutdown`, sweep every still-pending marker (loop `findLatestInvocationMarker`, chopping the scanned tail per marker), same path. In-memory choose-once set keyed on `markerId`; a filename-key collision (only possible as a genuine double-write given the monotonic clock below) **throws and is caught per-record** in the sweep — reported via `notify`/`console.error`, never crashes teardown, never overwrites, never skips silently.

**Read-back / provenance resolution**: `resolveProvenance` parses `pointer.sessionPath` with pi's exported `parseSessionEntries` (already the test-fixture substrate in `test/spend.test.ts:93`) and asserts both `firstEntryId` and `lastEntryId` exist among entry ids. Entry ids are stable under append and compaction (append-only JSONL; `appendCompaction` re-parents, never rewrites), so a file that grows after the write still resolves. Missing file → `session-missing`; ids absent → `range-missing`.

### The three required decisions

1. **Seat session file already pruned at write time.** The pointer never targets seat sessions — they live under the run dir (`hub-tools.ts` spawns children with `sessionDir: dir`), their usage is already folded into the exit-time `subtree` sum, and the card's provenance pointer is the *invoking* session. If the run dir is pruned before the write, `spendRecord` already degrades to subtree-zero (`test/spend.test.ts` T4) and EV-31 persists that record unchanged — **never recomputing** — with `basis.manifestsObserved` and `trigger` stamped so a reader sees the moment and its horizon. No recompute basis beyond that stamp exists because EV-31 never recomputes (ruling item 6).

2. **Compute time on the store key.** The key carries R-3's ISO-basic write timestamp only; the compute-time/basis honesty lives **inside** the record (`writtenAt`, `basis.trigger`, `basis.manifestsObserved`). One twist the R-3 name forces: a shutdown sweep can emit several same-`(runId, command)` records within one `Date.now()` millisecond, so the sweep uses a **monotonic store-side write clock** (`writtenAt = max(now, prev + 1)` — injectable `now` makes this testable). Each stamp is "at or within this millisecond", documented in the README.

3. **No invoking-session JSONL resolvable** (`getSessionFile() === undefined`, e.g. in-memory sessions). Write anyway with `sessionPath: null`, `pointerStatus: "no-session-file"`. Rationale: EV-30's fail-closed precedent applies to *values*, not existence — silently dropping the write would lose the invocation's very record (the eval-store lesson: "silent loss makes the ledger less honest, not more", wiki [[eval-store-contract]]), and EV-32's R-5 demands explicit states over blanks. Never fabricate a path, never skip silently. Same rule for an unresolved boundary: zero-half record with `boundaryResolved: false` is persisted.

### Edge cases

- Two invocations of the same command in one session share the hub `runId` → distinct markers, distinct records; the monotonic clock is what keeps their R-3 keys distinct in a same-ms sweep.
- Headless teardown mid-forest: the shutdown sweep persists with whatever settled; `basis.trigger: "session-shutdown"` says so. A hard crash persists nothing — honest.
- Corrupt/partial record on read → skipped (`readManifests` precedent); `resolveProvenance` on a corrupt session file → `range-missing`/`session-missing`, never a throw.
- Retention: the store grows unboundedly by design (durable = not pruned); a retention/compaction card is explicitly *forward*, not in EV-31's scope.

### Tradeoffs accepted

- **Forest-settle exit undercounts the parent's post-settle tail**: the record's own-session range stops at the leaf at compute time. Accepted because the basis stamp makes the range explicit (the human's traceability question is answered by the pointer, not by implied completeness), and the alternative — write only at session end — starves EV-32's command-exit blocks of a store record to read.
- **Wiring (ledger + hub onChange + sweep) rides in this card**, slightly past the store module: the goal is behavioral ("a completed invocation writes"), and a store nobody calls is dead code. Kept lean: one pending-ledger list, one composed hub callback.
- **Throw-on-key-collision instead of overwrite**: no silent supersede; the monotonic clock makes a collision bug-shaped, and loud is the house style.
- README at 0644 vs the ruling's "file mode 0600": record files are the 0600 subjects; the README is human-facing documentation. Stated here so the gate argument is settled before implementation, not during it.

### Cross-seam reading — what the contract actually is right now

- **There is no invocation-completion seam wired.** `spendRecord` is called only from `test/spend.test.ts`; production has exactly one EV-30 call site, `recordInvocationBoundary` at `index.ts:227`, which stamps the marker *before* the send. The card's "a completed invocation writes" names an event that does not exist in the tree. Extension side, `index.ts` registers `session_start` (144), `turn_end` (186), `session_shutdown` (187) — **no `agent_settled`**, though pi emits it: `agent-session.js:347-352` fires it once per `_runAgentPrompt` after retries/compaction/queued continuations, awaited (`await this._extensionRunner.emit`), before `waitForIdle()` resolves. So `agent_settled` is the only event that is (a) per-invocation, (b) post-settle, and (c) awaited before headless teardown. `turn_end` fires per tool-loop turn (N times per invocation); `session_shutdown` fires per session, not per invocation. The card must name this seam or it is unimplementable as stated.
- **Provenance path is available but only for on-disk sessions.** `ctx.sessionManager.getSessionFile()` is in `ReadonlySessionManager` (`session-manager.d.ts:140,209`) and returns `undefined` for `SessionManager.inMemory` (the substrate EV-30's T11 uses). `getSessionId()` exists but is not a path.
- **The store's injection precedent already exists.** `auth-store.ts:22-33` uses `path.join(getAgentDir(),"council",...)` with a default-parameter file path, and `test/mcp/oauth.test.ts:20-21` isolates via `PI_CODING_AGENT_DIR` (pi `config.d.ts:72,78`, read at call time). The dispatch's "injectable root" is already solved by the repo's own pattern; a second mechanism (a bespoke root param) would be a new convention.
- **The card's survival premise is false for a named invocation class.** `hub-tools.ts:184-185` and `dispatch.ts:108` pass `sessionDir: dir` where `dir = ensureRunDir(repoRoot, runId)` (`runs.ts:101`); `seats.ts:517` turns that into `--session-dir`. A seat child's session — including a council-runner's own — is *inside* the pruned run dir. The card says the session "is not under the run directory and therefore survives pruning." True for an interactive parent; false for the autonomous runner. `pruneRuns` (`runs.ts:164`) deletes exactly that directory.
- **Provenance covers only one of the record's two halves.** EV-30's `SpendBoundary` carries `firstEntryId`/`lastEntryId` for the **ownSession** half only (`spend.ts:17-30,137-201`); the subtree half is summed from `RunManifest.usage` (`spend.ts:181-193`). The card's "the entry range it was derived from" therefore does not explain the subtree number, whose entire basis (manifests + seat sessions) is what pruning removes.

### Blind spots, named separately

- **Store/owner slice** — sees a `ctx` and a settle after which the leaf is stable; cannot see that "a completed invocation" has no per-invocation event today, so it will reach for `turn_end` (fires N times) or `session_shutdown` (never fires in a live TUI session). It also cannot see, from inside the write, that the session path it stores is the very file the runner's run dir contains.
- **Exit/wiring slice** — sees the marker and the manifests; cannot see read-back semantics: a dangling provenance pointer must be a *stated* outcome, not a thrown error, and the store is a global (`getAgentDir()`) while the paths it stores are project- and run-local.
- **EV-32 render slice** — sees a number and a "session path + range" pointer; cannot see that the pointer legitimizes only the own-session half, so a rendered total will look fully traceable when half its basis is pruned. This is the cross-seam failure the successful acceptance test would hide.

### Reframe

**The durable unit is the invocation identity, and provenance resolvability is a recorded property, not an assumption.** Concretely:

1. **Write seam = `agent_settled`**, gated on an un-consumed on-chain `council-invocation` marker. Choose-once = the R-3 filename's `<ISO-basic>` is the **marker's `at`** (the invocation's own clock), not wall-clock compute time; the write then refuses to overwrite an existing file. This makes the key stable across recompute and makes the "second settle with the same still-on-chain marker" (any later plain TUI turn) a no-op. Stamping a *compute* time on the key would silently mint a duplicate record per recompute — reject that reading of R-3.
2. **The record states its provenance class**: `sessionPath` plus a derived `resolvable` (does the path exist *and* is it outside `runsDir`?), and states that the range explains the own-session half only. Read-back never throws; a pruned/dangling pointer reads back as the record with `resolvable:false`.
3. **When no session file is resolvable** (in-memory ctx, or `getSessionFile()` undefined): write the usage record with `sessionPath: null` + reason, or skip — but *state which*, because "drop the numbers" is worse for the traceability question than an explicit null pointer. R-3 does not cover this edge; it is EV-31's to rule.
4. **The acceptance test must include the runner-shaped case**: session file *inside* `runDir`, record written, `pruneRuns(repoRoot,0)`, read-back shows `resolvable:false` and the record survives. The card's current test (session outside the run dir) is a tautology — it constructs the survival it claims to prove and never tests the class that motivates durability.

The store module itself can still be a clean, small, pure-ish `write`/`read` pair; the reframe is about what the record *claims*, not about adding machinery.

### Testable claims

1. **Double-write on the settle seam:** build a session with one `council-invocation` marker, invoke the settle-write twice with no new marker. Claim: naive `findLatestInvocationMarker` + write produces two files (or two overwrites); keying on marker `at` + file-exists produces exactly one, byte-identical on the second call.
2. **Seam multiplicity:** in an invocation with ≥2 tool-loop turns, a `turn_end`-driven write writes ≥2 records; an `agent_settled`-driven write writes exactly 1. (Source-grounded today; a probe can count emissions via a fake agent loop without network.)
3. **Runner provenance dangle:** write a session file at `<repoRoot>/.pi/council/runs/<runId>/s.jsonl`, write the record referencing it, call `pruneRuns(repoRoot,0)`, then `readRecord`. Claim: `fs.existsSync(path)===false` and read-back returns the record with `resolvable:false` and does not throw. (Contrast the card's test, where the file is outside `runDir` and `resolvable:true`.)
4. **In-memory ctx:** drive the write with `SessionManager.inMemory()` (T11 substrate). Claim: `getSessionFile()===undefined` and the write path takes the stated unresolvable branch rather than throwing or writing an empty path.
5. **Store modes:** after a write, `fs.statSync(usageDir).mode & 0o777 === 0o700` and `statSync(file).mode & 0o777 === 0o600`, with the root under a `mkdtemp`/`PI_CODING_AGENT_DIR` dir and never the real home. `pruneRuns(repoRoot,0)` leaves the file's inode present (`runs.ts:164` operates under `runsDir`, not `getAgentDir()`), which is the card's third acceptance line and is trivially true only because the store is elsewhere.

New behavior needs a failing test first (AGENTS.md testing conventions); the store round-trip and the dangle case are the two that can be red before implementation.

#### Position — `designer`

I have grounded the seat: `getAgentDir()/council/` is the durable council-state home already (the `mcp-auth.json` precedent at `extensions/mcp/auth-store.ts:23-44` lives there with the `0600 atomic temp+chmod+rename` pattern); `runs/` is the ephemeral substrate that EV-31 must outlive; `spend.ts` (EV-30 Done) produces the boundary + the two half-`Usage` records; R-3 already binds the directory shape, filename shape, README presence, and modes. ---

- **Design position** — The store's discoverability rests on one self-explaining artifact: a README written **once** at first-mkdir that teaches a cold reader the directory, the filename grammar, the record schema in product voice (with the `subtree = stream-assistant lower bound` asymmetry surfaced prominently, not buried), the provenance pointer's chain-of-custody, and the unwritable-state behaviour; plus, inside each record, a **named provenance block** (`{ sessionPath, sessionId, range: { firstEntryId, lastEntryId } }`) whose `sessionPath` is the absolute path to the parent session JSONL — a path the card acceptance test can pin and a person can verify by hand. The directory is empty-state-coherent: a directory whose only non-system file is the README means "first invocation pending," and that sentence is the first thing the README says.

- **Gulf closed** — Evaluation gulf, primarily, for a maintainer who runs `ls ~/.local/share/<…>/council/usage/` and asks "is this what I think it is, and can I trust the numbers here?" Closes at three moments: arrival (the directory is named and the README leads with identity + empty-state semantics), per-record reading (filename → chronology + session-group + command; body → boundary + provenance + asymmetric accounting), and the failure moment (a write that fails names the absolute path of the failed target, byte-stably). Also closes a narrow execution gulf for a reader who needs to trace a number: opening the provenance `sessionPath` in a text editor must show entries whose ids include `boundary.firstEntryId..boundary.lastEntryId`.

- **Principle and evidence** — *Signifier over decoration.* A first-time reader who runs `ls` and sees only `README.md` + nothing must instantly know whether this is the right place and what to expect next — that's the empty-state signifier. *Conceptual model.* The record carries an *intentional asymmetry*: `ownSession` is exhaustive across assistant/toolResult/compaction/branch_summary entries on the leaf chain (`usageSource: "session-reconciled"`); `subtree` is a stream-projected lower bound (`usageSource: "stream-assistant"` — EV-28 Q4's reserved member, confirmed by the EV-30 ruling at `council/cards/EV-30.md`). A person reading the JSON must encounter that distinction within the first 20 lines of the README, not in a tail comment — the standing concern that "the gap between what the data implies and what the data knows is the largest design hazard" lives here. *Mapping.* The filename grammar `<ISO-basic>_<runId>_<command>.json` already maps three concerns to three tokens in a fixed order — chronological prefix (when the record was written), parent-session middle (`runId` is session-scoped, so all records with the same middle token came from one parent session — `extensions/index.ts:161` mints one `runId` per parent session, surfaced in EV-30's M1), and the procedure that produced it. The README's job is to teach that mapping by example, not to innovate a new filename shape. *Forcing function for unwritable.* A failed write must surface the absolute path in its notify line; we cannot let the silent-loss mode of the previous store ("usage record would be silently lost") persist by an unrelated mechanism. *Familiar-but-unearned check.* Conventions people may bring from comparable products (e.g., the empty-store-contains-a-`.gitkeep`, or directory `.jsonl` append-logs) are not the precedent here; the precedent is `mcp-auth.json` (atomic single-file), and the design owes nothing to either generic pattern.

- **Falsifiable predictions** —
  - **P1 (post-init)**: After `ensureUsageDir()` runs for the first time on a clean `getAgentDir()`: `ls -la <dir>` returns `README.md` and nothing else user-facing; `stat -c '%a' <dir>` returns `700`; `cat <dir>/README.md` line 1 begins with a heading that names "council usage" (or product voice equivalent), and the first paragraph contains the words "completed council invocation" and "read-back is supported". Both assertions fail under current code (no `usage/` dir exists).
  - **P2 (after one completed invocation)**: `ls <dir> | grep -E '\.json$' | wc -l` equals 1. The filename matches `^[0-9TZ._-]+_[0-9TZ._-]+-[a-z0-9]+_.+\.json$` (ISO-basic + runId + command; no whitespace). The README **mtime** is unchanged from P1 (write-once discipline). `stat -c '%a' <dir>/<file>` returns `600`.
  - **P3 (provenance resolves across prune)**: After `pruneRuns(repoRoot, 0)` removes the entire `runs/` directory, opening `<dir>/<file>.json` and reading `.provenance.sessionPath` yields an absolute path; `fs.existsSync(path)` returns true; `fs.statSync(path).isFile()` is true; the file's first line's `id` field equals `.boundary.sessionId` (or, after a marker roll-over, an entry with that id is reachable from the leaf chain — pick one and make it literal). All three checks pass; the test the card names is exactly this run.
  - **P4 (asymmetry is discoverable in the README, not just in the record)**: `grep -ciE 'lower bound|subtree' <dir>/README.md` returns ≥ 1 line; `grep -c 'usageSource' <dir>/README.md` returns ≥ 1 line. A consumer who only reads the JSON and prints `.subtree.cost` will *not* know it's a lower bound; the README has to teach them before they get there.
  - **P5 (unwritable surfaces a path-named failure)**: After `chmod -w <dir>` then triggering a record-write, the TUI/headless output contains a line whose shape is byte-stable and `grep`-able, e.g. `[council-usage] write failed: <absolute-path>: EACCES (chmod 0700 on the store, then retry)`. The exact literal is a candidate Phase-1 ruling; the *presence of an absolute path in the failure message* is not.
  - **P6 (notify for the *successful* write)**: After the first successful record is written, an interactive session receives one notify line whose shape names command, runId, ISO-basic, and the recorded line `usage record written: <file> (<cost> <basis>, subtree = lower bound)`. The exact phrasing is a candidate Phase-1 ruling; the *absolute-path-stamped-with-context* shape is the design claim.

  Each prediction above maps to an **out-of-band CDP smoke** or a pure-seam/unit test: P1/P2/P3 to a `test/usage-store.test.ts` using `fs.mkdtemp` and reading the on-disk shape; P4 to a `grep` over the canonical README asset; P5/P6 to a TUI notify mock that captures `ctx.ui.notify` and asserts the literal. None of these requires a running browser or a real model dispatch.

- **Preferences, ranked last** — I lean toward the README being written as a *shipped asset* (under `council/scaffold/...` or `extensions/usage-store-README.md`) rather than generated from a constant in `index.ts`, because copy that mentions "first invocation pending" reads better as a hand-tuned document, and a TypeScript template literal would impose an unnatural narrative shape. I also lean toward the README ending with a one-paragraph "what this is **not**" section (not the run transcripts, not the MCP secrets, not a transcript log) — adjacent durable homes are confusingly similar and the parent has no reason to remember which is which. Both are taste, neither is a principled position; the owner should pick on writing-convenience grounds. I have **no preference** on whether the record's `schemaVersion` lives inside the JSON body or as a leading README-segmented "current version" header; either works, both are legible.
