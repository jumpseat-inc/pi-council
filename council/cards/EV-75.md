## Intent

An upgraded consumer must never be silently de-enabled nor have enablement
silently preserved; the fail-loud line names the deprecated file and its
replacement (the EV-62 `FAIL:` surface).

## Acceptance

- A `mode`-bearing `policy.json` produces the named `FAIL:`.
- A tuning-only `policy.json` resolves unchanged.
- The packaged default stays `off`; no auto-migration writes a consumer's
  committed file.

## Round 1 — independent first pass (owner job-4.1, principal job-4.2, designer job-4.3)

### Owner (job-4.1)

**The design.** A two-line surgical change to `extensions/gate.ts`'s
`loadGatePolicy` (verified at head `16e8f5e`, post-EV-73), plus a test rewrite
in `test/gate.test.ts`. Nothing else.

The specialization point: `loadGatePolicy`'s unknown-key loop currently throws
the generic gateFail. Place a dedicated `mode` pre-check **before** the loop
(and therefore before all value validation):

```ts
if ("mode" in raw) {
	const detail = `unknown key; gate enablement moved to gate.mode in ${configFile} — remove this key and set gate.mode there`;
	throw new Error(`FAIL: ${file} has an invalid mode — ${newlineSanitized(detail)}`);
}
```

where `configFile = path.join(repoRoot, COUNCIL_CONFIG_FILE)`. This produces
byte-for-byte the adopted candidate copy with `<file>` = the actual read path
(from `readGateFile`, so it names the repo-local shadow, never the packaged
file) and `<repoRoot>/.council.json` = the absolute config path. `gateFail`
itself cannot be reused — its template tail is fixed at `— set a valid value
or remove the key to use the packaged default`, and the candidate tail is
`— remove this key and set gate.mode there` — so this is a dedicated
single-line throw with the same newline-sanitization discipline the module
header promises.

**Why pre-check, not in-loop branch.** The loop as written is JSON
insertion-order dependent: a legacy file carrying both `mode` and `bogus`
currently fails on whichever key parses first. An in-loop branch would let
`{bogus: 1, mode: "advisory"}` name `bogus` and mask the migration pointer —
violating the card goal and R5 for exactly the messiest real files, which are
precisely the ones an upgraded consumer has. The migration signal must never
be masked by an unrelated diagnostic. Placement is pinned by test T3 below.

**What must not change** (each guarded by an existing or kept test):
`loadGateConfig` untouched (packaged default stays off); the generic
unknown-key FAIL for every other unknown key — unchanged bytes; the
tuning-only resolution path untouched; the FAIL fires on every gate read
including the off path; `gate-state.ts`'s lenient reader not touched (EV-73's
recorded follow-up item (4), not this card); **no auto-migration** —
`loadGatePolicy` is a pure read path, nothing writes `policy.json` or
`.council.json`, no scaffold change.

**TDD test plan (all in `test/gate.test.ts`, mkdtemp fixtures):**
- **T1 (red first — replaces the EV-73 placeholder test at ~84–93**, which
  asserts the generic copy AND `expect(msg).not.toMatch(/\.council\.json/)` —
  written to be flipped by this card): repo-local `policy.json` =
  `{policyVersion, mode: "advisory", model, endpoint}` + `.council.json`
  `{"gate":{"mode":"off"}}` → throws exactly
  `FAIL: ${file} has an invalid mode — unknown key; gate enablement moved to gate.mode in ${root}/.council.json — remove this key and set gate.mode there`
  — full `toBe` byte identity.
- **T2 (tuning-only unchanged):** explicit no-throw assertion on a 4-key
  tuning-only file plus resolved-mode-from-config.
- **T3 (pre-check ordering):** `{bogus: 1, mode: "advisory", …}` with `bogus`
  first → still the migration FAIL, never the `bogus` FAIL. Red against the
  in-loop-branch alternative.
- **T4 (no auto-migration):** snapshot `policy.json` bytes; assert no
  `.council.json` exists after the throw.
- **T5 (kept-green):** generic `bogus` FAIL bytes unchanged; packaged default
  off; mode-bearing FAIL fires with config `off`.

**Tradeoffs accepted:** malformed `.council.json` shows the config FAIL, not
the migration FAIL (config resolution precedes the policy read — EV-73's
landed order); the found legacy `mode` value is not echoed (copy not
embellished); gate-route-tool's wasted state-pack before the FAIL (cosmetic;
recorded follow-up owns the load-order invariant); dedicated throw instead of
generalizing `gateFail`.

**Open questions:** (1) pre-check placement vs in-loop branch — settle with
T3, not prose. (2) scope of "no new FAIL:" on the tuning-only path — reads as
byte-identical resolution and zero new diagnostics in every mode; T2 pins the
resolution half. (3) confirm `gate-state.ts`'s lenient reader stays a recorded
follow-up (EV-73 item (4)).

**Testable claims:** C1 the red-first step is real and scoped to message
bytes; C2 exact candidate copy with real paths interpolated, even with config
off; C3 tuning-only resolves to the identical GatePolicy before and after; C4
pre-check fires before value validation (`mode` + `policyVersion: ""` →
migration FAIL, not empty-string FAIL); C5 after any mode-bearing FAIL,
`policy.json` byte-unchanged and no `.council.json` created.
