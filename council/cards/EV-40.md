## Intent

This is the mechanism that actually addresses the intake. No retry API exists
for the parent's own provider call, so it is built from the `agent_settled`
event plus a continuation send, and it must hold in both the TUI and the
headless branches.

The intake's terminal word is `Continue`, the only affordance between the error
and the person's next action, so the surface is named by ruling rather than
left to the implementer. This card carries the epic's real risk; the Council
should expect it to be split if the continuation path turns out not to be
reachable from a handler.

## Orchestrator rulings (Phase 1, binding)

Recorded human decisions for this run. Immutable and binding on every seat,
`steward` included; a runner that hits one applies it and cites the ruling
rather than re-asking.

- **R5 (retry surface copy).** During backoff the input bar reads
  `Retrying in 2s (attempt 2 of 3) — Esc to abort`, and `Esc` aborts the
  remaining retries. When the budget is exhausted the session stops with
  `Retries exhausted after 3 attempts. The provider kept failing. Press Enter
  to try again.` The per-branch observable for the goal is the input bar's
  text delta in the TUI and the equivalent stdout line in the headless branch.

#### Owner position (`job-16.1`) — verbatim

## **Position** (the design)

**1. Continuation mechanism.** `agent_settled` is the only correct carrier — not because EV-43 proved reachability (it did), but because its contract is the only settle point pi *guarantees* no further automatic work will follow (types.d.ts:561-563: "after an agent run has fully settled and no automatic retry, compaction, or queued continuation will run"). `agent_end` (types.d.ts:556-559) fires *before* pi's own auto-retry (`auto_retry_start`, agent-session.d.ts:64-67) can interleave, so scheduling there would race pi's retry machinery. The backoff timer lives **outside the turn lifecycle, in closure state in the parent-mode section of `extensions/index.ts`** (a sibling of `flushChain`, ~line 285): the `agent_settled` handler (index.ts:379) arms a `setTimeout` and returns immediately. The send is `pi.sendUserMessage` using the exact branch pattern at index.ts:439-454 — TUI fire-and-forget; headless fire-then-poll-`ctx.isIdle()` then a guarded `waitForIdle` (the falsifier proved the event context lacks `waitForIdle`; types.d.ts:258 shows it exists only on `ExtensionCommandContext`).

**2. Policy.** `loadRetryConfig(repoRoot)` (seats.ts:267) is read **once at parent-mode init** (wrapped try/catch; a throw disables retry and notifies — the malformed-config session must not crash at init), cached beside the timer state. Delay = `min(baseDelayMs * 2^(attempt-1), maxDelayMs)`, halved/doubled when `jitter` (scheme must be pure and testable; I'd put a `computeBackoffDelay(policy, attempt, rand)` pure fn in `extensions/retry.ts` next to `classifyRetry`). Attempt counting: the failed turn is attempt 1; retries are attempts 2..maxAttempts — matching R5's copy literally ("attempt 2 of 3"). Note this repo's `.council.json` has **no `retry` key**, so defaults `true/3/2000/30000/true` (seats.ts:229-235) govern; R5's example "2s" matches the default baseDelay exactly — the copy must interpolate the real delay, not hardcode 2s.

**3. Esc abort.** This is the weakest seam. `ctx.abort()` aborts "the current agent operation" (types.d.ts) — while idle (backoff is between runs) I cannot confirm it does anything useful. The only proven key-capture mechanism in this repo is the EV-8 custom-editor overlay (`focus-nav.ts`/`navigator.ts`, editor interception at navigator.ts:775+). My design: during backoff, the TUI branch installs a passthrough custom-editor wrapper whose key handler watches Escape → sets a closure abort flag, clears the countdown surface, and disarms the timer. Headless: Esc doesn't exist; R5's "equivalent stdout line" prints the ruled string as-is, and SIGINT is the de-facto abort — I'd record this as a designer/skeptic question, not silently decide it.

**4. Terminal message.** TUI: after exhausting the budget, clear the countdown widget and `ctx.ui.notify("Retries exhausted after 3 attempts. The provider kept failing. Press Enter to try again.", "warning")` — the notify is the input-bar-adjacent surface council already uses. Headless: `console.log(...)` (the index.ts:439/448 dual-route pattern). "Press Enter to try again" is left inert copy — the session simply stops, and Enter re-submits whatever the user types; making Enter *itself* re-trigger the retry would require editor capture I wouldn't build.

**5. Floor re-entry.** Yes, and that's fine: `before_provider_request` (index.ts:66-81) patches any outgoing payload by model id, so the continuation re-enters the `max_completion_tokens` floor. No special handling; a test can assert a continuation payload for a floored model carries the floor.

**6. Error detection.** `agent_settled` has **zero payload** (types.d.ts:561-563), so the signal must be cached from `agent_end`, whose extension event carries `messages: AgentMessage[]` — inspect the last assistant message for `stopReason === "error"` and classify `errorMessage` with the R1 predicate. `classifyRetry` takes a `JobReport` (retry.ts:80-101), so I'd extract the pattern test into a message-side pure predicate in `retry.ts` shared by both; the parent-turn adapter treats the turn as settled-with-error. `stopReason === "aborted"` must never schedule. Edge case to rule on: if the error *does* match pi's own retryable list, pi already retried before settle — council's loop stacks on top of pi's. I'd engage anyway (the epic wants survival, not dedup) but flag it.

**7. Split judgment.** Split into two cards: **(A)** continuation + policy + detection + terminal message, both branches, **without** interactive Esc (backoff abortable only headless-via-SIGINT; TUI Esc not yet wired); **(B)** the Esc-abort editor overlay. A is EV-43-proven reachable end to end; B is unproven surface work in the hardest part of the TUI (editor interception), and is designer/judge territory. Shipping A alone still satisfies the epic goal minus abortability.

# EV-40 — principal (first pass, deliberation only)

## Framing critique

The card's load-bearing premise — "No retry API exists for the parent's own provider call, so it is built from `agent_settled` plus a continuation send" — is **falsified by the installed pi**. Verified first-hand: pi ships a first-class parent-turn auto-retry loop.

- `core/agent-session.js:2286` `_prepareRetry(message)`: `_retryAttempt++`, `delayMs = baseDelayMs * 2 ** (attempt-1)`, abortable `sleep(delayMs, this._retryAbortController.signal)`; `:2335 abortRetry()`; `:2342 autoRetryEnabled`; `:2339 isRetrying`.
- Settings are a real policy surface: `core/settings-manager.d.ts:17-22` `RetrySettings { enabled?, maxRetries?, baseDelayMs?, provider? }`, read at `agent-session.js:2287`, also honoured by compaction/branch-summary summarisation (`:1453`, `:2552`).
- The gate is a **pure predicate**, not a hook: `_isRetryableError` (`:2248-2253`) → `isRetryableAssistantError(message)` (`node_modules/@earendil-works/pi-ai/dist/utils/retry.js:167`) which reads only `{stopReason, errorMessage}` against `RETRYABLE_PROVIDER_ERROR_PATTERN` (`retry.js:20-60`). `Provider finish_reason: error` is absent from that list — that, and only that, is why the intake doesn't retry.
- The loop already drops the errored assistant message before re-issuing (`agent-session.js:2306-2310`, `messages.slice(0,-1)`) and already renders an Esc-abortable indicator (`modes/interactive/interactive-mode.js:2802-2816`).

So the seam is not "who re-issues the turn". It is **where the retryable verdict enters pi's loop**. The card builds a parallel loop one layer up, and therefore has to re-earn four semantics pi already has: budget/reset (`:410-417`), error-message drop, abort, and surface. A continuation send does *not* drop the errored assistant turn — it appends a user message after it. That is a different conversation shape and my highest-risk prediction (below).

Second premise mismatch: `AgentSettledEvent` is `{type:"agent_settled"}` with no payload (`core/extensions/types.d.ts:559-562`). The card's signal is not *on* that event; it must be recovered from session state. `AgentEndEvent.messages` (`:554-558`) and `MessageEndEvent.message` (`:603-606`) carry it directly, and `message_end` additionally allows replacement (`MessageEndEventResult{message?}` `:841-844`; applied in place at `agent-session.js:515-525`).

## Recommended mechanism (and rejected alternatives)

**Push the verdict down, don't stack a loop on top.** Ranked:

1. *(Preferred, needs pi)* Widen the predicate pi itself consults. No such API exists today — I found no retry/verdict hook in `ExtensionAPI.on` (`types.d.ts:918-937`), none in `ExtensionContextActions` (`:1266-1279`), and `isRetryableAssistantError` is not in `pi-coding-agent`'s public exports (only re-exported internally via `@earendil-works/pi-ai/compat`, `agent-session.js:18`). This is a small upstream ask (a retryable-verdict hook or configurable extra patterns) that would make EPIC-9's entire parent half pi-owned.

2. *(Rejected)* The `message_end` rewrite hack — return `{message: {...m, errorMessage: "overloaded"}}` so pi retries. It **provably works** (`:384` emit awaited, then `:404 _lastAssistantMessage = event.message`, then `:793` → `_prepareRetry`), but it persists a falsified `errorMessage` into the session JSONL (`:388-400 appendMessage`), corrupting EV-42's per-attempt identity, usage attribution and `runs/` transcripts (AGENTS.md §12). Reject.

3. *(Fallback, if council owns it)* Reuse pi's *semantics* without lying:
   - **Detect** at `message_end` (payload present; fires before `agent_end` and settle).
   - **Drop, don't append**: filter the errored assistant message out of the next request via the `context` hook (`ContextEvent{messages}` `:514-517` / `ContextEventResult{messages?}` `:814-816`) — this reproduces pi's `slice(0,-1)` without mutating persisted history. Do **not** issue the retry from `message_end`/`agent_end`: pi's own `_willRetryAfterAgentEnd` (`:429-441`) may be about to retry and you would double-issue.
   - **Re-issue** at `agent_settled` only — the one event documented as "no automatic retry, compaction, or queued continuation will run" (`types.d.ts:559`), consistent with EV-43's measured falsifier.
   - **Timer**: `setTimeout(...).unref()`, cleared in `session_shutdown` (pattern already in `extensions/index.ts:388-405`). A new prompt during backoff must **abort** the pending retry (R5's Esc semantics), else a stale "Continue" is injected after the human's own message. Never let the pending timer touch `ctx` unguarded — wiki [[headless-pi]]: captured ctx getters `assertActive()` and throw after session replacement.

#### Designer position (`job-16.3`) — verbatim

# Designer Position — EV-40 Surface State Machine Around R5

## Surface state machine

A person who hits this surface traverses six states, four of them visible:

| # | State | Surface they see | Source / mechanism |
|---|---|---|---|
| 1 | **idle** | empty input bar (or pi default placeholder) | pre-state |
| 2 | **turn in flight** | pi's own streaming render; council surfaces (active-jobs widget, inline tree) unaffected | `widgetLines` ticker at `extensions/index.ts:336`, 5s |
| 3 | **provider error** | **invisible as a state** — `agent_settled` fires (`extensions/index.ts:379`) and the next visible thing is the countdown. Partial streamed assistant text is *already in the transcript above* the input bar (pi writes it during streaming; council never intervenes). | `agent_settled` event |
| 4 | **backoff (countdown)** | ruled string in input bar / headless stdout | R5 |
| 5 | **attempt N** | `sendUserMessage` fires (`extensions/index.ts:442` TUI fire-and-forget; `:448–454` headless pattern). Returns to state 2. | EV-43 falsifier, closed-green |
| 6 | **exhaustion** | ruled terminal copy; session halts | R5 |

**The transition #3→#4 is the largest design gap:** no surface ever says "the provider errored because…" — only the countdown appears. The error reason is the literal `Provider finish_reason: error` (R1, `extensions/retry.ts:54`), and a person who sees the countdown with no error context cannot form a correct conceptual model of *why* they're waiting. State 3 is invisible by design; that is the ruling. The Design position holds it should at minimum leave a transient toast/log line naming the failure, distinct from the countdown itself.

**EV-43's skeptic falsifier (card EV-43 §9, observation 7)** proved that **no input-bar text delta exists today in any arm** — the only visible delta is in conversation-tail rows above the input bar. R5 names "input bar" as the location; the implementation will have to *create* an input-bar text surface where today none exists (likely via `setEditorComponent` in the `installTreeEditor` pattern at `navigator.ts:348–356`). This is the largest open seam and the seat flags it as a ruling tension, not a settled fact.

## Discoverability / failure tolerance

The affordance `Esc to abort` is **one string-embedded hint inside a passive countdown.** No styled glyph (no ⎋, no styled span), no separate hint line, no second-row affordance list. A person who didn't read the R5 ruling cold may read "Retrying in 2s (attempt 2 of 3)" as informational, miss the dash-and-verb pattern, and never realise they can cancel. The 1-second tick is itself the only corroborating cue that the system is still working.

If they ignore Esc, the countdown completes, the retry fires, and the budget ticks. After 3 attempts the conceptual-model payoff lands: they are *forced* into the terminal state because nothing else is offered. This is acceptable for a transient error but punishing for a *permanent* provider outage — three ~30s waits then a stop, with no "give up early" surface other than Esc.

## Terminal state model — the load-bearing ambiguity

R5: `Retries exhausted after 3 attempts. The provider kept failing. Press Enter to try again.`

The copy says "try again" — but "again" is genuinely ambiguous along three axes, and R5 doesn't pick:

1. **What does Enter do?** Re-send the *same* user prompt that just failed (the continuation behavior R5's mechanism describes), or return to a fresh idle input bar? The word "again" reads either way.
2. **What survives in the transcript?** The failed-turn's partial assistant tokens are *already committed to the JSONL* before `agent_settled` fires. Enter does not roll them back. The person will see `…partial assistant text… / countdown / exhaustion copy / Press Enter / (next attempt) → new assistant entry` — a stacked history, not a clean retry.
3. **Is the attempt budget reset?** Enter does what: one more attempt with the budget already exhausted, or a fresh `1 of 3`?

Conceptual model the ruling hands the person: **a paused, resumable state** — *not* an error, *not* idle. The affordance name "Press Enter" implies the same surface already has Enter-bindable behavior (it does — submit), so the affordance is at least signposted by the host widget. The Design position: rule these three axes explicitly before implementation; the current copy alone does not close the Gulf of Evaluation.

## Headless parity

EV-43 closed-green established that the headless pattern requires fire-then-poll-`ctx.isIdle()` then `await ctx.waitForIdle()` (`extensions/index.ts:448–454`), because `agent_settled`'s event context lacks `waitForIdle`. For a backoff loop the same pattern must wrap **each retry's** continuation — otherwise the parent process exits between agent_settled and the next attempt's sendUserMessage, and the countdown stdout line is observed by no one.

What the headless stdout line must carry to preserve TUI parity:
- attempt `n/N` + remaining `s` (or trigger for 1s re-emit)
- an *abort* affordance — but headless has no Esc. The only honest equivalents are SIGINT to the parent or a JSONL marker a wrapper watches. R5 does not name one; this is open.
- on exhaustion, the terminal copy + an exit code that *signals retryable exhaustion* distinctly from generic non-zero.

What is lost: editability, the per-second tick (headless is line-buffered), and the `Press Enter` affordance. The ruled copy's last clause has no headless equivalent — `Enter` in a `-p` shell means nothing. This is a **headless design question**, not a copy edit.
