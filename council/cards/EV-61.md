## Intent

The ledger is what makes the routing policy measured rather than asserted. It is
the tuning dataset, the audit trail, and the answer to "why did this card run
that way": every call records the packed state's hash, the question-set version,
every answer with its probabilities and confidence, the mode the pure decision
function resolved, and the policy version it resolved under. Once the card has
run, the outcome is appended to the same record.

The record is append-only and must be recomputable without re-running the model
— a recorded call's mode must follow from the recorded answers and the recorded
policy version alone. That is the testable form of "the ledger is the record, not
a log of something else".

Placement matters. The run directory is pruned and its reads are confined by
convention, so the ledger lives outside it as durable repo-scoped telemetry at
`$CONFIG_DIR_NAME/council/gate-ledger.jsonl`, written atomically, append-only,
with a reader module of its own. If the alternative is chosen — extending the
existing manifest usage surface — that is a deliberate amendment and the
convention text must change with it, never a silent widening.

## Acceptance

Two calls for the same state hash and policy version produce two records whose
`resolvedMode` is identical when re-derived from the stored answers; a record
carries every question's probabilities and confidence verbatim, including an
absent answer as absent rather than as a zero; a write failure is reported with
the absolute target path and never dropped silently; and a test asserts the
reader performs no direct read of the pruned run directory. The ledger file is
committed by default so that a pre-registration record's ledger citation is
readable by anyone running validation (a consumer may gitignore it, and loses
that citability); a test asserts a reader can resolve a recorded call's answers
and mode from the committed file with no network.
