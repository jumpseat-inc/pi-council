## Intent

Surface: the `/features-deliver` Phase 3 ledger line and the `council-runner`
completion report tag copy. Two more emitters consume the follow-up rule:
`features-deliver`'s Phase 3 at run scope, and the `council-runner` container.
This card routes both through the follow-up decision and pins the container's
failure route: an unresolved candidate returns as `ESCALATION` before any
write, never a silent drop. The disposition outcome rides `DONE` and
`ESCALATION` only; `RETIRED` keeps its documented card-withdrawal meaning.

## Acceptance

- Phase 3's follow-up sentence names the follow-up decision as the disposition
  source, agreeing with step 13 rather than restating an unbounded per-item
  rule.
- `council/agents/council-runner.md` records the decision per candidate and, on
  a failed/unresolved call, returns the candidate(s) as `ESCALATION` before any
  write; it never silently drops one.
- The report carries the disposition outcome at the action point on `DONE` and
  `ESCALATION` only — `DONE` carries the per-candidate outcome, `ESCALATION`
  carries the candidate id plus the `gate call failed: <reason>` / unresolved
  basis, and `HALT` pins "no disposition reached" or the partial state.
  `RETIRED` keeps its documented card-withdrawal meaning verbatim and never
  carries a candidate `Drop`; `<return_contract>` is not edited.
- A `test/hub.test.ts`-style runner dispatch on a failed call returns
  `ESCALATION` with the candidate in the report; a runner that writes a card
  without a resolved decision, or drops a candidate, fails the test.
- The repo's typecheck, the full test suite, `python3 council/validate.py`, and
  the repo's preflight pass.

### Round 1 — owner (first pass, job-13.1)

**Module placement: a `followup` grant keyword mirroring `hub`, exposing the existing
parent tool pair to the granted seat.** The runner is a child seat; `extensions/child.ts`'s
`isCallAllowed` structurally blocks every tool not builtin-, hub-, or MCP-granted. The
`council_followup_gate`/`council_followup_render` pair is registered only on the parent
path (`extensions/index.ts` ~628, behind a comment claiming "EV-83's runner seam is the
exported runFollowupReview, **not a tool**"). Evaluated as an open design question, that
comment is **half right**: right that the composition must stay `runFollowupReview`
(FLLWUP-96: one site, up to two callers — `extensions/followup-tool.ts:103–156`); wrong
that the seam isn't a tool. A child seat is an LLM in a sandboxed pi session — it cannot
`import` a TS function. The only ways it reaches engine capability are (a) a registered,
granted tool, or (b) shelling out through `Bash`. A bash-invoked importer is a second
composition surface with no sandbox accounting, exit-code error handling, and no
ledger/widget parity — it fragments exactly what FLLWUP-96 exists to keep single. The
`hub` grant is the in-repo precedent for the correct answer: **a grant keyword in seat
frontmatter that mints engine tools** (`grantsFor` in seats.ts:579–581, `buildChildArgv`
seats.ts:614–616, `runChildMode` child.ts:22–27).

**Proposed mechanism: the `followup` grant, mirroring `hub` exactly.**

1. `extensions/seats.ts` — `grantsFor` returns `{ hub, followup }`; `followup:
   t.has("followup")`. `buildChildArgv` pushes `council_followup_gate,council_followup_render`
   into `--tools` when followup-granted (same line as the hub tools push).
2. `extensions/child.ts` — `runChildMode` calls
   `registerFollowupGateTool`/`registerFollowupRenderTool` when `grantsFor(seat).followup`;
   `isCallAllowed` permits those two names under the grant. The tools' `execute` already
   guards `ctx.hasUI` (`followup-tool.ts:197`), so headless child sessions work unchanged —
   `setWidget` is optional by design (`RunFollowupReviewOpts`, followup-tool.ts:93–96,
   "optional so tests and EV-83's runner path can run headless" — the code itself
   anticipated this seam).
3. `council/agents/council-runner.md` frontmatter — `tools: Read, Grep, Glob, Edit, Write,
   Bash, task, hub, followup`.
4. The index.ts comment is rewritten to name the actual seam: the *composition* is the
   exported `runFollowupReview` (never a second composition); the *transport* into a child
   container is the granted tool pair. Registration stays out of `registerHubTools`
   (hub-granted seats must not get it implicitly — only the explicit `followup` grant).
5. `council/procedures/features-deliver.md` and `council/agents/council-runner.md` prose
   changes below.

Conventions check: this extends the tool-grant vocabulary (convention 8) with one keyword,
exactly as `hub` did; it does not touch the seat schema's frontmatter fields (convention 2
— `followup` is a `tools:` value, not a new field); no hardcoded `.pi`, no clone paths.

### Round 1 — designer (first pass, job-13.3)

**Design position.** The two surfaces EV-83 changes are read at two different action
points — the Phase 3 ledger line by the human/orchestrator after a run closes (deciding
what got filed), and the `council-runner.md` `<return_contract>` clauses by the orchestrator
the moment a runner's report lands (deciding what to do next). Both must **enumerate the
surfaced follow-up candidates at the read point** — Phase 3 by agreeing with step 13's
follow-up decision as the disposition source (not restating step 13's per-item rule), and
the runner's report by carrying the per-candidate disposition (`DONE`), the candidate id
plus the verbatim `gate call failed: <reason>` / unresolved basis (`ESCALATION`), and a
"no disposition reached" or "partial state — dispositions reached for N of M candidates"
pin (`HALT`). The four-tag list and `RETIRED`'s verbatim meaning are load-bearing
constraints, not anchors to drift around — they bound what the runner can ever say.

**Gulf closed.** Gulf of **Evaluation**, for two readers at two distinct moments:
(1) the **orchestrator at the report's arrival** — must perceive which candidate was held
without writing, on what basis, and what to record in Phase 3; (2) the **human reading the
Phase 3 ledger line after the run** — must perceive, per surfaced candidate, whether
disposition was reached and which path it took (so the ledger audits against the gate
ledger and against any candidate the runner ESCALATION'd).

**Principle and evidence.** Signifier + knowledge-in-the-world: the disposition outcome
rides verbatim from the gate ledger's recorded line into the report — not a paraphrase.
EV-82 already ships the verbatim grammar in `decisionLine` (`extensions/gate-ledger.ts`)
and exports `FollowupRunResult.failure: {kind, reason}` precisely so EV-83's report copy
doesn't have to string-match `basis`. The runner's report must **cite the literal
`Mode: <disposition> — <basis>` byte sequence per candidate on `DONE`** and the verbatim
`gate call failed: <reason>` (where `reason` is the ledger's failure.reason) on
`ESCALATION` — both already exist as bytes elsewhere in the system; the report copy's job
is to surface them, not invent new strings. Constraint: the four-tag list is structural —
`features-deliver.md` Phase 2's rows are the orchestrator's only routing key; adding a
fifth tag forks the table; the compression is on the prose inside each tag's clause, not
the tag list. Mapping — report line ↔ gate ledger row: the runner's `ESCALATION` report
names candidate ids that map 1:1 to `FollowupReviewCandidate.title`; the per-candidate
outcome on `DONE` maps 1:1 to the gate-ledger.jsonl line via `callId`. The contract must
make that mapping explicit so the orchestrator can audit.

### Round 1 — principal (first pass, job-13.4; first dispatch 429-rate-limited, re-dispatched once)

**Cross-seam reading.** `council.md` step 13 is the canonical contract: record via
`council_followup_gate` → render via `council_followup_render` → present verbatim →
confirm before any write → apply the recorded disposition. `features-deliver.md` Phase 3
currently offers only a pointer with no disposition-source and no failure route.
`council-runner.md` says nothing about the follow-up decision at all. `runFollowupReview`
(`extensions/followup-tool.ts:96–158`) is the one composition site;
`renderFollowupLinesFromRepo` (`extensions/followup-render.ts:193–197`) is the pure render
half; both exported. But the only callers are the two parent-session tools registered at
`extensions/index.ts:636–637` on the parent path only. `runChildMode`
(`extensions/child.ts:15–40`) registers only hub tools plus built-ins; the child process's
tool surface is frozen at spawn (`buildDispatchArgv` emits an exact-name `--tools`
allowlist, `extensions/seats.ts:615–617`); `isCallAllowed` blocks anything else at
`tool_call`.

**The index.ts comment is wrong as written.** "EV-83's runner seam is the exported
runFollowupReview, not a tool" is a category error: an LLM container does not import TS
functions. A child-mode runner can only act through `--tools`-listed, child-registered
tools. As shipped, a runner following EV-83's prose would have **no callable surface** that
reaches `runFollowupReview`. The comment's operative purpose — never fold into
`registerHubTools` — is correct for the parent pair, but it conflates "the parent tools are
not exposed" with "the runner has a TS-import path." EV-82 explicitly deferred this
("runner-side access is EV-83's seam, not pre-built here"), and the deferral is real engine
work.

**The fail-safe trap on the data side.** `runFollowupGate` writes a ledger line on both
arms, and on a transport/credential failure the recorded `resolvedMode` is the literal
`File` — the human-confirm fail-safe default (`docs/superpowers/specs/2026-09-21-EV-81-design.md:88–89`;
`extensions/gate-run.ts:363`). The discriminator is the sibling `failure: {kind, reason}`,
which the mechanical result (`FollowupReviewCandidate`) deliberately drops — it carries
only `status` + a generic `message`. Per-candidate failure identity therefore only survives
through the render half joining the ledger by `callId`. Any runner that keys "resolved" off
`resolvedMode` will write a card on a failed call — precisely the silent write the card
forbids.

**Blind spots.** Owner cannot see the dispatch allowlist — the capability boundary
(`--tools` in `seats.ts`, `isCallAllowed` + registration in `child.ts`) is three files away
and not named by the card; the likely wrong turn is folding the follow-up tools into
`registerHubTools` or writing prose that names a tool the runner cannot see. Designer
cannot see that a "success-looking" line is the failure case (`Mode: File — …` is also
what a failed call records) and cannot see that R6 forbids editing `<return_contract>`, so
the disposition-outcome content contract has to live *outside* the block a reader would
check. Skeptic cannot see that a Hub+stub "runner dispatch" proves plumbing, not obedience
— the house pattern (`test/ev69-verify-manifests.test.ts:236–270`) dispatches a stub-child;
EV-69 itself recorded the honesty caveat that this claims NOTHING about whether a live
facilitator would call the tool. Product-owner cannot see that `off` has no autonomous
meaning — in an autonomous container there is no human, so `off` is neither a failure nor a
decision; the card's R6 doesn't assign it an arm.

**Reframe.** The proposed design is **not** sound as framed; it needs a scope correction,
not a replacement. EV-83 was carved by the design seat as a *copy/ledger* card (Finding E,
`vault/raw/2026-09-21-design-epic10-re-cut-surface.md:181–200`), but the composition it
requires is **engine**, not copy. **Minimal engine change = one child-mode tool that wraps
both exported halves.** A `council_followup_review` tool whose implementation calls
`runFollowupReview(...)` then `renderFollowupLinesFromRepo(...)`, returning the mechanical
per-candidate facts *plus* the rendered lines (so the failure basis is the exact bytes
`gate call failed: <reason>` / `credential unresolved` / `followup decision not recorded`).
That is still FLLWUP-96's one composition function — the tool is a second *caller*, not a
second composition. It must be wired at all three allowlist sites: a grant token
mapped/allowlisted in `seats.ts:615–617`, registered inside `runChildMode` (`child.ts`), and
permitted by `isCallAllowed`. Registering it only in `child.ts` is insufficient — the model
never sees a tool absent from `--tools`. **If product-owner rules the engine tool out of
EV-83**, then the card cannot meet its own Acceptance ("a container … returns
`ESCALATION`", "a runner fixture asserting `ESCALATION`") and must split into a prose card
plus an engine-card — the current goal is unachievable by prose alone.

**The two surfaces, worded to agree without restating step 13.** Phase 3: one sentence
naming *step 13's follow-up decision* as the disposition source for filed follow-ups, and
that a candidate whose decision failed/unresolved is recorded as an escalation, never a
filed card. Pointer, not rule. `council-runner.md`: a new block (not `<return_contract>`)
that (a) says the decision comes from step 13's mechanism, (b) pins
**ESCALATION-before-any-write** and **never silently drops one**, and (c) pins that a
*failed* call is never applied — keyed on the record's failure state, never on
`resolvedMode` (the fail-safe `File` trap above). The four-tag list stays byte-unchanged,
so the disposition-outcome content contract is stated in this block; the flagship risk is
a reader of `<return_contract>` alone not knowing DONE should carry it. `HALT`'s "no
disposition reached / partial state" pin belongs here too, and `off` in a container must
route (ESCALATION or HALT), not default to `File`.
