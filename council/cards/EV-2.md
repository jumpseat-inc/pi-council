## Intent

User-visible surface: the customization file the consumer edits — this card
makes the theme editable without touching engine code.

`.council.json` already exists as the committed repo override file for seat
model/thinking (AGENTS.md 9.5, `loadCouncilConfig` / `applySeatOverride` in
seats.ts). The theme section lives alongside, e.g. a top-level `theme` key
(sibling of `council`) carrying `name` (default `pi-council`), dark and
light palette `vars`, and per-token `colors` overrides. The exact shape is
for the Council to fix, subject to these requirements:

- Lives in the scaffold's `.council.json` so `/council-init` writes it into
  consumer repos, non-clobbering (a consumer's existing `.council.json` is
  never overwritten — scaffold invariant).
- Parsed and validated by the same config machinery: malformed JSON or an
  invalid token name / value throws with a message naming the file, like the
  seat overrides do today.
- Merge semantics: repo values win over shipped defaults; an absent section
  means "no theme config" (activation card decides what that implies).
- Editing a var or token recolors the next session; the shape should be
  small enough to hand-edit in a text editor.

> EV-2 reads the shipped theme JSON off disk via
> `path.join(PKG_ROOT, "themes", ...)`. Do NOT use `getPackageDir()` — that
> is pi's install dir, not pi-council's root, and would silently load pi's
> built-in theme (accent `#8abeb7`) instead of the shipped omp palette. See
> spec §4 (corrected).

## Acceptance

- `loadCouncilConfig` returns the parsed theme section; unit tests cover
  happy path, missing section, malformed JSON, invalid token, and override
  merge (repo wins).
- Scaffold test: a fresh `scaffoldInto` into an empty temp repo writes the
  theme section; re-running into a repo with an existing `.council.json`
  leaves it byte-for-byte untouched.
- The default scaffold section matches the shipped omp palette from EV-1.

## Phase 1 Ruling (recorded, binding)

Recorded 2026 by the human before the run: the exact shape of the `.council.json` theme section was surfaced in the rulings preflight and **deliberately delegated to the Council** ("let the Council decide"). The Council fixes the shape within this card's stated requirements (sibling of `council`, name `pi-council`, repo-over-shipped merge semantics, non-clobbering scaffold) and must **not** escalate the shape question — it is a working decision, not an open-judgment dispute.

## Deliberation Record

### Round 1 — independent first pass (owner, principal, designer)

**owner** (engineering): Shape fixed: top-level `theme` (sibling of `council`) as `{ "enabled"?: boolean, "variant": "auto"|"dark"|"light", "dark"?: { "vars"?, "colors"? }, "light"?: { "vars"?, "colors"? } }` — replaces the spec's variant-agnostic `overrides` working proposal with per-variant override blocks. Forced, not cosmetic: the two shipped variants have **disjoint var namespaces** (dark: 15 vars incl. `accent`/`cyan`; light: 14 vars incl. `teal`; only ~11 names overlap — verified against both files), so a variant-agnostic `vars` override silently no-ops in whichever variant lacks that var name, and per-variant blocks are the only way to validate "var-ref resolves to a declared var" exactly (a `light.colors.accent = "cyan"` must throw: `cyan` is undeclared in light). Also matches the spec's *settled* merge text, which already names `theme.dark.vars.accent` (§3). Implementation: sibling `loadThemeConfig(repoRoot): ThemeSection | undefined` — spec-settled, zero blast radius since `loadCouncilConfig`'s loop reads only `parsed.council` so a top-level `theme` is skipped with **no code change at all** to the existing loader — plus a pure `mergeThemeSection(baseJson, overrides?)` that shallow-spreads vars then colors over the base read via `path.join(PKG_ROOT, "themes", ...)`. One correctness trap on the record: **never resolve the base's var-refs to hex before merging** — keep un-overridden tokens as var-refs so a consumer vars edit transitively recolors everything referencing it. Scaffold: add `{ "enabled": true, "variant": "auto" }` (no override blocks — delta, not palette dump). Drops the card's `name` (default `pi-council`) key: the family is fixed, NAME-1 forbids bare `pi-council` as a theme name, and a key with exactly one valid value is speculative. Tradeoffs: per-variant blocks ~2 lines more than one flat `overrides` when recoloring both variants; `export` (pageBg/cardBg/infoBg) not overridable in EV-2 (validation vocabulary is ThemeColor ∪ ThemeBg; export survives merge untouched, deferred); strict unknown-key throwing inside `theme`; seeded `enabled: true` redundant (presence implies enabled) but accepted so the off switch is discoverable. Testable claims: (1) `loadThemeConfig` returns `undefined` for absent section, `"theme": false`, `"theme": {"enabled": false}`; returns `{variant:"auto"}` for `"theme": {}` — one off-path for EV-3. (2) malformed JSON → throws naming the file, same message shape as `loadCouncilConfig`. (3) `theme.dark.colors.nonexistent` throws naming the token; `accent = "#fff"` (3-digit hex, rejected by pi's `hexToRgb` at construction) throws at parse; `light.colors.accent = "cyan"` throws (undeclared in light). (4) Merge transitivity: `dark.vars.cyan = "#123456"` → `merged.vars.cyan === "#123456"` AND `merged.colors.borderAccent` still `"cyan"` (var-ref survives) AND `merged.colors.bashMode` still `"cyan"`. (5) Repo-wins: `dark.colors.mdHeading = "#123456"` → merged value is the override; untouched tokens byte-equal the shipped file. (6) Delta acceptance: `mergeThemeSection(loadShippedTheme("dark"), seededSection.dark)` deep-equals the shipped dark JSON, same for light. (7) Scaffold: fresh `scaffoldInto` → `.council.json` created and `loadThemeConfig(root)` returns the seeded section; rerun over a user-written file → `skipped`, bytes identical. (8) Zero blast radius: `loadCouncilConfig` on `{"theme": {...}}` returns `{}`, no existing test changes.

**principal** (cross-seam): Seam is config-surface ↔ engine ↔ merge-base. `scaffoldInto` (scaffold.ts:35-57) copies `council/scaffold/.council.json` non-clobberingly; `loadCouncilConfig` (seats.ts:116-140) iterates only `Object.entries(parsed.council)` (seats.ts:133-135) so a top-level `theme` sibling is invisible to that loop — adding it breaks nothing; the reserved-key skip is a guard for the mis-nested `council.theme` case only. Return-shape blast radius verified: `loadSeat` (seats.ts:179) passes `loadCouncilConfig` into `applySeatOverride` which does `config[seat.name]`; scaffold.test.ts:42 and seats.test.ts:263/270 read the return map directly — a return-shape change breaks all three, the sibling `loadThemeConfig()` breaks none. Merge-base side: shipped files are `{vars, colors, export}`; var sets differ per variant (dark has `vars.accent` #febc38, `vars.cyan`; light has `vars.teal` #5a8080, **no `accent` var**); var names and token names **collide** (in dark both `vars.accent` and `colors.accent` exist; `colors.accent = "accent"` + `colors.mdListBullet = "accent"` reference the var while `colors.border = "blue"` references another). The binding settled constraint is §3's transitive recolor — "a repo edit to `theme.dark.vars.accent` must transitively recolor `accent`/`border`" — which already spells the path **per-variant** with a **`vars` layer distinct from `colors`**. Blind spots: config-surface vantage cannot see that a var override has transitive downstream effects across multiple tokens, so it is tempted to flatten vars/colors into one `overrides` map — exactly what the settled semantics forbids; engine/activation vantage cannot see that `accent` is both a var and a token; the card's own draft is internally split ("dark and light palette vars" reads per-variant, but "name (default pi-council)" collides with NAME-1). Reframe: the shape is more constrained than "let the Council fix it" suggests — two decisions are effectively already made by settled constraints, only the third is open: (1) vars/colors split is **forced** — a flat `overrides` map cannot express "recolor the accent *var* (so `mdListBullet` follows transitively)" distinctly from "recolor only the accent *token*" because `accent` is both; the flat proposal is mutually incompatible with §3's settled transitive-var-recolor semantics. (2) Per-variant keys (`dark`/`light`) over a single `overrides` block — settled text already spells `theme.dark.vars.accent`, card says "dark and light palette vars", var sets genuinely differ per variant, so a single `vars` block is incoherent (an `accent` var override would be dark-only, meaning under `variant: auto` undefined). (3) The one genuinely open call: cosmetic shells — recommend scaffold ships minimal `{ "enabled": true, "variant": "auto" }` omitting empty `dark`/`light` shells (absent variant key = no delta for that base); satisfies "default scaffold section matches shipped omp palette" *because it is a delta*. `name` dropped (family fixed; NAME-1). Shape proposed: `theme: { enabled: true, variant: "auto", dark: { vars: {...}, colors: {...} }, light: { vars: {...}, colors: {...} } }` with `variant` ∈ `auto|dark|light` validated but **not resolved** by EV-2 (auto→dark/light is terminal-dependent, EV-3's job), and per-variant validation (a `vars` key must be a *declared* var of that variant — `theme.dark.vars.teal` throws; `colors` keys must be ThemeColor ∪ ThemeBg; values in the four accepted formats). Testable claims: (a) the flat shape has no defined semantics for colliding names — a test setting flat `overrides.accent: "#123"` and asserting `mdListBullet` can pass or fail depending on which side of the ambiguity the implementer picks, proving the shape underspecified. (b) Transitive recolor pin: `theme.dark.vars.accent → "#123"` recolors both `accent` and `mdListBullet`; `theme.dark.colors.accent → "#123"` recolors only `accent` — two assertions, same input key name, different merge layer. (c) Per-variant var validation: `theme.dark.vars.teal` throws (teal is light-only). (d) Spec §3's first "verified" example is **stale**: under current code `{"council":{"theme":"dark"}}` hits `qualifiedOrThrow` (seats.ts:82-86) and **throws** "must be qualified as provider/id" — it does not produce `{"theme":{"model":"dark"}}`; the object form `{"council":{"theme":{"enabled":true}}}` → phantom empty seat is accurate; the reserved-key skip resolves both. (e) Reserved-key isolation: `{"council":{"theme":{...}}, "theme":{...}}` → `loadCouncilConfig` returns no `"theme"` seat entry and `loadThemeConfig` returns the sibling. (f) Scaffold non-clobber with the split: fresh scaffold writes a `.council.json` whose `theme` resolves to the shipped palette post-merge (delta, not dump); re-run over a pre-existing `council`-only `.council.json` leaves it byte-identical — meaning existing repos get *no* theme config until the user adds it (absence = off) — that last consequence should be an explicit assertion, not an accidental one.

**designer** (human-centered): The consumer-developer's hand-edit mental model is flat — "I see X color in the TUI, I want to change X" — and the override surface should mirror what they perceive, with the layered vars↔colors abstraction available but not pushed in their face. Argues for **`theme.overrides` split into two optional sub-objects `colors` and `vars`**, each with its own validation vocabulary and merge order: `vars` resolves first (transitively driving any tokens whose shipped values are var-refs), then `colors` wins last so a specific token can always be pinned independently of any `var` change. Keys in `colors` are pi ThemeColor ∪ ThemeBg names; keys in `vars` are the shipped var names; values in either follow pi's accepted formats. Variant is a single top-level `variant: "auto" | "dark" | "light"`. Off is `enabled: false` (and absence; spec already accepts `theme: false` as equivalent). Gulf closed: *Execution* for the consumer who wants to recolor the accent — `colors` gives a 1:1 mapping from TUI-perceived color to a key they can type, no need to read the shipped asset; *Execution* for the rarer shared-color retune — `vars` is the right knob, discoverable from the seeded scaffold; *Evaluation* — empty `colors: {}` and `vars: {}` in the seeded scaffold teach the affordance before the user has typed anything; a one-line diff + next-session recolor is immediate feedback. Principles: the shipped file's layered vars↔colors structure (EV-1 round-2 verdict: "the affordance that makes the palette teachable"); hiding it behind a flat `overrides` is a teachability regression — but requiring the consumer to learn the structure to recolor one token is also wrong; splitting re-exposes the distinction at the user-facing edge. Knowledge in the world: with the split, the layered structure is on screen. Mapping: `colors.accent` ↔ accent in TUI (1:1); `vars.accent` ↔ every token whose shipped value references `"accent"` (transitive). Forcing function/error tolerance: validation rejects unknown `colors` keys and unknown `vars` keys with a message naming the file and listing the union of valid names. Merge (settled by spec): read `PKG_ROOT/themes/pi-council-{dark,light}.json`, apply `theme.overrides.vars` over shipped `vars` (repo wins), then `theme.overrides.colors` over shipped `colors` (repo wins, after vars); var-refs compose (EV-1 round-2 principal verdict: var-refs are THE load-bearing fact). Rejects principal's flat-overrides proposal (a user writing `blue: "#336699"` edits a var without knowing; visual change spans border/borderAccent/thinkingLow/mdLink/bashMode — a feedback surprise the layered structure was built to avoid; Gulf of Evaluation widens). Rejects the spec's working proposal (same flat problem). Falsifiable predictions: (1) token-level override compose — `theme: { variant: "dark", overrides: { colors: { accent: "#ff8800" }, vars: {} } }` → merged `colors.accent === "#ff8800"`, other tokens equal shipped dark. (2) var-level transitive — `overrides.vars.blue = "#336699"`, empty `colors` → `colors.border`, `borderAccent`, `thinkingLow`, `mdLink`, `bashMode` all `"#336699"` in dark; `colors.mdHeading` (literal `#febc38`, not a var-ref) unchanged. (3) Override-wins layering — `vars.blue = "#336699"` AND `colors.border = "#888"` → `border === "#888"`, other four blue consumers `#336699`. (4) Validation fail-fast names the file and lists valid token names for `colors.accemt` typo. (5) Validation var vocabulary — `vars.amber` throws (no `amber` var in either file — spec §1's amber trap). (6) Off switch vocabulary — `theme: false`, `theme: { enabled: false }`, `theme: { variant: "dark" }` distinct states, loader return makes the distinction visible to EV-3. (7) Scaffold invariant — fresh scaffold writes theme section; rerun over user-edited file is byte-for-byte no-op (extend scaffold.test.ts:42-65, don't duplicate). (8) Identity — freshly scaffolded section with both sub-objects empty merges against shipped dark to byte-identical JSON. Preferences (taste): seeds `"variant": "auto"` explicitly; seeds both empty `colors: {}` and `vars: {}` (lean) vs omitting; no strong view on bare `theme: false` acceptance; exact error-message wording is a copy decision for the implementation card.
