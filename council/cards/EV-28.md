## Intent

`Job.usage` currently keeps only input, output, a catalogue-estimated dollar
total and a turn count. The session JSONL the hub already parses carries
cacheRead, cacheWrite, cacheWrite1h, reasoning, totalTokens and a per-component
cost breakdown, but ingestion drops them, and the persisted `Usage` has no field
to receive them. Nothing downstream can be honest before the tuple exists. The
user-visible surface is the `council_wait` report head line — today
`cost=$X turns=N`, read by every facilitator and hub-enabled seat — and the
on-disk run manifest a person inspects under `/council-tree`. The head line must
report the token split (input, output, cacheRead, cacheWrite, reasoning, total)
and show the dollar value with its basis signified distinctly from a reported
charge; the manifest carries the same fields plus `costBasis` valued
`catalogue-estimate`. Zero usage renders as zeros; a dispatch that produced no
assistant message produces no head line.

## Acceptance

- A fixture assistant message carrying input 100, cacheRead 900, cacheWrite 0,
  output 10 and a per-component cost breakdown accumulates `cacheRead` 900
  (today it is dropped) and every token field separately.
- The persisted manifest and the `council_wait` report agree on the accumulated
  tuple and on `costBasis` = `catalogue-estimate`.
- The `council_wait` head line names the token split and the basis; it is not a
  scalar dollar total.
- `bun test`, `bunx tsc --noEmit`, `python3 council/validate.py` stay green.

## Phase 1 rulings (features-deliver, binding for this run)

- **R-1 money signifier** — an estimated dollar figure renders
  `cost≈$0.1234 (catalogue)`; a provider-reported figure renders
  `cost=$0.1234 (reported)`. The `≈` is U+2248.
- **R-2 token split** — the `council_wait` head line carries the token
  split (input, output, cacheRead, cacheWrite, reasoning, total) alongside
  the labelled cost, replacing the bare `cost=$X turns=N` scalar.
- **R-3 manifest** — the run manifest carries the same fields plus
  `costBasis` valued `catalogue-estimate`.

### (a) Design I would settle on

**1. One `Usage` type, four inline copies deleted.** Extend the persisted `Usage` in `runs.ts` to the full flat tuple, field names mirroring pi-ai verbatim, and replace the four duplicated inline tuple declarations (`hub.ts:19`, `eval-runner.ts:272`, `eval-rubric.ts:80`, `eval-rubric.ts:212` param) with an import of `Usage`:

```ts
export type CostBasis = "catalogue-estimate" | "reported";
export interface Usage {
  input: number; output: number;
  cacheRead: number; cacheWrite: number;   // accumulated, never folded into input
  reasoning: number;                        // subset of output — accumulate independently, never re-add
  totalTokens: number;
  cost: number;                             // scalar total — KEPT, this is the compatibility anchor
  costInput: number; costOutput: number; costCacheRead: number; costCacheWrite: number;
  turns: number;
  costBasis: CostBasis;
}
export type UsageMetric = Exclude<keyof Usage, "costBasis">;
```

**Flat cost-component scalars, not a nested `cost` object** — see rejections. New numeric fields are required (the write path always emits them); disk-tolerant reads already go through `?? 0`. `sumSubtree`'s `metric` parameter retypes from `keyof Usage` to `UsageMetric` (tsc forces this — otherwise `sum += node.usage[metric]` is a `number | string` type error). This is the only mandatory touch to `sumSubtree`, and it *grows* it: subtree sums of `cacheRead`/`totalTokens` come for free, which the eval layer's "three cost columns" ruling (grader-topology wiki page) can adopt later without another schema change.

**2. Ingestion** (`hub.ts:194-199`): add four accumulation lines next to the existing three — `cacheRead += u.cacheRead || 0`, `cacheWrite += u.cacheWrite || 0`, `reasoning += u.reasoning || 0`, `totalTokens += u.totalTokens || 0` — and set the four `cost*` components from `u.cost` the same way (`|| 0` guards every one; partial cost objects like the stub's `{total: 0.001}` must not produce `NaN`). The `costBasis: "catalogue-estimate"` stamp lives in the single `Job.usage` initializer at `hub.ts:133`; both `JobReport` (`hub.ts:265`, spread) and the manifest (`hub.ts:101`) copy `job.usage`, so **manifest/report agreement is by construction, not by a sync discipline** — which is exactly what the acceptance demands. The `"reported"` union member is future-proofing: when a provider-reported figure exists upstream, the one seam to change is that initializer.

**3. Head line** (`hub-tools.ts:45-47`) — extract a pure, exported composition function so EV-32's sibling surface (same R-1 money signifier, verified in `council/cards/EV-32.md`) reuses one implementation and a test can assert string equality:

```ts
export function formatUsageSegment(u: Usage): string {
  const money = u.costBasis === "reported"
    ? `cost=$${u.cost.toFixed(4)} (reported)`
    : `cost≈$${u.cost.toFixed(4)} (catalogue)`;   // ≈ is U+2248

}
```

## Cross-seam reading

The contract as it stands today, both sides opened:

**Capture side (inside the hub).** `extensions/hub.ts:19` declares `Job.usage` as an *inline anonymous* `{ input; output; cost: number; turns }` — a second, unshared declaration of the same tuple that `extensions/runs.ts:6-11` defines as `Usage`. `hub.ts:191-198` is the only accumulation point: it parses the child's **stdout NDJSON** `message_end` events, and it increments only when `event.message?.role === "assistant"`. It reads `u.input`, `u.output`, `u.cost.total` and drops `cacheRead`, `cacheWrite`, `reasoning`, `totalTokens`, and every cost component. `hub.ts:265` returns `usage: { ...job.usage }` — a shallow copy that is harmless only because `cost` is a primitive.

**The source pi actually has.** `@earendil-works/pi-ai/dist/types.d.ts:265-285`: `input`, `output`, `cacheRead`, `cacheWrite`, optional `cacheWrite1h`, optional `reasoning`, `totalTokens`, and `cost: { input, output, cacheRead, cacheWrite, total }`. Two load-bearing facts live in that type's own comments: `reasoning` is a **subset of `output`** (types.d.ts:274-280), and `cacheWrite1h` is a **subset of `cacheWrite`**. `pi-ai/dist/models.js:530-548` shows `cost.total = input + output + cacheRead + cacheWrite`, and that the 1h premium is folded *into* `cost.cacheWrite`. `totalTokens` is **not** re-derivable: Anthropic computes it (`api/anthropic-messages.js:414-416`) while Google/Vertex copies the provider's `totalTokenCount` (`api/google-vertex.js:181`).

**Consumer side.** `hub-tools.ts:47` is the entire report head line: `... turns=${r.usage.turns} cost=$${r.usage.cost.toFixed(4)}`. `sumSubtree` (`runs.ts:160-167`) returns a **number** keyed by `keyof Usage`; `cellCost` (`eval-runner.ts:218-224`) does `driverUsage?.cost ?? 0` and adds it to a number; `TerminalTelemetry.usage` (`eval-runner.ts:272`, assigned at `:313`), `CellScope.usage` (`eval-rubric.ts:80`) and `projectVerdictRecord` (`eval-rubric.ts:212-217`) all pin `cost: number`. Roughly seven test files construct `usage: { …, cost: 0, … }` literals.

**The mismatch the card's premise hides.** The card says "the session JSONL the hub already parses." The hub does **not** parse the JSONL; it parses stdout NDJSON, and `transcript.ts` parses the JSONL only into display blocks, with no usage accumulation. More importantly, pi's own session accounting counts three sources — `agent-session.js:2661-2688` iterates assistant messages **plus `toolResult` messages (`message.usage`) plus `branch_summary`/`compaction` entries (`entry.usage`)**; both entry kinds carry `usage?: Usage` (`session-manager.d.ts:44,55`) and tool results carry optional usage (`extensions/types.d.ts:732`). The hub's stream capture counts only assistant messages. Tool-result usage is on stdout but filtered out at `hub.ts:191`; **compaction usage never appears on the stream at all** — it only lands in the session JSONL. So the manifest tuple and the child's session JSONL are two views of the same spend, and for any seat that compacts they disagree.

- **Owner/engine view (inside `hub.ts`):** sees only the stdout NDJSON contract. - **Data/pipeline view (JSONL):** sees the complete usage enumeration and therefore assumes the hub manifest is the same number. It cannot see the assistant-only filter at `hub.ts:191`.
- **Frontend/report view (inside `hub-tools.ts`):** sees a `usage` object and will render each field as a number. It cannot see that `reasoning` is optional *by design* to distinguish "provider does not expose it" from "zero", nor that `totalTokens` is provider-reported rather than the sum of the six named fields.
- **Eval/leaderboard view:** reads `usage.cost` as a number across ~25 sites. It cannot see that a union-typed or optional reshape (`number | object`) would let `tsc` stay green while `sumSubtree`/`cellCost` silently produce `NaN` on on-disk manifests that `readManifests` casts to `RunManifest[]` without validation (`runs.ts:74-88`).

## Reframe

The card's framing — "add fields to `Job.usage` and `Usage`" — is a local widening of `hub.ts`'s accumulation loop, and the ruled shape (tuple + `costBasis = catalogue-estimate`) is sound. But the true seam is not the field list; it is **what the tuple is a projection of**.

The manifest is a *stream projection*: assistant `message_end` events only. EV-30's own-session half is a *session enumeration*: assistant + toolResult + compaction. EV-31 persists the record, EV-29 attaches provider-reported components, EV-32 renders it at the exit points — and every one of those descendants will treat the manifest tuple as the invocation's real spend. If EV-28 leaves capture stream-side and silent about it, the epic ships a durable record whose subtree half and session half are on different accounting bases — the exact honesty defect the epic exists to remove.

Concretely, the boundary I would put between capture and consumers:

- **Capture (`hub.ts:191-198`) owns faithful accumulation from pi's `Usage` verbatim** — every field, including `cacheWrite1h` and `reasoning`, never deriving `totalTokens` from components, never summing `reasoning` into a total. It imports `Usage` from `runs.ts` and deletes the inline duplicate at `hub.ts:19`, so there is exactly one shape.
- **Persistence at settle owns reconciliation and provenance.** The child session path is already derivable at settle — `runs.ts:110-131 findSessionFile(repoRoot, runId, jobId)`, with `sessionDir`/`sessionId` set at dispatch (`hub-tools.ts:187-190`). If EV-28 reconciles the persisted tuple from that JSONL at settle, the manifest and EV-30's session parse share one basis by construction. If reconciliation is too much for this card, the lighter compliant option is to make the record **name its source and scope** (stream-assistant vs session-all-entries) so no downstream consumer mistakes a projection for the total — silence is the only inexcusable option.
- **Consumers own projection only.** `cost.total` stays the scalar aggregate metric so `sumSubtree`, `cellCost` and the verdict records keep their meaning; the components are additive. Whether `cost` nests (`cost.input`, per the goal) or the components sit beside a scalar `cost` is a mechanical choice, but `hub.ts:265` must deep-copy once `cost` is an object, or `report()` hands callers a live alias into `job.usage`.

The alternative seam I reject: **treating the change as a local widening of `processLine` + `Job.usage`, with `runs.ts`/`hub-tools.ts` as passive sinks.** It satisfies every acceptance line for a single hub instance, but it (i) leaves the source-of-truth question unasked, (ii) leaves two declarations of the same shape free to drift, and (iii) lets `costBasis` be a report-only decoration — while EV-30/31 read the *manifest*, not the report, so a manifest without the basis would still pass a report-level test.

#### Position — `designer`

## Position

The head line is a single dense line read under time pressure by a facilitator (LLM or person) scanning a batch that often settles several jobs at once. The two binding constraints are:

1. R-2 forces six token fields + labelled cost into the same line that today carries two scalars.
2. R-1 forces the `$` / `≈` + `(catalogue|reported)` distinction to be unambiguous at a glance.

If I just append fields, the line will be unreadable in a batch of 4–8 settled jobs (which is normal: a 3-wave deliberation settling simultaneously). The design problem is **legibility under density, not completeness**.

### Proposed head line shape

```
[job-1] seat=owner state=done stopReason=stop elapsed=2.3m turns=3 tokens=in 1,200 / out 340 / cacheRead 9,000 / cacheWrite 0 / reason 1,800 / total 12,340 cost≈$0.0421 (catalogue)
```

**Reading order rationale** — left-to-right scan matches the cognitive path a person uses when a batch settles: *who* (id, seat) → *what happened* (state, stopReason, elapsed, turns) → *what it cost in tokens* (the split) → *what it cost in money* (the labelled basis). Money is rightmost because it is the most consequential number for budget reasoning but requires the most interpretation.

**Token split compression** — six fields, comma-free, separated by `/`, each labelled by a 2–6 char prefix: `in`, `out`, `cacheRead`, `cacheWrite`, `reason`, `total`. `reason` (not `reasoning`) because `reasoning` collides with the *stopReason* earlier on the line. (A preference, ranked last.)

**Number formatting** — thousands separator (`,`) only, no unit suffix. `cost` stays 4dp because R-1 is meaningful only at dollar-cent granularity.

**Label placement** — `(catalogue)` / `(reported)` directly after the money figure, no space before the parenthesis.

**Width prediction** — at the values shown above, the line measures ~145 columns on a fixed-width terminal; fits 160-col, **wraps** at 120-col. **This is the legibility risk.**

### Batch scanning

1. **Right-edge alignment of the cost figure** — `cost≈$X.XXXX (catalogue)` rightmost on every line, so a vertical scan down the right edge yields a clean column of comparable money figures. This is the affordance I most want.
2. **Token-split fields have stable internal order** — `in / out / cacheRead / cacheWrite / reason / total`, so a person can pattern-match a single column without reading every label.

### Estimated vs reported

# EV-28 ruling — five items, binding on resumed runner

## Q1 — Cost-component shape (flat vs nested)

**Ruling.** Flat. Persisted record is `Usage.{input, output, cacheRead, cacheWrite, reasoning, totalTokens, costInput, costOutput, costCacheRead, costCacheWrite, cost, turns, costBasis}` with scalar `cost` retained as the aggregate; the wire shape `Usage.cost.{input, output, cacheRead, cacheWrite, total}` (pi-ai) is the inbound shape that ingestion flattens one-to-one. Concretely, the type's `cost` stays `number`; four new `costInput / costOutput / costCacheRead / costCacheWrite: number` siblings are added with `?? 0` guards in the ingestion loop and `cost.total === costInput + costOutput + costCacheRead + costCacheWrite` as the post-condition (and a test for it).

The single one-clause wire→record ratification: **"on ingestion, `u.cost.input → usage.costInput`, `u.cost.output → usage.costOutput`, `u.cost.cacheRead → usage.costCacheRead`, `u.cost.cacheWrite → usage.costCacheWrite`, and `u.cost.total → usage.cost`; partial cost objects (e.g. `{total:0.001}`) coerce the missing components to 0, never NaN; the goal's dotted `cost.input|…` refer to the wire components that ingestion flattens, not to a nested record shape."** This clause goes in a doc-comment on `Usage` in `runs.ts` (alongside the scope doc from Q4) so a judge reading the goal's dotted paths is not guessing.

**Options rejected.**
- **Nested `cost: { input, output, cacheRead, cacheWrite, total }`.** Breaks retained legacy manifests through `readManifests`'s unvalidated cast (O3 `closed-green`), aliases `JobReport.usage.cost` into `job.usage.cost` through `hub.ts:265`'s shallow spread when nesting arrives (O4 `closed-green`), and migrates ~25 typed consumer sites plus every persisted `VerdictRecord.gradingUsage.cost` in append-only eval stores (CONFIRM-2 class). Cost is identical data delivered under the flat shape.
- **`cost` plus a separate nested `costBreakdown` object.** Two representations of the same numbers drift; flat fields have one.

**Grounding.** Goal sentence names cost components; acceptance names none. R-3 is silent on nesting. Skeptic O3 + O4 (`closed-green`). Consolidator's open-judgment #1.

**Reversibility.** Flat is reversible to nested on this card only by a clean-break migration with a `GradingUsage`/eval-store follow-up that records the change in `eval-store-contract`. Cheap-to-reverse under the flat shape because the alternative is one card wide; expensive under the nested shape because records on disk in `council/eval-results/` cannot be un-writ.

## Q2 — "No head line" scope, suppression predicate, and `turns` survival

**Options rejected.**
- **Full-line suppression on zero assistant message.** Wipes id/seat/state attribution; the existing warning block cannot be tied back to a job in a multi-job wait.
- **`turns === 0` predicate alone.** Over-suppresses any job that emitted a `message_end` with zero usage (legal for short prompts or hit-cached responses); the `output === ''` clause keeps that case on the line with all-zero tokens and `cost≈$0.0000 (catalogue)`.

**Grounding.** Card `Intent` ("a dispatch that produced no assistant message produces no head line") read with the ruled scope above; `hub-tools.ts:50` warning text; Skeptic O5 (`closed-red` on grep-compat but outcome uncontested); consolidator's open-judgment #2.

**Reversibility.** Trivially reversible — the suppression predicate is one comparison pair; the identity prefix is unaffected by it.

## Q3 — `cellScope.usage` widening: whitelist vs recorded amendment

**Ruling.** **Whitelist at `eval-runner.ts:312-313`** (and at the `CellScope.usage` literal in `eval-rubric.ts:80`). Concretely, the `cellScope.usage` assignment picks the four token fields plus `cost` and `turns` (the recorded store shape), and explicitly **omits** `costBasis`, `costInput`, `costOutput`, `costCacheRead`, `costCacheWrite`, `cacheRead`, `cacheWrite`, `reasoning`, `totalTokens` — those live on the runtime hub record and the manifest, but they do NOT enter the persisted `StoredResultRecord.cellScope.usage` this card. The eval store contract (wiki: `eval-store-contract`, summary: append-only, `cellScope: {usage{input,output,cost,turns}, …}`) stays intact at the literal level; widening the record to carry the full tuple rides a follow-up card that records its own amendment in `vault/wiki/eval-store-contract.md`.

**Options rejected.**
- **Accept the widening and record it as an amendment in this card.** That is two shape changes: the schema widens AND the recorded shape doc amends. Both decisions belong together — splitting them risks an amendment that drops a field. The whitelist preserves the recorded contract unchanged, so no amendment is needed at all; the engineer who needs the full tuple on `cellScope.usage` earns the amendment via a separate card against a separate set of acceptance lines.
- **Whitelist by literal type narrowing only (changing `CellScope.usage`'s declared shape).** TypeScript's structural typing accepts extra properties on assignment if the literal widens; the whitelist has to be at the assignment site, not the type site. Hence `eval-runner.ts:312-313` is where the explicit pick happens.

**Grounding.** `eval-store-contract.md` summary; `eval-runner.ts:311-318`; `eval-rubric.ts:80`; CONFIRM-2 precedent (`cell-aggregation.md`). Consolidator's open-judgment #3 + Skeptic O10 fact half `closed-green`.

**Reversibility.** Whitelist is reversible in one site; the whitelist keeps the on-disk record shape intact, which is the cheapest-to-reverse call for records already on disk across `council/eval-results/`. No escalation to `steward`.

## Q4 — Capture-scope remedy: doc-comment floor vs persisted `usageSource` field

**Ruling.** **Persisted `usageSource: 'stream-assistant' | 'session-reconciled'` field on `Usage`.** Default value stamped at the `Job.usage` initializer (`hub.ts:133`) is `'stream-assistant'` (this card's capture is assistant `message_end`-only on stdout; tool-result and compaction usage are absent — Skeptic O1 + O12 fact half `closed-green`). The second value, `'session-reconciled'`, is reserved for the session-enumeration half — EV-30's goal — and is **not** written this card; the union member exists so a future ingest reconciliation at settle can flip the field without re-declaring the type. Document this addition in the card's "Phase 1 rulings applied" list when you resume, so an audit reader sees both R-3 and this card rule applying.

**Options rejected.**

- **Mark `Usage` as session-reconciled by default.** False — capture is provably stream-side only this card (O1 + O12 fact half).

**Grounding.** Skeptic O1, O12 fact half `closed-green`; durable record shapes are settled at the seam where they are written; the "two-shape-changes-to-a-durable-record" cost is CONFIRM-2 applied one layer up.

**Reversibility.** `usageSource` is a new field with no reader today; dropping it is a type-edit not a data-edit. The default `'stream-assistant'` is truthful for this card's capture.

## Q5 — Head-line width re-budget + tied sub-calls

**Ruling.**
- **Width budget target.** The head line fits in **≤160 columns** at the acceptance-fixture values. Skeptic O6 `closed-red` blocks implementation under any composition that wraps at 160. The 120-col fit is a stretch goal, not a constraint.
- **Concrete literal composition.** When the usage segment is rendered (Q2 predicate above), the line is:

  ```
  [${id}] seat=${seat} state=${state}${stopReason ? ` stopReason=${stopReason}` : ""} elapsed=${mins}m turns=${turns} tokens=in ${input}/out ${output}/cR ${cacheRead}/cW ${cacheWrite}/reason ${reasoning}/total ${totalTokens} cost≈$${cost.toFixed(4)} (${costBasis === "reported" ? "reported" : "catalogue"})
  ```

  Required reductions vs. the designer's round-1 verbatim proposal:
  1. **Label collapse for cache fields only.** `cacheRead` → `cR`, `cacheWrite` → `cW`. Persisted fields stay `cacheRead` / `cacheWrite`; the head-line label collapses.
  2. **Drop the thousands separator.** No `,`, no ` ` between orders of magnitude.
  3. **`/` separators with a single space each side, no trailing space before the next token-name prefix.**
  4. **Tighten the identity prefix.** `${state}` followed by ` stopReason=…` only when present; `elapsed=${mins}m` one decimal.
  5. **Rightmost money.** `(catalogue)` / `(reported)` directly after the figure, no space before the parenthesis. The figure stays rightmost — designer's batch right-edge-alignment affordance preserved.
- **Tied sub-calls.**
  - **Head-line label for the persisted `reasoning` field: `reason`.** Collision with `stopReason` earlier on the line; the persisted field stays `reasoning`.
  - **`turns` stays on the head line.**
  - **Money figure position:** rightmost; `turns` immediately before `tokens=`.
  - **No line wrapping.** The line must fit one line at 160 cols as composed. A future fixture exceeding 160 is a follow-up card, not a Q5 correction.

The acceptance-fixture variant (input 100 / output 10 / cacheRead 900 / cacheWrite 0 / reasoning 7 / totalTokens 1010 / cost 0.0013 / turns 1) must measure under 160 columns; the designer's `cacheRead 9,000` example variant must measure under 160 columns. A unit test pins the byte length at both fixtures against the 160-col threshold (O6's settling test rerun).

**Options rejected.**
- **`cacheRead`/`cacheWrite` full labels with thousands separators.** Refuted by O6 — 180 cols.
- **Adding `cacheWrite1h` as a seventh field.** Past any budget; not named in acceptance.
- **Wrapping to two lines.** Defeats vertical batch alignment.
- **`reasoning` as the head-line label.** Collides with `stopReason`; persisted field stays `reasoning`.

**Grounding.** Skeptic O6 `closed-red`; consolidator's open-judgment #6; R-2 names the data, not the label.

**Reversibility.** Render-level, inside one formatter function (`formatUsageSegment`, lifted from `formatReport`). Reversible in one file.
