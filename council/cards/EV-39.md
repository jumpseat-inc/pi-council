## Intent

This card does not address the intake; it fixes a child seat's provider error.
Council already owns this path — the child's error is captured at
`hub.ts:196-205` and the parent can re-spawn the job — so it is the second,
easier half of the epic.

`maxDelayMs`, and `jitter` fields (R2), and the delay follows pi's existing
shape (`baseDelayMs * 2^(attempt-1)`, capped at `maxDelayMs`, jittered when
`jitter` is true). The final report carries an explicit attempts sentence.

# EV-39 — owner first-pass position

## Position

### 1. Where the loop lives

**A new module, `extensions/job-retry.ts`, supervising per-dispatch — not a loop inside `Hub`, not a loop around the tool calls.** The decisive fact is in `hub-tools.ts:243-261` (`council_dispatch` execute): the seat `input` exists only as a local (`params.input`), the prompt file is a per-dispatch `mkdtempSync` tmpdir, and the cleanup closure that deletes it is handed to `hub.spawnJob`. `Hub.spawnJob` (`hub.ts:106`) stores `command`/`args`/`env` only implicitly as the spawn call's inputs — the `Job` object holds none of them, and `settle()` (`hub.ts:251-259`) **runs and nulls `cleanup`**, deleting the prompt file the moment attempt 1 closes. So:

- **Hub-owned re-spawn** reusing stored `command`/`args`/`env` is impossible as-is: the spec isn't stored, the prompt file is already deleted, and the retry *decision* (policy classification) is not Hub's business — `Hub` would import policy concerns, violating its supervision-pure role.
- **A loop around dispatch/wait at tool granularity** is impossible: `council_dispatch` is one-shot stateless per call and `council_wait` *blocks the parent's turn* — nobody is home between tool calls to run a loop.
- **The seam is therefore post-spawn, pre-forget**: `council_dispatch` already holds everything the retry needs (the full spawn spec, the prompt tmpdir, the resolved seat/model). It hands that bundle to a `RetrySupervisor` (new `extensions/job-retry.ts`) as fire-and-forget (`void`), which subscribes to the Hub's existing `onChange` (composed in `getHub`, `hub-tools.ts:34-52`) to observe settles — no new Hub→supervisor callback API. The supervisor classifies, sleeps (injected timer, unref'd), re-spawns via `hub.spawnJob`/a small new `Hub.respawn`, and finalizes. `hub-tools.ts` keeps only wiring; the supervisor's decision core is injectable and unit-testable. Keeping it out of `hub.ts` honors AGENTS.md §7 — the Hub gains only small, additive, individually-tested deltas (listed under 4), never a policy import.

Cost accepted: one more module and one more indirection (dispatch → supervisor → hub) versus a Hub that "just knows". The indirection is the price of keeping `hub.ts`'s battle-tested stall/kill semantics untouched.

### 2. Identity across attempts

- **Job id: reused.** R4 ("one job-tree row per dispatch") makes this non-optional — the tree (`tree.ts:64-67`, `navigator.ts:344`) reads `readManifests` keyed by manifest `id`; a sibling id would mint a second row, which R4 forbids. The supervisor re-spawns under the same id; `Hub.jobs.set(id, job)` (`hub.ts:156`) replaces the Job object.
- **Manifest: one file, overwritten per attempt.** `writeManifest` (`runs.ts:111-113`) writes `<id>.json` atomically-overwriting; the final write is the last attempt's settled state. That is exactly R4's "no extra rows". EV-39 must **not** invent per-attempt manifest filenames — that plus `attemptGroupId` is EV-42's deliverable.
- **`attempt` field: added now, name agreed, semantics minimal.** R4's `attempt 2/3` is rendered from manifests (the only channel the passive renderers read — the navigator is a component over `readManifests`, `navigator.ts:344`), so without the field R4 is unexpressible. EV-40 §2.8 (spec:313-316) explicitly leaves the run-substrate `attempt` field to "EV-39, EV-42" with only the *name* agreed — so EV-39 mints `attempt?: number` (current attempt; **absent for attempt 1**, so every existing non-retry manifest stays byte-identical) and EV-42 later adds `attemptGroupId` + sibling binding. EV-39 must not pre-empt: no `attemptGroupId`, no sibling ids, no second field name for the total.
- **The "of 3" total** comes from the policy, not the manifest: the renderers compose `attempt ${n}/${loadRetryConfig(repoRoot).maxAttempts}` — no new un-agreed manifest field.
- **Session dir: same run dir.** **Session file: one per attempt, session-id-suffixed for n ≥ 2** (`--session-id ${id}-attempt2`). Today `writeJobManifest` hardcodes `sessionId: job.id` (`hub.ts:96`); two attempts sharing it would leave two `.jsonl` files with identical first-line ids and `findSessionFile` (`runs.ts:139-160`) returning an arbitrary one — the navigator would tail the *wrong* attempt's transcript live. `id` vs `sessionId` are already distinct manifest fields, so the substrate supports this without new identity machinery; the suffix naming is **provisional, EV-42 finalizes it**.
- **Usage accumulator: carried, cumulative.** A fresh `spawnJob` zeroes usage; attempt 2's spend would be lost from the manifest and the parent's usage block would under-count (an EPIC-7 honesty violation). New `Hub.respawn(id, opts)` carries `prev.usage` into the new Job (resetting `startedAt`/`output`/`stopReason`/`errorMessage`/`exitCode`/state). Every attempt's manifest then carries the *cumulative* tuple; `sumSubtreeUsage` stays correct (one file per id, containing the true total); per-attempt breakdown lives in the per-attempt session JSONLs.

### 3. The retry decision

**Reuse `classifyRetry(report)` (`retry.ts:103-123`) and `computeBackoffDelay(policy, attempt, rand)` (`retry.ts:155-168`) verbatim — no second copy.** The EV-40 watch item warns precisely against two diverging delay functions, and `classifyRetry`'s state-independent clause is the settled R1 semantics; re-deriving either is divergence by construction. The supervisor's decision step is: on settle → `classifyRetry(hub.report(job))`; `"retry"` and `attempt < maxAttempts` and `policy.enabled` → backoff+respawn; `"retry"` with budget spent → exhausted finalize; `"terminal"`/`undefined` → final settle (unchanged behavior).

**`loadRetryConfig(repoRoot)` is read per dispatch** inside `council_dispatch` execute (cheap file read; a mid-session policy edit applies to the next dispatch; tests inject the policy directly into the supervisor, bypassing the file). On **malformed config**: catch the throw, **dispatch proceeds with retry disabled, and the tool result carries a loud warning line** (same posture as EV-40's parent path — "a throw disables retry and notifies; the malformed-config session must not crash", EV-40 spec §3.3). Refusing the dispatch because its *policy file* is malformed would conflate a legitimate dispatch with a config defect. This does not violate gate-parity (that rule constrains write/validation layers being stricter than runtime, not runtime read-leniency).

### 4. Interaction with the supervisor

The Hub deltas — each additive, each with a failing test first (AGENTS.md §7):

- **New `JobState "retrying"`** (`hub.ts:5` union) used only during the backoff window: set by the supervisor synchronously in the settle-observation path, *before* any 200ms wait poll can see the settled inter-attempt state. During `"retrying"`, `tick()` already ignores the job (it monitors only `"running"`, `hub.ts:233`) — correct: no live process to stall or time out. An attempt that itself stalls or times out is unaffected (stall → terminal per `classifyRetry`; timeout informational → close → classify).
- **`isSettledForWait` gains a `"retrying" → false` clause** (`hub.ts:291-297`) — this is the Q5 fix; see 5.
- **`cancel` handles `"retrying"`** (`hub.ts:261-274`): today it bails on `exitCode !== null` — true during backoff — so a parent couldn't abort a retry. New: state `"retrying"` → set `"cancelled"`, write manifest, fire `onChange`; the supervisor's post-sleep check (`job.state !== "retrying"` → abort loop, run cleanup) is the arbitration point — no new Hub→supervisor edge needed. Cancel during attempt-N *running* is today's path and lands as terminal.
- **`shutdown`/teardown during backoff**: the supervisor gets `dispose()` called from the same place `shutdownHub()` runs in `index.ts` (session_shutdown), disarming pending timers (all unref'd so nothing holds the event loop) and finalizing supervised jobs (run real cleanup, leave the last manifest). `shutdown()`'s live-pid loop naturally skips retrying jobs (no live pid).
- **`writePids`** needs no change: during backoff `exitCode !== null` so the pid file correctly omits the job; after respawn the new pid is listed (`hub.ts:160`, `writePids` at settle/spawn).
- **Cleanup lifetime: the supervisor owns it under retry.** `settle()` runs `job.cleanup?.()` (`hub.ts:254`) — if the dispatch's tmpdir-removal closure reaches `spawnJob` while a retry is armed, attempt 1's settle deletes the prompt file out from under attempt 2. So: retry disabled → pass the closure through unchanged (byte-identical behavior); retry armed → pass a no-op to the Hub, hold the real one, and run it exactly once at loop end (clean settle, exhaustion, cancel-during-backoff, or dispose), best-effort wrapped.

### 5. Observation from a blocked `council_wait`

The hazard is real and I traced it: attempt 1 settles → `exitCode` set, state `done/failed` → `hub.wait`'s poll (`hub.ts:300-311`, 200ms interval, `isSettledForWait` `hub.ts:291-297`) would resolve **mid-retry**, handing the parent a report that looks final; the parent then `cancel`s or moves on while the supervisor is about to re-spawn — a cancelled-but-actually-retrying job. The fix is the `"retrying"` state + the `isSettledForWait` clause (4): the supervisor flips the state synchronously inside its settle observation, which fires before the next 200ms poll, closing the window by construction. `council_wait` therefore resolves once, after the *final* attempt — or at its deadline, returning an honest `state=retrying` report with the `attempt 2/3` label (the parent re-waits; that is the documented never-cancel-on-timeout contract).

`council_cancel` during backoff: "Cancelled job-5.", the chain aborts, no attempt 2 ever spawns (spawn-count falsifiable, P2 below), row renders `⊘ … attempt 2/3`.

### 6. The final report

Produced in **`formatWaitReport` (`hub-tools.ts:106-122`)** — it already receives `manifests` (source of `attempt`) and is called from `council_wait` execute, which has `repoRoot` (for the policy's `maxAttempts`); plus one line in **`formatReport` (`hub-tools.ts:78-104`)**. Shape:

- **Head fragment** (only when the job made >1 attempt; single-attempt reports stay byte-identical — EV-28's byte tests hold): `[job-5] seat=skeptic state=done stopReason=stop attempts=2/3 elapsed=3.1m <usage-segment>` — `key=value` matches the head's existing grammar.
- **Explicit sentence** after the body/error sections, before the usage block, for jobs with `attempt ≥ 2` in the manifest:
  - clean: `Settled on attempt 2 of 3.` 
  - exhausted: `Retry budget exhausted after 3 of 3 attempts; last error: <errorMessage>.`
- The usage block (EV-32 point 5) is appended unchanged and now reflects cumulative cross-attempt spend via the carried usage.

The exact sentence copy remains designer territory (R4 leaves it open — facilitator record, step 1); my commitment is the *shape*: head fragment + one sentence, count = attempts made, total = policy max.

### 7. Budget exhaustion

The last failed attempt leaves: state = that attempt's settle state (typically `done` with `stopReason="error"` + a retryable `errorMessage` — EV-37's own comment, `retry.ts:5-8`, notes provider-errored children exit 0), manifest `attempt = maxAttempts` with cumulative usage, cleanup run, supervisor disarmed for the id. The loop distinguishes exhausted from clean-settle-on-2 **without extra state**, derivable in `formatWaitReport`: `classifyRetry(finalReport) === "retry"` ∧ `attempt === policy.maxAttempts` ⇒ exhausted sentence; `attempt ≥ 2` otherwise ⇒ clean sentence. No supervisor memory leak, no new persistence.

## Risks & unknowns

- **EV-42 pre-emption is the biggest risk.** The session-id suffix (`-attemptN`) and cumulative-vs-per-attempt manifest usage are provisional decisions EV-42 may want to make differently. Mitigation: record both as provisional in the card record; EV-42 owns the final naming and must keep `sumSubtreeUsage` from double-counting once per-attempt manifest files exist.
- **The `"retrying"` state leaks into every state consumer** (tree glyph, navigator copy/order/tokens, `classifyRetry`'s SETTLED_STATES — which correctly returns `undefined` for it, `formatWaitReport`'s settled set — which must exclude it so no usage block renders mid-backoff). Each is a small additive edit with a test, but the blast radius is wider than hub.ts alone.
- **The settle-observation window** relies on the supervisor's synchronous flip ahead of the 200ms poll. It is order-by-construction (same synchronous callback chain), but if a future change makes `onChange` async, the window reopens — P4's test pins it.
- **A mid-run policy edit** changes only the denominator "of N" in rendered copy for already-running jobs (read per render). Cosmetic, accepted.
- **Wiki gap:** no wiki page covers retry; the hub page's "stable semantics" warning is the only standing constraint. The landed design should seed a wiki page (hub-retry) at close.

## Position

**The epic's "hub retry is the second, easier half" is false at this tree, and it is false in a way that changes who owns the card.** `Hub` owns *settle observation*; it does not own *spawn*. `council_dispatch` owns spawn and bakes the seat `input`, the prompt file path, the model and the MCP allowlist into `args`/`env` at the moment of spawn (`hub-tools.ts:170-206`). Three consequences are already visible in the code, not hypothetical:

1. `Job` does **not** store the spawn spec. The facilitator's grounded fact ("takes the full child spec … and stores it on the `Job`") is wrong — `Job` carries `seat/model/pid/state/timeoutMs/stallMs/cleanup/usage` (`hub.ts:11-30`) but **no `command`, `args`, `cwd` or `env`**. The Hub cannot re-spawn from its own table.
2. The prompt file is deleted *at settle* — `settle()` calls `job.cleanup?.()` and then nulls it (`hub.ts:253-255`), and that cleanup is `fs.rmSync(tmpDir)` (`hub-tools.ts:203-208`). So even handing the Hub the argv would re-spawn against a deleted `--append-system-prompt` file.
3. `pi -p --session-dir D --session-id X` with an existing X **resumes** that session (`dist/main.js:335-341`: `findSessionByExactId` → `SessionManager.open`). `buildChildArgv` sets `sessionId = jobId` (`hub-tools.ts:195-198`, `seats.ts:600-625`). So a re-spawn that *reuses the job id* hands attempt 2 attempt 1's errored assistant turn in context — the exact payload class EV-40's structural filter exists to strip (EV-40 spec §2.4), and the Hub has no such filter.

**Reframe:** the loop is not "Hub or tool layer" — it is a **split-ownership capability**: the Hub owns the lifecycle state machine (attempt counter, backoff timer, cancel, wait visibility, manifest state), and the **dispatch layer owns a `respawn` closure** (fresh prompt file, fresh session id, fresh argv) registered at `council_dispatch` time. Neither existing layer owns retry today, and the reason is structural: retry needs settle observation (Hub-only) *and* spawn inputs (tool-layer-only) *and* a timer that must outlive the parent's `council_wait` call.

The two latent alternatives, both of which I name and reject:

- **`council_wait`-driven loop** (tool layer classifies the returned report and re-dispatches): fails the card's goal. `council_wait` is LLM-invoked; if the parent doesn't re-call it, no retry happens. A module-level registry with an unref'd timer would survive the call, but then a respawn can be armed while the parent's turn is ending — exactly the window where `flushUsage("agent-settled")` (`index.ts:741`) freezes the usage record. It also makes `cancel` impossible mid-backoff (the parent is blocked inside the tool call).
- **A parent-invoked `council_retry` tool**: worse — the retry becomes a request the model may forget. The epic's word is "is re-spawned", not "may be re-spawned".

**Blind spots, named separately.**

- *From inside the pipeline/hub slice:* the Hub cannot see that its spawn inputs came from a tool-layer closure, nor that `settle()` deletes them; it reads `Job` as self-sufficient. It also cannot see that `wait`'s settledness is what the *parent's next action* keys on.
- *From inside the tool/UI slice:* the tool layer cannot see that `settle()` is the only place the retry decision can be taken without a window (see §Wait), nor that `buildTree`'s orphan rule (`tree.ts:17`) will light up during every backoff.
- *From inside the run substrate:* "one row per dispatch" (R4) looks like a render request; it is actually a statement about **manifest cardinality**, which is why EV-42's premise is at stake (below).

### Wait semantics — the precise hazard

Today, with the loop nowhere, attempt 1's provider error sets `state=failed, exitCode!=null` in `settle()`, `onChange` fires, and `wait` returns the retryable report. Any design that arms a backoff **after** that point has already handed the parent a settled report. Concretely, an unmodified `council_wait` returns during backoff because:

- `isSettledForWait` is true (exitCode set) — `hub.ts:291-295`;
- even if you keep the job `running`, the 200 ms poll (`hub.ts:307`) races the timer arm.

And if you keep the job `running` with attempt 1's `startedAt`, a second, sharper defect appears: `isSettledForWait` returns **true for `timeout`** (`hub.ts:292`), and `tick()` sets `timeout` on `now - startedAt > timeoutMs` (`hub.ts:244-247`) — so a dispatch whose first attempt used most of its 15-minute ceiling flips to `timeout` at attempt 2's start and `wait` returns mid-retry. Meanwhile `tree.ts:17` renders that same job `☠ orphaned` (state `running`, pid dead) during every backoff — precisely the window R4 wants labelled `attempt 2/3`.

Minimal honest fix, and it is *cheap under §7*: retry gets its **own non-settled job state** (e.g. `retrying`), with (a) `tick()` unchanged — it already `continue`s on `state !== "running"` (`hub.ts:233`), so no stall/timeout interplay and no stale-pid SIGTERM; (b) `isSettledForWait` false for it; (c) `cancel` disarms the timer and returns true; (d) `startedAt`/`lastActivityAt` re-based at re-spawn; (e) `orphaned` false for it. Yes, `wait` must see the retry: it must block, so that the parent's next action (`council_cancel`, or a duplicate dispatch of the same seat) cannot race a pending re-spawn. The identity line of a window-elapsed report must also carry the attempt count, or the parent cannot distinguish "attempt 2 of 3 in flight" from "attempt 1 failed".

## Surface state machine

The retry loop's two states that the row must distinguish are **(a) an attempt is running** and **(b) the loop is between attempts in backoff**. R4 forbids extra rows; it does not forbid the manifest's existing state from reflecting "between attempts." I propose the hub writes a sidecar `{id}.retry.json` next to the manifest (one sidecar per dispatch, owned by the loop in `extensions/hub-tools.ts`; the manifest schema is unchanged — EV-42 owns the `attempt` manifest field, scheduled after EV-39). The sidecar carries `{attempt: number, maxAttempts: number, status: "running"|"waiting"|"done"|"failed"|"exhausted", nextAttemptAt?: number}` and is the single source the renderer reads for `attempt N/M` plus the backoff copy.

The widget reads manifest + sidecar atomically per refresh. R4's "labeled `attempt 2/3` while retrying" is read as: **show `attempt N/M` whenever `N > 1`**, including after the final attempt settles (so the operator opening the tree at attempt-3-clean sees the count, not a mysterious `settled`). The label is omitted when `N = 1` (no retry happened; the row reads as it does today).

The label sits **between the seat field and the `·` separator**, not at the tail. Three reasons:
- The label is a status fragment; it groups with `state`, not with `pid`/`elapsed` (debugging metadata).
- "running attempt 2/3" reads as a phrase; "running 0.5m attempt 2/3" reads as a mistranslation.
- Truncation at narrow widths preserves the high-priority `attempt N/M` and drops the trailing age, not the count.

A few specifics worth naming:

- **(b) reuses the `⏸` glyph** (the existing stalled glyph). ### The final report's attempt sentence — `extensions/hub-tools.ts` `formatReport`

The sentence is appended at the end of `formatReport`'s output, **after the `err` clause and before the trailing newline**, so it lands at the very end of each per-job block. `formatWaitReport`'s `\n\n====\n\n` separator still separates jobs; the runner-usage block is appended after the attempt sentence (the runner-usage block is meta-aggregated and the attempt sentence is per-job — keeping the attempt sentence on the per-job line keeps the per-job block self-contained).

The four cases:

| Outcome | Sentence |
|---|---|
| N = 1, clean settle | `Completed after 1 attempt.` |
| N = 1, non-retryable failure | `Failed after 1 attempt.` |
| N > 1, clean settle (retry succeeded) | `Completed after 3 attempts (1 initial + 2 retries).` |
| N = maxAttempts, exhausted | `Exhausted after 3 attempts.` |

The singular `attempt` vs. plural `attempts` is the small but real affordance — a first-time reader sees `Completed after 1 attempt.` and learns that "completed" without retry is the default shape; the plural form signals "this took multiple attempts."

The exhaustive copy deliberately does NOT mirror EV-40's `Retries exhausted after ${maxAttempts} attempts. The provider kept failing. Press Enter to try again.` (R5 verbatim). EV-40's copy invites the user to press Enter; EV-39 has no input bar (it's a tool layer, not the parent turn). Mirroring the full sentence would import a half-action ("Press Enter to try again") that does nothing here. I propose `Exhausted after3 attempts.` — the operator on a hub-retry-exhausted case can read the parent's tool result and decide whether to re-dispatch.

**Open question** (filed below): does the exhausted copy need a verb explaining *what happened* (e.g., "Exhausted after 3 attempts; final error: Provider finish_reason: error")? My position is no — the `--- provider error ---` clause is already in the report, just above the attempt sentence, with the final attempt's full errorMessage. The attempt sentence and the error clause together tell the whole story. Naming the error in the sentence is redundant.

## Discoverability & failure tolerance

**At the moment of "is this seat retrying?"** — the operator glances at the row. The `attempt N/M` label answers: "yes, on attempt 2 of 3" (or 3 of 3). Without the label, the row reads as a normal running job; the operator cannot distinguish a retrying dispatch from a single-shot dispatch until the report lands. **The label closes the evaluation gulf** at the moment the operator wonders "why is this taking so long?"

**At the moment of "how long until the next attempt?"** — the backoff gap's `retrying in Ns` copy answers (case (b)). Without this copy, the row briefly reads `✓ settled4s` after attempt 1 settles retryable, and the operator concludes the job is done. **The retrying copy is the forcing function** against the slip "the seat finished; let me move on." This is Norman's distinction: a slip (right intention, wrong execution) deserves a control fix; the row needs to *tell* the operator the system is in the middle of a retry.

**At the moment of "how many attempts in total?"** — R4 forbids extra rows for history, so the tree shows only the current state. The operator who lands on attempt-3-clean sees `✓ designer attempt 3/3 · settled 3m` and learns the count. **The label is the comprehension affordance for "this was a multi-attempt dispatch."** Whether it's *enough* depends on whether the operator needs to know WHY it took 3 attempts. The final report carries the last attempt's errorMessage; prior attempts' errors live in their (now-overwritten) manifests and their (preserved) JSONL session transcripts. The operator who needs the history reads the report and the prior transcripts. R4 explicitly accepts this trade-off ("no extra rows").

**Failure tolerance — the slip "I assumed attempt 2 of 3 means attempt 2 succeeded."** The label is `attempt 2/3`, not `attempt 2/3 (retrying)`. A naive read could conflate "on attempt 2" with "attempt 2 done." Mitigation: the backoff copy (`retrying in Ns`) and the running copy (`→ ran ls`) disambiguate by context. The row is never `attempt 2/3` alone — it's always paired with a state (`running`, `waiting`, `stalled`) and a copy. The label is a status fragment, not a complete sentence.

**Failure tolerance — the mistake "I thought the row was a different dispatch."** R4 forbids two rows for one intent. The manifest's `id` is constant across attempts (the loop reuses the same id; the manifest is overwritten). The widget sees one row per id. There is no possible confusion. **R4 eliminates this whole class of mistake.**

**Failure tolerance — the slip "I read the row and assumed the seat failed."** On attempt 2 of 3 running, the glyph is `●` (running), not `✗` (failed). The state and the label are independent; the operator reads the glyph for state and the label for retry context. **No false-positive failure signaling.**

**Comparison with EV-40's input-bar countdown (R5):** the two surfaces are adjacent but non-redundant. The parent input bar shows `Retrying in 2s (attempt 2 of 3) — Esc to abort` for the **parent's own provider-error retry** (a separate loop keyed on `agent_settled`, settled by EV-40). The hub tree row shows `⏸ designer attempt 2/3 · retrying in 1s` for a **child dispatch's retry** (EV-39's loop). The two loops read different signals (`classifyParentTurnRetry` on a `message_end` vs `classifyRetry` on a settled `JobReport`); per AGENTS.md 12 and the EV-40 watch item, they never share state. An operator watching a child retry and the parent idle sees the hub row's countdown; an operator whose parent turn itself failed sees the input-bar countdown. The two surfaces never both fire at once for the same event.

**The slight format tension — `attempt 2/3` (R4) vs `attempt 2 of 3` (R5).** R4's ruling-text specifies the slash form on the tree row; R5 specifies the spelled-out form on the input bar. Both forms reference the same number with the same word `attempt`; the visual difference is one punctuation. I preserve R4's literal wording on the tree row and flag the format divergence as a discoverability question (below).

## Open design questions (flagged for ruling)

These I could not ground and would not have the designer seat unilaterally close. Each names what needs a ruling.

1. **Format divergence `attempt 2/3` vs `attempt 2 of 3`.** R4 says `attempt 2/3`; R5 says `attempt 2 of 3`. Both forms coexist on adjacent surfaces. A first-time operator may or may not parse them as equivalent. **Needs:** a unifying ruling — either both surfaces use `attempt N/M` (slash) or both use `attempt N of M` (spelled). I lean slash for the row (compact) and spelled for the input bar (sentence), but the divergence is a discoverability hazard and the ruling should be deliberate. **My recommendation: keep R4's literal wording on the row (slash), keep R5's literal wording on the input bar (spelled), and document the equivalence in `vault/wiki/` so the operator learns the mapping.** Risk: a brand-new operator sees both forms and asks "are these different?" in a forum thread.

2. **Where does `attempt N/M` sit on a row whose state is `failed` (settled non-retryable on attempt 1)?** Today this never occurs — `classifyRetry` would say "retry" and the loop would re-spawn. But if the classifier is bypassed (a future EV-42 change, or a `policy.enabled = false` case), the row is `✗ designer · failed` with no label. **My position:** if `N = 1` and the row is `failed`, the label is omitted (matches the no-label rule for `N = 1`). If `N > 1` and the row is `failed` (exhausted), the label is `attempt M/M`. **Needs:** a ruling that confirms this — or a ruling that says the label should always be present (even on `N = 1`) for consistency.

3. **Does the final report accumulate prior attempts' error history?** Today the report carries only the final attempt's `errorMessage` clause. The operator on attempt-3-exhausted sees `Exhausted after 3 attempts.` + `--- provider error --- Provider finish_reason: error` (the last attempt's error). Prior attempts' errors are NOT in the report; they live in the (preserved) JSONL session transcripts. **My position:** the attempt sentence + the last error is enough for the operator; prior errors are deep-debug material accessible via transcripts. **Counter-argument:** a multi-attempt exhaustion is a "this failed repeatedly" signal and the operator should see all N errors inline. **Needs:** a ruling on whether the report's attempt sentence should include a one-line error history (e.g., `Exhausted after 3 attempts: Provider finish_reason: error, Provider finish_reason: error, Provider finish_reason: error.`) — and whether the JSONL transcripts are a sufficient alternative.

4. **Does the backoff gap's `retrying in Ns` copy need a countdown to the second (matching EV-40's input bar)?** Today the widget renders the verb-first copy once per refresh (every 2s for the inline widget; instantly for the modal). The `retrying in Ns` value would update on each refresh — meaning the operator sees `retrying in 2s` → `retrying in 1s` → `retrying in 0s` → spawn. **My position:** the copy is `retrying in ${ceil((nextAttemptAt - now) / 1000)}s` and refreshes with the widget's 2s tick. The operator sees whole-second ticks, not sub-second. **Counter-argument:** EV-40's input bar ticks every 1s; the hub row should match for cross-surface consistency. **Needs:** a ruling on the tick interval — 1s (matches EV-40) or 2s (matches the existing widget refresh). I lean 2s (no new tick, no new render cost) but the consistency argument is real.

5. **The sidecar file's location and lifetime.** I propose `{runDir(repoRoot, runId)}/{id}.retry.json`. The run dir is gitignored (`runs/` is ephemeral telemetry). The sidecar lives and dies with the run dir (AGENTS.md 12: `runs/` is ephemeral; pruned to last 15 at parent `session_start`). **Needs:** confirmation that a sidecar in the run dir is consistent with AGENTS.md 12 (it is — the run dir is the substrate, and the sidecar is part of it). No new directory needed.

6. **The widget's read path for the sidecar.** The widget refreshes every 2s and reads `readManifests(repoRoot, runId)`. I propose adding `readSidecars(repoRoot, runId)` that returns `Map<id, RetrySidecar>` for the same run dir; the widget reads both. **Open:** whether the sidecar read should be inside the manifest read (one file system walk) or separate (two walks). **My position:** separate, lazy — the widget doesn't need the sidecar for non-retrying dispatches. **Needs:** confirmation that the per-refresh cost (one extra `fs.readdirSync` + a few `fs.readFileSync`s) is acceptable.

7. **Stall during backoff — does the operator need a different copy from the `⏸ stalled4m` copy?** Stall requires a live process (hub.ts tick kills on stall). During backoff there is no process; stall cannot fire. The widget's `settledCopy` returns `stalled {age}` for `state === "stalled"`; the sidecar's `status: "waiting"` produces `retrying in Ns` instead. **No conflict.** But the row uses the same glyph (`⏸`) for both states — a first-time operator might confuse "stalled mid-attempt" with "waiting in backoff." **Needs:** a ruling on whether the glyph should differ (a new glyph would violate the minimal-vocabulary preference) or whether the verb-first copy is enough to disambiguate. **My position:** the verb-first copy disambiguates (`stalled 4m` vs `retrying in 1s`); one glyph is fine.

8. **Is `Exhausted after3 attempts.` the right copy, or should it mirror EV-40's `Retries exhausted after ${maxAttempts} attempts. The provider kept failing. Press Enter to try again.`?** My current position: no — EV-40's copy invites an action (Enter) the hub cannot honor. But the divergence means the operator on a hub-exhausted case sees a terser message than on a parent-exhausted case, which could read as "the hub exhausted less gracefully." **Needs:** a ruling on whether the two exhaustion copies should be unified (and, if unified, which form wins — R5's verb-heavy form or the hub's terser form).

## What I am not arguing

- I am not arguing for a new state in `JobState` (`waiting`). The hub's `Job.state` remains `running | done | failed | cancelled | stalled | timeout`. The sidecar's `status` field is the loop's vocabulary, not the hub's. **The widget reads the sidecar's status; the manifest's state reflects the current attempt's lifecycle, which during backoff is `done`/`failed` (the prior attempt's final state).** This keeps the hub's stable state machine untouched (AGENTS.md 7: `hub.ts` is battle-tested; behavior changes need a failing test first). The sidecar is a non-invasive layer above the hub.
- I am not arguing for an `attempt` field on `RunManifest`. EV-42 owns that field; EV-39 precedes it. The sidecar is the temporary carrier that EV-39 ships; EV-42 will likely promote sidecar fields into the manifest.
- I am not arguing for a new glyph. `⏸` reused. AGENTS.md 9.6 and the EPIC-1 token-only drawing rule favor minimal vocabulary.
- I am not arguing for a new theme token. The widget's existing `STATE_TOKEN["stalled"] = "warning"` is reused for `status: "waiting"` (same semantic family: paused, waiting for something).
- I am not arguing for changes to `extensions/runs.ts`'s retention policy. `runs/` is ephemeral; pruning the last 15 runs at parent `session_start` keeps sidecars in the same lifecycle as manifests.
