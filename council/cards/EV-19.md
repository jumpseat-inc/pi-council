## Intent

A run's artifacts alone must support grading, so this card turns each
fixture into a rubric of checkable criteria and builds the scorer that
applies it. Deterministic criteria are preferred — gates green, `validate.py`
clean, expected artifact present, exact expected content — so the score is
reproducible. Where a criterion is open-ended (did `/council` actually
resolve the card sensibly), the existing `judge` seat records a verdict and
the scorer counts it, so judgment enters through a seat rather than a
hand-rolled heuristic. The output is a normalized, comparable score plus
per-criterion pass/fail.

Not surface-touching (scoring internals; no person-facing surface).

## Acceptance

- Every fixture in EV-18 has a rubric with at least one criterion, and each
  criterion is graded by a deterministic gate or a recorded judge verdict.
- The scorer emits a normalized numeric score and per-criterion pass/fail
  for a captured run, and the same run re-graded produces the same score.

### Round 1 (step 2) — owner (job-11.1), verbatim

**Approach** — A new pure module `extensions/eval-rubric.ts` implementing
`gradeCell`, which reduces all four frozen check kinds and the judge
criteria onto a single injected `GradeIO` seam, and stamps a `CellRecord`
whose numeric score is `passes/total`. Judge criteria are **never executed
by this module** — at first grade the harness (EV-20) supplies fresh
verdicts as input; at re-grade those verdicts are replayed from the prior
record. Per-criterion pass/fail and score fall out of the rubric's ordered
criteria, so reproducibility (C1) and append-only-by-`gradedBy` (C2) are
structural.

Grounding: `validateRubric` and the entire rubric vocabulary are already
landed and frozen in `extensions/eval-fixtures.ts:95–113`
(`RubricCheck`/`RubricCriterion`/`Rubric`) and `:399–433` (`CHECK_KINDS =
gates|settled|artifact-present|artifact-contains`; judge =
`{id,type:"judge",prompt}`). The 16 shipped rubrics confirm the shapes:
`gates` always carries `argv`+`expect{exitCode,stdoutContains?}`, `settled`
always carries `role`, artifacts use literal `contains` tokens, and judge
criteria are standalone `prompt`s. `eval-fixtures.ts:12` + EV-18 spec §3
already commit that **EV-19 imports `validateRubric` from here** — I do not
re-validate, I only consume.

**The `GradeIO` seam and gate executor (per check kind):**
`eval-rubric.ts` touches the outside world only through injected `GradeIO`
(so the module is pure and unit-testable without `node:fs`/
`node:child_process`, matching the A4 spirit EV-16 §10 A4):
`readFile(path): string|undefined` (undefined = absent);
`jobState(role): string|undefined` (terminal state done|stalled|timeout);
`run(argv, opts?): {exitCode, stdout}`.

Check-kind reduction (finite truth table): `gates` → pass iff
`exitCode === expect.exitCode` and (`stdoutContains` absent or
`stdout.includes(stdoutContains)`); `artifact-present` → `readFile !==
undefined`; `artifact-contains` → `(readFile ?? "").includes(contains)`;
`settled` → with `role`: `jobState(role) === "done"` (all shipped rubrics
use `role`); judge → never calls `io`, first grade consumes
`judgeVerdicts[criterionId]`, re-grade replays from prior record. The real
`GradeIO` (real readFile/jobState/run bound to the cell's persisted
snapshot dir) belongs to EV-20, consistent with `applyRulings`' purity
split (`eval-fixtures.ts:445–475`).

**Result record and replay mechanics** — `CellRecord` matches §6.3:
`{ cellId, taskId, model, thinking?, repeat, fixtureVersion, rubricVersion,
gradedBy, perCriterion:[{criterionId, verdict:"pass"|"fail", evidence}],
score, gradedAt, gradingUsage:{input,output,cost,elapsedMs,stopReason?} }`.
`gradeCell({ rubric, io, judgeVerdicts, metadata })`: per criterion in
rubric order, gate → `io`, judge → `judgeVerdicts[criterionId]` (fresh or
replayed); `score = passes / criteria.length` (judge criteria count toward
the total); returns a new immutable record. **Re-grade (C1):** call
`gradeCell` again with the same `io` and `judgeVerdicts` from the prior
record's perCriterion — gates re-run deterministically, judge criteria
replay verbatim → identical perCriterion and score. **Replay/append-only
(C2):** because pure, re-grading under a different `gradedBy` produces a
new record; original untouched/byte-identical. Enforcement of "second
verdict keyed by gradedBy, never overwrite" is EV-20's writer choosing the
filename from identity `(cellId, gradedBy)`.

**The one implementation ambiguity, resolved** — "deterministic gates are
re-runnable" (C1) needs the cell's post-state persisted. Resolution:
EV-19 defines `GradeIO` against a *persisted snapshot dir* it expects to
exist per cell (EV-20 copies the post-cell scratch worktree to
`eval-results/<cellId>/artifacts/` before grading); EV-19's own tests
inject a faked `GradeIO`, so this module places no requirement on how
EV-20 materializes it.

**Testable claims → `test/ev19-rubric.test.ts`**: (1) C1 reproducibility
— re-grade feeding the record's own judge verdicts back with a recording
fake `io` → identical perCriterion and score; assert `io.run` called for
the gate on re-grade but zero times for the judge. (2) C2 append-only —
`gradeCell` with `gradedBy=M2` vs existing `M1` returns a new record;
original byte-identical. (3) Check-kind truth table (2×N). (4) Scoring —
2 pass + 1 fail → 2/3; all pass → 1.0; all fail → 0; judge-only rubric
single pass → 1.0; judge criteria counted in denominator (fail gate + 2
pass judges → 2/3). (5) `validateRubric` (C3) — empty/>5 criteria rejects;
missing rubric.json fails loudly at loadFixture. (6) Time-bound gate —
`io.run` that never resolves → gate fails, no hang.

**Tradeoffs accepted** — judge dispatch excluded from this module by design
(D3 spirit — harness owns judge dispatch); EV-19 is intentionally not
self-sufficient for judge criteria (first-grade path exercisable end-to-end
only behind EV-20 integration). No per-criterion `kind` stored (derived
from rubric; record's rubricVersion pins interpretation). `settled` fail on
a stalled/timeout job is a plain per-criterion fail here; the
`stopReason=length → flag, not score 0` rule (EV-16 §8, E2) is
EV-20/EV-21 cell-level aggregation, out of scope.

### Round 1 (step 2) — principal (job-11.2), verbatim

**Cross-seam reading — what the contract actually is right now**

**1. Three of the four check kinds are pure; `gates` is the only impure one
— and the code already has the state shape.** `eval-fixtures.ts` freezes
`RubricCheck` as four kinds: `gates {argv, expect{exitCode,
stdoutContains?}}`, `settled {role?, path?}`, `artifact-present {path}`,
`artifact-contains {path, contains}`. Asymmetry in their inputs:
`artifact-present`/`artifact-contains`/`settled` read facts (file exists,
substring present — substring-only, no regex despite EV-18 §3 saying
"token/regex", `settled` = job ended done); `gates` runs a subprocess whose
argv are worktree-relative. The same module already ships `RulingsState
{jobs, reports, board, files}` and pure `applyRulings`. The scorer's three
non-`gates` kinds read exactly the same facts; so the pure/impure boundary
is: everything except `gates` is a pure function over a harness-supplied
normalized state; `gates` is `(criterion, artifactRoot) → {exitCode, stdout,
pass}` and is the one place `cwd` appears.

**2. The numeric score is *derived*, not a field on the verdict record —
and the card's two outputs are two different record types.** §6.3's record
`{cellId, gradedBy, fixtureVersion, rubricVersion, perCriterion, gradedAt,
gradingUsage}` is the *grader's contribution*: judge-criterion verdicts,
the grader's own spend, the linkage. The card's "comparable numeric score
+ pass/fail per criterion" is a **ResultRecord** (EV-20/21 domain) equal to
`scoreRubric(gateResults, verdictRecordFor(gradedBy))`. These must not
collapse into one type: a gate-dominant rubric (council, features-deliver,
owner, judge, wiki-lint, board-create-card's 2 gates, skeptic,
council-runner, wiki-ingest) gets **no grader dispatch and therefore no
verdict record**, yet still produces a full score. The verdict record's
`perCriterion` carries **judge criteria only**; gate per-criterion pass/fail
belongs in the ResultRecord, with `verdict` = computed and `evidence` = the
run's own (exitCode, stdout, path, content-fragment).

**3. The artifact-lifetime seam is the load-bearing open risk, and it's
genuinely unsigned.** Every `gates` argv and every `artifact-*` path is
relative to the scratch worktree; judge criteria read worktree files by
name ($design.md, synthesis.md, ruling.md). But the dispatch path hardcodes
`cwd: repoRoot` (`hub-tools.ts` → `hub.spawnJob({ cwd: repoRoot })`), and
the scratch worktree is a *different, disposable* directory (spec §3.1:
"only results records are written back"). C1 ("re-graded → identical
score") is only meaningful against a byte-identical tree in hand; the
settled contract never states whether the worktree survives grading,
whether the harness snapshots artifacts into `council/eval-results/`, or
whether "re-grade later" = re-materialize from the pinned seed + replay.

**4. `cellId` and `settled`-role both have latent gaps in the landed
code.** `cellId` is already a param on `council_dispatch` (`hub-tools.ts`)
but accepted-and-ignored — no manifest field, no persistence. Consistent
with §6.2 (harness stamps cellId at record-write), fine, but EV-19's record
writer owns the cellId ↔ grader-job mapping in-memory. Separately, `settled
{role}` uses roles that are not all manifest seats: shipped values are
`facilitator`, `skeptic`, `council-runner`, `judge`. `facilitator` is a
synthetic role — the harness's own command job — with no seat file. The
`role → job-state` map (already the shape of `RulingsState.jobs`) must be
authored by the harness with a pinned alias for `facilitator` = the command
job, and a pinned aggregation rule when a role appears more than once.
`settled {path}` (validated but never used by any of the 16 rubrics) has no
defined semantics in the landed types — dead vocabulary needing a meaning
or an EV-18-style freeze as unused.

**5. Grading telemetry has two sources and the verdict record sits at
their intersection.** `gradingUsage {input, output, cost, elapsedMs,
stopReason}` is cleanly mappable from `JobReport` (`hub.ts`: usage, elapsedMs,
stopReason) returned by `hub.wait` at grade time — needs **no** RunManifest
extension. The cell/command aggregation columns, by contrast, need the §7
RunManifest extension (runs.ts RunManifest persists neither). EV-19 can
land its grading column from in-memory reports without waiting on EV-20's
manifest work — but must not silently assume the two columns come from the
same source.

**Blind spots (per single vantage)** — scorer/owner sees `scoreRubric(rubric,
run)` and reaches for the worktree via process.cwd()/repoRoot; cannot see
the worktree is a different disposable dir whose lifetime EV-20 owns, so
the scorer must receive an injected artifactRoot + normalized state. It may
also write `gates` exec that audits can't replay. Leaderboard (EV-21) sees
"a record with one score" and prints it; cannot see the score is
*grader-relative* — judge criteria fold in only the verdict record for a
chosen `gradedBy`, so a ResultRecord without a stamped `scoredUnder:
gradedBy` is unauditable, and a fixture with judges re-graded under two
graders has two defensible scores; `ungraded` and `length-flagged` are
distinct non-scored states that must not both collapse to 0. Harness (EV-20)
assumes judge free text can be loosely parsed; cannot see that verdict
extraction must be pinned to `judge.md`'s own `output_format` (`**Verdict**
— \`PASS\`/\`REJECT\` + **Basis**) — that **is** the extraction contract,
already shipped; a judge dispatch that returns empty/stopReason=length/failed
is "indeterminate," not "fail."

**Reframe** — the card and binding contract are sound (gate-re-run vs
judge-replay, append-only keyed by gradedBy, topology ruling, one authority
in eval-fixtures.ts) — not reopened. One narrow framing correction:

**Redefine the scorer's input as an explicit injected `NormalizedRunState`
(reusing RulingsState jobs/reports/board/files vocabulary) plus a separate
`artifactRoot` for the `gates` subprocess — never "a captured run" as an
untyped directory the scorer is free to touch.** Split the record type:
`VerdictRecord` (§6.3, grader contribution, identity (cellId, gradedBy,
fixtureVersion, rubricVersion), written by the harness) vs `ResultRecord`
(merged per-criterion pass/fail + score, stamped `scoredUnder` +
`n_graded/n_total`, EV-20/21 domain). That moves the artifact-capture
question out of EV-19's hidden assumptions into EV-20's explicit
materialization contract, and makes C1/C2 testable in isolation.

Concrete module shape (behind an `eval-score.ts` / `eval-verdict.ts`
split): `runGates(criteria, artifactRoot)` — impure, only exec/fs site;
`evaluateStaticCriterion(check, state)` — pure, for present/contains/
settled, with the harness-pinned `facilitator` alias; `scoreRubric(rubric,
gateResults, verdictRecord?)` — pure, judge criteria without a verdict
record are `ungraded`, denominator is graded-only, never 0;
`appendVerdict(store, record)` — atomic, refuses duplicate
(cellId, gradedBy) for same (fixtureVersion, rubricVersion) ("first write
wins"), never mutates existing; `replayVerdict(store, cellId, gradedBy)` —
pure lookup, no dispatch.

**Testable claims** — `test/ev19-score.test.ts`: (1) judge-relative score,
not stored: `scoreRubric` over [{gate pass},{gate fail},{judge}] with
verdict record {judge: pass} → 2/3; same rubric with no verdict record →
2/2 judged gates, judge `ungraded`, `n_graded=2, n_total=3` — never
1/3-as-0. (2) Purity (A4-mirror). (3) `gates` determinism (C1-half) over a
byte-identical materialized seed tree twice; tree digests equal via
sha256Tree. (4) `settled` alias + aggregation pinned. `test/ev19-verdict.
test.ts` (C2): (5) append-only — G1 then G2 → two files; G1 bytes unchanged;
readVerdicts returns both keyed by gradedBy. (6) replay = no dispatch.
(7) first-write-wins — same (cellId,G1,fixtureVersion,rubricVersion) rejects.
(8) version guard. (9) extraction pinned to judge.md's `**Verdict**` shape;
empty/length/missing → indeterminate, not fail. (10) C3 is EV-18's — scorer
imports validateRubric (one authority), adds no second validator.

One claim that cannot be settled inside EV-19 and should be an explicit
EV-20-boundary acceptance: **grading operates against an artifactRoot
supplied by the harness; the same run re-graded is assertable only on a
tree whose sha256Tree equals the original cell's seed-plus-delta — the
harness must either grade before disposal or persist the artifact tree, and
C1's cross-run form is only meaningful once that is pinned.**
