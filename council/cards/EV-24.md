## Intent

This card owns the UI-to-data seam and the first `.council.json` write path
in the codebase. The writer merges, not rewrites, and emits `council.<seat>`
in the object form `{ "model": "provider/id", "thinking": "<level>" }` the
loader and scaffold seed already speak, validating the model against the
catalogue and the thinking level against `THINKING_LEVELS`
(`extensions/seats.ts:17`). Validation failures return an error message
without writing; filesystem-level failures (an atomic-rename error) throw.

The write is atomic — tmp file plus rename, like `mcp/auth-store.ts` — and
never disturbs the `theme` sibling, so the watcher at
`extensions/theme-watcher.ts:45` cannot misclassify a model-only edit as a
theme change or fire a spurious "theme removed" warning.

## Acceptance

- A round-trip test rewrites a fixture config carrying a `theme` section,
  other seats, and unknown top-level keys, and byte-asserts the untouched
  regions.
- The emitted `council.<seat>` shape is byte-asserted (qualified
  `provider/id`, object form).
- The `theme` block is SHA-asserted byte-identical before and after the
  write, including key order.
- A validation failure returns an error message and writes nothing.

### Round 1 — owner (verbatim)
New module `extensions/council-config-writer.ts` exporting `writeSeatOverride({ repoRoot, seat, model, thinking, catalogue }): { ok: true } | { ok: false; error: string }`. Validate first, pure and I/O-free: model must equal some `ModelEntry.qualifiedId` in the flat catalogue array (the same array EV-22's resolver consumes — the writer does no registry refresh); thinking must be a member of `THINKING_LEVELS`, which requires exporting that currently-private set from `seats.ts:17` (one-line surface change, zero behavior — no duplicated grammar). Then **splice, don't re-serialize**: parse the file for validity, string-aware scan to locate the `council.<seat>` value's byte span, and replace/insert only that span with the object form `{ "model": ..., "thinking": ... }` (model first, thinking second, matching the scaffold seed's key order), indented to the file's own unit/depth. Theme, every other seat, unknown top-level keys, indentation, and trailing newline are byte-identical **by construction**; the edit lands via the auth-store atomic pattern (tmp + `renameSync`, recursive mkdir; mode preserved from the existing file), and rename failures throw while validation failures return an error message and write nothing.

Why splice over re-serialize: the naive writer passes the card's byte/SHA acceptances only when the fixture is already canonical 2-space. The repo's scaffold seed is **tab-indented** (`council/scaffold/.council.json`, verified `^I`), so a re-serialize writer would reformat a consumer's committed file on the first model-only edit — changing the theme block's bytes, which is exactly the "never disturbs the theme sibling" contract the SHA-assertion enforces.

Tradeoffs: (1) scanner complexity over re-serialize simplicity — byte-preservation by construction beats preservation contingent on canonical input. (2) Malformed existing JSON → error message, not throw (flagged OPEN — card names only validation→message and atomic-rename→throw). (3) Validation intentionally not stricter than loader/dispatch — NO per-model supportedThinkingLevels check (loader only checks grammar). (4) Always object form, replacing string shorthand; model-only edit omits the thinking key. Missing council/file: insert council first, canonical 2-space + trailing newline.

Testable claims: discriminating test (splice vs re-serialize) copying the real tab-indented scaffold seed; acceptance round-trip fixture; emitted-shape byte-assert; validation-failure-writes-nothing; malformed-file→error-message; rename-failure→throw; loader round-trip.
