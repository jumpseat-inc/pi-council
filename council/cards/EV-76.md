## Intent

The preflight that matters is the one `/features-deliver` runs at **every run
start** — Phase 0's `bash council/preflight.sh` — and `/council` step 0 runs the
same script. `council/preflight.sh` is data-class and never refreshed by
`/council-update`, so a check that lives only in the scaffold script reaches
fresh consumers and silently misses every repo already `/council-init`-ed.
The check therefore belongs on a **packaged, override-resolved path** the
run-start procedures invoke, so existing consumers get it immediately.

The safety property already partially holds: the existing OpenRouter check is
unconditional and already halts a run when no credential resolves. The delta is
to name the **decisions gate** as the consumer and name **both** remediations
(set `OPENROUTER_API_KEY`, or use the stored `openrouter` `api_key` the runtime
also accepts) — never a symptom-only message, and never a check stricter than
the runtime ([[gate-parity]]).

## Acceptance

- Run-start (`/features-deliver` Phase 0 and `/council` step 0) fails with the
  named single-line `FAIL:` when the resolved mode is not `off` and no credential
  resolves.
- The check reaches **existing** consumers without a `council/preflight.sh`
  refresh (packaged/override-resolved path; it does not depend on the scaffold
  script being updated).
- The mode comes from invoking `loadGateConfig`, not a shell re-parse.
- A stored `openrouter` `api_key` satisfies the check (runtime parity, not
  env-only).
- The existing unconditional OpenRouter check and the off-mode output stay
  byte-identical; `off` adds no new `FAIL:` line.
- If the packaged path and the scaffold script both report, exactly one is
  authoritative — no double `FAIL:`.
