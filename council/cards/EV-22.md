## Intent

This card owns the catalogue side of the data-to-UI seam. It reads
`ctx.modelRegistry.getAvailable()` (optionally after an async `refresh()`) —
never raw provider HTTP — and turns the flat `Model` list into
provider-grouped entries using `getProviderDisplayName` and each model's
`id`/`name`/`thinkingLevelMap`. Because dispatch validates against the same
`getAvailable()` set (`extensions/index.ts:355`, `extensions/dispatch.ts:64`),
listing from it guarantees a picked model is accepted by dispatch later.

The resolver also exposes each seat's current state — its name, whether a
`.council.json` override exists, and the effective model and thinking after
`loadCouncilConfig`/`applySeatOverride` (`extensions/seats.ts`) — so the
modal can render what the seat uses now and the person can see that
frontmatter still owns the value underneath when no override exists.

## Acceptance

- A unit test stubs the registry and asserts grouping, ordering,
  thinking-level extraction, and the per-seat current-state fields
  (name, hasOverride, currentModel, currentThinking).
- The module performs no raw provider HTTP — no HTTP client import; the
  registry is the single source of the catalogue.

### Round 1 — owner (verbatim)
**Core finding: pi's own canonical "supported thinking levels" semantics differ from the card's grounding, and that divergence is the one thing that will bite the acceptance test if copied naively.**

The card's grounding says: *"a MISSING key means the provider default applies; a null value marks that level as UNSUPPORTED."* That is the docstring on `Model.thinkingLevelMap` (pi-ai `types.d.ts:702-705`) — but it is **not** how pi computes the level set. pi ships `getSupportedThinkingLevels` (pi-ai `models.js:548-559`, exported from index at `models.d.ts:193`), and pi's own settings selector uses exactly that (`settings-selector.js:424`):

```js
const EXTENDED_THINKING_LEVELS = ["off","minimal","low","medium","high","xhigh","max"];
export function getSupportedThinkingLevels(model) {
  if (!model.reasoning) return ["off"];
  return EXTENDED_THINKING_LEVELS.filter((level) => {
    const mapped = model.thinkingLevelMap?.[level];
    if (mapped === null) return false;
    if (level === "xhigh" || level === "max") return mapped !== undefined; // key REQUIRED
    return true; // absent key on these = supported (provider default)
  });
}
```

Decisive: **for `xhigh` and `max`, a missing key means *unsupported* (key required), while for `off`/`minimal`/`low`/`medium`/`high`, a missing key means *supported* (provider default).** A resolver that implements "missing → supported" uniformly (the card's literal reading) will offer `xhigh`/`max` where pi itself would clamp them away. This is not a taste call — pi's `clampThinkingLevel` (models.js:560) would reject such a picked level at spawn.

So my contract:

- **Shape** — a two-section array result (arrays, not objects, so ordering is an observable, testable property):
  ```ts
  interface ModelEntry { qualifiedId: string; /* `${provider}/${id}` */ id: string; name: string; reasoning: boolean; supportedThinkingLevels: string[] }
  interface ProviderGroup { provider: string; displayName: string; models: ModelEntry[] }
  interface SeatState { name: string; hasOverride: boolean; currentModel: string; currentThinking?: string }
  interface ResolverResult { providers: ProviderGroup[]; seats: SeatState[] }
  ```
  `qualifiedId` is the **selection key** — it is byte-identical to the `${provider}/${id}` strings dispatch validates against (hub-tools.ts:111, index.ts:355), so any picked value round-trips into an accepted dispatch by construction.

- **Ordering** — providers ascending by `provider` id; models ascending by `id`; seats in `listSeatNames` order (already sorted, seats.ts). Rationale: ids are the unique, present-in-stubs keys; `name`/`displayName` are labels. Deterministic → `resolveCatalogue(x) === resolveCatalogue(x)` is assertable.

- **Thinking extraction** — a local pure `supportedThinkingLevels(model)` replicating pi's exact filter (NOT a uniform missing-key rule), iterating THINKING_LEVELS order. I deliberately do **not** import `getSupportedThinkingLevels` from `@earendil-works/pi-ai` via a bare specifier, because pi-council declares no direct `@earendil-works/pi-ai` dependency (package.json deps are only `@modelcontextprotocol/sdk`), and the v0.12.1 theme-module bug (wiki `2026-08-26-theme-module-resolution-fix`) already taught this repo that bare `@earendil-works/*` specifiers are NOT reliably covered by pi's extension remap. Replication keeps the module hermetic and the typecheck green without adding a version-skewed dependency. The parity test below pins that the replication matches pi's contract.

- **Dispatch-validity** — `getAvailable()` is auth-filtered (model-runtime.js:171: `available: all.filter(m => snapshot.configuredProviders.has(m.provider))`), and dispatch validates against that same set. So the resolver lists exactly the dispatch-acceptable set; no extra filtering needed. This is the elegant property the card wants and it falls out for free.

- **Current state** — `hasOverride = key-presence in loadCouncilConfig(repoRoot)` (an `{ "owner": {} }` entry still counts — the file declares an override). `currentModel`/`currentThinking` come from `loadSeat` (seats.ts), which already folds `applySeatOverride` precedence (`thinking key > :suffix > frontmatter`) and is the *same* call dispatch uses — so the picker's "what the seat uses now" is exactly the model dispatch would spawn `--model`/`--thinking` with. `currentThinking` is `undefined` when neither frontmatter nor override pins one.

- **Purity / no-HTTP** — pure core is `resolveCatalogue(source, repoRoot)` taking a minimal structural `CatalogueSource { getAvailable(): CatalogueModel[]; getProviderDisplayName(p): string }` (assignable from the real `ModelRegistry`), plus a thin async `resolveCatalogueFor` that does `await source.refresh()` then delegates. The module imports only `seats.ts` and node stdlib — no HTTP import, matching acceptance (2). `getProviderDisplayName` is total (model-registry.js:68-70 falls back to the provider id), so a minimal stub is safe. "refresh" is the registry's own network, never the resolver's.

**Tradeoffs accepted**

- **Replicating the level filter locally** rather than importing pi's function risks drift if pi changes the contract — accepted because it avoids the bare-specifier remap trap and a new direct dependency; the parity test is the guard.
- **Structural `CatalogueModel` type** instead of importing pi's `Model<Api>` — slightly weaker static typing on the input, but it keeps tsc hermetic (no pi-ai in the dependency graph) and `getAvailable()`'s return is structurally assignable to it. Worth it.
- **`loadSeat` runs per seat and re-parses `.council.json` each time** (N+1 config reads) — accepted; N is ~9 and correctness/reuse-of-dispatch's-own-path outweighs micro I/O. I will not change `loadSeat`'s signature (scope creep).
- **Loud failure on a malformed seat** — the resolver inherits `loadSeat`'s throw. A picker can't show a seat that dispatch would also fail; louder config errors are on-brand. Not adding per-seat resilience.

**Testable claims (for the Skeptic to falsify)**

1. **xhigh/max need an explicit key.** For `{ id:"m", provider:"p", name:"M", reasoning:true, thinkingLevelMap:{ low:"LOW" } }`, assert `supportedThinkingLevels === ["off","minimal","low","medium","high"]` — **not** containing `xhigh`/`max`. This fails on any uniform missing-key implementation and passes on pi-ai's contract.
2. **null excludes, non-reasoning collapses.** With `thinkingLevelMap:{ high:null }` assert no `high`; with `reasoning:false` assert `["off"]` (mirrors settings-selector.js:424's runtime branch).
3. **Order determinism.** `resolveCatalogue(src, repo)` run twice over one fixture is deeply equal; providers sorted by provider id, models by `id`, seats by name.
4. **hasOverride semantics + precedence.** Temp repo, seat frontmatter `openrouter/a/fm:medium`, override `{ "owner": { "model": "openrouter/b/m:high", "thinking": "low" } }` → `seats` entry: `hasOverride===true`, `currentModel==="openrouter/b/m"`, `currentThinking==="low"` (explicit `thinking` beats the `:high` suffix). Absent `.council.json` → `hasOverride===false`, `currentModel==="openrouter/a/fm"`, `currentThinking==="medium"`.
5. **Dispatch round-trip.** Build `known` as `Set(resolver.providers[].models[].qualifiedId)`; assert every `qualifiedId` is in the modelled `getAvailable()` set — proving the picker can only ever emit a dispatch-accepted id.

One open question I'd want ruled before implementation: whether the **Skeptic** agrees `hasOverride` should be *key presence* (an `{}` entry counts) rather than *"something actually differs from frontmatter"* — the two diverge exactly on empty-override entries, and the test in (4) pins whichever is chosen.

### Round 1 — principal (verbatim)
## Cross-seam reading

The contract EV-22 sits on is real and already two-sided, and the two sides do not agree yet:

- **Catalogue side (pi registry).** `ctx.modelRegistry.getAvailable()` is **synchronous** (`model-registry.d.ts:27`, returns `Model<Api>[]`), `refresh()` is **async** (`:22`, must be awaited before sync reads), and `getProviderDisplayName(provider)` is sync (`:34`). Each `Model` carries `provider`, `id`, `name` (optional, defaults to `id` per `models.md:205`), `reasoning`, and a **tristate** `thinkingLevelMap` (`models.md:261-300`). Dispatch's known-set is built from the same `getAvailable()` (`extensions/index.ts:355`, `extensions/dispatch.ts:64`), so same-snapshot listing ⇒ acceptance is a true guarantee — but it is **snapshot-scoped**, not a promise about the next dispatch.

- **Seat side (`seats.ts`).** `loadCouncilConfig` → `Record<seat, {model?, thinking?}>`; `applySeatOverride` resolves *explicit `thinking` > `:suffix` on model > frontmatter*, with model and thinking independent (`council-config` wiki). `listSeatNames()` returns `[...names].sort()` (alphabetical, `seats.ts:432`). The trap: **`loadSeat` (`seats.ts:437`) re-reads and re-parses `.council.json` on every seat** and returns a *collapsed* seat — it gives you the effective model/thinking but **destroys the `hasOverride` bit**. `hasOverride` can only come from config-map presence, and only by reading the map once.

- **The ruled consumers.** EV-23 R-3 renders exactly two markers — `using <provider>/<id>[:thinking] (override)` vs `frontmatter default` — and a *shared* seat list → provider → model cascade (the catalogue is repo-wide, not per-seat). EV-25 R-2 lists `<seat>: <provider>/<model>[:thinking] (override)` vs `<seat>: frontmatter default`. Both renderers consume the same two facts: per-seat effective state and a global provider→model catalogue. Nothing in either ruling asks for the frontmatter value to be rendered — only the *marker*.

## Blind spots

- **The data/import vantage (whoever builds the resolver from inside `seats.ts`):** cannot see that `loadSeat`'s per-seat config re-read is the wrong primitive here, and that "supported thinking levels" has already been *decided by pi* — pi's own `getAvailableThinkingLevels()` delegates to `getSupportedThinkingLevels(model)` (`agent-session.js:1396-1399`) and `setThinkingLevel` clamps to that set (`:1360`). A resolver author who hand-rolls "keys of `thinkingLevelMap` with non-null value" is wrong in three ways at once: omitted map ⇒ standard levels *are* supported (through `high`) while `xhigh`/`max` are *not*; `null` means hidden; and `reasoning:false` models support no thinking at all. This vantage will silently offer levels dispatch later clamps away.

- **The frontend/surface vantage (EV-23 modal, EV-25 command):** cannot see that the pick value must be the **qualified `provider/id`** string (dispatch validates `${provider}/${id}`, `index.ts:355`), not the bare `id` — a bare-id in the echo/confirm step produces a write that `loadCouncilConfig`'s `qualifiedOrThrow` will reject on the next load. It also cannot see the `hasOverride` trap: a `.council.json` entry whose value happens to equal frontmatter still must render `(override)` (per R-3/R-2's "when an override exists"), yet `applySeatOverride` returns the *unchanged* seat object in that case, so "did the effective value change?" is the wrong predicate.

## Reframe

The proposed design is directionally right (pure resolver, registry as sole catalogue source, no HTTP) but **under-specified in exactly the three places that are the seam**. Concretely:

1. **Flat two-array shape, not nested.** Return `{ seats, providers }`, where `seats: [{name, hasOverride, currentModel, currentThinking}]` (in `listSeatNames` order) and `providers: [{provider, displayName, models: [{provider, id, name, thinkingLevels}]}]`. The catalogue is **shared** — nesting it under each seat duplicates it 9× and forces EV-23 to reconcile. Keep `provider` *on each model entry* so EV-23's echo, EV-24's write, and EV-25's selection-encoding contract all read one self-contained value with no group-context join. `currentModel` is always the **qualified `provider/id`** string.

2. **Thinking extraction = mirror pi, don't reimplement.** `thinkingLevels` must equal pi's own `getSupportedThinkingLevels(model)`: tristate (`omitted` ⇒ off..high supported / xhigh+max unsupported; `string` ⇒ supported; `null` ⇒ hidden), gated on `reasoning`, emitted in canonical `THINKING_LEVELS` order. If that function is importable from `@earendil-works/pi-ai/compat`, use it; otherwise encode the documented table and pin the test to the three documented fixtures (`deepseek-v4-pro` holes, `always-thinking-model` `off:null`, omitted map). `thinkingLevels: []` is a legal per-model state (model-only override) and must not be conflated with "provider has no models".

3. **`hasOverride` = config-map presence, not effective-diff.** Derive from `loadCouncilConfig(repoRoot)` key presence (read once); derive `currentModel`/`currentThinking` from `applySeatOverride(rawSeat, map)`. The test must cover "override present but value equals frontmatter → `hasOverride: true`". The resolver owns per-seat derivation so EV-23/EV-25 never recompute the precedence ladder.

4. **Pin the ordering here and only here.** Seats: `listSeatNames` order. Providers: `displayName` ascending, tiebreak `provider` id. Models: `name ?? id` ascending, tiebreak `id`. Thinking levels: canonical set order. EV-23 and EV-25 render array order and must not re-sort — one sort owner.

5. **Keep the resolver pure over plain data** — signature takes `(models, providerDisplayNames, rawSeats, overrideMap)` (or a `providerDisplayName` lookup fn), not `ctx`. The async `refresh()`/`getAvailable()` fetch lives in the EV-25 handler **once**, and the same flat list is passed to the resolver *and* EV-24's catalogue validation — otherwise EV-24 validates against a different snapshot than EV-22 listed. Empty catalogue ⇒ empty `providers`, **no throw** (EV-23 owns empty-state copy).

**Testable claims**

- **Falsifier for the Skeptic (thinking extraction):** for a fixture set {`reasoning:false` model, omitted-map model, `deepseek-v4-pro`-style holes, `off:null` always-thinking model}, EV-22's `thinkingLevels` for each model equals pi's `getAvailableThinkingLevels()` for that model. A reimplementation that fails this is offering levels dispatch clamps away.
- **Falsifier for `hasOverride`:** a config entry `{model: "<same-as-frontmatter>"}` yields `hasOverride: true` and `currentModel` = the frontmatter value (not the unchanged-object sentinel `applySeatOverride` returns).
- **Falsifier for the pick-value seam:** every `(provider, id)` emitted by the resolver, when fed into dispatch's known-set predicate (`known.has(`${provider}/${id}`)`, `index.ts:355`), is accepted — and the reverse, no model outside `getAvailable()` is ever emitted.
- **Falsifier for independent resolution:** model-only override keeps frontmatter `thinking`; thinking-only override keeps frontmatter `model` — asserted via `currentModel`/`currentThinking` (mirrors `council-config` precedence).

*Grounding: `vault/wiki/index.md` → `[[council-config]]`, `[[seats]]`; `extensions/seats.ts` (THINKING_LEVELS, loadCouncilConfig, applySeatOverride, listSeatNames, loadSeat); `extensions/index.ts:355`, `extensions/dispatch.ts:64`; pi `dist/core/model-registry.d.ts:22,27,34`, `dist/core/agent-session.js:1360,1396-1399`, `docs/models.md:205,261-300`; `council/cards/EV-23.md` R-3, `EV-25.md` R-2.*

The ruled markers (EV-23 R-3, EV-25 R-2) say "when an override exists"; PO D4 says show "whether a `.council.json` override exists." `loadCouncilConfig` already returns `{ "owner": {} }` as a *valid, present* `AgentOverride` — `parseAgentOverride` accepts the empty object — so "key presence in the map" is the already-implemented semantic.   5. **Data pull / purity** — split the difference on the actual seam. Owner's *structural `CatalogueSource`* is right and I adopt it: the pure core `resolveCatalogue(source: CatalogueSource, repoRoot: string)` is sync, ctx-free, refresh-free, HTTP-free — that is the acceptance-tested export.   - **Empty-state confirmation**: `thinkingLevels: []` is legal and distinct from "provider has no models." `[]` = "this model exists but every level is nulled" (e.g. an always-thinking model with `off:null` and nothing else); a provider with zero models has an empty `models` array (or is omitted as a group — EV-23 owns that copy). The two must not be conflated: a `[]` model is still rendered as a selectable model with no thinking sub-selection, never skipped and never folded into the provider-empty state.
