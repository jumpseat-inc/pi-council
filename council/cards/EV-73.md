## Intent

Enablement (`mode`) belongs in the committed config file the repo already has, as
a reserved top-level sibling like `theme`/`retry`; the `typesafe/jev-1.13` model
pin and the decisions endpoint stay hard constants enforced in `gate-run.ts`,
never user config. The loader's one-line `FAIL:` is the visible surface on invalid
config.

## Acceptance

- off/advisory/active each resolve from a fixture `.council.json`; absent `gate`
  ⇒ byte-identical `off`.
- The pin still throws in `gate-run.ts`; a non-pinned model cannot reach the
  transport.
- The four refusal classes each throw one line naming file+key — including the
  newline-bearing override id (the restored FLLWUP-74 class).
- Packaged `council/gate/decision.json` validates clean; no `policyVersion` bump
  and no re-registration (no threshold moved).

## Round 1 — independent first pass (owner, principal, designer)

### Owner (job-1.1)

loadGateConfig lands in extensions/gate.ts as the single resolver of the reserved top-level `gate` section; loadGatePolicy composes it internally (calls loadGateConfig first, then validates the policy file), so all three readers — and the fourth call site in gate-route-tool.ts's recheck — keep their exact current shape and get mode through the one resolver with no second mode copy and no reader edits.

(a) loadGateConfig(repoRoot): { mode: GateMode }, importing COUNCIL_CONFIG_FILE from seats.ts (gate.ts already imports PKG_ROOT from seats.ts — no new dependency direction). Posture mirrors loadRetryConfig's structural spine (seats.ts:268–283) with gate's FAIL: line for section content: file absent → { mode: "off" }; absent `gate` key → { mode: "off" }; malformed JSON or non-object root → FAIL: <file> has an invalid JSON — not parseable as JSON: … (single line via gateFail's sanitizer; the FAIL: shape rather than seats.ts's bare malformed-JSON convention because the card's intent names the one-line FAIL: as the loader's visible surface); `gate` present but not an object → FAIL: <file> has an invalid gate — expected an object, found …; unknown key inside `gate` → FAIL: <file> has an invalid gate.<key> — unknown key; expected one of mode — …; `gate.mode` not in GATE_MODES → FAIL naming gate.mode; `gate: {}` (absent mode) → resolves off. All messages single-line via gateFail.

(b) Composition, not reader surgery. loadGatePolicy becomes: (1) loadGateConfig first — mode resolved BEFORE the policy file is read (ruling 6's ordering; every reader's off short-circuit sits after its existing loadGatePolicy call, which now resolves mode from .council.json internally); (2) read + validate policy.json exactly as today minus `mode`: POLICY_KEYS drops "mode" → a policy.json carrying `mode` hits the existing unknown-key FAIL (the migration signal, ruling 3), firing regardless of resolved mode — a stale policy file is loudly dead even on the off path; (3) EV-64 clause 2 re-expressed: `if (gateStateBudgetTokens === undefined && config.mode !== "off") throw` — same message, "resolved mode" now meaning the config-resolved mode; (4) return { policyVersion, mode: config.mode, model, endpoint, gateStateBudgetTokens? }. GatePolicy keeps `mode: GateMode`; runGate's off guard and pin guards (gate-run.ts:139–151) untouched; readers change only in comments. Byte-identical off: no file + no section → config off, packaged policy validates clean → same no-op shapes. Considered having the three readers call loadGateConfig directly with a separate loadGatePolicyData — rejected: four call sites re-composing two loaders is how a second mode copy appears.

(c) The four refusal classes, all in loadGateDecision, each a single-line gateFail naming file+key: (1) thresholds.verify requires > 0 (direct keeps ≥ 0 plus the verify ≤ direct cross-check); (2) unknown floors/thresholds sub-key refused (today extras are silently ignored — the hole FLLWUP-74 closes); (3) override.question absent from weights refused (weights parsed before overrides, so no reordering); (4) a basisSafeString check (non-empty, no \r/\n — input refused, not sanitized) on every string that can reach a basis line: overrides.<i>.question, .option, .basis, and the weights keys (basis template `${id}: confidence …`). Order within an override rule: shape checks (class 4) before the referential check (class 3). Packaged decision.json validates clean under all four. No policyVersion bump, no threshold moved.

(d) Budget rule: packaged policy (off resolved from absent config, budget present) validates; repo with gate advisory + budget-less repo-local policy.json FAILs clause-2; off-mode omission legal; present-⇒-validated-unconditionally unchanged and before any short-circuit.

(e) Packaged policy.json loses its "mode" line; pristine repo = loadGateConfig (absent ⇒ off) + packaged file validating clean. Existing repos with mode-carrying repo-local policy.json: every loadGatePolicy call throws the unknown-key FAIL naming mode, including on the off path — intended migration signal; no deprecation shim. Scaffold gains nothing (council/scaffold/.council.json unchanged; gate/policy.json is data-class, never written).

(f) Test plan (TDD, mkdtempSync roots): test/gate.test.ts heaviest (packaged-default asserts off via absent config; loadGateConfig block — absent file/section ⇒ off, three modes resolve, invalid mode FAILs, unknown gate sub-key FAILs, gate:{} ⇒ off, malformed JSON single-line; policy.json with mode FAILs unknown-key with the allowed-key list updated; budget clause-2 tests set mode via .council.json fixture; four refusal classes incl. the newline-bearing override id and weights-key variants; packaged decision.json clean). test/gate-tool.test.ts (off no-op unchanged; advisory reachable purely from .council.json). test/gate-route.test.ts (step-1 short-circuit driven by .council.json). test/gate-run.test.ts (mode originates from config; off/pin guards unchanged).

(g) Open questions: (1) class-4 scope on weights keys — inclusive (they render into basis) vs only the three override fields; leans inclusive. (2) gateFail tail wording for .council.json errors ("remove the key to use the packaged default" is literally true — removing `gate` ⇒ off — but "packaged default" reads oddly about .council.json). ### Principal (job-1.2)

Cross-seam reading. Producers: loadGatePolicy (only producer of GatePolicy; reads mode from policy.json, uses it for the EV-64 budget-absence check and returns it) and resolveGateStateBudget (gate-state.ts ~L110–150) — a SECOND, type-import-only read of the same policy.json, reading only gateStateBudgetTokens, NOT reading mode, NOT rejecting unknown keys. Readers of policy.mode: (1) gate-tool.ts R3 short-circuit; (2) gate-route.ts resolveRoute step 1; (3) gate-route-tool.ts recheck (passes policy to runGate); (4) gate-run.ts's pre-POST off guard — a fourth runtime read the card's "three readers" framing does not name. The transitively-correct design: loadGatePolicy calls loadGateConfig once and injects the resolved mode into the returned object's `mode` field — the three readers keep their policy.mode checks, gate-run.ts keeps reading the same resolved value (no fourth direct caller), the EV-64 budget check can be re-expressed inside loadGatePolicy. Alternative — strip mode from GatePolicy, three direct callers — strictly worse: forces gate-run.ts to become a fourth direct reader, triples the .council.json parse sites, opens a mid-call divergence window, breaks the pinned GatePolicy test fixtures (test/gate-run.test.ts:41, test/gate-route.test.ts:437). Contract sentence: GatePolicy.mode survives as the resolved field; loadGatePolicy populates it from loadGateConfig; the three readers and gate-run.ts's pre-POST guard all read that one resolved value — so "three readers" remains true by construction. Also state `gate: {}` ⇒ off and reject a bare-string `gate` shorthand (parity with theme/retry, ruling #1's object shape).

.council.json seam: loadCouncilConfig reads only parsed.council (seats.ts:478) — a top-level `gate` sibling is invisible to it by construction, like top-level retry (loadRetryConfig L267) and theme (L175). loadGateConfig follows the loadThemeConfig/loadRetryConfig precedent: independent loader, re-parses .council.json, fail-loud naming file+key, absent section ⇒ off. Blast radius: the readers call loadGatePolicy lazily at tool-call time (index.ts only prereads retry in try/catch, L606), so loadGateConfig must be invoked lazily from loadGatePolicy, never eagerly at parent init — a malformed gate section throws one FAIL at the gate/route tool call and never crashes unrelated session startup. Eagerly prereading "for symmetry" would let a typo'd gate section break every session — wrong contract; pin against it.

Migration seam: removing mode from ALLOWED_POLICY_KEYS means an existing repo-local .pi/council/gate/policy.json carrying mode hits the unknown-key FAIL — correct, loud; silently ignoring would leave the repo believing it is opted in while resolving off. Qualifications: (i) the generic tail "set a valid value or remove the key to use the packaged default" — for `mode` the accurate advice is "move it to .council.json"; the ruling only blesses the generic FAIL as the signal, so a specialized copy is a residual, not an objection; (ii) the packaged policy.json must drop mode in the same change, or the package itself fails; validate.py's check_gate_registrations reads policyVersion only — no edit, no registrations.jsonl churn.

Where the four refusals belong: all four in loadGateDecision, gate.ts, adjacent to decide() — the anti-drift choice (renderer's field set and validator's field set side by side); at the loader, not gate-run/gate-transport, so bad data fails before any call. Class (1) closes the exact gap gate-run.ts's header documents as out of scope (verify=0 breaks failed-call re-derivation). Class (2) needs explicit sub-key allowlists on floors (extras silently ignored today) and thresholds. Class (3) is within-decision.json. Class (4) is a single-line \r\n refusal on the fields decide() interpolates into basis: override.question, override.option, override.basis (template `${rule.question}? ${rule.option} (${rule.basis})`).

Blind spots: in-code view can't see gate-run.ts as a fourth policy.mode consumer nor the on-disk consumer migration (repo whose committed policy.json carries mode gets a FAIL after upgrade; any ledger already written under the old opt-in). Card/product view can't see the duplicate lenient policy.json reader in gate-state.ts, nor that gate-state.ts also short-circuits on the reader before ever seeing an off-mode policy. gate-render.ts loads zero policy (ledger-only) — structurally blind to this seam, correctly. Config-author view can't tell gate shorthand/mid-session-flip consequences vs theme/retry.

Testable claims: (1) transitive-equality — loadGatePolicy(repo).mode === loadGateConfig(repo).mode for gate.mode ∈ {absent, off, advisory, active}; absent ⇒ off. (2) single resolution site — no module outside extensions/gate.ts reads .council.json's `gate` key (import/grep canary mirroring gate-route.test.ts's T1 import fence). (3) off short-circuit ordering under the new resolver — budget-less repo-local policy.json + .council.json off loads clean and no-ops; same policy with .council.json active throws one FAIL naming policy.json and gateStateBudgetTokens. (4) migration FAIL — policy.json containing mode throws single-line FAIL naming policy.json and mode; packaged policy.json has no mode key and still resolves off. (5) refusal/renderer coupling — for every decision policy loadGateDecision accepts, firing each override yields a basis containing no \n/\r; each defect class throws exactly one FAIL naming file and key. (6) malformed gate is gate-scoped — session_start completes, throws only at the gate tool call.

Open questions: (a) snapshot vs lazy — loadRetryConfig read once at init and injected; loadGatePolicy lazy at every call; a mid-run .council.json edit flips routing and the merge-check input (run-config-stability hazard). Name the intended behavior. (b) cross-file override invariant (class 3 sufficiency) — override.question ∈ weights is necessary but not sufficient: gate-run.ts filters answers to knownIds from questions.json (~L230), so an override whose id is in weights but absent from questions.json can never fire; the noulProbabilityOf-vs-questions check in gate-run.ts is the precedent; residual beyond the four ruled classes. (c) scaffold visibility — /council-init seeds theme and retry as concrete data but the card seeds no gate section; wiki-only discoverability vs seeding "gate": {"mode": "off"}. (d) wiki drift — vault/wiki/metered-deliberation-routing.md still says consumers opt in via a repo-local policy.json; EV-64/65/66/69 specs and plans encode mode:"off" inside policy.json; sweep or spawn the sweep card.

### Designer (job-1.3)

Position: the {"gate": {"mode": …}} shape is the right home; the four refusal FAILs fit the existing single-line template. One load-bearing copy defect: ruling #3 binds the migration to "the existing unknown-key FAIL:", but that FAIL ends "set a valid value or remove the key to use the packaged default" — the packaged default for policy.json is now mode-less and resolves to off. An operator whose repo-local policy.json carries mode: "advisory" sees a FAIL that, if obeyed, silently demotes their gate from enabled to off, with no in-band signal that enablement moved to .council.json; "set a valid value" is also misleading — there is no valid value for mode in this file post-card. The same gateFail mechanism can carry a specialized `mode` line naming .council.json and gate.mode, keeping ruling #3's fail-loud single line while closing the migration gulf. Second, smaller: council/scaffold/.council.json should seed "gate": {"mode": "off"} mirroring retry/theme seeding, else the only visible form of the new key is a FAIL.

Gulf closed (evaluation, upgrade-day operator with mode: "advisory"/"active" in policy.json): obeying the generic FAIL silently disables the gate; invisible until an ungated card passes. The FAIL should carry the migration: e.g. FAIL: <file> has an invalid mode — gate enablement moved to <repoRoot>/.council.json > gate.mode — remove this key and set gate.mode in .council.json. Load-bearing claim: .council.json and gate.mode are named, not that the wording matches verbatim.

Principle/evidence: knowledge in the world / forcing function (anything the operator must remember is design debt; the FAIL is the one surface they're forced to read — gate.ts:125, test/gate.test.ts:84). Signifier: the unknown-key list is a perfect closed-form negative for a typo'd key and a misleading one for a key removed by design; the mode case is the one that needs a tailored line because the loader recognizes it by name. Conceptual model: policy.json post-EV-73 is the gate's tuning file; .council.json > gate.mode is enablement — the FAIL copy must honor the split.

Falsifiable predictions: P1 case sensitivity — {"gate":{"mode":"Active"}} → FAIL: <repoRoot>/.council.json has an invalid gate.mode — expected one of "off", "advisory", "active", found "Active" — … (dotted key form names both section and field). P2 migration copy broken (the load-bearing critique): existing unknown-key FAIL → obeying silently demotes; should read a line naming .council.json and gate.mode. P3 gateStateBudgetTokens absent under non-off resolved mode → existing test's message at test/gate.test.ts:212 with the mode source updated; falsifier: "resolved mode" sourced from loadGateConfig's output, never re-derived from policy.json. P4 gateStateBudgetTokens: 0 under off mode still FAILs positive-integer (off does NOT relax the present-value shape). P5 newline-bearing override id — the loader detects \n/\r BEFORE gateFail sanitization, else the sanitized message hides the cause; message names the field and states the one-line basis contract. P6 override question absent from weights → FAIL: … invalid overrides.0.question — question id "nope" is not declared in weights (expected one of a, b) — …. P7 unknown floors/thresholds sub-key → each parent enumerates its own allowed set (floors.bogus — unknown sub-key; expected one of choice, score); a unified list hides which parent is wrong. P8 fresh repo byte-identity (snapshot + end-to-end no-call smoke). P9 explicit gate.mode "off" vs absent section both resolve {mode:"off"} (JSON.stringify equality smoke); scaffold seeds "gate": {"mode": "off"}. P10 two-source redundancy ordering (loadGatePolicy's unknown-key FAIL vs loadGateConfig's clean enablement — which is the operator's first signal); current FAIL-on-unknown path is correct.

Preferences (ranked last): seed gate off in scaffold .council.json; keep existing template wording style for the refusal classes; keep the generic "set a valid value" half everywhere except specialize for `mode`; a tiny per-key specialization table over a generic helper.

Sharp critique: P2 — the migration copy must not say "remove the key to use the packaged default" for the `mode` key in policy.json; the packaged default has no mode and obeying silently demotes the gate.
