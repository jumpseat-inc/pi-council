## Intent

Rollout step 3 enables the gate for the mechanical class and surfaces its
decision inside the approval gate that already exists, in the command that
already produces the cards. The single decision gate stays the single decision
gate: the human still approves, edits, or drops each card exactly as before, and
the verdict arrives as information attached to the card they are already
looking at — one line per card, naming the mode and the one-line reason.

That one line is the whole surface, and it is where the honesty of the feature
lives for a human. A verdict that reads as an instruction converts the existing
approval gate into a second decision point by implication; a verdict that reads
as a fact about the card's shape lets a human overrule it by editing the card,
which is the intended affordance. The line must also be readable when the gate
had nothing to say — a failed call resolves to the full mode and says so —
because a missing line would read as "no routing" and an invented one would read
as confidence the system does not have.

The basis is not authored at render time. It is the string the decision function
recorded, derived deterministically from the answers and the override that fired,
so the line a person reads and the ledger record they can audit cannot drift
apart. The rendering is a pure function of the recorded decision and the card,
so the byte-identity test is cheap and is the load-bearing evidence that no
second gate was introduced.

## Acceptance

One line per card, containing the resolved mode and a one-line basis; the
approve/edit/drop prompt and the card body text are byte-identical to the
pre-gate rendering in a golden test; a card whose gate call failed renders the
fallback mode with the failure named rather than omitting the line; and no
additional prompt, keystroke, or state transition exists in the step. The line
renders as `Mode: <mode> — <basis>`, placed immediately below the card body and
above the approve/edit/drop prompt; `<basis>` is the string recorded by the
decision function, rendered verbatim, and a test proves the render function
receives it as input and produces no prose of its own; a card whose gate call
failed renders `Mode: Deliberate — gate call failed: <reason verbatim>`.

## Phase 1 Rulings (recorded before dispatch — binding for this run)

- **R1 — merge authorization, every card in this run.** The human authorized
  the run-scoped admin bypass: the merge is `gh pr merge <PR> --squash --admin
  --match-head-commit <X>`, where `<X>` is the exact head SHA the `gates`
  workflow `SUCCESS` (merge-check criterion 2) was read against. This
  authorization is for this run only and is not extended to any later run; a
  SHA mismatch is a HALT, not a retry.
- **R3 — packaged gate default.** The packaged `council/gate/policy.json` ships
  `mode: "off"` (no gate call, no ledger line by default); consumers opt in per
  repo via a repo-local `policy.json`. Tests that exercise the gate set the
  mode explicitly; the default is never relied on to be on.
