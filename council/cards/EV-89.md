## Intent

Phase 1's front-loading is today a prose paragraph: it names the predictable open-judgment classes in passing and records rulings on the card faces, but it enumerates nothing, so the reader can rephrase it into nothing and proceed. This card gives Phase 1 a closed, ordered class list and a durable record that survives across runner generations. The surface is the operator's Phase 1 workflow and the text it reads: the class list, the refusal that halts dispatch when a class is unresolved, and the not-applicable reason field. The refusal is a distinct named literal, not the run's generic `HALT:` environment-failure line, so an operator can locate the unresolved class from the refusal text alone. The record is run-level and class-level, not card-level: settled runner jobs cannot be re-entered, fresh runners rewrite card faces on resume, and some classes have no single owning card — so it cannot live only on a card face, and its path must be discoverable by a fresh runner through `<escalation_contract>` step 1. A recorded class ruling binds every seat for that class only; it does not remove `designer` from deliberation and does not narrow any other design dispute's routing.

## Acceptance

1. `council/procedures/features-deliver.md` Phase 1 names a closed, enumerated set of predictable open-judgment classes (at minimum: surface copy; state/field naming; uncertainty display; error/empty-state text; the gate user-visibility question), and that list is the single source the run reads.
2. The Phase 1 record is durable and named — a file/record that survives a runner restart and is distinct from any card face, because Phase 1 rulings are run-level and class-level: settled runner jobs cannot be re-entered, fresh runners rewrite card faces on resume, and some classes have no single owning card.
3. A `test/` prose pin (the `test/prose.test.ts` pattern) asserts every named class appears in the packaged procedure, and a second prose pin on the same pattern asserts the refusal sentence — that Phase 1 does not dispatch any `council-runner` while a named class carries neither a recorded ruling nor a not-applicable reason — appears in the packaged procedure; deleting or materially weakening either reds the test.
4. A Phase 1 record that leaves a named class with neither a ruling nor a not-applicable reason does not dispatch a `council-runner` (enforced via the pin in bullet 3, not an engine check).
5. The refusal is issued as a distinct, named literal — distinguishable from the run's generic `HALT:` environment-failure convention and locatable from the refusal text alone; its exact wording is settled in deliberation.
6. The record's path/naming convention is named on the card such that a fresh `council-runner` can locate it via `<escalation_contract>` step 1; where it lives and how it is validated is settled in deliberation.
7. The not-applicable reason carries a structured literal prefix consistent with the project's existing structured unavailable-state grammars; the exact prefix is settled in deliberation.
8. The class list renders ordered by stakes — per-card reversible (surface copy, naming) → run-committing (uncertainty display, error/empty-state text) → portfolio-level (the gate user-visibility question) — not as a flat checklist of equal items.
9. A Phase 1 recorded ruling binds every seat for the named classes only, per `<escalation_contract>` step 1; it does not remove `designer` from deliberation on surface-touching cards and does not narrow any other design dispute's routing under council.md step 6.
10. `python3 council/validate.py` and `bun test` pass.

#### designer

**Design position**

The Phase 1 list must read as an ordered, prompted, structurally tiered checklist — each class carries a stable snake_case identifier, a question-shaped prompt the operator answers (not a rephraseable noun), and a ruling SHAPE keyed to its stakes tier (string for per-card reversible; trade-off object for run-committing; boolean for portfolio-level); the runner reads the array in declared stakes order and refuses the first class whose `ruling` is null and whose `n/a:` is missing or fails the anti-shrug check. The refusal literal `Phase 1 unresolved: <class_id>` (P1-5) is locatable by stable identifier from text alone, and a `version: phase1-rulings-1` field on the record gives the runner a distinct refusal literal (`Phase 1 version mismatch: record=<v>, runner expects=<v>`) when the class set drifts across epic versions. The `n/a:` reason grammar (P1-6) is structurally too weak as a bare prefix; it must mirror the existing `usage  partial = <definition>` grammar in `extensions/usage-block.ts:48-54` — a length floor (≥16 chars) and a definition-shape predicate (contains a deferred-work noun, an action verb, or a blocking question), enforced by `validate.py` on the same fence as the board (per P1-4).

**Gulf closed**

Gulf of **Execution** at the human operator's moment: they read the Phase 1 procedure paragraph once at epic start and must produce complete rulings without having attended prior deliberations. Today's noun-style class list ("user-visible copy, what a state is named, how much uncertainty to show..." — `council/procedures/features-deliver.md:127-141`) is rephraseable into nothing; the question-stem + stakes-tier + ruling-shape binding closes that.

Gulf of **Evaluation** at the fresh `council-runner`'s moment under `<escalation_contract>` step 1 (`council/agents/council-runner.md:90-115`): the runner must apply or escalate a dispute without re-reading the procedure, and the refusal text must be locatable from the run log without grepping for `EV-<n>`. The stable snake_case identifier in the refusal literal + the version-mismatch literal + the disjointness with the generic `HALT:` environment-failure line close that.

**Principle and evidence**

- **Signifier + conceptual model** (Finding A + B): each class entry must be a prompt, not a noun. Evidence: the EPIC-11 setup interview finding (vault/raw/2026-09-22-design-epic11-recut-surface.md, Finding A) that the seat-composition question's header was mis-attributed — same failure class: a noun-shape whose meaning is invisible to the first-time reader. The three stakes tiers must be STRUCTURAL (a `tier` field on the JSON), not just a render order — FLLWUP-71's `userVisibility` boolean (council/cards/FLLWUP-71.md) is a different ruling shape than `surface_copy`'s verbatim string, and forcing one shape loses the information that the portfolio-level class gates routing.
- **Mapping** (Finding E): the procedure renders the class list as three stakes headers ("Per-card reversible / Run-committing / Portfolio-level") with ruling-shape hints next to each class — same byte-pin pattern as EV-66's step-4 byte-identical block (test/prose.test.ts:62-79) and the step-13 pre-write pin (`confirmed at ledger level`).
- **Forcing function / anti-shrug** (Finding C): the `n/a: <reason>` prefix (P1-6) is structurally too weak. The project's structured unavailable-state grammar uses `key = <definition>` shape (extensions/usage-block.ts:48-54 — `usage  partial = reported figure excludes unaccounted attempts`); the same discipline belongs on `n/a:` — length floor + definition-shape predicate, validated by `validate.py` on the same fence as the board (P1-4). Without this, the operator writes `n/a: TBD` and the run dispatches.
- **Discovery seam** (Finding D): the runner's `<escalation_contract>` step 1 is silent on what happens when the record's class set differs from the runner's hard-coded set. Symmetric with the EV-70 mode-aware HALT lines (`HALT: EV-<n> has no recorded execution mode — the merge check cannot infer one; route the card at the approval gate`, council/procedures/features-deliver.md:166) — a distinct literal for "I cannot infer" the version, locatable from text alone.

**Preferences, ranked last**

- I would prefer the stable class identifiers be snake_case (`uncertainty_display`) over human-pretty (`uncertainty display`) or kebab-case, because the refusal literal `Phase 1 unresolved: uncertainty_display` is the most grep-stable. This is taste; the project's identifier conventions are mixed (board entries use prose, gate questions use camelCase like `publicContract`).
- I would prefer `validate.py` to enforce the anti-shrug rule directly, not just the prose pin. The card's acceptance bullet 10 names `python3 council/validate.py` as a pass condition but the prose pin (bullet 3) is the only structural enforcement on `council/phase1-rulings.json`.
