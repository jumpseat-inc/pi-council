## Intent

OpenRouter fronts many upstream inference providers, so a single catalogue rate
per model id can diverge from what was actually charged, and the human's
evidence localises to the cache component. This card asks the provider what it
actually charged and records the per-component figures alongside the catalogue
estimate, so divergence is visible per component rather than denormalised into
one total. When actual figures cannot be retrieved, each component carries the
same explicit, non-empty unavailable marker rather than silently standing on the
estimate. The marker literal and its placement are decided at design time and
surfaced through the EV-32 usage block; the store location and record shape are
EV-31's.

## Acceptance

- A fixture provider response carrying per-component values that differ from the
  catalogue estimate is persisted with the response's values.
- A fetch-failure fixture persists the same non-empty unavailable marker for
  every component.
- An implementation that never fetches fails the first test; an implementation
  that always returns the estimate fails the second.
- `bun test`, `bunx tsc --noEmit`, `python3 council/validate.py` stay green.

## Phase 1 rulings (features-deliver, binding for this run)

- **R-1 money signifier** — a reported actual figure renders
  `cost=$0.1234 (reported)`; the catalogue estimate renders
  `cost≈$0.1234 (catalogue)`.
- **R-2 unavailable marker** — an unavailable component renders the literal
  `n/a` in that component's slot, with the legend line
  `n/a = provider figure unavailable`; never a blank.
- **R-7 scope** — persist the routed upstream provider id alongside the
  per-component actual cost, so divergence is attributable.

## 1. Approach

## 2. The EV-32-deferred seam — the in-band provider-figure-unavailable signal

**Signal:** `ProviderCostReport.status: "unavailable"` + one non-empty deterministic `reason` literal. **Storage:** the optional `provider` field on `StoredUsageRecord` — deliberately **not** on `SpendRecord` (frozen byte-verbatim by EV-31's ruling), **not** on `Usage` (frozen EV-28 shape; also `CostBasis` has no unavailable member and the unavailability is per-half, not per-field; adding a third `CostBasis` value would put an unavailable label on a truthful `cost≈$0.0000 (catalogue)` half — the exact relabeling EV-32 rejected), **not** a sidecar second file per invocation (fragments the ruled one-record-per-invocation contract), **not** a render-time re-fetch (choose-once forbids amendment, and it would make the surface network-dependent). **Path to `unavailableCost`:** composed at the flush's `written` transition from the *persisted* report, so "what was shown" and "what is on disk" are equal by construction — the EV-32-settled render-at-written property holds and extends naturally.

The alternatives I reject, named: (i) child-side fetch at settle writing a run-dir sidecar — keeps the flush sync but splits retrieval across two processes, adds a new child-mode network+write surface, and makes the "never fetches" falsifier untestable at the flush seam; (ii) in-band via `usage:{include:true}` injection through `before_provider_request` — buys nothing (pi-ai discards the wire cost at `parseChunkUsage`, so the figures would still need a separate fetch), and it's dependency surgery; (iii) `cost: null` / sentinel on `Usage` — does not compile / relabels truthful zeros; this is EV-32's own recorded rejection and I inherit it.

## 3. R-7 — routed upstream provider id

`provider_name` is returned per generation and is persisted **per `ProviderGeneration` entry** with its `generationId` and `jobId`. I deliberately do **not** denormalize a single report-level `providerName`: a multi-turn job can route successive generations to different upstream providers, and R-7's purpose — divergence *attributability* — requires the per-generation pairing. Divergence is then attributable three ways: job → generation → upstream provider, each with its own `totalCost` beside the catalogue estimate for the same tokens.

## 4. Per-component actuality — the honest statement

The provider does **not** hand one dollar figure per component. Verified today: both the in-band `usage` object and the generation endpoint report **generation-level dollars** (`usage.cost` / `total_cost`, plus `upstream_inference_cost` and a nullable `cache_discount`) and **per-component native tokens** (`native_tokens_prompt/completion/reasoning/cached`). Therefore:

- The **scalar** `cost` of the subtree half becomes genuinely reportable: the sum of the generations' `total_cost`, rendered `cost=$… (reported)` (R-1) — this is the only dollar figure the word "reported" may attach to.
- The four dollar component slots (`costInput/costOutput/costCacheRead/costCacheWrite`) **stay catalogue**. Deriving a per-component dollar split (e.g. prorating `total_cost` by catalogue component share) and calling it reported would be exactly the plausible-but-false figure this epic exists to kill; I do not persist it as reported.
- What *is* reported per component is the **token** split: the fixture's `native_tokens_*` land in the record beside the catalogue-derived tokens, so divergence localizes per component in tokens (which is precisely the human's cache-component evidence pattern — `native_tokens_cached` vs the counted `cached_tokens`).
- `cache_discount` is persisted verbatim when present (a response value) but is **not rendered as a reported cache dollar** — its semantics are undocumented in the pages I fetched; see ruling items.

So the word "reported" in the block applies to the half's money slot only, and the acceptance fixture asserts the response's *values* — total, provider, native tokens — landed in the record.

2. **Fetch-failure fixture → same non-empty marker for every component.** Injected fetcher rejects (`fetch-failed:ECONNREFUSED`). ## 7. Tradeoffs accepted, alternatives rejected, and ruling-seat items

**Accepted:** fetch-before-write makes the record's figures final at write time, at the cost of a bounded async phase in the flush (latency, a wasted fetch on a rare double-trigger race, and a lost fetch if a TUI session quits mid-flight — the drain retries honestly); partial fetch failure marks the whole half unavailable even when some generations succeeded (their facts are retained on the record; the render is conservative); non-OpenRouter runs write no `provider` block at all (absence = not applicable); the runner block (point 5) keeps catalogue this card — its input is manifests, not a store record, and `council_wait` must stay fast and offline; its reported/n-a support is the natural follow-up once the store record exists.

**Ruling-seat items I am not allowed to rule (facts only, no recommendation dressed as fact):**
1. **Slot policy when reported exists:** R-1 binds `cost=$X (reported)`; EV-32 settled one money slot per row, ≤160 cols. If the slot is *replaced* (my design), the catalogue estimate remains only on the record, and divergence is not visible at a glance without opening the record — which the epic's intake arguably wanted. Whether the row should additionally carry the estimate is a copy/grammar question a ruling seat owns.
2. **The exact unavailability reason literals** (`no-generation-id`, `session-missing`, `fetch-failed:<…>`, `timeout`, `no-api-key`) — copy candidates in the EV-31/32 literal tradition, ruled at step 6 of this run; I propose, not rule.
3. **`cache_discount` as a reported cache-component dollar:** the field exists and is nullable; its semantics are not documented in the pages I fetched; a live probe could settle whether it is a dollar figure attributable to cached tokens. I persist it verbatim and do not render it as a component figure.
4. **Omitted vs explicit-unavailable for non-OpenRouter models:** I omit the `provider` block; an alternative writes an explicit not-applicable marker. Facts: omission is indistinguishable from a pre-EV-29 v1 record only to a reader who ignores `schemaVersion`.

## Cross-seam reading — the contract as it actually is

**Files read on both sides:** `extensions/hub.ts`, `extensions/hub-tools.ts`, `extensions/index.ts`, `extensions/runs.ts`, `extensions/spend.ts`, `extensions/usage-store.ts`, `extensions/usage-block.ts`, `extensions/usage-format.ts`, `test/usage-block.test.ts`, `test/stub-child.ts`, plus pi's `pi-ai/dist/api/openai-completions.js`, `pi-ai/dist/models.js`, `pi-ai/dist/types.d.ts`, `pi-coding-agent/dist/core/extensions/types.d.ts`. Wiki: [[index]], [[run-transcripts]], [[hub-job-supervision]], [[eval-store-contract]], [[headless-pi]], [[council-runner]], [[procedures-vs-commands]], [[repository-grounding]], [[seats]]. **Wiki gaps, stated:** there is no page for the EV-28/30/31/32 usage lineage (confirmed — the nearest pages are the three above), and [[hub-job-supervision]] says the hub parses `message_end` "accumulating output tokens/cost" without recording that the cost is a *catalogue estimate* — the wiki is silent at exactly this card's seam.

**The provider mechanism — carried-in evidence confirmed, one clause refuted.** Confirmed: pi's `usage.cost` is `calculateCost(model, usage)` from catalogue rates (`pi-ai/dist/models.js:530-549`), and every adapter — including the one OpenRouter uses — builds `cost: {0,0,0,0,0}` and calls it (`api/openai-completions.js:1203-1205`), mutating the object in place. **Refuted as understated:** OpenRouter's figure is not merely "retrievable out-of-band." pi-ai already sends `stream_options: { include_usage: true }` (`openai-completions.js:594-596`), so the provider's `usage.cost` / `usage.cost_details` **is on the wire, one function away**, and `parseChunkUsage` reads only the token fields and overwrites cost (`:1186-1206`). The provider's money is discarded, not absent.

**Granularity (verified live):** `usage.cost_details` = `{ upstream_inference_cost, upstream_inference_prompt_cost, upstream_inference_completions_cost, server_tool_cost? }` (openrouter.ai/docs/api-reference/overview), and `GET /api/v1/generation?id=<gen-id>` = `{ total_cost, upstream_inference_cost, provider_name, native_tokens_prompt/completion/cached/reasoning, tokens_* }`. **There is no input/cacheRead/cacheWrite/output money split anywhere on the provider surface** — cached tokens exist only as *counts*. The card's four per-component actual figures have no provider-side counterpart at that granularity. This is the contract mismatch.

**The generation id exists in-band and is dropped.** `output.responseId ||= chunk.id` (`openai-completions.js:374`) and `responseId?: string` is on `AssistantMessage` (`pi-ai/dist/types.d.ts:314`). `MessageEndEvent.message` is that message (`pi-coding-agent/…/types.d.ts:603-606`), and `hub.ts:189-221` reads `usage`, `content`, `stopReason`, `errorMessage` off it and drops `responseId`. So the *only* carrier of "which generation to ask about" is already flowing past `hub.ts` and past every record type (`grep responseId extensions/` → no matches).

**Seam 2 — pi gives no in-band money hook.** `after_provider_response` carries `status` and `headers` only (`types.d.ts:531-537`) — no body. The provider money cannot be recovered inside pi's provider plumbing by any extension; EV-29 must make its own HTTP call, with its own credential (env `OPENROUTER_API_KEY` or `getAgentDir()/auth.json`).

**Seam 3 — the store gate is synchronous and choose-once, which is the sharpest constraint.** `flushPendingInvocations` gate 3 is "every manifest with `startedAt >= markerAt` has `exitCode !== null`" (`usage-store.ts:288-306`) — i.e. the forest fully exited; then it computes `spendRecord` and persists, once, never recomputed (`:307-330`, and EV-31's ruling: no recompute ever). The trigger chain is fully synchronous: `Hub.settle()` → `writeJobManifest` → `onChange` → `flushUsage("forest-settle")` (`hub.ts:244-252`; `index.ts:155-160`). **Consequence: there is no window between "last child exited" and "record written" in which an async parent-side fetch could land.** A parent-side fetch started at settle resolves *after* the durable record exists, and the record can never gain it.

**Seam 4 — the record cannot express per-component provenance anyway.** `Usage.costBasis: CostBasis` is **single-valued per `Usage`** (`runs.ts:18,34`) and `"reported"` has no production writer today (`hub.ts:137` is the only writer, `"catalogue-estimate"`; `"reported"` appears only in tests). So a record whose generation total is reported while three components are estimates/unavailable is *unrepresentable* — setting `costBasis: "reported"` on that half makes `formatMoney` print `(reported)` next to a figure that is not (`usage-format.ts:15-19`).

**Seam 5 — the renderer has no per-component money slot.** `measurementRow` emits one `formatMoney(u)` fragment per half (`usage-block.ts:39-45`), and `unavailableCost?: Half[]` is **per-half** (`:31, 60-64`; `test/usage-block.test.ts:144-161`). R-2's literal is reused by this card for four *components*; the shipped surface can only carry two *halves*. EV-32's F ruling moved the descriptor off the block for the ≤160-column budget, so re-adding four money slots is a surface change to a frozen (R-6) grammar.

## Reframe

**The card is asking for a unit the provider does not report and the record cannot hold — so what it is really asking for is: record what the provider charged at the provider's own granularity (one figure per generation), attributed per generation, fetched inside the child before it exits, because the store's write is synchronous at forest-settle and choose-once forbids any later enrichment.**

That reframe makes three things testable that the card's literal wording cannot:

1. **Identity binding.** The persisted reported figures must be answerable by *the invocation's own observed generation ids* (from its session/stream), not by any list a fixture can supply. Without this, acceptance 1 is green for a mapper fed by the fixture and red-free for a production path that fetches nothing.
2. **A gate-ordering assertion.** Reported data present in a record ⇒ it was written before the `forestFullySettled` transition. Nothing in the card's acceptance constrains *when* retrieval happens, and the only legal window is pre-exit.
3. **A granularity assertion.** Every reported figure is a generation-level (or provider-declared `cost_details`) figure; no per-component actual is ever fabricated by pro-rating a total. The card's acceptance, as written, mandates the fabricated case.

## R-7 — the routed upstream provider id

`provider_name` is a **per-generation** fact on the generation endpoint; pi-ai's `OpenRouterRouting` (`pi-ai/dist/types.d.ts:496, 629-633`) has `allow_fallbacks` defaulting true, and council sets no routing (no `openRouterRouting` anywhere in `extensions/`), so the upstream host may differ request-to-request — including within one seat's turns. A per-invocation record therefore **cannot honestly carry one provider id**; the honest persistence is the multiset of `{provider_name → generation count and/or reported cost}` (or a bounded per-generation list), plus an explicit statement that no single provider is claimed. Additional fact: for `is_byok: true` requests `total_cost`/`upstream_inference_cost` reflect credit accounting, not the user's actual bill — so `(reported)` must not be read as "the truth," only as "what this provider reported for this generation."
