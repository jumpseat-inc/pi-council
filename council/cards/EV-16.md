## Intent

This is the "where to start" answer and the epic's design authority. The
Council deliberates and settles the definitions every later child builds on:
what "accurately measure" means for a multi-step agent command (gates green?
goal met? a judge verdict? cost and latency?) and for a single seat turn;
the harness architecture; how a model id is injected per run without
editing committed files; the rubric shape; and the confidence method (how
many repeats per cell, what variance means, when a difference is real).

Produces `docs/superpowers/specs/<date>-council-eval-design.md` and a
matching plan, self-reviewed for placeholders, internal consistency, scope,
and ambiguity, then committed. Nothing in the spec asserts a design choice
as settled that the deliberation left open.

Not surface-touching (documentation; no designer seat).

## Acceptance

- Spec + plan files exist under docs/superpowers/ and define the five items
  in the goal with falsifiable acceptance criteria each.
- The spec records the model-injection mechanism EV-17 implements, the
  fixture schema EV-18 fills, the rubric EV-19 grades by, and the matrix and
  variance semantics EV-20/EV-21 rely on.
- `python3 council/validate.py` still passes after the docs edits.

## Phase 1 rulings (features-deliver, binding for this run)

- **R-1 (storage)**: eval results records live under `council/eval-results/`,
  local-only telemetry, self-gitignored like `runs/` (the convention-12
  pattern). Not committed to git. The spec names this location; EV-20 writes
  there; EV-21 reads from there and its empty state is truthful on a fresh
  checkout.
- **R-2 (repeat default)**: the default repeat count is **3**; the caller
  raises or lowers it explicitly via `--repeat N`. There is no implicit
  all-models sweep — the matrix contains only what the caller names. The
  spec records this default and its cost rationale; EV-20 implements it.

## Deliberation record

### Round 1

#### owner (job-1.1)

**Approach** — the spec pins each of the five items to a mechanism that
already exists: the hub's `JobReport` (hub.ts) carries cost, tokens, turns,
elapsedMs, and stopReason per run — cost/latency instrumentation needs zero
new plumbing; run manifests (runs.ts) already persist `model` per job, and
`readManifests` returns `[]` on a missing dir — the exact contract EV-21's
truthful empty state needs. Critically, the child's model is argv-driven
(`buildChildArgv` emits `--model`), while the child's own `loadSeat`
(child.ts → `runChildMode`) only resolves tools/grants/body — so a per-run
model override is a purely parent-side change and does not need child-side
plumbing.

1. **"Accurately measure"**: for a multi-step procedure run and a single
   seat turn alike, score = fraction of rubric criteria passed, 0..1;
   cost, elapsed, tokens are REPORTED dimensions, not score inputs.
   "Accurately" means only the model varies: same fixture, same rubric
   version, same repo starting state — each cell runs in a scratch state,
   not the live tree.
2. **Harness architecture**: engine module (new `extensions/eval*.ts`) +
   data files (fixtures/rubrics under `council/`, repo-local shadowing per
   convention 5) + EV-20 as a slash command whose handler calls engine code
   directly — NOT an LLM-orchestrated loop. Reuses hub dispatch/wait and
   `council_dispatch`'s shared path (convention 7). Each cell executes
   against a disposable scratch worktree seeded from the fixture (smoke-test
   precedent — procedures like /council merge branches, set board state,
   commit; running them against the caller's live tree would corrupt
   comparison state). Only results records are written back to the caller's
   `council/eval-results/`. The spec must state why runs/ cannot be the
   comparison store: `pruneRuns` keeps only the last 15 runs at
   `session_start` — mid-matrix pruning would silently delete evidence.
3. **Per-run model injection**: resolution chain is frontmatter →
   `.council.json` (`loadSeat` → `applySeatOverride`). EV-17 adds a third
   layer that beats `.council.json`: `council_dispatch` gains optional
   `model`/`thinking` params (hub-tools.ts), applied to the resolved seat
   before `buildChildArgv`; the override must be written into the spawned
   job's manifest `model` field (currently `spawnJob({model: seat.model})`)
   — EV-17's "visible in the transcript" acceptance. Override id must be
   qualified (`provider/id`, matching `qualifiedOrThrow`) and pass the same
   loud catalogue check `council_dispatch` already runs (unknown model →
   refuse, no fallback). For the procedure direction ("driven under one
   model"), every seat the procedure dispatches must see the override — so
   the mechanism is a SESSION-SCOPED override honored by any dispatch in
   the eval session (hub-level/env), not just an explicit param. The spec
   must name one of these; EV-17 cannot implement "both directions" if the
   spec leaves it ambiguous.
4. **Rubric shape**: ordered list of named criteria; each criterion is
   either a deterministic gate (definite pass/fail: gates green, validate.py
   clean, artifact present) or a recorded judge verdict (existing judge.md
   PASS/REJECT used as data). Unweighted pass/total — weighting is a policy
   debate for a future card; unweighted scores are stable across rubric
   versions. Resolve the tension in EV-19's own acceptance: "same run
   re-graded produces same score" cannot hold if re-grading re-runs the
   judge (verdicts stochastic). Resolution: deterministic gates are
   re-runnable; judge verdicts are RECORDED at grade time into the result
   record and re-graded by replay, with the grader's model id stored in the
   record. Rubrics schema-validate at load, fail loudly when a fixture
   lacks one (no silent `[]`).
5. **Confidence method**: n=3 default (R-2), per-cell (task × model) mean,
   sample σ, and n computed from the records alone (each record carries
   task, model, thinking, repeat index, per-criterion pass/fail, score,
   cost, elapsed, tokens, stopReason, rubric version, fixture version, repo
   state). "A difference is real" = the confidence interval on the mean
   difference excluding zero. Honestly: at n=3 that interval is wide, so
   the leaderboard renders TRIAGE, not asserted ordering between close
   models — "do not claim an ordering whose variance doesn't support it"
   is a first-class rule. R-2's no-implicit-sweep is a cost guard; the cost
   rationale belongs in the spec verbatim (a full 16-inventory × M-models ×
   3 sweep is hours of dispatch).

**Tradeoffs accepted** — scratch-repo-per-cell (costs setup time, only way
"only the model varies" holds); unweighted criteria / separate cost
dimension (gives up seductive single "best model" number; keeps quality vs
price separate); judge verdicts as recorded data not re-runnable evidence
(open-ended criteria aren't bit-reproducible; EV-19's re-grade acceptance
becomes satisfiable); in-session sequential matrix execution (18 cells can
be hours, waitForIdle blocking per headless rules).

**Testable claims** — (1) override is parent-only: resolve seat, apply
override, assert `buildChildArgv` emits `--model <override>` and the
spawned manifest records it, while `runChildMode`'s seat resolution never
consulted for model; (2) only-the-model-varies enforceable: same fixture ×
model × rubric run twice in scratch state scores identically; (3) re-grade
reproducibility: record R re-graded yields same per-criterion pass/fail and
score (judge criteria replayed, gates re-run); (4) variance honesty: two
n=3 cells with overlapping score CIs render as tied/adjacent;
(5) empty state: fresh checkout with no council/eval-results/ dir renders
empty state; validate.py remains green.

#### principal (job-1.2)

**Approach** — the five items are ONE contract, not five definitions. The
load-bearing invariant the spec must state in its first paragraph: *the
only thing that varies across cells is the model id — the fixture, the
grader's model, the harness-as-human policy, and the environment are pinned
as part of the fixture.* Every one of the five items is a clause of that
invariant; rubric shape and confidence method are downstream of it.

Seams as they exist in the code:

1. **Model injection (EV-17)** — `council_dispatch` resolves the seat via
   `loadSeat` (frontmatter → `.council.json` via `applySeatOverride`), then
   `buildChildArgv` hardcodes `--model seat.model` / `--thinking
   seat.thinkingLevel`. The override must be a THIRD LAYER applied only on
   the eval dispatch path, above `.council.json`, threaded as a parameter —
   never a mutate-then-restore of `.council.json` (EV-17's acceptance
   "without writing to seat frontmatter or .council.json" fails by
   construction otherwise). Two contracts to pin: (a) the override reuses
   the SAME qualified-model + optional `:thinking`-suffix grammar that
   `.council.json` and frontmatter share (one parser, qualifiedOrThrow-
   style, not a second grammar); (b) it passes the SAME
   `ctx.modelRegistry.getAvailable()` catalogue check the seat's resolved
   model already does in `council_dispatch` — else the child dies later
   with a confusing exit instead of refusing loudly.
2. **Storage (R-1)** — `council/eval-results/` is deliberately OUTSIDE the
   ephemeral `runs/` boundary; runs/ is pruned to 15 at `session_start`
   (`runs.ts::pruneRuns`) and read ONLY by the runs/tree/transcript/
   navigator quartet. Eval results are durable evidence; they must not
   inherit runs' retention, and must not be read by `navigator.ts`. The
   spec must name the read-owner (EV-21's view) explicitly, or someone
   wires the leaderboard into the tree and records silently vanish under
   the 15-run prune.
3. **Measurement unit is the job FOREST, not the job** — a single seat turn
   is one dispatched child; /council and /features-deliver are a TREE of
   children (`parentJobId` in RunManifest, reconstructed by tree.ts). Hub
   only knows flat jobs; cost/latency/turns accumulate per-job. The spec
   must define command-level aggregation as "sum over the forest rooted at
   the command's job," or EV-20 sums one way and EV-21 renders another and
   the cost column is wrong for every multi-step command.
4. **"Accurately measure" already exists — inherit it.** The smoke test's
   philosophy ("never trust a claim, re-run reality": typecheck, bun test,
   exact CLI-output probes re-run by the harness, not taken from seat
   prose) is the operational definition of accuracy for a multi-step
   command. EV-19's rubric already encodes it (deterministic gate preferred,
   judge verdict recorded and counted). The spec should generalize the
   smoke definition to an N×M×repeat matrix, not invent a new definition.
5. **The grader introduces a second model.** A deterministic gate is
   model-free; a judge verdict is not — the judge seat runs under its OWN
   resolved model. If the rubric's open-ended criteria are graded by the
   judge's repo-resolved model while the cell measures a different model,
   σ compares apples to oranges. The spec must pin the grader's model as
   PART OF THE FIXTURE (a fixed reference model resolved from the fixture
   file, not from `.council.json`), or "when a difference is real" is
   meaningless.

**Tradeoffs accepted** — terminal-state variance, not just numeric σ: this
codebase exhibits variance as DIFFERENT TERMINAL STATES (smoke's
"flash-model variance" pause state, stalled, informational timeout,
stopReason=length empty-done surfaced as model-config defect). A confidence
method defined only over numeric score variance is blind to the observed
failure modes; require a per-cell terminal-state histogram alongside
mean/σ, and classify stopReason=length as a distinct excluded/flagged state
rather than a score. The harness must play the human, and that's a fixture
property: /council and /features-deliver contain human-in-the-loop gates
(merge gate, delivery rulings); the smoke fixture resolves this with
pre-authored standing rulings + the driver merging the branch. If EV-18's
"runnable from a fresh checkout with no manual setup" holds, the
harness-as-human policy is PART OF THE FIXTURE, and the spec (not EV-18 in
isolation) must name it. `task` naming is a cross-slice contract:
/council-eval [task] [model...] assumes a task identifier; EV-18 assumes a
fixtures directory; EV-19 assumes a rubric-per-fixture. The spec must
define the task-id → fixture-dir → rubric-file wiring once.

**Reframe** — lead with the cell-invariance contract and derive the five
items from it as clauses, in dependency order: fixture pins everything-but-
model → rubric grades against pinned grader → override is the only free
variable → forest is the measurement unit → variance is terminal-state +
numeric.

**Testable claims** — (1) override is the only free variable: dispatch
with model M; loadSeat(repoRoot, seat).model unchanged (no .council.json /
frontmatter write), child argv contains --model M, manifest model field is
M; omitting override yields .council.json-resolved model. (2) Forest, not
job, aggregation: fixture command dispatches a grandchild; command-level
cost/turns = sum over readManifests for the subtree rooted at the command's
parentJobId. (3) Grader-model invariance: rubric resolves its judge model
from the fixture file, not loadCouncilConfig. (4) Variance includes state:
a cell with 2/3 done + 1/3 stopReason=length must report the state
histogram; leaderboard does not collapse it to a bare mean/σ. (5) Durable
vs ephemeral: eval record survives pruneRuns; navigator.ts/runs.ts never
read council/eval-results/.

### Round 2

#### owner (job-1.3) — round 2

Grounding verification — position cites code, wiki, and AGENTS.md
convention #12. Key facts checked: `pruneRuns(repoRoot, keep=15)` truncates
to the last 15 runs at parent session_start (extensions/runs.ts:147–162);
`council_dispatch`'s schema today is `seat|input|timeout_minutes|stall_minutes`
only — no model/thinking params (extensions/hub-tools.ts); `spawnJob` already
accepts `model` and writes it into the manifest's `model` field
(extensions/hub.ts:88–109); `buildTree` links purely by `parentJobId`
(extensions/tree.ts:23); the hub already records `stopReason` per job and
`formatReport` already calls length-death a "model-config problem, not a seat
problem" (hub-tools.ts); `model-floors.json` exists for exactly that failure;
consumer repos carry a repo-root `council/` (board.md, cards/, preflight.sh,
validate.py — council/scaffold/council/), so repo-root `council/eval-results/`
fits the scaffold without touching PKG_ROOT or the runs/ quarantine.

- **Q1 — concede threading, drop session-scoped as a mechanism.** Ambient
  state (env inheritance, mutate-then-restore) is precisely what makes
  cells non-reproducible — a session-scoped override would leak into EVERY
  dispatch in the eval session, including the grader edge, silently
  violating "only the model id varies." The harness holds the model list in
  its own code — "run everything under X" is harness config that emits
  per-dispatch params, not ambient state. Spec sentence: model injection is
  one layer — optional `model`/`thinking` on `council_dispatch`; effective
  model = param → `.council.json` override → frontmatter; same
  `qualifiedOrThrow` parser and same live catalogue check; effective value
  written to the manifest `model` field by the existing `spawnJob` path.
  There is no session-scoped layer.
- **Q2 — agree: grader is fixture-pinned, plus one addition.** Open-ended
  judge criteria grade under a reference model resolved from the fixture
  file, not from the repo's `.council.json`. The same third-layer injection
  applies on the grader dispatch edge. Addition: every verdict record
  carries `gradedBy` (the actual grader model id), and replay re-grades
  under a different pinned grader append-only — the record never
  overwrites.
- **Q3 — histogram accepted; a length-repeat is FLAGGED, never scored 0.**
  Score is over COMPLETED repeats only; the cell record carries
  `n_attempted` vs `n_graded` plus a terminal-state histogram; a
  majority-flagged cell renders as indeterminate triage, not a low number.
  Grounded in engine precedent: the hub records stopReason per job and
  formatReport already classifies length-death as a model-config problem;
  model-floors.json exists for exactly that failure. Scoring length as 0
  conflates config failure with capability and makes the score unstable
  under the documented remediation (raise the floor, re-run, the same
  capability scores differently — the two numbers were never comparable).
- **Q4 — three refinements, not disputes.** (a) The invariant is the
  (model, thinking) PAIR, and it's only as strong as the dispatch surface:
  buildChildArgv exposes no sampling knobs, so the harness pins file state
  and policy but controls sampling only STATISTICALLY — the repeat
  dimension is the control for the unpinnable dimension. (b) The forest
  root settles aggregate scope but WHO DISPATCHES THE JUDGE settles CELL
  scope: per-cell mean/σ is well-defined only if the cell's driver job
  dispatches its own grader, giving parentJobId = cell job id. Spec
  sentence: each cell driver dispatches its own grader; cell scope =
  subtree rooted at the cell job, command scope = subtree rooted at the
  command's job. (c) Standing rulings must be MACHINE-APPLICABLE STRUCTURED
  POLICY, not smoke-style prose: smoke's rulings work because a human
  driver applies them; eval has no human in the loop, and a
  deterministic-gate rubric criterion can't consult prose. The ruling
  engine must be pure and unit-testable. (d) Storage: council/eval-results/
  is repo-root consumer data, COMMITTED for leaderboard comparability,
  never PKG_ROOT, never under CONFIG_DIR_NAME/runs. Read-owner must be a
  module OUTSIDE AGENTS.md #12's closed quarantine list — a new eval module
  owns it exclusively; harness writes happen end-of-run (cells write only
  to their scratch worktree).

Tradeoffs accepted — dropping session-scoped costs an ergonomic shortcut
for "this whole run under X" (worth it: harness config explicit, recorded
per job in the manifest); fixture-pinned grader ignores a repo's
.council.json judge tuning during eval (the experiment definition wins);
flag-and-exclude length repeats produces an explicit "not measured" instead
of a false-precise 0; structured rulings are more work than prose fixtures
(necessary: prose rulings are not engine-applicable).

Testable claims — (1) Injection precedence (pure): with a model param,
buildChildArgv receives the param and manifest.model = param; without,
behavior unchanged vs today. (2) Length semantics (pure): cell-summary over
[{stopReason:length, done, empty}, {done, ok}] yields {completed: 1,
lengthFlagged: 1, score: 1.0} — not {score: 0.5}. (3) Aggregation wiring
(pure, real buildTree): judge's parentJobId = cell job id sums per-cell
cost correctly; judge as direct child of the command job changes the
per-cell sum. (4) Replay append-only (pure): re-grading under a different
pinned grader writes a second verdict keyed by gradedBy; original record
byte-identical. (5) Quarantine (grep): no file in the runs/ set references
the eval-results path; only the new eval module does.

#### principal (job-1.4) — round 2

Cross-seam reading. Q1 — override mechanism: session-scoped is not merely
acceptable, it is NECESSARY for the procedure direction, and I retract
"threaded as a parameter" as the whole answer. A grandchild's model is
resolved INSIDE the child process by that child's own council_dispatch
(child.ts runChildMode → registerHubTools → same execute in hub-tools.ts). A
per-dispatch parameter on the parent's call never reaches the LLM's
subsequent tool calls; only ambient state (env) rides the tree.
initHubIdentity(process.env.COUNCIL_RUN_ID, process.env.COUNCIL_JOB_ID) in
child.ts and childEnv spreading process.env already exist. Mechanism the
spec should name unambiguously: (1) ONE env-carried third layer, read in
council_dispatch AFTER loadSeat and BEFORE both the catalogue check and
buildChildArgv (the same insertion point where seat.model/thinkingLevel are
currently resolved and checked, hub-tools.ts ~89–130); (2) same
:thinking-suffix grammar + same qualifiedOrThrow +
ctx.modelRegistry.getAvailable() loud check; (3) set on the SPAWNED JOB's
env, not the parent's global process.env (else it leaks into every non-eval
dispatch); childEnv propagates it to grandchildren with no further work;
(4) explicit per-dispatch model/thinking params are optional sugar that, if
present, win over the env var — but the spec should name the env var as
canonical so EV-17 implements one path, not two.

Q2 — cost report-only vs forest aggregation: consistent. But a real seam:
JobReport carries usage/stopReason/elapsedMs ONLY in memory;
writeJobManifest persists id/seat/model/parentJobId/pid/sessionId/state/

readManifests (the parent's only forest view) has structure but not
telemetry. Command-level cost = "sum over the forest" is therefore NEW
PLUMBING: persist per-job usage/stopReason/elapsedMs into the manifest at
settle() (a RunManifest extension), then sum over the readManifests subtree
rooted at parentJobId. The spec must name this, or EV-20 sums one way and
EV-21 renders another.

Q3 — judge model invariance: the owner's mechanism (record the grader's
model id, re-grade by replay) is TRACEABILITY, not invariance. judge.md
pins openrouter/qwen/qwen3.6-35b-a3b:medium but loadSeat →
applySeatOverride lets .council.json silently re-model it. Recording the id
DETECTS drift, it does not PREVENT it. The spec must pin the grader's model
IN THE FIXTURE, and the grade step must dispatch the judge under the SAME
third-layer override (fixture pin beats .council.json). The recorded
graderModel field then serves as the verification that the pin held — not
as the pin itself.

Q4 — dispute on the merits: the "zero new plumbing" claim for cost/latency
is true only for the single-job direction, false for the forest direction.

Blind spots — engine/owner view: report() looks complete so cost/latency
looks like free instrumentation, but the only parent-side forest reader
(readManifests) never sees usage/stopReason because the manifest write path
drops them. EV-21/leaderboard view: it assumes per-record
cost/tokens/stopReason exist in council/eval-results/ — it cannot see those
fields must be snapshotted by EV-20 at settle time.

Reframe — ONE mechanism observed at two depths, not two mechanisms:
(1) Override: env-carried third layer, applied at the single point in
council_dispatch (post-loadSeat, pre-catalogue-check, pre-buildChildArgv),
propagated via spawnJob env + childEnv. Single seat turn = the mechanism at
depth 0; procedure = the same mechanism re-applied at depth ≥1 inside the
child. My round-1 "parameter" and the owner's "session-scoped" are the SAME
design, with env as the carrier. (2) Telemetry: persist per-job
usage/stopReason/elapsedMs at settle(); forest aggregation = Σ over the
readManifests subtree. This is the one genuinely new piece of plumbing.
(3) Grader: fixture pins the judge model; grade step dispatches under the
third-layer override; record stores graderModel as verification.
(4) Still-unaddressed and needing explicit spec text: harness-as-human
policy as fixture content (/council merge gate, /features-deliver delivery
rulings), and task-id → fixture-dir → rubric-file wiring defined once.

Testable claims — (1) Override propagation: dispatch seat S under env
COUNCIL_EVAL_MODEL=M; root argv contains --model M; if S spawns a
grandchild, the grandchild's manifest model field is M; frontmatter and
.council.json untouched. (2) Precedence: env beats .council.json; explicit
param (if kept) beats env; all three parse the same :thinking suffix.
(3) Forest telemetry: a procedure that spawns a grandchild, after settle,
has usage/stopReason in the grandchild's manifest; command-level cost =
root.usage + grandchild.usage. (4) Grader invariance: fixture pins judge
model M1 while .council.json pins M2; the grade step's judge dispatch argv
carries --model M1; record.graderModel === M1. (5) stopReason=length: a
cell with 2/3 done + 1/3 stopReason=length renders a terminal-state
histogram and is flagged, not collapsed to a bare mean/σ.

### Round 3

#### owner (job-1.5) — round 3

All code claims verified. Verification summary: depth ≥1 resolution —
runChildMode registers council_dispatch INSIDE the child (child.ts —
initHubIdentity(process.env.COUNCIL_RUN_ID, process.env.COUNCIL_JOB_ID);
registerHubTools(pi, repoRoot, { allowedSeats: seat.spawns })), and the

sets COUNCIL_RUN_ID/COUNCIL_JOB_ID). buildChildArgv's --model/--thinking
argv reaches depth 1 only. Q2: RunManifest (runs.ts:8-20) and
writeJobManifest (hub.ts:89-101) persist id/seat/model/parentJobId/pid/
sessionId/state/startedAt/settledAt/exitCode — no usage/stopReason;
report() (hub.ts:256-268) holds them in memory. Q3: judge.md pins
openrouter/qwen/qwen3.6-35b-a3b:medium; loadSeat applies
applySeatOverride — a consumer .council.json can silently re-model the
judge. Judge's grants are Read/Bash → no hub grant → a judge LLM itself
cannot re-dispatch; only dispatcher in a grade cell is whatever code makes
the call.

Approach — Concede Q1 on the merits; the code claims are verifiably
correct and round-2's "no session-scoped layer" was an overcorrection. The
spec names ONE env-carried third layer as canonical: a single COUNCIL_*
env key carrying provider/id or provider/id:thinking (same suffix grammar,
same qualifiedOrThrow, same live catalogue check), read in council_dispatch
AFTER loadSeat and BEFORE the catalogue check and buildChildArgv. Critical
detail the spec must pin: the resolution must WRITE THE EFFECTIVE (model,
thinking) BACK ONTO THE SEAT BEFORE THE CATALOGUE CHECK — otherwise the
check validates the frontmatter model while the spawn runs a different one,
and the manifest/argv/getAvailable all diverge. Precedence: per-dispatch
param > env > .council.json > frontmatter. The env override is set on the
SPAWNED JOB's env (hub.ts:137 already honors per-job env:), never the
parent's process.env, so it is ambient inside the eval subtree and
invisible to every non-eval dispatch. Round-2 "param → .council.json →
frontmatter, no session layer" is withdrawn; the param remains optional
sugar that wins when present; Q3's judge pin rides the same layer (fixture
pin via env at the grade-run root; post-settle the manifest model must
equal the pin or the cell is invalid). Q2: concede forest-direction
plumbing — extend RunManifest with usage + stopReason at settle() and sum
the subtree rooted at the command job's parentJobId; elapsedMs is already
derivable from persisted startedAt/settledAt, so only two fields are
truly new. Harness-as-human rulings and task-id → fixture-dir → rubric-file
wiring: converged — one machine-applicable structured policy block per
procedure (/council merge-gate verdict, /features-deliver delivery ruling)
evaluated by a pure, unit-testable engine, and one wiring table defined
once in the spec, referenced by both run and grade.

Tradeoffs accepted — ambient state is invisible at the tool call site;
auditability preserved only because the effective model lands in the
manifest via the existing spawnJob({ model: seat.model }) path. The
param-wins escape hatch could theoretically defeat a pin if an LLM driver
passed an explicit param; closed by harness-owned grade dispatch plus the
manifest-model assertion. One new env key is ambient surface area, but it
rides an existing, already-propagating family, and is subtree-scoped so no
non-eval dispatch sees it. Q2's manifest extension touches the "hub.ts is
stable" boundary (convention 7) — exactly why the spec must carry a failing
test first rather than a silent field addition.

Testable claims — (1) Precedence (pure): extract resolveEffectiveModel
(seat, envVal?, param?); assert param > env > .council.json > frontmatter
for all four combinations, including :thinking suffix parsing in all three

#### principal (job-1.6) — round 3

Cross-seam reading — the dispatch seam has two edges, and they resolve
models DIFFERENTLY today. Parent edge (hub-tools.ts): council_dispatch
calls loadSeat → frontmatter → .council.json, runs the catalogue check,
then buildChildArgv emits --model seat.model and spawnJob({model:
seat.model, env: childEnv(...)}). Descendant edge: a hub-enabled
cell-driver calls council_dispatch INSIDE the child process; that same
execute() re-runs loadSeat for the grandchild and resolves it from
frontmatter/.council.json — with NO override input at all. So today there
is no mechanism that reaches a grandchild. The owner's "harness emits
per-dispatch params" is true only for the root dispatch; the harness has no
call site at the grandchild edge, because the grandchild is dispatched by
the cell-driver LLM, not by the harness. "Run everything under X" is
therefore UNSATISFIABLE by a parent-side param alone. The decisive existing
precedent: env already rides the tree — childEnv (runs.ts) copies
process.env forward and injects COUNCIL_RUN_ID/COUNCIL_JOB_ID per-spawn;
tree.ts's parentJobId is literally sourced from COUNCIL_JOB_ID via
initHubIdentity in child.ts. That is scoped, deterministic, spawn-time
state — not process.env mutation. An override written into the spawned
job's env argument (not the parent's process.env) is subtree-scoped:
siblings (the grader, the next cell) never see it, and there is nothing to
restore.

Blind spots — owner (inside the parent/engine slice): sees council_dispatch
as a single dispatch surface and concludes param-only suffices; cannot see
that the same council_dispatch code re-enters inside the child process for
grandchildren, where the harness cannot inject a param. Also conflates
"env" with "mutate-then-restore ambient state" — while the codebase already
ships COUNCIL_RUN_ID/COUNCIL_JOB_ID as per-spawn env that makes the job
forest work. Grader/leaderboard slice (EV-19/EV-21 side): cannot see that
Q4b (grader as cell-driver descendant, parentJobId = cell job id) puts the
reference-model grader INSIDE the measured subtree — so forest-summed
cost/latency would count the fixture-pinned grader's spend as if it were
the cell model's, contradicting "only the model varies." It also cannot see
that a grader dispatched from inside the cell-driver's process inherits
COUNCIL_MODEL=X unless that dispatch is explicitly overridden.

Reframe — the override is ONE layer with two delivery surfaces, not
"param-only vs env." (a) Name-in point: the council_dispatch model/thinking
param — the harness names X for the root, which sets that job's --model
argv and manifest field. (b) Carry point: the same effective value is
written into THAT SPAWN's env (COUNCIL_MODEL), riding the existing childEnv
path to descendants. Every dispatch edge then applies the uniform chain
explicit param → inherited COUNCIL_MODEL → .council.json → frontmatter,
re-runs qualifiedOrThrow + ctx.modelRegistry.getAvailable() against the
EFFECTIVE model, and writes the effective value to argv + manifest + child
env. No process.env write, no restore, no session scope. The layer is
spawn-scoped, exactly like COUNCIL_RUN_ID. Direct answer to the posed
question: YES — setting the override on the spawned job's env (never the
parent's process.env) does not leak into sibling dispatches, including the
grader. The leak the owner warns about is a property of WHERE the value
lives (mutable global) not of env as a mechanism.

ONE DISPUTE ON THE MERITS: Q4b (cell-driver-dispatches-own-grader).
Recommend the grader be a HARNESS-DISPATCHED SIBLING with the fixture pin
as an explicit param and cell↔verdict linkage carried by a cellId field on
the verdict record (which Q2's gradedBy already establishes as the pattern)
— not by tree topology. If the grader is instead kept as a cell-driver
descendant, the spec must then require: (1) the grader dispatch always
carries the explicit fixture pin so it shadows the ambient COUNCIL_MODEL=X,
and (2) grader nodes are excluded from cell/command cost-latency
aggregation. Keeping it as a sibling removes both requirements for free.
All other refinements (grader fixture-pin + gradedBy append-only, flagged
length semantics, structured machine-applicable rulings, repo-root
committed eval-results/ with a new eval-module read-owner) are sound —
converged, no dispute.

Testable claims — (1) Subtree scope, no residue: dispatch cell A under X,
cell B under Y, grader G pinned P; every descendant manifest in A's subtree
has model == X, B's == Y, G's == P; process.env.COUNCIL_MODEL is undefined
in the parent after all dispatches. (2) Env carries the descendant edge: a
hub-enabled cell-driver dispatches a grandchild via its own council_dispatch
with no model param; grandchild's manifest.model == X (env-resolved), not
its .council.json value. (3) Grader isolation (if sibling): grader.parentJobId

### Ruling (step 6 — product-owner/steward, applied verbatim on resumption)

- **Ruling** — The grader is a **harness-dispatched sibling of the cell** (parent = the command job, same parent as the cell driver). Cell↔verdict linkage is by an explicit `cellId` field on the verdict record — not by `parentJobId`. Cell-subtree cost = the cell driver and whatever it spawns; the grader is structurally outside that subtree, so no exclusion rule is needed in cost/latency aggregation.

- **Options rejected** — Owner's Option B (cell-driver descendant) loses because defending the cell-invariance contract under Option B requires two pieces of new plumbing (grader dispatch must explicitly shadow `COUNCIL_MODEL` ambient override, plus every cost aggregator must exclude grader nodes from cell/command sums). Option A removes both requirements structurally, and the owner's "per-cell mean/σ is well-defined" claim is true under either topology — mean/σ is over the score, not the spend — so it does not bear the weight the owner asks it to bear. The actual distinction is in cost/latency aggregation, where sibling topology wins.

- **Grounding** — `council/cards/EV-16.md` rounds 1–3 + Skeptic report (the dispute as left by the deliberation); `extensions/hub-tools.ts:107` (the `childEnv({ ...process.env, ... })` propagation point that makes Option B's ambient-inherit risk real); `extensions/hub.ts:89–101` + `extensions/runs.ts:8–20` (manifest structure — no usage/stopReason persisted, so forest cost is new plumbing either way); `extensions/child.ts` (`runChildMode` re-enters `registerHubTools` inside the child, so a grandchild's dispatch has no override-input channel); `council/agents/judge.md` (`tools: [Read, Bash]`, `spawns: []`, no hub grant — judge cannot dispatch itself); `vault/wiki/hub-job-supervision.md` + `vault/wiki/run-transcripts.md` (engine context for job forest + manifest structure); AGENTS.md convention 7 (`hub.ts is stable — change with a failing test first`, bear in mind for the RunManifest-with-usage extension). Full record at `vault/raw/2026-09-03-po-ev16-grader-topology.md`.

- **Reversibility** — Trivial at the spec level. The downstream cards (EV-17, EV-19, EV-20) are still `Backlog` per EPIC-4 and have not started implementation, so even a wrong ruling here costs a spec edit, not a re-implementation. The spec text the runner writes:
  1. Grader dispatch site = the harness (never the cell driver). The harness spawns the judge after the cell driver settles, with `cellId` (a new param on `council_dispatch`, same injection point EV-17 adds for `model`/`thinking`) and the fixture-pinned grader model as an explicit `model` param so it beats `COUNCIL_MODEL` env inheritance.
  2. Cell subtree = `parentJobId`-chain rooted at the cell job. Grader's `parentJobId` = the command job, structurally outside the cell subtree. Three aggregation columns: `cell`, `command`, `grading`. No exclusion rule.
  3. Verdict schema = `{ cellId, gradedBy, fixtureVersion, rubricVersion, perCriterion: [{criterionId, verdict, evidence}], gradedAt, gradingUsage: {input, output, cost, elapsedMs, stopReason} }`. `cellId` is the linkage field; topology is not.
  4. Cell drivers have NO authority to dispatch graders. Judge's `spawns: []` stays correct; the harness owns all grade dispatches.
  5. Both env-carried `COUNCIL_EVAL_MODEL` (round-3 converged) AND harness-owned grader dispatch with explicit `model` param are required and stated in that order — the cell-model carrier and the grader-pin carrier are different surfaces with different precedence rules.
  6. The `council/eval-results/` prose mismatch (owner round-2 + principal round-3 said "committed for leaderboard comparability") is corrected to R-1's wording verbatim — local-only, self-gitignored, NOT committed. This is application, not a judgment call.
