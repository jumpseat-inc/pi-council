## Intent

User-visible surface: a new slash command (name settled in deliberation —
candidates `/eval`, `/council-eval`) with an argument hint like
`[task] [model...]`. The person types the command, sees progress in the
session transcript, and receives a summary when the matrix finishes. It runs
each task under each requested model for N repeats (N configurable), writes
one on-disk record per run, and aggregates mean and variance per
task-and-model cell. Results records live outside the ephemeral `runs/`
telemetry boundary (convention 12) — the spec (EV-16) names the storage
location.

This is the command surface: which command, which screen (the in-session
transcript where progress and the summary render), and which states
(in-progress, done, failed).

## Acceptance

- The command accepts a task, one or more models, and a repeat count, runs
  the full matrix, and reports a per-cell summary.
- One results record per run is written, and records alone suffice to
  recompute every aggregate (mean and variance) shown in the summary.
- Progress and the final summary render in the session transcript.

## Owner position — EV-20

Grounded in: `docs/superpowers/specs/2026-09-03-EV-16-design.md` (§1–§8, binding R-1/R-2, step-6 ruling), `2026-09-03-EV-19-design.md` (settled types + O1 ruling), and landed code `extensions/eval-fixtures.ts`, `eval-rubric.ts`, `hub-tools.ts`, `hub.ts`, `runs.ts`, `index.ts`.

### Two structural findings that must be settled this round (not later)

**F1 — the settled `ResultRecord` (§2 of EV-19) is insufficient for EV-16 §8's aggregates.** EV-16 §8 requires records to carry, per repeat: cost, elapsed, tokens, **stopReason**, and repeat-level `n_attempted` vs `n_graded` + terminal-state histogram (E2/E3). The settled `ResultRecord` (§2, `eval-rubric.ts`) carries only `score`, `perCriterion`, and provenance; it has no cell-side `stopReason`/`usage`. EV-19 §11 explicitly defers "E2 length-flag at repeat level" and "repeat-level accounting, terminal-state histogram" to EV-20/EV-21. So the on-disk record EV-20 writes must be `gradeCell`'s `ResultRecord` **plus a cell-scope terminal block**: `{ state: "done"|"stalled"|"timeout"|"failed", stopReason?, cost, elapsedMs, input, output, tokens }`. The `gradingUsage` on the VerdictRecord is the *grader's* spend (judge scope) — it is the wrong scope for the cell's terminal state, so this cannot ride the verdict record. Without F1, "records alone suffice to recompute every aggregate" breaks for E2/E3 and the histogram.

**F2 — the store key `(cellId, repeat, scoredUnder)` collides across re-runs unless `repeat` is monotonic-per-cell.** The matrix is re-runnable by design (repeat is the control for the unpinnable sampling dimension, EV-16 §1). A second run of the same cell writes `repeat` 1..N again → the writer's "divergent payload → throw" (EV-19 §8) fires on every record. The clean resolution: **`cellId` is stable per `(taskId, model, thinking, fixtureVersion, rubricVersion)` and `repeat` continues from the cell's existing max (first run 1..3, second run 4..6).** This keeps the triple unique, lets deliberate re-runs accumulate `n`, and matches the deterministic-function clause (score is a function of seed+verdicts *within a version* — so version must be inside `cellId`, or old and new measurements corrupt one mean). `cellId` example: `council|openrouter/deepseek/deepseek-v4-flash-0731|@1.0.0+1.0.0`.

### Deliberation item 1 — command grammar

`/council-eval [task] [model...] [--repeat N]`, registered in `index.ts` like other commands. One task per invocation (the card's grammar is singular; do not add multi-task scope). Parse in the handler:

- **No args** → print `listFixtureTasks(repoRoot)` (already shipped in `eval-fixtures.ts`) as a plain sorted list + usage line. Return immediately.
- **`task`** → first positional, resolve via `loadFixture(repoRoot, taskId)`; unknown task throws loudly with the available list (the loader already does this).
- **`model...`** → remaining positionals, each parsed through `parseQualifiedModel` (the shared grammar, not a second one) and **pre-validated against `ctx.modelRegistry.getAvailable()` up front** — so one repeat of one cell isn't burned at position M before a typo in model 3 refuses (B3). A bare id or unknown `:thinking` suffix fails at parse, naming the model.
- **`--repeat N`** → accept `--repeat N` and `--repeat=N`; N positive integer, default 3 (R-4). I will add one guardrail within the validation item: reject N above a hard cap (I propose 20) with a loud error rather than a silent hours-long sweep — consistent with EV-16's cost-guard posture; the caller lowers the cap by editing the constant, never needed in practice.
- Errors render in the transcript, non-fatally (no session crash), reusing the existing `ctx.ui.notify` / print pattern.

Deliberation scope not to creep: no seat-name→model resolution, no implicit all-model sweep (R-4). Models are literal `provider/id`.

### Deliberation item 2 — progress + summary; recompute from records

The handler runs **synchronously** and **is not an LLM loop** (EV-16 §3.1): it drives dispatch→wait→grade→aggregate directly. Progress and the final summary render in the transcript.

- **Progress**: a per-cell/per-repeat line streamed as the loop runs — e.g. `[council-eval] cell council × openrouter/... repeat 1/3 dispatched job-7.3`, `✓ repeat 2/3 score=0.67`, and for a non-`done` settle `⚠ repeat 3/3 stalled — not graded`. The existing `council` live widget already shows active jobs; the transcript lines are the durable, additive record the card wants.
- **Summary**: per cell — `n` (graded repeats), `mean`, **sample σ** (Bessel-corrected; EV-16 §8 says "sample σ"), `n_attempted` vs `n_graded`, `lengthFlagged`, and the terminal-state histogram (E3). Overlapping CIs at n≤3 render as **tied/adjacent, never an asserted ordering** (E1 — first-class rule). E2: a `done`+`stopReason=length` repeat is flagged and excluded from the mean, never scored 0.
- **Recompute from records alone**: the summary is *computed* by a pure `aggregateCell(records) -> CellSummary` over the on-disk ResultRecords for that cellId (per `scoredUnder`), **not** from in-memory loop counters. Because the summary is a pure function of the records, "records alone suffice" is true by construction and unit-testable.

### Deliberation item 3 — engine module + cell execution

New module `extensions/eval-runner.ts` (matches the `eval*.ts` glob). It imports `loadFixture`/`listFixtureTasks`/`applyRulings` from `eval-fixtures.ts` and `gradeCell`/`replayJudgeVerdicts`/`projectVerdictRecord` + record types from `eval-rubric.ts`. It does **not** fork hub dispatch — it calls `hub.spawnJob`/`hub.wait` and `buildChildArgv` directly (convention 7/"shared path").

Per cell × repeat: (1) seed a disposable scratch tree from `fixture.seed.dir` (verify `sha256Tree` ≥ the pinned digest); (2) run the cell driver with the model override; (3) after settle, dispatch the grader with the fixture-pinned `graderModel` as an explicit `model` param (beats the env, D2) and `cellId` set (EV-17 seam); (4) grade through a `GradeIO` bound to the persisted snapshot (freeze-before-disposal, EV-19 §5); (5) write VerdictRecord (first-write-wins `(cellId,gradedBy)`) and ResultRecord (monotonic triple) under `council/eval-results/`; (6) dispose the scratch tree.

**The load-bearing open piece is the driver-spawn mechanism — I will state my position plainly.** `council_dispatch` hardcodes `cwd: repoRoot` (`hub-tools.ts:167`), and `repoRoot = process.cwd()` at parent (`index.ts:103`) and child alike. If EV-20 drives cells through the live session's `council_dispatch`, the whole cell subtree runs in the **live repo tree** → a `/council` procedure cell merges branches, writes board/cards, and commits in the caller's working tree → **violates A1** (cell run leaves live tree byte-identical). The runner must therefore spawn each cell driver with `cwd = scratch` — either a direct `hub.spawnJob({ cwd: scratch, ... })` + `buildChildArgv` from the runner (each descendant's `process.cwd()` then resolves to scratch, so the subtree stays isolated), or an external headless `pi` subprocess with `cwd = scratch` and `COUNCIL_EVAL_MODEL` in its spawn env (the exact smoke-test precedent, EV-16 §3.1, and the EV-17 §4.2 "spawned-job env, never parent `process.env`" carrier). Both satisfy A1/B2/B4/D2; the `pi`-subprocess form is the cleaner match for procedure-kind fixtures (SEV-16 §3.4) and for the smoke-test precedent. This is the one corner where the two specs leave a real gap (neither names the cwd/isolated-spawn mechanism), and I flag it as a must-settle decision rather than an implementation detail.

**Cell drivers have no grader authority** (step-6/D3): the runner owns every grader dispatch; `judge`'s `spawns: []` stays.

Three aggregation columns (cell/command/grading) require the **§7 RunManifest extension** — add `usage` and `stopReason` to `RunManifest` at `settle()` and a pure `sumSubtree(rootId)` (`runs.ts:12` currently has neither). Per EV-16 §7 this ships **with a failing test first** (convention 7; the one allowed touch of the `hub.ts is stable` boundary). Column feasibility is coupled to F2's driver-spawn choice (whether cell manifests land in the command's run dir or a scoped child run dir), which is why F2 must be settled now.

**Store writer** (EV-19 §8): `council/eval-results/` in the caller's repo, self-gitignored exactly like `ensureRunDir`'s `.gitignore = "*\n"` pattern, idempotent and non-clobbering (scaffold convention 6/12). Filenames keyed from the triple, sanitized for filesystem safety (cellId/scoredUnder contain `/` and `:`): `sanitize(cellId)__r<repeat>__sanitize(scoredUnder).json`. Atomic write via `writeAtomic`; absent triple → new; existing + divergent payload → throw (defect); same payload → no-op.

### EV-21's need

Satisfied by F1 + F2 + the pure `aggregateCell`: EV-21 reads `council/eval-results/`, groups by `cellId` (which carries task/model/thinking/version), aggregates on the explicit `scoredUnder` dimension (one row per grader per cell, EV-19 ruling item 4), aggregates on `scoredUnder as a dimension`, and derives mean/σ/n/histogram purely from records. No in-memory or cross-run state. R-6 (`/council-eval` naming) is already honored by R-3.

### Tradeoffs accepted

- **Repeat-monotonic-per-cell**: re-running the same matrix grows `n` on existing cells rather than replacing them. Acceptable because the repeat dimension is explicitly the control for the unpinnable sampling dimension (EV-16 §1) — accumulating is the honest semantics — and the no-implicit-sweep guard keeps invocations deliberate. Cost: a user expecting "re-run replaces last run's three" must delete records (I'll document, not implement, a delete — out of scope).
- **Record extension beyond the settled `ResultRecord`**: the `cellScope` block is a superset EV-19 §11 explicitly reserved for EV-20/EV-21; carrying it inside the record (rather than a sidecar) is what makes "recompute from records alone" literal.
- **Single task per invocation**: richer grammar rejected as scope creep; the card's grammar is singular.
- **Hard `--repeat` cap (20)**: a small guardrail in the validation item; a typo'd huge repeat shouldn't launch a silent multi-hour burn.

## Cross-seam reading

The contract EV-20 must implement is **two frozen record types + two store keys + one dispatch topology, all already settled upstream**. The runner sits exactly at the join, and that join is where it breaks.

**What is actually bound, read as contracts built by other seats:**

- `ResultRecord` (eval-rubric.ts, interface at ~line 55; `repeat` at line 65) = `{cellId, taskId, model, thinking?, repeat, fixtureVersion, rubricVersion, scoredUnder, perCriterion, score, gradedAt}`. Store key **`(cellId, repeat, scoredUnder)`** (O1 ruling). No cost, no elapsed, no tokens, no stopReason, no repo-state.
- `VerdictRecord` = `{cellId, gradedBy, fixtureVersion, rubricVersion, perCriterion, gradedAt, gradingUsage}`. Store key **`(cellId, gradedBy)`, first-write-wins per `(cellId, gradedBy, fixtureVersion, rubricVersion)`**. **No `repeat` field.**
- `gradeCell({rubric, io, judgeVerdicts, meta})` is the per-run scorer: `meta.repeat` is a scalar, `judgeVerdicts` is a single map, score = `passes/criteria.length`. The harness calls it **once per repeat**, feeding a per-repeat judge-verdict map.
- Grader topology: grader is a harness-dispatched sibling, `parentJobId` = command job, linked by `cellId`, carrying the fixture pin as an explicit `model` param that beats `COUNCIL_EVAL_MODEL`.

**Three places where those contracts don't meet, all landing on EV-20:**

1. **VerdictRecord has no repeat dimension.** `gradeCell` needs a *separate* `judgeVerdicts` map per repeat; `replayJudgeVerdicts(record)` produces exactly one map from one record. Six fixtures carry judge criteria (wiki-query; the five judge-only seats consolidator/designer/principal/product-owner/steward). For any of them with N=3, the harness must grade each repeat's distinct output. If it dispatches the grader once per repeat, the three verdict records all key `(cellId, gradedBy)` and **first-write-wins silently deletes two of them** — two repeats' ResultRecords lose their judge verdicts and their scores become un-reconstructible. If it dispatches the grader once per cell, then a single flat `perCriterion` can only stamp one verdict onto all three repeats, and the five judge-only fixtures have σ ≡ 0 by construction — the whole repeat methodology is dead on exactly the fixtures that measure open-ended output. Moreover `cellId` is **overloaded**: the topology ruling says the verdict carries "the cell *job's* id" (per-repeat job id), while the ResultRecord key uses `cellId` as the (task × model) aggregation identity with `repeat` separate. EV-20 cannot disambiguate that without a `repeat` field on the verdict record. This is a binding-schema amendment, not a runner detail — the deliberation space as posed doesn't ask about it at all.

2. **The telemetry the summary needs has no record home.** EV-16 §8 (the design authority) promises each record carries `cost, elapsed, tokens, stopReason, repo state`. The frozen `ResultRecord` carries none of them. The card's summary is three cost columns (cell/command/grading), a terminal-state histogram, the `stopReason=length` flag, `n_attempted` vs `n_graded`, and triage — **none of it is recomputable from the two record types alone.** Mean/σ works (score is on `ResultRecord`), so the verbatim R-5 acceptance is *technically* satisfiable while the summary it feeds is not. The three cost columns come from the job forest, which lives in ephemeral `runs/` (pruned to 15 at `session_start`, runs.ts `pruneRuns`) — so whatever the harness computes must be **stamped onto the durable record at settle time**, or it's gone.

3. **The job forest is split across two repoRoots, and §7's "Σ over readManifests subtree" only describes the command column.** Cells run in a disposable scratch worktree (EV-16 §3.1). A cell driver spawned by the caller's hub has its descendant seats dispatched *inside* the scratch process, whose own `getHub` writes manifests to `scratch/.pi/council/runs/<same-runId>/` — not the caller's runs dir. So the caller's `readManifests` sees the cell driver and grader nodes but **not** the cell's internal subtree. The "cell column" is genuinely cell-driver-usage + scratch-side subtree sum, which must be read before disposal. `GradeIO.jobState(role)` and `RulingsState.jobs` both bind against that scratch-side manifest set, and the `facilitator` role alias maps to the cell driver job on the *caller* side. The freeze-before-disposal rule (EV-19 §5) is the only thing holding all of this together, and it currently has no named owner or artifact path.

## Blind spots

- **EV-19 / the pure-scorer slice** cannot see the per-repeat call site. It authored `gradeCell` with `meta.repeat` and a single `judgeVerdicts`, and froze `VerdictRecord` without `repeat`, because from inside a pure function a "repeat" is just a field it stamps, not a store-collision generator. It also deferred `n_attempted`/histogram/E2 to EV-20 "referenced, not bound".
- **EV-16 / the design-authority slice** wrote §8's per-record telemetry list and §6.3's verdict schema as two separate paragraphs and never joined them at the store key.
- **The designer / rendering slice** will naturally propose a progress UI for the matrix, but can't see that the hub already owns job-level progress (inline tree + widget, EV-9) and that cell/grader jobs will surface there for free. A second progress surface is the temptation; the actual rendering decision is *one shared pure renderer* whose bytes EV-21 also consumes.
- **EV-21 / the reader slice** is promised "records alone suffice" and will design its read against whatever EV-20 writes. It can't see that two of the three columns it will render have no source field unless EV-20 amends the record.

## Reframe

The card is framed as "wire the runner: parse args, run the matrix, render a summary" — three questions that will settle quickly. The actual risk is that **two frozen record schemas are each missing one dimension, and the forest-telemetry model doesn't survive the scratch boundary.** The seam itself is the deliverable. I propose the card be re-scoped around four load-bearing decisions:

1. **Amend `VerdictRecord` to carry `repeat` and change its store key to `(cellId, repeat, gradedBy)`.** The grader is dispatched once per `(cell, repeat)`. This is the symmetric mirror of the O1 ruling and makes `replayJudgeVerdicts` per-repeat-replayable. Define `cellId` = the (task × model) aggregation identity (not a job id), and `repeat` = the sub-run index.
2. **Amend `ResultRecord` to carry the telemetry EV-16 §8 already promised** (`usage`, `elapsedMs`, `stopReason`, and a `repoState`/`treeDigest` field for C1). This keeps the O1-frozen key `(cellId, repeat, scoredUnder)` intact — O1 bound the *key* and the *scoredUnder* semantics, not the field set.
3. **A shared pure aggregate module** — mean, n−1 sample σ, CI-vs-zero triage, terminal-state histogram, length-flag. One home, imported by **both** EV-20's summary and EV-21's leaderboard.
4. **A named snapshot boundary.** The harness must persist, per cell, the scratch artifact tree + scratch-side manifests long enough for `GradeIO`/`jobState`/`applyRulings` to bind *and* for EV-21's C1 re-grade to be byte-identical (`sha256Tree` equality). Grade-before-disposal *or* persist — the spec must pick one and name where the snapshot lives.

On the three deliberation-space items, my position is brief because they are low-risk:

- **Arg grammar** — a pure `parseEvalArgs(args)` in the seat of the runner: one positional `[task]` (singular), `[model...]` ≥1, each model token through the existing `parseQualifiedModel`, `--repeat N` as a positive integer prior to the positionals or trailing. No-arg → `listFixtureTasks(repoRoot)`. The parser is unit-testable; it must not live inside the I/O handler.
- **Progress/summary** — reuse the hub's existing job-level progress (cells and graders surface in the inline tree free of charge). Add only a matrix-level line and the end-of-run summary via the `council-jobs`/`notify` pattern, rendered by the same pure aggregate module EV-21 uses. No second progress widget.
- **Cell-run mechanics** — one engine module `extensions/eval-runner.ts` as the I/O harness; `extensions/eval-aggregate.ts` as the pure aggregate; the store writers and the GradeIO adapter as thin I/O boundaries of the runner. **Extract the dispatch-primitive from `council_dispatch`'s `execute()` body** (override resolution → catalogue check → spawn-env construction → `childEnv`) into a reusable function the harness calls directly — otherwise EV-20 forks EV-17's override path and the two implementations drift.

## Testable claims

1. **Verdict-repeat round-trip (fails against today's schema):** run a fixture with one judge criterion under `--repeat 3` with a recording harness. Assert three distinct `VerdictRecord` files exist keyed `(cellId, 0/1/2, gradedBy)` and three `ResultRecord`s each carry a *different* judge verdict for that repeat. Today this test cannot pass: keys collide at `(cellId, gradedBy)`.
2. **Telemetry-on-record (fails against today's schema):** after a cell settles, read `council/eval-results/` and assert the per-run `ResultRecord` carries `usage`, `elapsedMs`, `stopReason`; from those fields alone rebuild the terminal-state histogram and the cell cost column.
