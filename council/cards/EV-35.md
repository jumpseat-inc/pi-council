## Intent

The user-visible surface is the inline progress transcript's header line and
its focus/expand affordances. Today the header advertises keys the view does
not honor: the arrow cursor is never drawn as a signifier, and the follow
state is named in the header string but not drawn anywhere. The keymap must
be honest — every advertised key has a defined behavior, and the keys that
change a rendered line are asserted to. Keys that clamp correctly at a
boundary (up at the top, down at the bottom) are defined no-ops, not
failures. The `g` and `G` jump keys already work in handleInput and must be
advertised in the header rather than removed.

The focus signifier reuses the council's existing selection marker
(`TREE_ROW_MARKER`, U+258C) so the transcript does not invent a second
idiom. The visible-index versus absolute-index split between the focus
cursor and the expanded set must be resolved so the signifier marks the
block `e` will actually expand.

The production key gate is part of this card's change set (product-owner
ruling, 2026-09-15, Q1): `classifyProgressKey` at
`extensions/focus-nav.ts:67-70` must classify `e`, `t`, `f`, and `g` with
`matchesKey` rather than raw `===`, so the advertised keys are the keys the
surface actually consumes on kitty/modifyOtherKeys terminals. The rest of
`classifyProgressKey` stays; `G`, arrows, enter, and esc are already correct.
`routeEditorFocus` and the routing kernel are untouched.

The full-screen modal transcript is out of scope. Depends on EV-34 for the
composed line shapes.

## Acceptance

- For each key the header advertises, a handleInput-driven test asserts a
  rendered line changes, except boundary clamps, which are asserted no-ops.
- `g` and `G` are advertised in the header and continue to jump.
- The focused block carries the U+258C signifier and it tracks the block
  `e` expands.
- Follow and thinking state changes are visible in the rendered output.
- EV-8's navigation suite stays green.

**1. Header copy — apply R-KEYMAP verbatim, keep the dynamic `(on)`.** The ruled copy `…f follow(on) · g/G jump · esc back` matches the on-state rendering; the honest reading is `${this.follow ? "(on)" : ""}` survives and `· g/G jump` is inserted between follow and esc. `g`/`G` need zero behavior change — they already work and set `follow=false` (navigator.ts:770–774).

**2. The one structural change: pin the header as row 0 of the rendered viewport.** Falsifiable prediction about today's code: the header is element 0 of `all` (navigator.ts:787–789) and the viewport slice is `all.slice(topLine, …)` (navigator.ts:800) with `topLine = maxTop = all.length − viewportRows` whenever follow is on (navigator.ts:798) — so **in follow mode with content exceeding the viewport, the entire keymap line, including the `(on)` suffix, is scrolled off-screen.** The follow indicator is invisible in exactly the state it describes, and after `G` (jump to bottom, follow off, navigator.ts:773–774) the header is equally gone. A keymap that scrolls away cannot satisfy "every advertised key has well-defined behavior" as a user-visible contract, and "follow state visible in rendered output" would only be testable on transcripts short enough that the header happens to still be on screen. Pinning makes the invariant trivial: rendered row 0 is always the header; the body window is the remaining `viewportRows − 1` rows, with the existing focus-anchor math (`focusLine − 2`, navigator.ts:799) applied to the body sub-slice. This is the only place I'd spend the card's structural budget; the alternative (a `↓ following` badge in the body) competes with the ruled header copy and still leaves the keymap invisible.

**3. Index/signifier resolution — the focus cursor lives entirely in visible-index space.** Do not key the marker by absolute index. So "the marker marks the block `e` will expand" holds by construction, not by a mapping that can drift. The failure mode to design against is the opposite choice: a marker keyed by absolute `i` desynchronizes the moment `showThinking` filters units (visible index ≠ absolute index). Render already clamps `focused` into range when `vis` shrinks (navigator.ts:786), which keeps the marker well-defined as blocks stream in.

**4. Marker rendering.** `theme.fg("accent", TREE_ROW_MARKER) + " "` prefixing the focused unit's head line only (body lines never carry it), reusing focus-nav.ts:37 exactly as the tree rows do (navigator.ts renderTree, `▌ ${base}` idiom). Visibility for `t` is a body assertion, not a header assertion. No new glyphs, no new colors.

#### Position — `designer` (job-11.3)

## Design position

EV-35's surface is a small, named-signifier problem on a one-row header and on the head of every block in a 1–31-row inline transcript: four signifiers (the focus marker on the head, the header keymap, the header's follow-suffix state, and the existence of thinking blocks in the body) must each be the **single source of truth** for one piece of state, with no duplication, no silent flip, and no cursor-jump surprise when toggling. The smallest change that satisfies the card is: add a `▌` glyph at column 0 of the head of the **focused unit only**, keep the head itself marker-only (no extra accent/background — token scarcity), render the U+258C **always on the focused unit regardless of scroll position**, recompute `focused` against the absolute-unit index after a `t` toggle so the marker never desyncs from what `e` will expand, and change the header's follow-suffix from a ternary `f follow` / `f follow(on)` to the ruled literal `f follow(on)` rendered with the trailing `(on)` styled as a separate token (`accent` when on, `dim` when off) so the state is honestly visible at one glance without the header copy mutating.

## Gulf closed

- **Evaluation gulf, at the moment of "what will `e` do?"** Today the transcript has no on-screen marker for the unit a keypress will target; the cursor exists only as an invisible `focused` integer. Add `▌` to the head and the question answers itself by reading. (closes)
- **Evaluation gulf, at the moment of "is follow on?"** Today the answer is in the header (`f follow` ↔ `f follow(on)`) but the literal copy changes between two strings; the ruled copy `f follow(on)` is pinned, so the state must be carried by the suffix token, not by copy mutation. (closes)
- **Execution gulf, at the moment of "I just pressed `t`."** Today the focused index doesn't move with the visible list; toggling thinking can leave the marker on a different block than `e` will expand. Track focus by absolute-unit index and the slip disappears. (closes)
- **Execution gulf, at the moment of "what if follow is on and a new block lands?"** Today follow-on is honored by the scroll window, but `t`'s visibility recomputation isn't. (closes)

## Principle and evidence

- **Single source of truth = one signifier per state.** The card lists four state-bits (focus, expand, follow, thinking). Each already has a state slot: `focused` (visible-index today), `expanded` (Set keyed by absolute `i`), `this.follow`, `this.showThinking`. The marker, the header suffix, and the body filter must each read from exactly one of these — no computed flag duplicated across two. Apply at `extensions/navigator.ts:783-805` (the `render` and `unitLines` site) and `extensions/navigator.ts:761-768` (the toggle site). Specifically:
  - `▌` reads `this.focusedAbsolute` (renamed from `focused`).
  - header follow suffix reads `this.follow` via `theme.fg(this.follow ? "accent" : "dim", this.follow ? "(on)" : "(off)")`.
  - `visible()` reads `this.showThinking`.
  - `expanded.has(i)` continues to key by absolute `i` (do not change).

- **Knowledge in the world beats knowledge in the head.** The header pin copy per R-KEYMAP is `<title> — ↑↓ move · e expand · t thinking · f follow(on) · g/G jump · esc back`. The `(on)` literal is part of the published contract. The state-bit must therefore ride the **token** of the suffix, not the presence/absence of parentheses. Apply by replacing the ternary `this.follow ? "(on)" : ""` with a conditional-token styled suffix; the visible cells are always "(on)" or "(off)" so the published copy stays byte-stable.

- **Mapping: head line ↔ cursor position.** The marker must live on the head line of the focused unit only — never on a body line (the body mutates with `e`; the head is the stable identifier). The current `unitLines` already produces `[head, ...body]` for every unit (extensions/navigator.ts:694-733); adding the marker as the first emitted cell of `unitLines` when `u === vis[focused].u` keeps the row → unit mapping one-to-one and avoids tracking a separate "focus line offset" alongside `starts[]`.

- **Constraint: marker on the focused unit, not on the focused visible-slot.** The card calls out the visible-index/absolute-index split explicitly. The fix is one rename plus a recompute hook:
  1. Rename `focused` → `focusedAbsolute: number` (stores the absolute unit index, consistent with `expanded.has(i)`).
  2. Add `focusedVisible(): number` that returns `this.visible().findIndex(v => v.i === this.focusedAbsolute)`, returning 0 if -1 (clamped).
  3. In `render()`, after computing `vis`, call `this.focusedAbsolute = vis[Math.min(this.focusedVisible(), vis.length - 1)]?.i ?? vis[0]?.i ?? 0` (the canonical recompute).
  4. `up`/`down` mutate `focusedAbsolute` to `vis[next].i` (the absolute index of the next visible unit). `g`/`G` mutate to `vis[0].i` and `vis[vis.length - 1].i` respectively.

## Index-split failure modes (explicit, ranked)

If the visible-index/absolute-index split is left as-is (current code), the following slips occur — each grounded in the existing code:

1. **`t` adds a thinking block BEFORE the focused unit.** Visible indices shift; the marker (when added) lands on the unit that moved into the focused slot, but `e` still expands the unit at the absolute index stored in `expanded`. Marker and `e` desync. Severity: high — the marker lies about what `e` does.
2. **`t` hides the focused unit itself.** `focused` points at a now-hidden unit; the render clamps to `vis.length - 1`; the marker jumps to a different unit than the one the user was watching. Severity: high — visible cursor jump.
3. **`g`/`G` jump to absolute index 0 / last.** When thinking is hidden, that's a unit the user can't see. Severity: medium — silent out-of-sight.
4. **`e` toggles `expanded` on the absolute `i` of the focused VISIBLE unit.** If `focused` was renumbered to absolute index but `expanded` is keyed absolute, the toggle works. If `focused` stays visible-index, `e` reads `vis[focused].i` and toggles the correct absolute — by accident, because both indexes meet at the call site. The desync only happens after `t` shifts the visible list. Severity: latent — works today, breaks the next time someone touches the toggle.

The single-rename to `focusedAbsolute` (plus the recompute hook in `render`) eliminates all four by construction.

- I prefer the suffix wording `(off)` (symmetric with `(on)`) over dropping the suffix entirely.
