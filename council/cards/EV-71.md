## Intent

The gate's own spend is the cheapest number in the feature and it must not be
the dishonest one. The decisions response carries its cost inline, so the ledger
records it with a reported basis rather than an estimate — the only basis the
provider actually gave.

The gap this card closes is narrower than it first appears, and the correction
matters. A decision generation id is not invisible to the generation-lookup API:
`GET /api/v1/generation?id=<gen-dec-…>` returns `200` carrying `total_cost`,
`provider_name`, `api_type: "decisions"`, and native token counts, and the
existing extraction reads exactly those fields. What the reconciler lacks is the
id itself: it harvests generation ids only from assistant entries in seat
session transcripts, and a gate call produces no session entry, so the id never
enters its input set. Left alone, gate spend would be silently under-reported by
a path that believes it has accounted for everything, which is exactly the
failure class the usage-accounting work exists to prevent.

The shape is settled. The ledger carries the reported cost and the generation id
that produced it, and the reconciliation path accepts ids sourced from the
ledger, so gate spend is accounted for and independently verifiable rather than
silently absent. The usage block still names gate spend as excluded from the
invocation total, because folding a reported-basis number into a half whose
`basis=` label would then assert a provenance the number does not have is the
same class of plausible-but-false assertion the block's runner-omission rule
exists to prevent. The ledger remains the authoritative gate total.

What is not acceptable is an unaccounted call whose cost is neither carried nor
named.

## Acceptance

The ledger's gate total equals the sum of reported per-call costs; a
ledger-sourced decision generation id is looked up by the reconciliation path
and its reported `total_cost` resolves into that total, proven with an injected
fetch double; an invocation whose window contained gate calls carries a
conditional legend line `usage  gate = excluded from this total`, present iff at
least one gate call falls in the window and absent otherwise, composed with the
existing prefix, label column and legend stack order, and a golden test proves
the block's grammar is unchanged when gate calls are present and no legend is
emitted when they are absent; and no gate call's cost is derived from a
catalogue estimate.

## Position — EV-71, owner first pass

### 1. What the goal requires (my read)

Three obligations, one per existing seam, and I verified each against the tree:

- **Ledger half — already built, needs proving, not rebuilding.** EV-65 landed `GATE_LEDGER_SCHEMA_VERSION = 2` (`extensions/gate-ledger.ts`): `appendGateCall` writes `usage {input_tokens, output_tokens, cost}` and `generationId` atomically on the call line, taken verbatim from the decisions response (`gate-run.ts` success path; `gate-transport.ts` `parseDecisionsResponse`). The reported basis is **structural, not a field**: the ledger's only writer path stores the response's `usage.cost` verbatim and computes nothing, so `costBasis REPORTED (never estimate)` holds by construction. What EV-71 adds here is a pure total helper + the test that "the ledger's gate total equals the sum of reported per-call costs".
- **Reconciliation half — the real gap.** `fetchProviderReport` (`extensions/provider-cost.ts`) harvests generation ids **only** from seat session transcripts via `collectGenerationIds` (assistant `responseId`s), and its eligibility filter is `model.startsWith("openrouter/")`. A gate call produces no session entry and its model (`typesafe/jev-1.13`) is not openrouter-prefixed — the id is doubly invisible. The reconciler must accept decision ids **sourced from the gate ledger**, look each up through the existing `GET /api/v1/generation?id=` transport (the existing `toGeneration` extraction already reads `total_cost`/`provider_name`/native tokens; `api_type` is simply tolerated/ignored — no extraction change), and the reported `total_cost` resolves into the reconciliation's gate total. The **ledger stays the authoritative gate total** — the lookup is independent verification riding the durable record, not an alternate source.
- **Surface half — a conditional legend, nothing more.** `formatUsageBlock` gains `usage  gate = excluded from this total`, present iff ≥1 gate call falls in the window, composed with the existing `usage  ` prefix, the single-word label column (sibling of `n/a`, `partial`), and the legend stack order. Gate spend is **never** folded into `ownSession`/`subtree` — a reported-basis number inside a half labelled `basis=session-reconciled`/`stream-assistant` would assert provenance it doesn't have. No gate cost row is rendered; the ledger is the total.
- **Hard edge:** no gate call's cost is ever derived from a catalogue estimate — the only two gate cost figures in the system are the ledger's stored `usage.cost` and the lookup's reported `total_cost`.

### 2. Design

**Modules and import edges** (all one-way, no cycles; no new network surface — the generation transport is reused):

- **`extensions/gate-ledger.ts`** — add pure `sumGateSpend(calls: GateLedgerRecord[]): number | null`: Σ of `usage.cost` over call lines where `usage?.cost` is a finite number; `null` iff none carried. A v1 line or a failed call (no `usage`) contributes nothing — absent, never zero-derived. No schema change, no writer change.
- **`extensions/provider-cost.ts`** — extend `FetchProviderReportInput` with optional `gateCalls?: { callId: string; generationId: string | null }[]` (values passed in; this module stays ledger-agnostic). Add `GateProviderReport { callsInWindow: number; lookedUp: number; failedLookups: <class count>; generations: ProviderGeneration[]; totalCost: number | null }`. `ProviderCostReport` gains optional `gate?: GateProviderReport`. Gate lookups run through the same injected `fetchGeneration`/apiKey/timeout **after** the seat-job loop; each id → `toGeneration` with `jobId` = the gate `callId` (R-7 attribution unit = the call) plus a new optional `source?: "seat" | "gate"` discriminator (absent = seat, so persisted legacy records stay byte-identical). **Gate generations never enter the seat `generations` array** — `routedMultiset`, `totalCost`, and `providerComponentFigure` are seat-scoped and must not be polluted. Two control-flow changes: (a) the `jobs.length === 0 → null` early return becomes "no jobs **and** no callable gate ids"; (b) the `apiKey === null` early return still returns, but carries `gate.callsInWindow` so the legend survives a keyless run. A failed gate lookup (timeout/HTTP error) lands in `gate.failedLookups` and does **not** poison seat-scoped `report.status` — the ledger carries the cost, so nothing is unaccounted.
- **`extensions/usage-store.ts` (`flushPendingInvocations`)** — after `readManifests`, one `readGateLedger(input.repoRoot)` per flush pass; per pending invocation, window-filter `Date.parse(call.recordedAt) >= p.markerAt` and build `gateCalls`. The persisted `provider` sibling therefore carries `gate`, and the write-transition notify composes the block from the **persisted** record — shown == disk by construction. Import edge `usage-store → gate-ledger` is clean (gate-ledger imports only node + `CONFIG_DIR_NAME`). `USAGE_RECORD_SCHEMA_VERSION` stays 2 (additive-inside-provider; the EV-42 precedent).
- **`extensions/usage-block.ts`** — `GATE_LEGEND_LINE = "usage  gate = excluded from this total"`, pushed after `LEGEND_LINE` (last in the stack), iff `provider?.gate !== undefined && provider.gate.callsInWindow > 0`. No other row changes.

**Tests** (`test/gate-spend-reconcile.test.ts` new; additions to `usage-block.test.ts`, `usage-store.test.ts`; all mkdtemp + injected doubles, no network, no timers): ledger-fixture `sumGateSpend` = Σ reported per-call costs; injected fetch double receives the ledger-sourced `gen-dec-…` id exactly once and its `total_cost` equals both `gate.totalCost` and `sumGateSpend` over the same fixture; a seat transcript with ordinary `responseId`s triggers no decision lookup; window filter (call `recordedAt` < `markerAt` → no lookup, no legend); failed-call shape (legend present, zero lookups, `totalCost: null`, never an estimate); golden block tests — gate present ⇒ existing rows byte-identical + one gate line in the stack, gate absent ⇒ byte-identical to today's render (existing goldens stay green untouched); flush integration proving the persisted record carries `provider.gate`.

### 3. Open questions / risks

- **Legend predicate on failed calls.** The card's IFF is "at least one gate **call** falls in the window". A failed call (e.g. `no-api-key`) carries no `usage` — zero spend — yet the literal reading still emits "gate = excluded from this total". I take the literal reading (deterministic, ledger-derived, matches the acceptance text) but flag it: the alternative (key on calls with `usage.cost != null`) makes the legend a spend claim rather than a call claim. Worth a skeptic falsifier, cheap to flip.
- **Ledger `costBasis`.** The binding context says the ledger records cost "with costBasis REPORTED", but the PO-ruled v2 key set carries no `costBasis` field — the reported basis is structural. I read it as a statement of fact about EV-65's ledger, not a new field; if the judge reads it as a schema requirement, that's an escalation (a v2→v3 additive field), not something I'd decide unilaterally.
- **Cross-session attribution.** The ledger is repo-scoped and committed; another session's gate call landing inside this invocation's window would be included in the lookups. The legend is unaffected (still true), but the reconciliation's gate figure could over-attribute. No cheap fix exists (no session id on the call line); accepted and named, not silently ignored.
- **Runner form.** `formatRunnerUsageBlock` (hub-tools.ts) has no provider sibling and no legend stack. The acceptance speaks of the invocation usage block's legend stack — I scope to `formatUsageBlock`; extending the runner form is a separate concern I'd flag rather than grow this card.
- **`api_type: "decisions"`** is returned by the lookup but read by nothing today. I won't add a field for it; the `source: "gate"` discriminator plus the `gen-dec-` prefix is sufficient provenance. (If the judge wants it captured verbatim, it's one optional field.)

## 1. What the goal requires

Four conjuncts, one of which names a seam and is the whole card:

1. The ledger line carries the decisions response's `usage.cost` with **reported** basis and the response's `generationId` (`gen-dec-…`).
2. The **provider reconciliation** accepts decision generation ids **sourced from the gate ledger** (in addition to transcript-harvested seat ids), proven with an injected fetch double: a `gen-dec-…` lookup's reported `total_cost` resolves into a **gate total**.
3. A seat transcript with no decision generation id triggers **no** decision lookup; no gate cost is ever catalogue-derived.
4. The usage block emits a **conditional** line `usage  gate = excluded from this total`, present iff ≥1 gate call is in the invocation window, composed into the existing prefix/label column/legend stack; golden test pins grammar identity and absence.

The card is explicit that the gate spend is **excluded from the invocation total** and "the ledger remains the authoritative gate total." So (2) is a *second* reconciliation and a *second* total, not a fold-in.

## 2. Cross-seam reading — what the contract actually is right now

**The ledger (writer side).** `gate-ledger.ts:63-67` — `GateUsage = {input_tokens, output_tokens, cost}`; there is **no `costBasis` field anywhere** on `GateLedgerRecord` (`gate-ledger.ts:79-130`). `gate-run.ts` success path appends `usage: parsed.usage` and `generationId: parsed.generationId` (from `gate-transport.ts`'s `parseDecisionsResponse`). The record is **repo-scoped and append-only** (`gateLedgerPath`, `gate-ledger.ts:135-137`) and carries **no invocation/marker/run key**; the only time field is `recordedAt`, a write clock. So "a ledger-sourced generation id" has no invocation-window membership built in — the card's phrase "falls in the window" has to be *defined*, and the only candidate field is `recordedAt`.

**The reconciliation (reader side).** `provider-cost.ts` is the single "provider reconciliation." `collectGenerationIds` (`:117-135`) harvests **only assistant `responseId`s** from session entries. `fetchProviderReport` (`:286-350`) filters `jobs` by `j.model.startsWith("openrouter/")` (`:296`), and a job with `sessionPath === null` pushes `session-missing` into `failures`, which makes `status: "unavailable"` (`:340`). `totalCost` is Σ generation `total_cost` (`:336-339`), and it is rendered as the invocation's `usage  reported …` row. `ProviderCostReport` also drives the `routed=` multiset and the `partial` predicate.

**The store (window + materialization).** `usage-store.ts` `flushPendingInvocations` (`:343+`) is where the window is known: `openrouterInWindow = manifests.filter(m => m.model.startsWith("openrouter/") && m.startedAt >= p.markerAt)` (`:417-420`), then `fetchProviderReport` (`:444`), then `persistInvocationUsage` (`:452`), then `notify(formatUsageBlock({record: res.record.spend, provider: res.record.provider}))` (`:466`).

**The block (surface).** `usage-block.ts` `formatUsageBlock` is pure, no `node:fs` (stated in its header, `:1-4`). Row stack: two measurement rows → boundary row → conditional reported row → conditional partial legend → conditional `n/a` legend.

**The intake seam.** `council_gate` is registered parent-side (`gate-tool.ts:130`) and invoked by `/features-new` after the invocation marker is stamped (`index.ts:167-178`), so gate calls *do* land inside a marker window — the intake invocation's, not the deliberation's.

### Invariants that must hold

- **INV-1 (no fold-in).** Gate spend must never reach `ProviderCostReport.totalCost`, `generations[]`, the `routed=` multiset, or `partial`. This is the card's own "excluded from this total" clause; folding also asserts a provenance the record does not have.
- **INV-2 (separate vehicle).** Gate ids cannot ride `fetchProviderReport`'s `jobs` array. Two independent hazards: (a) a gate pseudo-job with the pinned model `typesafe/jev-1.13` is **silently dropped** by the `openrouter/` prefix filter at `provider-cost.ts:296` — the exact silent under-report the card exists to kill; (b) forcing an `openrouter/` model to pass the filter, with `sessionPath: null`, pushes `session-missing` and flips the invocation report to `unavailable` (`provider-cost.ts:308-318, 340`), corrupting the seat report to account for the gate.
- **INV-3 (window predicate is a write-time fact).** The block is pure and fs-free, so "present iff ≥1 gate call in the window" must be materialized into `StoredUsageRecord` at flush, exactly as `provider.partial` is. A block that re-reads the ledger at render time violates the purity contract and the "what was shown == what is on disk" property (`usage-store.ts:459-466`).
- **INV-4 (no catalogue estimate).** If a call's `usage.cost` is absent and its `generationId` yields no `total_cost`, the gate total must name it unaccounted, never estimate. A costless/failed call (`gate-run.ts` `failRun` writes **no** `usage` and **no** `generationId`) is a real, reachable shape the acceptance does not name.

## 4. Reframe

**The proposed design is sound in shape, but the vehicle named by the goal is the wrong one, and this card earns a concrete reframe: reconcile gate spend as a second sibling parallel to `provider`, not as extra entries in the provider report.**

Concretely:

1. **A distinct gate-spend reconciliation** (new function, sharing `FetchGeneration` only) that reads `readGateLedger(repoRoot)`, selects calls by the pinned window predicate over `recordedAt`, looks up each `generationId` via `fetchGeneration`, and produces `{calls, totalCost, basis: "reported"}` — leaving `fetchProviderReport`, `ProviderCostReport`, and its `jobs`/`sessionPath`/`routed`/`partial` semantics byte-identical.
2. **A new sibling on `StoredUsageRecord`** (e.g. `gate?`), present iff the window contained ≥1 gate call; the block's conditional legend reads that sibling, exactly as it reads `provider.partial`.
3. **An explicit `costBasis: "reported"` on the ledger call line**, added to the v2 union additively (EV-65's reader is tolerant; `EV-66/67/71` read call-line fields). Otherwise "journalled with costBasis reported" has no machine-readable home, and INV-4 has no anchor.
4. **Pin the window predicate**: gate calls with `recordedAt >= markerAt` (no upper bound needed within a session, but the test must prove a prior invocation's call is excluded), attributed to the intake invocation that issued the call.

If the owner instead folds ledger ids into `fetchProviderReport`, INV-1/INV-2 break and the card's own acceptance contradicts itself. That is the falsifiable core of this position.

- **Q1 — Total precedence.** The card says both "the ledger's gate total equals the sum of reported per-call costs" and "the lookup's `total_cost` resolves into that total." When ledger `usage.cost` and generation `total_cost` disagree, which is authoritative? Ledger-word vs lookup-word gives different totals. Pin it.
- **Q2 — Legend slot.** "Composed with the existing prefix, label column and legend stack order" does not say whether `usage  gate = …` goes before or after the `partial` and `n/a` legends. The golden test will silently pick one; the ruling should pin it.
- **Q3 — Costless/failed calls.** A `failRun` line has neither `usage.cost` nor `generationId` (`gate-run.ts` `failRun`). Does the legend fire (a call happened) and is that call named unaccounted? "An unaccounted call whose cost is neither carried nor named" is the card's stated unacceptable, so the failed-call path needs a named disclosure or a scoped exclusion.
- **Q4 — Attribution command.** Gate calls happen inside `/features-new` intake; the legend will therefore appear on the intake invocation's block, not the deliberation's. - **Q5 — `api_type`.** The card asserts the existing extraction reads `api_type: "decisions"`. It does not; `GenerationResponse` has no such field. Either drop the assertion from the spec or add the field — but the spec must not claim a mechanism that is absent.

## (1) How a person reads the block today, and what this legend changes

The resolved form a reader meets today is, with both conditional legends:

```
usage  ownSession  basis=session-reconciled  turns=N tokens=… cost≈$X.XXXX (catalogue)
usage  subtree     basis=stream-assistant   turns=N tokens=… cost≈$Y.YYYY (catalogue)
usage  boundary=session=… entries=… jobs=…
usage  reported  cost=$Σ.XXXX (reported) routed=<name>x<n>     ← conditional
usage  partial = reported figure excludes unaccounted attempts ← conditional
usage  n/a = provider figure unavailable                      ← conditional
```

A reader's eye-path is a **scan-and-land**: scan the two catalogue rows for
a number, land on `cost≈$… (catalogue)`, glance at the boundary row for
provenance, and decide whether the legends matter to them. The existing
legends work because they **qualify a figure the reader already saw**:
`partial` explains why a reported figure is short of whole; `n/a` explains
why a catalogue slot rendered `n/a`. Both legends have an antecedent on
the screen.

EV-71 adds one conditional legend:

```
usage  gate = excluded from this total         ← conditional, NEW
```

The legend does not qualify a figure the reader already saw. It
**annotates the block as a whole**: "by the way, the figures you just
scanned are not the whole story — gate spend is in the ledger, not in
these halves." Its work is therefore different from `partial` and `n/a`.
That difference is the load-bearing design fact and the source of every
comprehension hazard below.

A second change happens at the same time and is invisible on the surface:
the reported row's `routed=<multiset>` now includes the gate calls'
`gen-dec-…` ids alongside the seat transcripts' ids (the reconciliation
path is widened; the multiset field is unchanged in grammar). A reader
who counts entries in the multiset will see a higher count than they
would have before, with no per-row marker telling them which entries are
seat calls and which are gate calls. This widens a Gulf of Evaluation the
new legend only partially closes.

## (2) Comprehension predictions (falsifiable)

Each prediction names what a cold reader does, and the seam-test or smoke
that would falsify it.

**P1 — "this total" anchors to the wrong antecedent.** A reader who lands
on the legend without re-scanning the block will most naturally read
"this total" as the reported row's dollar sum (the most dollar-prominent
figure on the screen), not the catalogue halves. The intended antecedent
is the catalogue halves; the strongest visual antecedent is the reported
row. *Falsifier*: copy-string read-cold test — show a fresh reader the
resolved block and ask, without prompting, "what does 'this total'
refer to?" Record what they point at. A majority pointing at the
reported row falsifies the legend as written.

**P2 — the legend reads as boilerplate.** Tail-of-block annotations on
deterministic grammar look identical to legal disclaimers. A reader
already satisfied by the catalogue rows (their daily case) will skip it.
*Falsifier*: time-to-correct-recall — show the block, give the reader
60 seconds of unrelated work, then ask "what does the gate line say?"
If recall drops below the existing `n/a` legend's recall rate, the
position in the tail is the cause and a different surface is needed
(an inline note on the affected half, or a different key that does not
sound like a legal disclaimer).

**P3 — the legend leaves the reader stranded.** It says gate is excluded
from the total but does not say where the reader can find it. A reader
who wants to audit will look at the block, see no figure, and have no
signposted next step. *Falsifier*: a "find the gate spend" task — give
a reader the block, the repo, and the wiki; measure time-to-source. If
the median time exceeds the median for "find the `partial` reason in the
ledger," the legend is silently dropping information that needs a
signposted affordance.

**P4 — the legend reads identically whether gate ran once or many
times.** It does not distinguish a 1-call gate from a 12-call gate; it
does not say which mode the gate ran in (Deliberate / Verify / Direct);
it does not say whether any gate call failed. The reader gets a binary
"gate spend is excluded" with no granularity. *Falsifier*: a count-bearing
counterpart — does adding `usage  gate = N call(s) excluded from this
total` collapse the legend's grammar or break the conditional predicate?
If the legend stack can carry a count, the current literal is the
less-informative variant of the same shape.

**P5 — the legend will not render in the whole-block empty / unresolved
/ failed states.** The card's conditional predicate ("iff at least one
gate call falls in the window") is silent on what happens when the block
falls into `no usage recorded`, `accounting boundary unresolved`, or
`accounting failed`. If a gate call ran and the catalogue halves are
both zero, the whole-block state takes precedence today and the
gate-legend never appears — leaving the gate spend silently absent from
the visible surface, which is precisely the failure class the card
exists to prevent. *Falsifier*: a fixture where `allZeroUsage(ownSession)
&& allZeroUsage(subtree) === true` AND ≥1 gate call in the window — does
the rendered block include the `usage  gate = …` line? If no, the
card's intent ("What is not acceptable is an unaccounted call whose
cost is neither carried nor named") is violated in the edge case it
needs most. **This is the load-bearing prediction; it is the one I would
falsify first.**

**P6 — the legend is invisible to the reported row's multiset.** The
multiset shows provider names; the gate calls' `gen-dec-` ids route to a
`provider_name` that lands in the multiset alongside the seat calls. A
reader who looks at `routed=Infermaticx3,BlackForestx2` cannot tell which
entries are gate calls. The legend says gate spend is excluded from the
catalogue halves but is **not** excluded from the reported row — that
fact is nowhere on the surface. *Falsifier*: a "which entries in the
multiset are gate calls?" task. The legend as specified gives no
signposted affordance for this distinction.

**P7 — a first-time reader does not know what "the gate" means.** The
key `gate` is project-internal vocabulary (the EPIC-13 deliberation
gate). A cold reader who has never run `/council` against a metered repo
will not parse `gate` as a noun referring to a routing decision. The
existing `n/a` and `partial` keys are self-describing (`n/a` is a
typographic convention, `partial` is a property of the figure); `gate`
is the first key that requires external knowledge. *Falsifier*: a
read-cold test on the key in isolation — "what does `gate = …` mean
here?" A majority failing to identify it as the EPIC-13 deliberation
gate falsifies the key choice.

## (3) Composition concerns

**Stack order.** The existing discipline (PO C/D/E/F, EV-32;
`usage-block.ts:88-89, 116-119, 142-146`) is: ownSession → subtree →
boundary → reported → partial → n/a. Every legend is a **qualifier on a
figure already on screen**. EV-71's legend is **not** a per-figure
qualifier — it is a global annotation on the block. There is no
precedent for that shape in the existing stack.

The card says "composed with the existing … legend stack order," which
does not pin a position. Three defensible placements:

- **After `n/a`** (tail) — matches the "legends at the bottom"
  convention; reads as a closing caveat. Risk: it is far from the figures
  it qualifies, and P2's boilerplate trap bites.
- **Before the reported row, after the boundary row** — anchors it
  physically to the catalogue halves it qualifies ("these two exclude
  gate; the figure below is what the provider reports, including gate").
  Breaks the convention that legends only stack at the bottom. Risk: the
  boundary row is currently followed by a conditional row; inserting a
  legend there is the first mixed-position legend.
- **After the reported row, before partial** — couples it to the
  reported figure but inverts the natural reading order ("here is the
  total … and gate is excluded from it … and by the way the total is
  partial").

I argue for **after `n/a`** as the position of least surprise: it keeps
the legend-stack convention intact, costs no rule change, and makes the
legend the last thing a reader sees. P1 (wrong antecedent) is the price
of that choice; the legend's wording, not its position, is what makes the
antecedent ambiguous.

**Label column.** The existing convention is `usage  ` (literal `usage`
+ two ASCII spaces) + `<key>` (no padding) + ` = ` + `<short definition>`.
The proposed line `usage  gate = excluded from this total` follows this
exactly. Compositionally clean. The label column width is **not** fixed
(the partial legend's key is `partial`, 7 chars; the n/a key is `n/a`,
3 chars; `gate` is 4 chars). The proposal sits in the middle. No issue.

**Prefix grammar.** `usage  ` is the prefix of every line in the block,
including the conditional legends. The proposed line uses it. No issue.

**"key = short definition" shape.** The proposed definition is **12
words** ("excluded from this total"). Compare:

- `n/a = provider figure unavailable` (4 words, the noun phrase)
- `partial = reported figure excludes unaccounted attempts` (6 words)
- `gate = excluded from this total` (4 words)

Word count is fine, but **shape** differs: `n/a` and `partial` both
name the property being qualified; `gate = excluded from this total`
names a verb phrase describing an action on an unnamed antecedent. The
definition reads as a sentence fragment rather than a definition. P1 is
the surface symptom.

**Conditional predicate.** "Present iff at least one gate call falls in
the window" matches the existing legend discipline (PO D/E):
`input.X === <state>` ⇒ legend; otherwise silent. The block does not
need a counter — `count > 0` is sufficient. P4's prediction (1 call vs
12 calls reads identically) is a follow-on question, not a grammar
violation.

**Golden test (acceptance).** The card commits to a golden test that
proves the block's grammar is unchanged when gate calls are present and
no legend is emitted when they are absent. I would add three more
golden assertions to the same file:

- A fixture where ≥1 gate call AND the block is in
  `no usage recorded` state (whole-block precedence). Asserts whether
  the gate legend renders in a whole-block state — see P5, which the
  acceptance does not cover.
- A fixture where ≥1 gate call AND `n/a` legend already renders.
  Asserts the **exact stack order** of `partial` → `n/a` → `gate`
  (or whatever position the card settles on).
- A fixture where ≥1 gate call AND no reported row (no `provider`
  sibling). Asserts the gate legend renders without a reported figure
  — the catalogue halves are the only thing the legend qualifies, and
  the legend must work in that case.

## (4) Open design questions I believe need a ruling or a test

**O1 — Whole-block state precedence (load-bearing).** Does the gate
legend render in the `no usage recorded`, `accounting boundary
unresolved`, or `accounting failed` states when ≥1 gate call falls in
the window? The card's conditional predicate says "present iff at least
one gate call falls in the window," which on its face covers those
states. The existing whole-block-state precedence (failed > unresolved
> empty, `usage-block.ts:108-114`) returns before any conditional row.
A gate call in an unresolved-boundary invocation would today be silently
absent from the surface, which violates the card's intent. I argue the
gate legend must render in the `no usage recorded` state (the empty
state) when ≥1 gate call is in the window — that is the only state
where the legend is **both** conditional AND not preceded by other
content. The unresolved and failed states are harder — the legend
would have to render after the whole-block line, breaking the
single-line whole-block-state rule. *Recommendation*: a PO ruling
fixing this; failing that, a test that pins the behavior so the
question is not silently decided at implementation time.

**O2 — Antecedent for "this total".** The wording is ambiguous between
(a) the catalogue halves (ownSession/subtree, the figures most
prominently scanned) and (b) the reported row (the dollar figure with
the strongest visual weight). The card's Intent makes clear the
intended antecedent is (a), but the literal text reads more naturally
as (b) for a cold reader. *Recommendation*: the wording is settled by
the card; the falsifier for P1 should run on the literal as given. If
P1 is confirmed (majority of cold readers point at the reported row),
I would push back to the card, not to the implementer.

**O3 — Where can the reader find the gate spend?** The legend names the
exclusion but does not point at the ledger. A reader who wants to audit
must already know about `gate-ledger.jsonl` (and the
`extensions/gate-ledger.ts` shape) — that knowledge is not in the
block. Two design responses: (a) extend the legend to name the ledger
("`gate = excluded from this total — see gate-ledger.jsonl`"), which
widens the definition past the "short definition" shape; or (b) accept
that the block is not the audit surface — the ledger is — and do not
extend the legend. *Recommendation*: (b) on the grounds that the
reported row's multiset already surfaces the gate calls' provider
names and ids, and a reader who follows the multiset gets to the
ledger. The legend's job is the **exclusion**; the multiset's job is the
**trace**. I would write this into a one-line note in the implementation,
not into the legend.

**O4 — Reported-row multiset composition.** The multiset
(`usage-block.ts:65-78`) currently aggregates `providerName × count`
over `status === "reported"` generations from seat-transcript
harvesting. EV-71 widens the input set to also include ledger-sourced
`gen-dec-` generations. The multiset's count will increase with no
signifier distinguishing seat calls from gate calls. The block's reader
sees a higher count and may form a wrong model of "how many provider
calls this invocation made." *Recommendation*: a downstream test
(not this card) that pins a count assertion comparing pre-EV-71 and
post-EV-71 multiset counts on a fixture with ≥1 gate call. The card's
acceptance does not require this, but the prediction is falsifiable.

**O5 — Runner form.** `formatRunnerUsageBlock` (`usage-block.ts:153-161`)
is used at the runner's own autonomous exit. Does the runner invoke
the gate? If yes, the gate legend must also be added to the runner
form's conditional stack — and the runner form has **no** conditional
legend stack today (the boundary row is composed directly). If no,
the runner form is unaffected. *Recommendation*: a one-line ruling from
PO: does the runner ever emit a gate call? If yes, EV-71 must touch
both forms; if no, the runner form is out of scope and a test should
pin "runner invocation never issues a gate call" as an upstream
property.

**O6 — Advisory-mode gate calls.** EV-65 wrote `advisory: true` onto
the ledger. An advisory gate call still spends tokens (the decisions
endpoint is still called). The card's predicate "at least one gate
call falls in the window" naturally includes advisory calls. *No
design issue*, but a fixture should pin this so a later implementation
choice does not filter advisory calls out and silently under-report
again.

**O7 — The literal text vs the wording alternatives.** I considered
and rejected the following before arguing for the card's literal as
given:

- `usage  gate = not in ownSession or subtree` — too algebraic; breaks
  prose shape; widens the label column.
- `usage  gate = catalogue totals exclude gate spend` — narrows the
  antecedent correctly but reads as a sentence, not a definition.
- `usage  gate = ledger-only (see <path>)` — too long; the ledger
  path is environment-specific.
- `usage  gate = accounted in ledger, not in halves` — describes the
  mechanism, not the block's exclusion.

The card's literal is the cleanest of the alternatives that preserve
the "short definition" shape. P1 is a real comprehension hazard but is
not resolvable inside the legend without widening the definition past
its current word count.

## Summary

The surface change is small and the legend discipline is honored. The
card closes a real Gulf of Evaluation — the **silent absence of gate
spend from the visible block** — with a tail-of-block annotation. The
load-bearing risks are P1 (wrong antecedent), P5 (whole-block-state
precedence swallowing the legend), and P3 (no signposted affordance
for finding the gate spend). P5 is the only one I would not let
through to implementation without an explicit ruling, because it
silently reproduces the failure class the card exists to prevent in
exactly the edge case the card needs most: a gate call on a
no-other-spend invocation.

position, not an implementation. I yield to `consolidator` (or to
`owner` if no other seat has weighed in this round).
